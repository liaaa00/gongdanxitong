# 后端权限体系分析报告

## 一、权限架构概览

### 1. 权限控制层级（从外到内）
```
请求进入 
  ↓
① JwtAuthGuard（全局）- JWT 身份验证
  ↓
② PasswordChangeGuard（全局）- 强制改密验证
  ↓
③ RolesGuard（全局）- 角色/业务权限验证
  ↓
④ FieldPermissionInterceptor（全局）- 字段权限过滤
  ↓
业务逻辑
```

### 2. 核心组件清单

**守卫（Guards）**：
- `JwtAuthGuard` - JWT 认证，检查 @Public 装饰器跳过
- `PasswordChangeGuard` - 首次登录改密强制，检查 @AllowBeforePasswordChange 跳过
- `RolesGuard` - 角色和业务权限验证，支持 @Roles 和 @BusinessPermission
- `AdminOnlyGuard` - 独立守卫，仅用于字段权限管理接口

**装饰器（Decorators）**：
- `@Public()` - 公开接口，跳过 JWT 验证
- `@AllowBeforePasswordChange()` - 改密前可访问
- `@Roles(...roles)` - 要求用户具备指定角色之一
- `@BusinessPermission(action)` - 要求业务操作权限
- `@FieldPermissionScenario(scenario)` - 标记字段权限场景
- `@CurrentUser()` - 注入当前用户信息

**拦截器（Interceptor）**：
- `FieldPermissionInterceptor` - 响应数据字段过滤

## 二、权限验证流程

### 阶段 1：身份认证（JwtAuthGuard）
- **位置**：`backend/src/common/guards/jwt-auth.guard.ts`
- **优先级**：APP_GUARD 第 1 位
- **逻辑**：
  1. 检查方法/类是否有 `@Public()` 装饰器
  2. 若有，直接放行
  3. 否则调用 Passport JWT 策略验证 token
  4. 验证失败抛出 `UnauthorizedException('Token 无效或已过期')`

### 阶段 2：强制改密检查（PasswordChangeGuard）
- **位置**：`backend/src/common/guards/password-change.guard.ts`
- **优先级**：APP_GUARD 第 2 位
- **逻辑**：
  1. 若接口标记 `@Public()` 或 `@AllowBeforePasswordChange()`，放行
  2. 检查 `user.mustChangePassword` 标志
  3. 若为 true，抛出 `ForbiddenException('请先修改初始密码')`

### 阶段 3：角色与业务权限验证（RolesGuard）
- **位置**：`backend/src/common/guards/roles.guard.ts`
- **优先级**：APP_GUARD 第 3 位
- **逻辑**（优先级从高到低）：
  1. **业务权限优先**：若有 `@BusinessPermission(action)`
     - 调用 `RoleActionPermissionService.hasAnyRoleAction(user.roles, action)`
     - 查询用户角色是否拥有该业务操作权限
     - 无权限抛出 `ForbiddenException('业务权限不足')`
  2. **角色验证**：若有 `@Roles(...roles)`
     - 检查 `user.roles` 是否包含任意一个所需角色
     - 不满足抛出 `ForbiddenException('角色权限不足')`
  3. **无装饰器**：放行

### 阶段 4：字段权限过滤（FieldPermissionInterceptor）
- **位置**：`backend/src/modules/field-permissions/field-permission.interceptor.ts`
- **优先级**：APP_INTERCEPTOR
- **逻辑**：
  1. 若无 `@FieldPermissionScenario` 或用户是 admin，不过滤
  2. 根据装饰器参数解析场景（如 'main'、'dispatched:contract'）
  3. 查询该用户在该场景下的字段权限配置
  4. 拦截响应数据，对 `extraData`、`fields`、`feedbackData`、`pendingModify` 等字段进行过滤/脱敏/只读标记

## 三、角色定义与权限映射

### 3.1 角色等级（RoleLevel）
- `EXECUTION` - 执行层
- `SUPERVISOR` - 主管层
- `MANAGEMENT` - 管理层
- `GLOBAL` - 全局层

### 3.2 业务操作权限（RoleActionCode）
**定义位置**：`backend/src/modules/role-action-permissions/role-action-permission.service.ts`

共 54 个业务操作权限，分为：
- 工单操作权限：view/view_team/view_all/create/import/update/withdraw/void/urge/export/delete
- 路由访问权限：dashboard、notifications、work_orders、各子模块入口
- 模块管理权限：contract.manage、onboarding_contact.manage 等
- 批量操作权限：batch_import、batch_export、batch_accept 等

### 3.3 默认角色权限矩阵（部分）
```javascript
admin: 全部 54 个权限
biz_manager: [view_all, export, dashboard, dispatched_detail, leader_dashboard]
biz_leader: [view_team, create, import, update, withdraw, void, urge, export, ...路由入口, batch_urge]
biz_member: [view, create, import, update, withdraw, void, urge, ...路由入口]
shared_leader: [view_team, export, ...合同/入职/离职模块全权限]
contract_specialist: [view, export, ...合同模块权限]
```

## 四、API 路由权限控制实例

### 4.1 用户管理接口（admin/users）
```typescript
@Roles('admin')  // 整个 Controller 要求 admin 角色
@Controller('admin/users')
export class UsersController {
  @Get() list() {}         // 继承 @Roles('admin')
  @Post() create() {}      // 继承 @Roles('admin')
  @Delete(':id') disable() {}
}
```

### 4.2 工单接口（work-orders）
```typescript
@Controller('work-orders')
export class WorkOrderController {
  @Get()  // 无装饰器，RolesGuard 放行，但业务层会过滤数据
  @FieldPermissionScenario('main')
  findAll() {}

  @Post()
  @BusinessPermission('work_order.create')  // 业务权限验证
  @FieldPermissionScenario('main')
  create() {}

  @Delete(':id')
  @Roles('admin')  // 仅 admin 可删
  remove() {}

  @Post('batch-delete')
  @Roles('admin')
  batchDelete() {}
}
```

### 4.3 认证接口（auth）
```typescript
@Controller('auth')
export class AuthController {
  @Public()  // 跳过所有 Guard
  @Post('login') login() {}

  @AllowBeforePasswordChange()  // 改密前可访问
  @Post('logout') logout() {}

  @AllowBeforePasswordChange()
  @Get('me') me() {}

  @AllowBeforePasswordChange()
  @Post('change-password') changePassword() {}
}
```

## 五、不同模块权限差异

| 模块 | 权限控制方式 | 特点 |
|------|------------|------|
| admin/* | @Roles('admin') | 整个 Controller 级别锁定 |
| work-orders | @BusinessPermission + 业务层过滤 | 细粒度业务操作权限 |
| auth | @Public / @AllowBeforePasswordChange | 认证流程特殊豁免 |
| dispatched-orders | @FieldPermissionScenario('dispatched:auto') | 动态字段权限场景 |
| 健康检查 | @Public | 无权限要求 |

## 六、当前实现存在的问题与混乱点

### 🔴 问题 1：AdminOnlyGuard 未全局注册，使用不一致
- **现象**：`AdminOnlyGuard` 是独立守卫，仅在字段权限管理接口手动 `@UseGuards(AdminOnlyGuard)`
- **问题**：功能与 `@Roles('admin')` 重复，且需手动引入，容易遗漏
- **建议**：统一使用 `@Roles('admin')`，移除 AdminOnlyGuard

### 🔴 问题 2：@Roles 与 @BusinessPermission 优先级不直观
- **现象**：RolesGuard 内部先检查 `@BusinessPermission`，再检查 `@Roles`
- **问题**：若同时使用两个装饰器，`@BusinessPermission` 会覆盖 `@Roles` 的检查
- **建议**：文档明确说明优先级，或禁止同时使用

### 🟡 问题 3：字段权限与业务权限验证时机割裂
- **现象**：RolesGuard 在请求阶段验证业务权限，FieldPermissionInterceptor 在响应阶段过滤字段
- **影响**：部分接口（如 GET /work-orders）无 @BusinessPermission，依赖业务层过滤，新人容易误以为无权限控制
- **建议**：为高频查询接口补充明确的 @BusinessPermission 或在文档中说明防御层次

### 🟡 问题 4：角色权限矩阵存储在 SystemSetting 表，运行时动态查询
- **现象**：每次权限验证调用 `RoleActionPermissionService.hasAnyRoleAction` 都会查库
- **影响**：高并发下可能成为性能瓶颈
- **建议**：增加缓存层（Redis 或内存），定期同步更新

### 🟢 设计优点
- **层次清晰**：认证 → 改密 → 角色/业务权限 → 字段过滤，职责明确
- **灵活度高**：支持角色、业务操作、字段三层权限控制
- **默认安全**：除非明确 @Public，所有接口默认需认证
