**核心实体关系（ER 简图）：**
```
users (用户)
  ├─ 1:N user_roles (用户角色关联)
  │    └─ N:1 roles (角色)
  ├─ 1:N work_orders (发起的主工单, createdBy)
  └─ 1:N dispatched_orders (处理的子工单, handlerId)

work_orders (主工单)
  ├─ 1:N dispatched_orders (子工单, parentOrderId)
  ├─ N:1 customers (客户)
  └─ N:1 branches (分公司)

dispatched_orders (子工单)
  ├─ N:1 work_orders (主工单)
  ├─ N:1 module_handlers (模块处理人配置)
  ├─ 1:N order_attachments (附件)
  └─ 1:N operation_logs (操作日志)

field_permissions (字段权限)
  ├─ N:1 roles (角色)
  └─ scenario (场景)：dispatched:<moduleCode>

module_handlers (模块处理人)
  ├─ N:1 users (处理人)
  └─ moduleCode + province (省份维度派单)

in_service_orders (在职直单)
  ├─ N:1 users (发起人)
  ├─ N:1 users (办理人, handlerId)
  └─ orderType: single_business / certificate / renewal

out_of_province_orders (省外直单)
  ├─ N:1 users (发起人)
  └─ business_scope: out_of_province
```

**权限架构（四层守卫）：**
1. **JwtAuthGuard**：验证 JWT token，提取用户 `sub` 和 `roles`
2. **PasswordChangeGuard**：首次登录强制改密拦截（除改密接口、登出、刷新 token 外全拦截）
3. **RolesGuard**：
   - 优先校验 `@BusinessPermission` 装饰器（业务权限码，如 `order.update`）
   - 回退校验 `@Roles` 装饰器（角色枚举，如 `['admin', 'biz_manager']`）
4. **FieldPermissionInterceptor**：
   - 读取 `@FieldPermissionScenario` 装饰器
   - 按场景（如 `dispatched:labor_contract`）过滤响应字段
   - 支持 `visible` / `hidden` / `readonly` / `masked` 四种状态

**数据库迁移策略：**
- `synchronize: false` 强制关闭自动同步
- 18个已执行的 migration，包括：
  - 1715400000000-InitSchema：初始化 41 张表
  - 1715800000000-P7Extend：扩展字段配置
  - 1715900000000-StageABackend：审批流程阶段表
  - 20260520003000-CreateWorkflowDefinitions：工作流定义表
- 新字段/索引/外键必须通过 `npm run migration:generate` 生成

**种子数据（Seed）：**
- 9个启用角色 + 9个停用历史角色（角色归一化兼容）
- 字段配置：入职63字段、离职字段、在职字段
- 字段权限：按角色×场景预配置可见性
- 模块处理人：入职/续签/离职按模块分配专员
- 导出模板：劳动合同速创/E签宝双模板
- 系统设置：roleActionPermissions.v1 默认权限矩阵

**核心设计模式：**

**1. 路由权限控制：**
```typescript
// routeVisibility.ts 定义可见性矩阵
export const ROUTE_VISIBILITY: Record<string, readonly CanonicalRole[]> = {
  '/work-orders': BUSINESS_ORDER_ROLES,            // 入职/离职主工单
  '/onboarding': ONBOARDING_ROLES,                 // 入职模块
  '/my-dispatched': INITIATED_WORK_ROLES,          // 我发起的
  '/my-dispatched/pending': PENDING_WORK_ROLES,    // 我的待办
  '/admin': [ROLE.ADMIN],                          // 管理后台
  // ... 180+ 路径
};

// 路由守卫：RoleRoute.tsx
function RoleRoute({ children, path }) {
  const userRoles = useUserStore((s) => s.user?.roles || []);
  if (!canAccessPath(path, userRoles)) {
    return <Navigate to="/403" />;
  }
  return children;
}
```

**2. 角色归一化：**
```typescript
// constants/roles.ts
// 后端历史角色码 → 前端规范角色码
const ROLE_CODE_MAP: Record<string, CanonicalRole> = {
  'admin': 'admin',
  'business_owner': 'business_owner',
  'biz_owner': 'business_owner',  // 兼容
  'business_group_leader': 'business_group_leader',
  'biz_leader': 'business_group_leader',  // 兼容
  // ... 18 个后端角色 → 9 个前端规范角色
};

export function canonicalRoleCode(code: string): CanonicalRole | null {
  return ROLE_CODE_MAP[code] || null;
}
```

## 3. 关键设计决策

### 3.1 为什么用三维权限模型（角色×字段×场景）

**问题背景：**
- 工单系统涉及63个入职字段、多个离职字段、在职字段
- 不同角色在不同业务场景下对同一字段的权限不同：
  - 业务员创建时可填写全部字段
  - 后道处理人只能修改本模块字段
  - 其他角色查看时部分字段脱敏

**设计方案：**
```
field_permissions (
  role_id,      -- 角色维度
  scenario,     -- 场景维度：dispatched:<moduleCode>
  field_key,    -- 字段维度
  field_view    -- 权限：visible / hidden / readonly / masked
)
```

**优势：**
1. 同一角色在不同场景有不同权限（如劳动合同签订 vs 入职联系）
2. 避免在每个接口硬编码字段过滤逻辑
3. 管理后台可配置字段权限，无需改代码

### 3.2 为什么有角色归一化机制

**问题背景：**
- 后端历史角色码不规范：`biz_owner` / `biz_leader` / `biz_member`
- 前端规范角色码：`business_owner` / `business_group_leader` / `business_group_member`
- 数据库存在 18 个角色（9 个启用 + 9 个停用历史角色）

**设计方案：**
- 后端保持历史角色码不变（避免迁移风险）
- 前端通过 `constants/roles.ts` 的 `ROLE_CODE_MAP` 归一化
- 权限判断统一使用规范角色码

**优势：**
1. 前端代码清晰，不散落历史角色码
2. 后端保持数据兼容性
3. 新增角色只需维护映射表

### 3.3 为什么派发机制按省份 + 模块 + 团队

**问题背景：**
- 在职单项业务和省外增减员需要按省份派单
- 27 个省份（不包含浙江本地、青海）
- 部分省份双人配置（湖北、江苏、山西、山东、福建）

**设计方案：**
```typescript
// module_handlers 表
{
  module_code: 'in_service_single_business',  // Sheet4
  province: '湖北',
  user_id: 'xxx',
  is_backup: false,   // 主办
  weight: 100
}
{
  module_code: 'in_service_single_business',
  province: '湖北',
  user_id: 'yyy',
  is_backup: true,    // 备选（仅转派可用）
  weight: 1
}
```

**派发策略：**
1. 读取 `module_handlers` 按 `module_code + province` 匹配
2. 优先选择 `is_backup=false` 的主办
3. 无主办时进入模块池（待指派）
4. 禁止跨 Sheet 兜底（Sheet4 不回落 Sheet5）

**优势：**
1. 清晰的省份维度隔离
2. 支持双人省份（主办 + 备选）

## 4. 技术债务与改进点

### 4.1 已识别的技术债务

**后端：**
1. **历史兼容代码堆积：**
   - `dispatch_rules` 表的 `assignee_user_id` / `fallback_user_id` 为保留死字段（禁止读取但未删除）
   - 18 个角色（9 个启用 + 9 个停用），历史角色码散落在种子和迁移中
   - `LEGACY_SCENARIOS` 字段权限场景仍在代码中引用但未清理

2. **JSONB 扩展字段缺乏结构约束：**
   - `work_orders.extra_data` 存储 63 个入职字段，但无 Schema 校验
   - `dispatched_orders.extra_data` 混合存储不同模块字段，查询困难
   - 建议：使用 Ajv 或 class-validator 对 JSONB 增加运行时校验

3. **N+1 查询风险：**
   - 子工单列表查询未使用 `leftJoinAndSelect` 预加载 handler / parent 关系
   - 仪表盘统计未使用聚合查询，可能对每个工单单独查询状态

4. **导入导出模板硬编码：**
   - 劳动合同速创/E签宝模板字段配置分散在代码中
   - 导入字段校验规则与前端动态表单规则不统一
   - 建议：迁移到 `import_template_fields` 表统一配置

5. **缺少批量操作事务保护：**
   - 批量接单、批量完成、批量退回未显式使用 transaction
   - 部分失败时可能导致数据不一致

**前端：**
1. **重复代码：**
   - 多个列表页面（我的待办/我的已办/团队工单/历史工单）复制粘贴相似逻辑
   - 表头筛选、月份筛选、分页逻辑未完全抽象到 `ProTablePage` 或 `MultiViewTable`

2. **状态管理混乱：**
   - 列表状态（筛选条件/页码/pageSize）部分使用 URL query，部分使用组件 state
   - 导航状态记忆（lastPaths）与列表状态保留（listPageState）职责交叉

3. **缺少错误边界覆盖：**
   - 仅根组件有 `ErrorBoundary`，子模块复杂组件（如动态表单）未单独包裹
   - 一个组件崩溃可能导致整个页面白屏

4. **Mock 数据不完整：**
   - MSW handlers 仅覆盖登录、用户、主工单，缺少子工单详情、导入、导出的 mock
   - E2E 测试需要启动真实后端，无法纯前端测试

5. **性能瓶颈：**
   - 大列表（历史工单 1000+ 条）未使用虚拟滚动（react-window 已引入但未应用）
   - 详情页 63 个字段全部渲染，未做懒加载或分组折叠

### 4.2 安全漏洞排查

**已验证的安全措施：**
- ✅ 密码使用 bcrypt 加密（10轮）
- ✅ JWT 双 token 机制（access token 7天 + refresh token 30天）
- ✅ 全局 CORS 启用（生产需配置白名单）
- ✅ ValidationPipe 开启 `whitelist` 防止参数污染
- ✅ 字段权限拦截器防止越权查看

**潜在风险点：**
1. **SQL 注入风险：**
   - TypeORM QueryBuilder 使用了参数化查询，但部分原生查询（seed 脚本）未校验输入
   - 建议：全局禁止 `dataSource.query(raw SQL without params)`

2. **JWT 密钥管理：**
   - `.env.example` 中 `JWT_SECRET` 使用 placeholder，生产环境需强制校验密钥强度
   - 建议：启动时校验 `JWT_SECRET` 长度 >= 32 字符

3. **文件上传校验不足：**
   - `attachments` 模块校验了大小和 MIME 类型，但未校验文件实际内容（可能上传伪装的可执行文件）
   - 建议：使用 `file-type` 库校验 magic number

4. **敏感数据日志泄露：**
   - `operation_logs.changes` 字段记录了完整的修改内容，可能包含身份证号、手机号
   - 建议：日志记录前对敏感字段脱敏

5. **缺少请求频率限制：**
   - 登录接口、批量导入接口未限制请求频率，可能被暴力破解或 DoS 攻击
   - 建议：引入 `@nestjs/throttler`

### 4.4 性能优化建议

**后端优化：**
1. **查询优化：**
   - 子工单列表添加 `leftJoinAndSelect(['handler', 'parentOrder'])` 预加载
   - 仪表盘统计使用聚合查询（`COUNT(*) GROUP BY status`）而非循环查询

2. **缓存策略：**

   - 角色权限矩阵缓存（`roleActionPermissions.v1` 很少变更）

3. **异步处理：**
   - Excel 导入改为后台任务（当前同步导入，大文件超时）
   - 消息通知改为队列异步发送

**前端优化：**
1. **虚拟滚动：**
   - 历史工单列表使用 `react-window` 渲染 1000+ 条数据
   - 动态表单 63 个字段分组折叠

2. **代码分割：**
   - 管理后台模块按路由懒加载（`React.lazy`）
   - Ant Design 按需引入（已通过 Vite 自动实现）

3. **请求优化：**
   - 列表接口增加 `debounce` 防抖（筛选条件变更时）
   - 详情页避免重复请求（使用 SWR 或 React Query）

### D. 工单状态机（9种状态）

**子工单状态流转：**
```
pending (未接单)
  ↓ 接单
processing (已接单)
  ├─ 完成 → completed (已完成)
  ├─ 作废申请 → void_pending (作废审批中) → void (已作废)
  ├─ 撤回申请 → withdraw_pending (撤回审批中) → withdrawn (已撤回)
  ├─ 修改申请 → modify_pending (修改审批中) → processing
  └─ 退回 → returned (已退回)
```

**在职直单状态流转：**
```
dispatched (待受理)
  ↓ 受理
accepted (已受理待初审)
  ├─ 材料初审 → ready (完成材料初审)
  │    ↓ 选择渠道
  │  processing (办理中)
  │    ├─ 办理成功 → completed
  │    ├─ 办理失败 → failed
  │    └─ 补料 → pending_info → 重提 → processing
  ├─ 材料退回 → pending_info → 重提 → dispatched
  └─ 取消 → cancelled
```
