## 一、执行结论

这套系统不是一个单纯的“HR 入离职登记工具”，而是在两个月多的会议推进中逐步演变成了一个面向企服/外包业务的 **人事工单中台**：

1. **第一层：人员主数据**——员工基本信息、任职信息、社保公积金信息、入离职日期及附件。
2. **第二层：流程工单**——入职、离职、在职单项业务、派单、办理、退回、办结。
3. **第三层：协同管理**——任务、跟进记录、权限、操作日志、批量导入导出。
4. **第四层：外部执行**——四方系统、聚合 A、速创等外部平台报岗/上下岗，以及 Offer、证明、报销等自动化。

目前代码已经较好地覆盖了前三层的基础框架，但第四层仍主要停留在会议方案、人工操作手册或拟开发状态。系统已经具备可上线运行的骨架，但尚未完全成为会议中设想的“集约办理 + 自动派单 + 外部平台自动化 + 全链路闭环”系统。

**总体判断：**

- 核心 HR 工单能力：约完成 **75%—85%**。
- 在职/单项业务与派单能力：约完成 **60%—70%**。
- 外部平台自动化能力：约完成 **20%—35%**。
- 产品化、可配置化和治理能力：约完成 **40%—55%**。

以上比例是需求覆盖度判断，不等于代码质量或测试通过率。

## 二、资料所反映的项目演进

### 1. 2026-05-07 至 05-09：平台选型与方向确定

早期会议重点不是具体字段，而是确定用什么方式建设：妙搭、扣子、清流、简道云等低代码/AI 平台与本地自研方案进行比较，同时考虑本地部署、数据安全、成本、二次开发和后续扩展。

这一阶段形成的核心方向是：

- 系统应本地可控；
- 先实现高频 HR 工单，不一开始追求大而全；
- 表单必须支持批量数据处理；
- 后续要承接北仑项目、企服外包、财务/RPA 等更多业务；
- 权限与数据隔离不能依赖共享表格。

### 2. 2026-05-14 至 05-29：入离职 MVP 建设与高频测试

这是需求密度最高的阶段。会议围绕入职、离职工单反复确认字段、状态、日期逻辑、退回机制、任务分配和导入导出。

稳定下来的主流程可归纳为：

```text
业务提交/批量导入
  → 数据校验
  → 建立或匹配员工
  → 生成入职/离职工单
  → 派给办理人员
  → 办理/退回补充/重新提交
  → 办结
  → 同步员工在职状态及实际日期
  → 导出、留痕、统计
```

此阶段暴露的主要问题包括：

- 批量导入覆盖历史数据、误改员工状态；
- 导入模板字段与页面字段不一致；
- 离职日期、最后工作日、实际减员日期概念混用；
- 身份证、手机号、银行卡、日期格式校验不完整；
- 姓名不能作为唯一匹配条件；
- 退回以后缺少可追溯的补充和重新提交机制；
- 办理人、提交人、业务负责人之间权限边界不清；
- 列表、详情、导出字段不一致；
- 附件上传、批量附件和模板下载体验不足；
- 一个员工多次入离职时容易覆盖历史记录。

### 3. 2026-06-02 至 06-15：上线前收口、模板统一与宣贯

这一阶段项目从“能做”进入“能上线”。重点包括：

- 入职、离职导入导出模板收口；
- 页面字段、数据库字段、Excel 表头三方统一；
- 权限分配表落地；
- 上线前测试与问题清单关闭；
- 操作规范与宣贯；
- Offer 邮件、报销、开票、发票匹配等自动化需求开始从主系统中分流；
- 系统确定为内部自研、本地部署的正式业务工具。

会议资料也显示：上线并不意味着需求结束，后续仍持续发生字段调整、状态修正、导入兼容和交互优化。

### 4. 2026-06-23 至 07-09：从 HR 工单扩展到集约报岗和在职业务

业务范围由入离职扩展到：

- 聚合 A 平台服务单创建；
- 四方系统增员报岗；
- 本地/外地报岗差异；
- 上岗、下岗、增员、减员自动化；
- 社保、公积金模块；
- 批量附件；
- 单项业务、业务派单；
- 小微客户集约服务。

此时系统的目标已由“员工生命周期记录”变成“企服交付过程管理”。

### 5. 2026-07-15 至 07-28：省外扩展、日期异常、派单规范与证明业务

最新需求主要集中在：

- 省外业务与柜面业务的工单承接；
- 工单离职日期与员工实际离职日期不一致时的处理；
- 新增/减员自动化；
- 客户派单表格继续调整；
- 系统上线后的操作纪律和流程责任；
- 员工离职证明开具工单。

这表明系统已经进入“上线运营期”，当前主要矛盾不再只是开发 Bug，而是：

1. 业务边界不断扩张；
2. 字段语义和责任规则还没有完全标准化；
3. 外部系统自动化尚未形成统一接入框架；
4. 新业务仍倾向于通过加字段、加表格来实现，产品配置能力不足。

## 三、归并后的业务域

### 3.1 员工主数据

应作为全系统唯一人员底座，至少包含：

- 身份信息：姓名、证件类型、证件号码、性别、出生日期、民族；
- 联系信息：手机、地址、紧急联系人；
- 任职信息：客户、项目、部门、岗位、用工形式、合同主体；
- 日期信息：入职日期、预计/申请离职日期、最后工作日、实际离职日期；
- 薪资及账户信息：工资、开户行、银行卡等；
- 社保公积金信息：参保地、基数、增减员月份、账号等；
- 附件：证件、银行卡、合同、证明材料；
- 状态：待入职、在职、待离职、已离职，以及异常/撤销等辅助状态；
- 历史：每一次入职、转岗、离职均应保留独立履历，不能覆盖旧记录。

### 3.2 入职工单

核心规则：

- 单条创建与批量导入并存；
- 导入前必须预校验并反馈到行、列；
- 员工匹配应以证件号等稳定标识为主，不能仅按姓名；
- 同一员工重复入职需要区分“重复导入”“重新入职”“数据修正”；
- 工单办结后才同步最终状态，避免导入动作直接污染主数据；
- 支持附件、办理备注、退回原因、重新提交和操作日志；
- 页面、模板、导出字段必须由同一份字段定义驱动。

### 3.3 离职工单

会议中反复出现的关键规则是：

- “申请离职日期/最后工作日”“系统减员日期”“实际离职日期”必须分开；
- 业务提交日期和办理确认日期可能不一致，不能简单覆盖；
- 办理过程中允许修正实际日期，但必须保留修改前值、修改人和原因；
- 同一员工不能并行存在多个未关闭离职工单；
- 工单撤销或驳回时，员工状态要按规则回滚；
- 离职证明应基于已确认履历生成，不应手工重复录入姓名、任职和日期。

### 3.4 在职/单项业务工单

资料中的“派单 + 单项业务”已经超出传统入离职范围，包含：

- 证明开具；
- 社保、公积金事项；
- 柜面业务；
- 信息修改；
- 客户交付事项；
- 其他可配置服务项目。

理想模型应为：服务目录 → 表单定义 → 派单规则 → 办理步骤 → SLA → 结果附件/回执，而不是每新增一种业务就复制一套页面和数据表。

### 3.5 客户、项目与派单

- 工单必须明确客户、项目、业务类型、提交部门、责任人；
- 派单既要支持手工指定，也要支持按客户、地区、业务类型自动路由；
- 需要区分业务负责人、工单办理人、复核人和系统管理员；
- 客户维度的数据权限要与功能权限分开；
- 小微客户集约服务需要批量承接、统一分派和进度看板。

### 3.6 外部平台自动化

涉及四方系统、聚合 A、速创等平台。自动化不应直接写死在工单服务里，建议统一抽象为：

```text
工单事件
  → 自动化任务
  → 平台适配器
  → 登录/提交/查询
  → 结果回写
  → 截图或回执归档
  → 失败重试/人工接管
```

必须记录：请求参数摘要、执行时间、执行人/机器人、外部流水号、结果、失败原因、重试次数和最终回执。

### 3.7 截图确认的主工单—子工单结构

附件截图明确列出了 9 类工单：

| 工单 | 字段/录入要求 | 使用人 |
|---|---|---|
| 入职主工单 | 详情页单条新增 + 批量导入模板 | 业务团队 |
| 离职主工单 | 详情页单条新增 + 批量导入模板 | 业务团队 |
| 入职联系子工单 | 详情页 + 批量导入模板 | 业务团队、后道福保共享团队 |
| 劳动合同新签子工单 | 详情页 + 批量导入模板 | 业务团队、后道福保共享团队 |
| 增员报岗子工单 | 详情页 + 批量导入模板 | 业务团队、后道福保共享团队 |
| 社保公积金增员子工单 | 详情页 + 批量导入模板 | 业务团队、后道福保共享团队 |
| 离职材料收集子工单 | 详情页 + 批量导入模板 | 业务团队、后道福保共享团队 |
| 减员报岗录入子工单 | 详情页 + 批量导入模板 | 业务团队、后道福保共享团队 |
| 社保公积金减员子工单 | 详情页 + 批量导入模板 | 业务团队、后道福保共享团队 |

这不是普通的“工单分类”，而是明确的父子编排要求：一个入职主工单应能按客户服务配置拆出入职联系、合同新签、增员报岗、社保公积金增员等子工单；离职主工单同理拆出材料收集、减员报岗和社保公积金减员。子工单可由不同团队分别办理，最终状态再汇总到主工单。

现有代码虽然同时存在入离职工单和服务工单，但仍需重点核实是否具备：父子工单外键、拆单规则、子单并行办理、必做/选做配置、主单汇总状态、跨团队数据权限、子单失败/退回对主单的影响。如果没有，这应列入 P1 核心改造，而不是仅新增 7 个固定页面。

## 五、最重要的结构性问题

### 5.1 “员工、入离职工单、服务工单”之间存在重复事实

员工实体、入离职工单和服务工单都保存了姓名、客户、项目、入离职日期等信息。这样便于保留提交快照，但如果没有明确规则，就会造成多个“正确答案”。

建议明确：

- 员工表：当前状态快照；
- 任职记录：历史事实；
- 工单：申请和办理过程快照；
- 工单办结事件：触发主数据更新；
- 导出和证明：优先取任职事实，必要时引用工单快照。

### 5.2 固定字段模式无法持续承接新业务

5 月至 7 月需求不断从入离职扩展到社保公积金、柜面、证明、派单、省外和小微客户。继续在实体中追加字段会导致：

- 数据库字段快速膨胀；
- 页面和模板反复修改；
- 导入导出兼容困难；
- 不同客户差异无法复用；
- 测试成本线性上升。

建议下一阶段优先建设“服务目录 + 动态表单 + 流程模板”，而不是继续逐单开发。

### 5.3 自动化与工单主链路尚未解耦

外部平台自动化具有失败、重试、验证码、页面变化、人工接管等特殊性。如果把它当作普通 API 调用，会导致工单事务不稳定。必须采用异步任务和最终一致性：工单可显示“自动化处理中/失败待接管”，不因机器人失败而丢失业务数据。

### 5.4 需求追踪缺少统一编号

现有资料包含会议纪要、问题反馈、Excel 待办和测试用例，但缺少一个统一需求台账。相同事项多次出现，却难以判断是：

- 同一问题仍未修复；
- 已修复后回归；
- 字段含义再次变更；
- 新客户带来的差异需求。

建议每项需求建立唯一编号，例如 `HR-ONB-001`、`HR-OFF-012`、`SVC-CERT-003`、`INT-4PARTY-005`，并关联来源会议、负责人、代码提交、测试用例和上线版本。

## 六、建议的目标架构

### 6.1 核心领域

1. **Identity & Access**：用户、角色、权限、数据范围；
2. **Customer & Project**：客户、项目、合同主体、地区、服务配置；
3. **Employee Master**：员工当前快照与敏感信息；
4. **Employment History**：多次入转离事实记录；
5. **Service Catalog**：入职、离职、证明、社保、公积金、柜面等服务定义；
6. **Ticket Workflow**：工单实例、步骤、状态机、退回、撤回、转派、复核；
7. **Form & Template**：字段定义、校验、Excel 模板、文档模板、版本；
8. **Attachment**：材料类型、版本、关联对象、访问控制；
9. **Automation Hub**：四方、聚合 A、速创、邮件等适配器；
10. **Audit & Analytics**：日志、SLA、统计、导出审计。

### 6.2 建议状态机

```text
草稿
 → 已提交
 → 待分派
 → 待办理
 → 办理中
 → 待补充（可回到已提交/办理中）
 → 待复核（可选）
 → 已办结

旁路：已撤回 / 已取消 / 自动化失败待接管
```

员工状态与工单状态不能直接等同。员工状态应由已生效的任职事件计算或更新。

## 十二、最终判断

项目的方向是正确的：从共享 Excel 和人工传递升级为本地可控、可追溯的工单系统，已经形成了用户、权限、员工、工单、服务工单、任务、跟进、日志和导入导出的基础能力。

当前最大的风险不是“功能完全没做”，而是：

- 需求持续追加但缺少统一基线；
- 同一业务事实分散在员工、工单和模板中；
- 外部自动化需求尚未形成平台化设计；
- 固定字段模式将越来越难承接省外、柜面、小微客户和证明业务；
- 代码工作树状态存在误操作风险。

因此，下一阶段不建议直接继续堆功能。应先完成 **代码基线确认、需求台账、字段字典、状态机和数据一致性规则**，再进入 P0/P1 开发。这样才能把现在的“可用项目”升级为“可持续运营的平台”。
