# 工单系统全量需求追踪矩阵（V1）

> 版本日期：2026-07-29  
> 本版范围：入职主工单、离职主工单、七类子工单、父子编排、提交/退回/重提、撤回/作废、催办、批量导入、日期一致性、数据权限。  
> 审计方式：会议资料与当前代码静态对照；**尚未据此宣称构建、迁移或 E2E 已通过**。

## 1. 结论摘要

1. 系统不是“父子工单尚未开发”，而是已经形成 `work_order + dispatched_order` 的父子模型，并具备拆单、办理、退回、重提、撤回、作废、催办、日志、附件、动态字段和导入导出等核心骨架。
2. 当前实现仍带有明显的 Phase 1 边界：主列表限定北仑业务范围及入职/离职类型，模块可见性也按第一阶段规则过滤。后续扩业务范围不能只增加枚举。
3. 七类子工单代码枚举完整：入职联系、劳动合同新签、增员报岗、社保公积金增员、离职材料收集、减员报岗录入、社保公积金减员。
4. “全部模块都拆”与“按客户、人员、服务范围决定必做/选做/不适用”之间尚缺可验证的业务闭环，是当前父子编排的最大规则风险。
5. 退回后仅重开被退回子单、保留已完成子单的代码路径已经存在；主单状态由子单状态汇总，但并发、重复操作和异常状态仍需运行验证。
6. 导入能力已覆盖模板、预览、映射建议和导入任务，但去重键、返聘、数据修正、覆盖保护、事务回滚和员工主数据回写仍需专项验证。
7. 当前开发工作树存在未提交改动，本矩阵没有修改业务代码；测试前应先固定基线并区分既有改动与本轮验证结果。

## 2. 实现状态口径

- **已实现并有代码证据**：静态代码中存在完整主路径。
- **部分实现**：存在基础能力，但业务规则、覆盖面或闭环不足。
- **已实现但范围受 Phase 1 硬编码限制**：核心代码存在，但查询或模块范围被第一阶段规则约束。
- **已实现但尚未运行验证**：静态代码和/或测试文件存在，本轮尚未执行。
- **代码存在但工作树状态需确认**：版本代码可见，但基线或未提交改动影响结论可信度。
- **未发现实现**：在本轮审计范围内未定位到对应闭环。
- **需求规则不明确，需业务确认**：历史资料存在歧义或相互冲突。

## 5. 第一版缺口分级

### P0：上线或数据安全阻断项

1. 确认自动拆单的适用性决策：客户服务配置、用工形式、人员条件、必做/选做/不适用。
2. 验证主子状态汇总，特别是空子单、含作废子单、混合状态和并发办理。
3. 验证退回、重提、撤回、作废的幂等和并发保护。
4. 固化离职日期语义并完成页面—DTO—数据库—模板—员工—任职六方映射。
5. 禁止按姓名匹配或覆盖员工，明确重复导入、返聘和数据修正模式。
6. 验证导入事务、错误定位、可回滚和公式注入防护。
7. 确认工单办结到员工快照、任职记录的统一事务回写。
8. 完成客户维度、附件、敏感字段和导出权限的反向越权测试。
9. 将已提交/已办结工单的物理删除改为符合审计留存要求的策略，或由业务书面确认现策略。

### P1：核心可用性和运营效率

1. SLA 工作日、节假日、暂停计时规则。
2. 无办理人子单的显式告警和主管兜底。
3. 催办并发节流与通知失败重试。
4. 字段脏标记的前端确认闭环。
5. 时间线分页，避免 500 条硬上限截断。
6. 模块主管、临时代理和人员离职后的自动转派。
