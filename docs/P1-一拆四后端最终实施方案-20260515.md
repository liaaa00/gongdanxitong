# P1 入职一拆四后端最终实施方案（2026-05-15）

> 基于 `docs/P1-一拆四后端实施拆分-20260515.md`、`docs/入职一拆四-架构方案-20260515.md` 与用户本轮最终确认修订。  
> 本文定位：后端实施方案与拆分文档，不做正式业务代码实现。  
> 最终口径变化：**不做历史一拆三迁移；从现在开始，新提交入职工单直接一拆四**。  
> 编码约束：现有后端实体主键为 UUID；下文新增表字段类型应与现有实体保持 UUID 风格。

## 0. 最终确认结论

### 0.1 一拆四生成规则

| 顺序 | 内部 module_code | 页面中文名 | 生成规则 | 后端口径 |
|---:|---|---|---|---|
| 1 | `onboarding_contact` | 入职联系 | **仍按原条件生成** | 继续复用现有触发条件，例如 `need_onboarding_contact = 是`；不改为必生成。 |
| 2 | `contract` | 劳动合同 | **仍按原条件生成** | 继续复用现有触发条件，例如 `need_company_contract = 是`；新数据建议统一用 `contract`，兼容旧 `contract_signing` 显示。 |
| 3 | `data_entry` | 数据录入 | 所有入职工单必生成 | 保持现有必拆逻辑。 |
| 4 | `social_insurance` | 社保公积金办理 | **所有入职工单必生成** | `module_code` 建议沿用 `social_insurance`；中文展示由前端字典或后端 `moduleName` 输出为“社保公积金办理”。 |

### 0.2 本轮修订的关键取舍

1. **不做历史迁移**：当前没有历史数据或不需要兼容历史补数，本阶段删除“历史一拆三补社保子单”“迁移批次回滚”等必做项。
2. **杨杰账号暂不存在**：seed / 初始化只预留社保负责人角色、模块主管绑定能力，不假定数据库已有“杨杰”用户；后续创建账号后再绑定。
3. **Dirty 清除改为下游已阅清除**：负责人打开子工单详情或点击“确认已阅”后，清除该子单对应的所有 active dirty 标记。
4. **完成子单退回权限收紧**：已完成子单只能由该节点模块主管或 admin 退回；普通办理人如杨纯、毛雅妮在子单完成后不应有退回权限。
5. **退回原因必填**：完成子单退回必须填写原因，后端强校验，不只依赖前端。
6. **社保批量完成备注必填**：社保办理涉及月份、基数、操作类型等追溯信息，批量完成接口的 `remark` 必填。
7. **补充轻流式模块化配置模型**：以现有表驱动架构为基础，增加 `work_order_modules`、模块字段绑定、拆分规则、模块主管、动作配置等后端配置模型建议。

## 3. 一拆四派发服务实施口径

### 3.1 派发规则

短期继续使用现有 `dispatch_rules`：

| 规则名建议 | order_type | target_module | trigger_conditions | 说明 |
|---|---|---|---|---|
| `onboarding-default-data-entry` | `onboarding` | `data_entry` | null / 恒真 | 入职必生成。 |
| `onboarding-default-social-insurance` | `onboarding` | `social_insurance` | null / 恒真 | 社保公积金办理所有入职必生成。 |
| `onboarding-contact-when-needed` | `onboarding` | `onboarding_contact` | `need_onboarding_contact = 是` | 保留原条件。 |
| `onboarding-contract-when-needed` | `onboarding` | `contract` | `need_company_contract = 是` | 保留原条件。 |

### 3.2 服务兜底

即使规则可配置，后端服务仍建议有安全兜底：

1. `order_type='onboarding'` 提交时，最终结果中必须包含 `data_entry`。
2. `order_type='onboarding'` 提交时，最终结果中必须包含 `social_insurance`。
3. `onboarding_contact`、`contract` 不做兜底必生成，只按规则命中。
4. 新提交入职主工单可写 `onboarding_flow_version=4`、`modification_round=0`。
5. `social_insurance` 子单中文名输出为“社保公积金办理”；内部 code 保持 `social_insurance`。

### 3.3 杨杰账号未存在时的负责人处理

不可写死“按姓名查杨杰并必须存在”。建议分三层：

1. **优先配置层**：查 `module_handlers` 中 `module_code='social_insurance' and is_active=true` 的负责人。
2. **角色 / 模块主管层**：若尚无具体 handler，允许创建未指派子单或进入社保模块池，并通知 admin 配置负责人。
3. **未来用户绑定层**：杨杰账号创建后，通过后台或 seed 将其绑定为 `social_insurance` 模块 handler / supervisor。

推荐接口 / 行为：

- 找不到 handler 时，不阻塞主工单提交；`handler_id=null`，状态仍为待办理。
- 写一条系统通知给 admin：“社保公积金办理模块尚未配置负责人，请配置后处理待指派子单”。
- seed 中不要创建假杨杰账号，除非 Leader 明确要求初始化账号。

## 4. Dirty 标记与清除规则

### 4.1 Dirty 生成

业务员在当前轮所有子单均未完成时，可以修改业务员发起字段。后端保存时：

1. 比对 `work_orders.extra_data` 修改前后 diff。
2. 校验只修改业务员发起字段，不允许修改办理人回填字段。
3. 根据字段所在模块或字段权限场景计算受影响子单。
4. upsert `work_order_field_dirty_marks`。
5. 刷新受影响 `dispatched_orders.snapshot_refreshed_at`。
6. 给受影响模块 handler / 模块主管发送站内通知。
7. 写 `operation_logs`。

若当前轮存在已完成子单，则业务员修改接口必须拒绝，并返回中文原因和已完成模块列表。

### 4.2 Dirty 清除最终规则

用户最终确认：**下游节点查看后自动清除**。

后端支持两种入口：

| 清除触发 | 接口 / 服务 | 清除范围 |
|---|---|---|
| 负责人打开子工单详情 | `GET /api/dispatched-orders/:id` 内部调用 `DirtyMarkService.clearForDispatchedOrderRead(id, currentUser)` | 清除该子单对应的所有 active dirty 标记。 |
| 点击“确认已阅” | `POST /api/dispatched-orders/:id/dirty/confirm-read` | 同上，显式清除并写确认日志。 |

清除权限建议：

1. 当前子单负责人 / 当前认领人；
2. 该模块主管；
3. admin；
4. 其他只读查看者打开详情不自动清除，避免误清。

清除实现建议：

- 如果 dirty 表存了 `dispatched_order_id`，按 `dispatched_order_id + is_active=true` 置 inactive。
- 如果 dirty 表只存 `affected_module_codes`，则根据子单 `work_order_id + module_code + flow_round` 清除包含该模块的 active dirty。
- 清除时只置 `is_active=false`，写 `cleared_at/by/clear_reason`，不物理删除。
- `clear_reason`：自动打开详情为 `owner_open_detail`，按钮确认为 `confirm_read`。
- 写操作日志：实体 `dispatched_order`，动作 `dirty_cleared`，摘要包含清除字段数量。

### 4.3 返回结构建议

`GET /api/dispatched-orders/:id` 返回：

```json
{
  "id": "...",
  "moduleCode": "social_insurance",
  "moduleName": "社保公积金办理",
  "dirtySummary": {
    "activeCountBeforeRead": 3,
    "clearedByThisRead": true,
    "clearedCount": 3
  },
  "fields": [
    {
      "fieldCode": "employee_name",
      "fieldLabel": "员工姓名",
      "value": "张三",
      "dirty": false,
      "dirtyInfo": null
    }
  ]
}
```

注意：如果采用“打开详情即清除”，前端可能需要在清除前展示一次“已变更”提示。可通过 `activeCountBeforeRead` 或审计摘要展示“本次打开已自动确认 3 个变更”。

## 5. 已完成子单退回权限

### 5.1 最终规则

已完成子单退回必须满足：

1. 子单当前状态为 `completed`。
2. 操作者是该模块主管或 admin。
3. 普通办理人不可退回已完成子单，即使他是该子单原 handler。
4. 退回原因必填，建议后端校验去空白后不少于 5 个汉字或不少于 10 个字符。
5. 写退回记录表、子单状态、主单状态 / 可编辑态、通知和操作日志。

### 5.2 模块主管映射

本轮提到的主管示例：

| 模块 | 普通办理人示例 | 模块主管 / 负责人示例 | 退回权限 |
|---|---|---|---|
| `contract` | 杨纯 | 江璐 | 江璐或 admin 可退回；杨纯完成后不可退回。 |
| `onboarding_contact` | 毛雅妮 | 江璐 | 江璐或 admin 可退回；毛雅妮完成后不可退回。 |
| `data_entry` | 数据录入专员 | 安娜祯 | 安娜祯或 admin 可退回。 |
| `social_insurance` | 社保办理人 | 杨杰（账号后续创建） | 杨杰绑定为主管后可退回；未绑定前仅 admin。 |

### 5.3 权限判断服务建议

新增或扩展：`ModulePermissionService.canReturnCompletedDispatchedOrder(user, dispatchedOrder)`。

判断顺序：

1. `admin` 直接允许。
2. 查询 `module_supervisors`（建议新增）或 `module_handlers` 中 `is_supervisor=true` 的配置。
3. 若用户是该模块主管，允许。
4. 其他全部拒绝，返回中文错误：“已完成子单只能由模块主管或系统管理员退回”。

### 5.4 接口行为

`POST /api/dispatched-orders/:id/return`

请求：

```json
{
  "reason": "员工入职日期修改，需要重新核对合同信息"
}
```

后端校验：

- `reason` 必填；
- `status=completed` 时必须主管 / admin；
- 若未来允许未完成子单普通退回，可单独区分；本任务重点是已完成子单退回权限。

返回建议：

```json
{
  "id": "...",
  "status": "returned",
  "statusText": "已退回",
  "returnReason": "员工入职日期修改，需要重新核对合同信息",
  "returnedByName": "江璐",
  "returnedAt": "2026-05-15T15:30:00+08:00"
}
```

## 6. 社保批量完成接口

### 6.1 接口建议

`POST /api/dispatched-orders/social-insurance/batch-complete`

请求：

```json
{
  "ids": ["子工单ID1", "子工单ID2"],
  "remark": "2026年5月社保公积金新增，按客户确认基数办理完成"
}
```

### 6.2 后端规则

1. `remark` 必填，去空白后不能为空；建议不少于 10 个字符。
2. 只允许 `module_code='social_insurance'`。
3. 操作者必须是社保模块主管 / 社保负责人 / admin；普通非授权用户不可批量完成。
4. 已完成子单幂等跳过，返回 `skipped`。
5. `returned` 子单默认不允许批量完成，需重新进入办理态后再完成。
6. 每条写操作日志，日志摘要必须包含批量 remark。
7. 完成后调用主单完结检查。
8. 通知主工单发起人；必要时通知业务组长。

### 6.3 返回建议

```json
{
  "successCount": 10,
  "skippedCount": 2,
  "failedCount": 1,
  "items": [
    { "id": "...", "status": "success", "message": "已完成" },
    { "id": "...", "status": "skipped", "message": "已完成，无需重复处理" },
    { "id": "...", "status": "failed", "message": "非社保公积金办理子单，不能批量完成" }
  ]
}
```

## 7. 参考轻流的模块化配置后端模型

### 7.1 设计目标

参考轻流的“应用 / 表单 / 字段 / 流程 / 节点 / 权限 / 动作”模块化思路，把当前硬编码的一拆四逐步抽象为配置：

- 工单类型可配置：入职、续签、离职等。
- 子模块可配置：合同、入职联系、数据录入、社保公积金等。
- 字段可配置：字段定义、模块字段展示、字段权限、必填规则。
- 拆分规则可配置：什么条件下生成哪个模块。
- 处理人 / 主管可配置：办理人池、模块主管、备份、权重。
- 动作可配置：完成、退回、确认已阅、批量完成等动作的权限、表单、校验。

### 7.2 模型总览

| 模型 | 建议表 | 与现有表关系 | 本阶段建议 |
|---|---|---|---|
| 模块定义 | `work_order_modules` | 当前模块来自 `dispatch_rules.target_module + module_handlers.module_code` 去重，无独立模块表 | 建议新增，作为模块中文名、状态、动作配置入口。 |
| 字段定义 | `field_definitions` 或继续 `field_configs` | 已有 `field_configs` | 短期复用 `field_configs`；长期如跨工单类型更复杂，可改名或建视图。 |
| 模块字段绑定 | `module_fields` | 当前由 `field_permissions.scenario` 和 `dispatched_orders.visible_fields` 间接表达 | 建议新增，解决模块字段排序、分组、是否进入快照、是否用于 dirty 的配置。 |
| 模块字段权限 | `module_field_permissions` | 已有 `field_permissions(role, scenario, field)` | 短期复用；长期可新增并同步到 `field_permissions` 兼容旧服务。 |
| 拆分规则 | `module_split_rules` | 已有 `dispatch_rules` | 短期复用；长期新增以支持规则版本、必生成、互斥、模块编排。 |
| 办理人 | `module_handlers` | 已有 | 继续复用，可扩展 handler 类型。 |
| 模块主管 | `module_supervisors` | 当前无独立表，可用角色或 module_handlers 兼任 | 建议新增，支撑“主管退回已完成子单”。 |
| 动作配置 | `action_configs` | 当前动作权限多在代码 / Guard 中 | 建议新增，配置完成、退回、确认已阅、批量完成等动作。 |
| 版本发布 | `module_config_versions` | 当前无 | 可选，等后台可视化配置上线再做。 |

### 7.7 `module_split_rules`：模块拆分规则

短期复用 `dispatch_rules` 即可；长期建议新增更贴近“模块化搭建”的规则表。

| 字段 | 类型建议 | 说明 |

| 字段 | 类型建议 | 说明 |

| `id` | uuid | 主键。 |

### 7.10 `action_configs`：动作配置表

建议新增，表达不同模块上可执行动作、权限、表单和校验。适合参考轻流动作按钮配置。

| 字段 | 类型建议 | 说明 |
|---|---|---|
| `id` | uuid | 主键。 |
| `module_code` | varchar(64) | 模块；可为 `*` 表示全局动作。 |
| `action_code` | varchar(64) | 如 `complete`、`return_completed`、`confirm_read_dirty`、`batch_complete`。 |
| `action_name` | varchar(128) | 中文动作名。 |
| `allowed_roles` | jsonb | 允许角色 code 数组。 |
| `allowed_supervisor_only` | boolean | 是否仅模块主管。 |
| `required_fields` | jsonb | 动作表单必填字段，如退回原因、批量备注。 |
| `validation_schema` | jsonb | JSON Schema / 规则。 |
| `status_from` | jsonb | 允许的来源状态。 |
| `status_to` | varchar(32) | 目标状态。 |
| `side_effects` | jsonb | 触发通知、清 dirty、写日志等配置。 |
| `is_active` | boolean | 是否启用。 |

本次动作配置示例：

| module_code | action_code | action_name | 关键规则 |
|---|---|---|---|
| `*` | `confirm_read_dirty` | 确认已阅 | 负责人 / 主管 / admin；清除当前子单 dirty。 |
| `*` | `return_completed` | 退回已完成子单 | 仅模块主管 / admin；`reason` 必填。 |
| `social_insurance` | `batch_complete` | 批量完成 | 社保主管 / admin；`remark` 必填。 |
| `*` | `complete` | 完成办理 | 当前 handler / 主管 / admin；按字段权限校验。 |

### 7.11 配置读取服务建议

新增聚合服务：`ModuleConfigService`。

职责：

1. 获取工单类型下启用模块列表：`getModules(orderType)`。
2. 获取模块字段：`getModuleFields(moduleCode)`。
3. 获取模块动作：`getActions(moduleCode, user)`。
4. 判断模块主管：`isModuleSupervisor(moduleCode, user)`。
5. 模拟拆分规则：`simulateSplit(orderType, extraData)`。
6. 输出前端动态搭建所需 schema。

短期可以先封装现有 `dispatch_rules + module_handlers + field_permissions + field_configs`，不必一次性新增全部表。

## 12. 推荐实施顺序

### 阶段 A：最小一拆四与配置修订

1. Seed 新增 `social_insurance` 派发规则，保留联系 / 合同原条件。
2. 派发服务兜底确保 `data_entry + social_insurance` 必生成。
3. 新增中文 moduleName 映射。
4. 增加社保模块字段权限场景。
5. 处理社保负责人未配置 / 杨杰账号不存在的未指派逻辑。

### 阶段 B：Dirty 与退回规则

1. 新增 dirty 表和 dirty service。
2. 修改业务员更新接口：无 completed 子单才允许改，并生成 dirty。
3. 子单详情打开自动清 dirty；新增确认已阅接口。
4. 新增退回记录表。
5. 修改退回接口：已完成子单仅模块主管 / admin，原因必填。

### 阶段 C：社保批量完成

1. 新增批量完成 DTO，`remark` 必填。
2. 权限限制社保主管 / admin。
3. 幂等处理和逐项结果。
4. 操作日志、主单完成检查、通知。

### 阶段 D：模块化配置演进

1. 新增 `work_order_modules`，先 seed 四个入职模块。
2. 新增 `module_supervisors`，用于完成节点退回权限。
3. 评估是否新增 `module_fields`，替代散落的 `visible_fields` 配置。
4. `action_configs` 可先做后端常量，等管理后台搭建再落表。
5. `module_split_rules` 暂不替换现有 `dispatch_rules`，先保持兼容。

## 13. 后端验收口径

后端方案落地后应满足：

1. 新提交入职工单直接进入一拆四口径；不做历史补数。
2. 入职联系、劳动合同仍按原条件生成。
3. 社保公积金办理对所有入职必生成，内部 code 为 `social_insurance`，中文展示为“社保公积金办理”。
4. 杨杰账号不存在不阻塞提交；系统预留社保负责人 / 模块主管绑定能力。
5. 业务员改字段时生成 dirty；负责人打开子单详情或确认已阅后清除该子单所有 dirty。
6. 已完成子单退回仅模块主管 / admin 可操作，普通办理人不可退回，退回原因必填。
7. 社保批量完成备注必填，操作可追溯。
8. 模块化配置模型明确哪些复用现有表、哪些建议新增，为后续轻流式搭建打基础。
