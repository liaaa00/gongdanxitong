# 阶段1派单引擎扩展架构契约（在职管理 / 省外派单）

> 版本：2026-07-27  
> 状态：阶段1实施基线（架构师）  
> 范围：仅派单引擎底座和 Sheet4/Sheet5 映射契约；阶段2、阶段3的业务表单与状态机按本契约接入。  
> 说明：本文件纠正旧方案中“Sheet3 在职映射”和“将 businessScope 放入 appStore”的表述；旧表述不再作为实现依据。

## 1. 目标与非目标

### 1.1 目标

1. 在现有派单引擎上增加在职单项业务和省外派单两个映射分支。
2. Sheet4（单项业务省份映射）与 Sheet5（省外派单映射）独立读取、独立 seed、独立验收。
3. 保持入职、续签、离职和待遇申报现有派单行为不变。
4. 双人省份按配置表实际顺序派单：/ 前为默认接单人，后为转派备选；不轮询。
5. 保留 dispatch_rules.assignee_user_id、fallback_user_id 字段及旧接口，不在新逻辑中读取。

### 1.2 非目标

- 不重构整个 DispatchEngineService，不新增通用规则 DSL。
- 不把 businessScope 写入 appStore/Zustand；范围切换只保存前端本地偏好，后端以订单类型、模块码和省份字段判定。
- 不把 Sheet4 行拼接到 Sheet5，也不以一张表的缺省值兜底另一张表。
- 不删除 assignee/fallback 死字段。
- 省外增减员字段清单未提供，阶段3表单保留 TODO。

## 2. 模块边界图

~~~
WorkOrderService / ImportJob
        |
        | orderType + extraData.province + moduleCode
        v
DispatchEngineService.evaluateDetailed()
        |
        +-- 旧订单分支（ONBOARDING/RENEWAL/RESIGNATION/BENEFIT）
        |      -> 原有 dispatch_rules + module_handlers 算法（行为冻结）
        |
        +-- ModuleType.IN_SERVICE
        |      -> Sheet4 mapping key
        |      -> HandlerPicker.pick(..., MappingSource.SHEET4)
        |      -> in-service-single-business child order
        |
        +-- ModuleType.OUT_OF_PROVINCE
               -> Sheet5 mapping key
               -> HandlerPicker.pick(..., MappingSource.SHEET5)
               -> out-of-province child order
~~~

边界原则：

- DispatchEngine 负责识别模块类型、传递省份上下文和选择映射来源；不解析业务表格文本。
- HandlerPicker 负责候选人排序、激活状态、备选人和转派语义；不读取 dispatch_rules.assignee_user_id/fallback_user_id。
- province-handler.seed.ts 负责将 Sheet4/Sheet5 配置以稳定键写入现有 module_handlers，不建第二套人员表。
- 状态机仍在 dispatched-order.service.ts 末尾按现有风格追加；派单底座不改变既有九种状态。

## 3. 枚举与稳定键契约

在 backend/src/entities/enums.ts 增加以下枚举。已有枚举值不得重命名或删除。

~~~ts
export enum ModuleType {
  IN_SERVICE = 'in_service',
  OUT_OF_PROVINCE = 'out_of_province',
}

export enum TeamRole {
  IN_SERVICE = 'in_service_team',
  OUT_OF_PROVINCE = 'out_of_province_team',
}

export enum OrderType {
  ONBOARDING = 'onboarding',
  RENEWAL = 'renewal',
  RESIGNATION = 'resignation',
  BENEFIT = 'benefit',
  IN_SERVICE = 'in_service',
  OUT_OF_PROVINCE_INCREASE = 'out_of_province_increase',
  OUT_OF_PROVINCE_DECREASE = 'out_of_province_decrease',
}
~~~

约定：

- ModuleType 是派单路由分支，不等同于数据库角色；由订单类型/模块码推导。
- TeamRole 是映射语义标签，实际接单人仍由 module_handlers.handler_id 配置；不要要求 roles 表必须存在同名角色。
- IN_SERVICE 仅表示在职模块的单项业务主订单类型；三级业务分类放在订单字段，不扩展为新的订单类型。
- 省外增员/减员使用两个订单类型，但共享 ModuleType.OUT_OF_PROVINCE 和 Sheet5。
- 既有 DispatchStrategy、DispatchedOrderStatus、WorkOrderStatus 值保持不变。

建议的模块码（用于 module_handlers.module_code 和子工单）：

| 模块码 | ModuleType | 映射表 | 用途 |
|---|---|---|---|
| in_service_single_business | IN_SERVICE | Sheet4 | 在职单项业务 |
| out_of_province_dispatch | OUT_OF_PROVINCE | Sheet5 | 省外增员/减员共用派单 |
| 现有模块码 | 由现有订单类型推导 | 无 | 入职/续签/离职/待遇兼容分支 |

## 4. Sheet4 / Sheet5 数据表结构

两张表都使用文本配置的“行顺序”作为业务事实。seed 前必须 trim 空白、保留非空行、按首个 / 拆分接单人。

### 4.1 Sheet4：单项业务省份映射

Sheet4 每一行定义一个在职单项业务省份映射：

| 字段 | 类型 | 必填 | 约束 |
|---|---|---:|---|
| province | string | 是 | 省简称，不带“省”；与统一省份字典完全一致 |
| handlerText | string | 是 | 配置表原文；单人或“主办/备选” |
| handlerUsernames | string[] | 是 | 由 handlerText 按 / 拆分、trim、去空；1~2人 |
| moduleType | ModuleType | 是 | 固定 IN_SERVICE |
| teamRole | TeamRole | 是 | 固定 IN_SERVICE |
| moduleCode | string | 是 | 固定 in_service_single_business |
| rowOrder | number | 是 | 原表行顺序，从 1 开始；决定主办/备选 |
| isActive | boolean | 是 | 仅活动行参与派单 |

唯一键：moduleCode + province。同一省份重复活动行应在 seed 校验时报错，不静默覆盖。

### 4.2 Sheet5：省外派单映射

Sheet5 每一行定义一个省外（非北仑）增减员省份映射：

| 字段 | 类型 | 必填 | 约束 |
|---|---|---:|---|
| province | string | 是 | 省简称；北仑不进入 Sheet5 |
| handlerText | string | 是 | 配置表原文；单人或“主办/备选” |
| handlerUsernames | string[] | 是 | 同样按 / 拆分，最多两人 |
| moduleType | ModuleType | 是 | 固定 OUT_OF_PROVINCE |
| teamRole | TeamRole | 是 | 固定 OUT_OF_PROVINCE |
| moduleCode | string | 是 | 固定 out_of_province_dispatch |
| orderTypes | OrderType[] | 是 | 固定包含增员、减员两个省外订单类型 |
| rowOrder | number | 是 | 原表行顺序 |
| isActive | boolean | 是 | 仅活动行参与派单 |

唯一键：moduleCode + province。Sheet5 不读取 Sheet4 的行，也不把 Sheet4 的人员作为缺省备选。

### 4.3 现有表落地键

为避免新增迁移，province-handler.seed.ts 将每个映射候选写入现有 module_handlers：

- 主办：moduleCode = <moduleCode>__<province>，isBackup=false，weight=100。
- 备选：相同键，isBackup=true，weight=1。
- handler_id 按 username 查找；账号不存在时记录 warn 并跳过该候选，不阻断整批 seed。
- 运行时由 resolveModuleTeamHandler 根据 MappingSource + province 生成 namespaced key；旧模块码查询路径完全不变。
- seed 非破坏式：不删除、不停用已有 module_handlers 行，不修改旧角色或用户。

## 5. 派单接口契约

### 5.1 DispatchEngineService

保留现有公开方法签名。私有方法允许增加可选上下文，不影响现有调用方：

~~~ts
type ProvinceDispatchContext = {
  moduleType: ModuleType;
  province: string;
  mappingSource: 'sheet4' | 'sheet5';
  teamRole: TeamRole;
};

private resolveModuleTeamHandler(
  moduleCode: string,
  strategy: DispatchStrategy,
  manager?: EntityManager,
  context?: ProvinceDispatchContext,
): Promise<string | null>;
~~~

分支规则：

1. context.mappingSource === 'sheet4' 只查 Sheet4 namespaced key。
2. context.mappingSource === 'sheet5' 只查 Sheet5 namespaced key。
3. 无上下文时执行原有 moduleCode 查询和 strategy 逻辑，保证旧订单零行为变化。
4. 省份缺失、未知或映射无活动候选时返回 null（进入待指派/模块池），不得偷读另一张表。
5. applyModuleConfig 重新解析 handler 时必须透传同一 context，不能把规则命中的负责人覆盖成旧模块默认人。

### 5.2 HandlerPickerService

在现有 pick(strategy, moduleCode, manager?) 后增加可选上下文：

~~~ts
pick(
  strategy: DispatchStrategy,
  moduleCode: string,
  manager?: EntityManager,
  context?: { province?: string; mappingSource?: 'sheet4' | 'sheet5' },
): Promise<string | null>;
~~~

- 无 mappingSource：维持现有候选加载、权重、轮询、负载均衡。
- 有 mappingSource：将 moduleCode + '__' + province 作为查询键；不得查询另一映射源。
- 固定策略：按 isBackup=false 且权重最高选主办；无主办时才选备选。
- 双人配置不走 ROUND_ROBIN/LOAD_BALANCE，排前永远默认接单。
- 转派时由业务服务显式选择 isBackup=true 候选；首次派单不把备选写成默认 handler。
- 仍过滤停用用户、停用 handler；候选为空返回 null 并记录结构化 warn。

### 5.3 状态机边界

- 在职单项业务状态机由阶段2追加到 dispatched-order.service.ts 文件末尾：draft -> dispatched -> processing -> pending_info -> completed/archived，补料可多次往返。
- 省外增减员阶段3复用入职/离职状态机；不复用 Sheet2 单项业务流程。
- 阶段1不得修改既有九种状态的名称、过滤或审批路径。

## 6. 迁移与兼容风险

| 风险 | 级别 | 触发条件 | 防护/回滚 |
|---|---|---|---|
| OrderType PostgreSQL enum 扩展失败 | P0 | 直接改实体但未生成迁移 | 先生成 ALTER TYPE ... ADD VALUE 迁移；部署前备份，迁移失败立即回滚代码 |
| Sheet4/5 省份重复或拼写不一致 | P0 | “浙江省”与“浙江”、重复活动行 | seed 预校验唯一键和统一省份字典；错误阻断该 sheet 并报告行号 |
| 双人顺序丢失 | P0 | 按姓名排序、权重相同或错误轮询 | seed 写死主/备 isBackup；单测验证原文顺序和转派候选 |
| 新分支覆盖旧订单 | P0 | 以 moduleCode 模糊匹配、applyModuleConfig 未透传 context | 无 context 走原路径；增加入职/续签/离职回归和命中 trace |
| 账号暂不存在 | P1 | seed 找不到 username | 跳过单个候选并 warn；不删除旧配置，允许后台补配 |
| handler key 过长/省份非法 | P1 | 任意用户输入直接拼接 moduleCode | 只接受统一省份字典；限制 namespaced key 长度并拒绝分隔符 |
| assignee/fallback 被误用 | P1 | 复用旧 dispatch rule DTO | 代码审查 grep；阶段1测试明确两字段不参与选择 |
| 前端范围状态泄漏 | P1 | 将 businessScope 写入 appStore 或请求全局污染 | 仅 localStorage 记忆选择；后端按订单类型/模块码/省份隔离查询 |
| Sheet4/5 混表 | P0 | 缺省映射跨表 fallback | context/source 强制枚举；两套 fixture 做数据隔离断言 |

## 7. 验收标准

### 7.1 底座与映射

- [ ] ModuleType、TeamRole、三个 OrderType 新值可编译，旧值无变化。
- [ ] Sheet4 单人省份命中正确主办；Sheet5 同省命中其独立人员。
- [ ] 双人省份配置含 / 时，排前首次接单，排后仅作为转派备选；重复派单不轮询。
- [ ] Sheet4 无记录时不读取 Sheet5；Sheet5 无记录时不读取 Sheet4。
- [ ] 停用用户、停用 handler、缺省省份均得到可观测的空 handler，不错误指派。

### 7.2 回归

- [ ] assignee_user_id / fallback_user_id 保留且新路径零读取。
- [ ] applyModuleConfig、模块池、转派和通知行为不受影响。
- [ ] 跑根目录 回归测试.ps1（可先 -SkipBuild）通过。

## 8. 阶段交接

阶段1完成条件是底座分支、seed、单测/集成测试和回归均通过。阶段2只能在此之后接入在职实体/DTO/状态机和 Sheet2 分类树；阶段3再接入省外切换器、数据隔离和增减员复用状态机。任何阶段不得反向修改 Sheet4/Sheet5 的独立性或旧模块派单兼容约束。
