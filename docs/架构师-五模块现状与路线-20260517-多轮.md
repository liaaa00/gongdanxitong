### 1.3 admin "删不掉" 的根因核对

#### 1.3.1 后端 service.remove() 源码（**无状态限制**）

`backend/src/modules/dispatched-orders/dispatched-order.service.ts:506-515`：
```ts
async remove(id: string, user: JwtUserPayload): Promise<{ success: boolean; id: string }> {
  const order = await this.loadDispatchedOrder(id);
  const before = this.snapshot(order);
  await this.dispatchedOrderRepository.delete(id);
  await this.writeLog('dispatched_order', id, user.sub, 'delete', before, {
    deletedAt: new Date().toISOString(),
    hardDelete: true,
  });
  return { success: true, id };
}
```
> 没有 `status === COMPLETED` 拒绝、也没有 `status === RETURNED` 拒绝。`assertCanHandle` 也没调。Admin 经过 controller 的 `@Roles('admin')` 就直达 delete。**服务端不会拒绝任何状态的子单删除**。

#### 1.3.2 单删 controller（看上去正常）

`backend/src/modules/dispatched-orders/dispatched-order.controller.ts:73-78`：
```ts
@Delete(':id')
@Roles('admin')
@Audit('dispatched_orders', 'delete')
remove(@Param('id') id: string, @CurrentUser() user: JwtUserPayload) {
  return this.dispatchedOrderService.remove(assertUuidParam(id, '瀛愬伐鍗曚笉瀛樺湪'), user);
}
```
> ⚠️ "瀛愬伐鍗曚笉瀛樺湪" 是 UTF-8 解码错乱的 "子工单不存在"。这是源文件编码事故，建议下一轮修复，但**不影响功能**。
>
> `assertUuidParam` 使用严格 v4 正则 `/^[0-9a-f]{8}-[0-9a-f]{4}-[1-5][0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$/i`（`backend/src/common/utils/uuid-param.ts:3`），任何不是 RFC 4122 v4 的 UUID 都会 404。

#### 1.3.3 批删 DTO 也严格 v4

`backend/src/modules/dispatched-orders/dto/batch-delete.dto.ts:1-9`：
```ts
import { ArrayNotEmpty, IsArray, IsUUID } from 'class-validator';

export class BatchDeleteDispatchedOrderDto {
  @IsArray()
  @ArrayNotEmpty()
  @IsUUID('4', { each: true })  // ★ 严格 v4
  ids!: string[];
}
```
> ✅ TypeORM 用 `@PrimaryGeneratedColumn('uuid')`、PostgreSQL 用 `gen_random_uuid()` / `uuid_generate_v4()`，**生成的都是 v4**，理论上能通过。
> ❗ 但如果数据库里混入手工 INSERT 的非 v4 UUID（极少），批删整批失败、单删 404。

#### 1.3.4 前端 handleDelete（**这是用户感受到 "删不掉" 的真正原因**）

`frontend/src/pages/TeamDispatched/index.tsx:98-106`：
```tsx
const handleDelete = async (id: string) => {
  try {
    await deleteDispatchedOrder(id);
    message.success('删除成功');
    actionRef.current?.reload();
  } catch {           // ★ 吃掉所有错误
    message.error('删除失败');   // ★ 只给一句空话
  }
};
```
> 后端真实错误（403/404/422/500 / FK 约束 / DTO 验证失败）**全部被这里的 catch 吞了**，用户只看到 `删除失败` 四个字。任何排查都要靠 Network 面板看后端原文。

#### 1.3.5 前端批删 handler

`frontend/src/pages/TeamDispatched/index.tsx:108-126`：用 Modal.confirm，调用 `batchDeleteDispatchedOrders(ids)`。失败时按 result.failed 计数显示，但**单条失败原因不展示**。

### 1.4 路径分项

| "删不掉" 的子原因 | 应对 |
|------------------|------|
| A. 静默 catch 吞错误（最高频） | **handleDelete 改为 `catch (err) { message.error(err?.response?.data?.message \|\| '删除失败'); }`** |
| B. 严格 v4 UUID 校验 | 改为 `@IsUUID()`（接受任意版本）或 `@IsString() + 自定义验证`；同时 `assertUuidParam` 也松绑 |
| C. UTF-8 错乱的中文 message | 修复 controller 的 `'瀛愬伐鍗曚笉瀛樺湪'` 为 `'子工单不存在'` |
| D. 残留测试数据无法识别 | 扩展 cleanup 脚本为 `WHERE order_no LIKE 'PH6-%' OR employee_name LIKE 'QA%' OR extra_data->>'source' IN ('phase6_seed','qa_dispatched_delete_acceptance')` |

function defaultPermission(roleCode, scenario, fieldCode): 'editable' | 'readonly' | 'hidden' {
  if (roleCode === 'admin') return 'editable';
  if (roleCode === 'business_owner') return 'readonly';
  if (scenario === 'main' || scenario.startsWith('create:')) {
    if (roleCode === 'business_group_leader' || roleCode === 'business_group_member') return 'editable';
    return 'readonly';
  }
  // ... 复杂规则
