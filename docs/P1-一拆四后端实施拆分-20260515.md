## 0. 最终架构口径摘要

### 0.1 入职一拆四最终子单

| 顺序 | 内部 code | 页面中文名 | 触发条件 | 一期负责人原则 |
|---:|---|---|---|---|
| 1 | `onboarding_contact` | 入职联系 | 仍按「是否需要入职联系 = 是」条件生成，待产品最终确认是否改为必生成 | 毛雅妮，江璐作为负责人/备份 |
| 2 | `contract` | 劳动合同签订 | 仍按「是否企服发起劳动合同 = 是」条件生成，待产品最终确认是否改为必生成 | 杨纯，江璐作为负责人/备份 |
| 3 | `data_entry` | 数据录入 | 所有已提交入职主工单必生成 | 安娜祯 |
| 4 | `social_insurance` | 社保公积金办理 | 所有已提交入职主工单一期默认必生成 | 杨杰或后台当前配置的社保负责人 |

### 0.2 业务员修改规则最终口径

| 场景 | 后端规则 |
|---|---|
| 当前轮所有子单均未完成 | 业务员可直接修改允许的业务员发起字段；后端生成字段级 dirty 标记、刷新下游快照、触发站内通知；下游详情页按 dirty 标红。 |
| 当前轮任一子单已完成 | 业务员不可直接修改；必须由已完成节点逐一退回并填写退回原因；全部完成节点退回后，业务员才能修改并重新提交；整条主工单重走完整一拆四流程。 |

### 0.3 历史一拆三兼容口径

对满足以下条件的历史入职主工单补 `social_insurance` 子单：

1. `work_orders.order_type = 'onboarding'`；
2. 已提交且未作废；
3. 已有原三类子单，至少包括 `data_entry`、`onboarding_contact`、`contract` 或兼容旧 `contract_signing`；
4. 尚不存在 `social_insurance` 子单；
5. 数据结构正常，可以找到主工单与负责人。

不自动补：草稿、作废、已存在社保子单、异常数据。

## 3. 任务包明细

## BE-P1-01 数据库迁移

### 3.1.1 目标

新增一拆四和业务员修改规则所需的数据结构，支持历史补子单和回滚。

### 3.1.2 迁移内容

#### A. `work_orders` 扩展字段

| 字段 | 类型建议 | 用途 |
|---|---|---|
| `onboarding_flow_version` | smallint | 入职流程版本：历史一拆三为 3，新一拆四为 4 |
| `modification_round` | int | 主工单流转轮次，首次提交为 0，每次退回后重走 +1 |
| `resubmitted_at` | timestamptz nullable | 最近一次重新提交时间，可选 |
| `resubmitted_by` | uuid nullable | 最近一次重新提交人，可选 |

说明：当前项目 `work_orders` 已有 `last_modified_at`、`last_modified_by`，无需重复新增。

#### B. `dispatched_orders` 扩展字段

| 字段 | 类型建议 | 用途 |
|---|---|---|
| `module_name` | varchar(64) nullable | 冗余中文模块名，历史快照与前端中文展示兜底 |
| `flow_round` | int default 0 | 当前子单属于第几轮流转 |
| `completed_by` | uuid nullable | 子单完成人 |
| `returned_at` | timestamptz nullable | 最近退回时间 |
| `returned_by` | uuid nullable | 最近退回人 |
| `snapshot_refreshed_at` | timestamptz nullable | 业务员改字段后刷新下游快照时间 |
| `migration_batch_no` | varchar(64) nullable | 历史补社保子单批次号，便于回滚 |

说明：当前项目已存在 `completed_at`、`return_reason`，不重复新增。

#### C. 新表 `work_order_field_dirty_marks`

用途：记录业务员在当前轮直接修改了哪些字段，供下游字段标红、通知和审计。

关键字段：

| 字段 | 类型建议 | 用途 |
|---|---|---|
| `id` | uuid 或 bigserial | 主键，建议与项目现有 UUID 风格保持一致 |
| `work_order_id` | uuid | 主工单 ID |
| `field_code` | varchar(128) | 字段编码 |
| `field_label` | varchar(128) | 字段中文名快照 |
| `old_value` | jsonb | 修改前值，敏感值按权限脱敏或仅审计可见 |
| `new_value` | jsonb | 修改后值 |
| `changed_by` | uuid | 修改人 |
| `changed_at` | timestamptz | 修改时间 |
| `flow_round` | int | 当前轮次 |
| `affected_module_codes` | jsonb | 受影响模块 code 数组 |
| `is_active` | boolean | 是否仍需下游提示 |
| `cleared_at` | timestamptz nullable | 清除时间 |
| `cleared_by` | uuid nullable | 清除人/系统 |
| `clear_reason` | varchar(128) nullable | 清除原因 |

建议索引：

- `idx_dirty_marks_order_active(work_order_id, is_active, flow_round)`；
- 活跃唯一索引：`work_order_id + field_code + flow_round` where `is_active = true`。

#### D. 新表 `dispatched_order_return_records`

用途：保留每次完成节点退回的历史原因，避免重新提交后覆盖 `dispatched_orders.return_reason`。

关键字段：

| 字段 | 类型建议 | 用途 |
|---|---|---|
| `id` | uuid 或 bigserial | 主键，建议与项目现有 UUID 风格保持一致 |
| `dispatched_order_id` | uuid | 子工单 ID |
| `work_order_id` | uuid | 主工单 ID |
| `from_status` | varchar(32) | 退回前状态 |
| `to_status` | varchar(32) | 退回后状态 |
| `return_reason` | text | 退回原因，必填 |
| `returned_by` | uuid | 退回人 |
| `returned_at` | timestamptz | 退回时间 |
| `flow_round` | int | 当前轮次 |

建议索引：

- `idx_return_records_work_order(work_order_id, flow_round)`；
- `idx_return_records_dispatched_order(dispatched_order_id)`。

### 3.1.3 注意事项

1. 当前代码实体主键普遍使用 UUID，架构文档 SQL 示例里有 bigint/bigserial；实际实施应与现有项目保持 UUID 风格，避免类型不一致。
2. `cancelled` 当前不在 `WorkOrderStatus` 枚举内，历史作废数据如用 `withdrawn` 或其他状态，需要按现有枚举修订迁移条件。
3. 迁移必须幂等，使用 `IF NOT EXISTS`。
4. 迁移需先只加结构，不建议在同一个迁移里做不可回滚的大批量补数；补历史子单建议单独迁移或脚本化。

## BE-P1-05 历史一拆三补社保子单

### 3.5.1 补数条件

补数对象：

```text
order_type = onboarding
status not in draft / withdrawn / 作废类状态
已有 data_entry 子单
已有 onboarding_contact 子单
已有 contract 或 contract_signing 子单
不存在 social_insurance 子单
```

异常数据不自动补，输出清单供人工确认。

### 3.5.2 补数字段

新增 `dispatched_orders` 记录：

| 字段 | 值 |
|---|---|
| `parent_order_id` | 历史主工单 ID |
| `module_code` | `social_insurance` |
| `module_name` | 社保公积金办理 |
| `handler_id` | 杨杰或当前配置负责人 |
| `status` | `pending` |
| `visible_fields` | `dispatched:social_insurance` 可见字段 |
| `flow_round` | 主工单当前 `modification_round`，默认 0 |
| `migration_batch_no` | `20260515_onboarding_v4` 或实际批次号 |

同时：

- 将补过社保子单的入职主工单 `onboarding_flow_version` 设为 4；
- 未补但属于历史入职的主工单可设为 3，便于前端兼容。

### 3.5.3 补数前输出清单

建议补数脚本先 dry-run 输出：

1. 可补主工单数量；
2. 已完成主单数量；
3. 处理中主单数量；
4. 缺少三原子单的异常主单；
5. 找不到社保负责人的主单；
6. 已存在社保子单的主单。

### 3.5.4 风险

1. 已完成主单补出 pending 社保子单后，主单状态是否回到 processing 需要产品确认。默认建议：不自动改历史主单状态，只在详情中提示“历史补建社保子单待办理”。
2. 如果修改主单状态，会影响报表、完成率、历史统计。
3. 补数必须有批次号，便于精准回滚。

## BE-P1-06 业务员修改规则

### 3.6.1 当前代码现状

当前 `WorkOrderService.update` 逻辑：

- 仅允许主工单创建人修改；
- `withdrawn` 禁改；
- `completed` 仍可改并触发通知；
- 使用硬编码 `assertSalesEditableFields` 禁止部分办理人字段。

### 3.6.2 新规则改造

#### A. 所有子单未完成

允许业务员修改，但必须满足：

1. 只能修改业务员发起字段；
2. 不能修改办理人回填字段；
3. 生成 dirty 标记；
4. 刷新所有受影响子单快照；
5. 给受影响模块办理人/负责人发站内通知；
6. 写 `operation_logs`。

#### B. 任一子单已完成

不允许直接修改，接口返回中文原因，例如：

```json
{
  "code": 业务错误码,
  "message": "已有子工单完成，不能直接修改。请先联系已完成节点退回并填写退回原因。",
  "data": {
    "canEdit": false,
    "completedModules": [
      { "moduleCode": "contract", "moduleName": "劳动合同签订" }
    ]
  }
}
```

### 3.6.3 字段权限建议

不建议继续用硬编码 deny list。建议：

1. 以字段权限/字段来源分类判定“业务员可改字段”；
2. 对 `bank_account` 等办理人字段进行后端强校验；
3. 主工单 `main` 场景里 readonly 的字段，业务员提交时后端也拒绝。

## BE-P1-07 Dirty 标记服务

### 3.7.1 建议新增服务

建议新增：

- `backend/src/modules/work-orders/work-order-dirty.service.ts`

职责：

1. 计算 before/after diff；
2. 过滤允许 dirty 的业务字段；
3. 查字段中文名；
4. 计算受影响子模块；
5. upsert `work_order_field_dirty_marks`；
6. 刷新 `dispatched_orders.snapshot_refreshed_at`；
7. 返回 dirty 摘要供详情接口使用。

### 3.7.2 受影响模块计算

建议第一期简单处理：

- 如果字段在某个子单 visibleFields 内，则该子单受影响；
- 如果无法判断，默认影响当前主工单下所有未完成子单；
- 不通知操作者本人。

### 3.7.3 Dirty 清除

默认建议：

- 当前轮所有受影响子单完成后，将对应 active dirty 标记置为 inactive；
- 审计记录不删除；
- 若产品要求办理人手动确认“已知悉”，再新增确认动作，P1 可不做。

## BE-P1-08 已完成节点退回与重走流程

### 3.8.1 接口影响

现有：

- `POST /api/dispatched-orders/:id/return`

需要增强：

1. 已完成子单允许退回用于业务员修改；
2. 退回原因必填；
3. 写 `dispatched_order_return_records`；
4. 更新 `dispatched_orders.status = returned`；
5. 写 `returned_at`、`returned_by`、`return_reason`；
6. 主单进入“待业务员修改”状态，现有可复用 `returned`；
7. 当所有已完成节点均退回后，通知业务员可修改。

### 3.8.2 重新提交

现有：

- `POST /api/work-orders/:id/resubmit`

需要保证：

1. 仅在允许修改状态下可重提；
2. `modification_round + 1`；
3. 清空当前子单临时退回原因，但保留退回记录表；
4. 整单重新按一拆四计算子单；
5. `data_entry` 和 `social_insurance` 必生成；
6. 联系/合同按产品确认规则生成；
7. 新轮子单 `flow_round` 更新；
8. 触发重提通知。

### 3.8.3 与现有 returned submit 的差异

当前 `WorkOrderService.submit` 对 returned 状态有 reset returned children 的旧逻辑；`WorkOrderResubmitService` 又会重算派发。P1 需要统一入口，避免一条路径重算、一条路径不重算。

建议：入职 P1 的退回后重提统一走 `resubmit`，并明确弃用 returned 状态下普通 submit 的重提逻辑或让其内部委托到 resubmit。

## BE-P1-09 社保批量完成接口

### 3.9.1 新接口建议

```text
POST /api/dispatched-orders/social-insurance/batch-complete
```

请求体建议：

{

返回建议：

### 3.9.2 后端规则

1. 只允许 `module_code = social_insurance`；
2. 只允许杨杰/当前社保负责人/模块负责人/admin；
3. 对已完成子单幂等跳过，不报错；
4. 对 returned 子单是否允许批量完成需产品确认，默认不允许；
5. 每条写 operation log；
6. 完成后调用主单完结检查；
7. 通知主工单发起人，必要时通知业务组长。

## BE-P1-11 回滚方案

### 3.11.1 回滚范围

仅回滚本次迁移批次自动补出的社保子单，不删除用户上线后手动或系统新生成的数据。

### 3.11.2 回滚原则

1. 删除条件必须带 `migration_batch_no`；
2. 不默认 drop 新增 dirty 表和退回记录表；
3. 回滚前导出影响清单；
4. 回滚后将不再有社保子单的历史入职主单版本恢复为 3；
5. 新提交的一拆四数据不纳入历史补数回滚。

### 3.11.3 回滚前导出字段

建议至少导出：

- 主工单 ID；
- 工单号；
- 员工姓名；
- 身份证号；
- 原三子单 ID 和状态；
- 新增社保子单 ID；
- handlerId；
- migration_batch_no。

## 6. 主要风险与处理建议

| 风险 | 说明 | 建议 |
|---|---|---|
| 杨杰账号不存在 | 迁移和新派发找不到负责人 | 实施前确认账号；找不到时生成未指派子单并通知 admin，不能阻塞主工单提交 |
| `social_security` 旧模块混淆 | 旧模块已软下线 | 本次只使用 `social_insurance`，不要复用 `social_security` |
| 历史已完成主单补 pending 社保子单 | 可能影响完成率和业务观感 | 默认不自动改主单状态，详情增加历史补建提示；最终展示口径需产品确认 |
| returned 重提路径不一致 | 当前 submit/resubmit 两条路径行为不同 | 入职 P1 统一重提入口，内部强制重算一拆四 |
| 业务员字段可改范围硬编码漏字段 | 当前 `bank_account` 等可能未被 deny list 覆盖 | 改为字段权限/字段来源驱动的后端校验 |
| Dirty 标记过多 | 频繁修改同字段可能产生多条提示 | 同字段同轮次 active 记录 upsert，审计细节放 operation_logs |
| 通知事务一致性 | 事务回滚后误发通知 | 主事务提交后再发通知，或使用事务内 outbox 模式 |
| 批量完成并发 | 多人同时批量操作同一子单 | 使用条件更新和幂等返回，已完成跳过 |
| 前端英文枚举泄漏 | 用户明确要求中文 | 后端补 `moduleName/statusText/permissionText`，前端只展示中文 |

## 8. 后端交付验收口径

后端完成后至少应满足：

1. 新提交入职主工单必有 `data_entry` 和 `social_insurance`；
2. 联系/合同按产品确认条件生成；
3. `social_insurance` 页面和接口中文名统一为“社保公积金办理”；
4. 杨杰/社保负责人能看到并批量完成社保子单；
5. 业务员在所有子单未完成时可修改允许字段，且产生 dirty；
6. 任一子单已完成时，业务员直接修改被后端拒绝；
7. 已完成子单可退回且原因必填；
8. 全部完成节点退回后，业务员可重新提交并整单重走一拆四；
9. 历史一拆三符合条件的数据可补社保子单，且可按批次回滚；
10. 接口返回关键中文展示字段，不把英文枚举直接交给用户界面展示。
