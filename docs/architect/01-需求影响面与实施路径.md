## 2. 核心实体与业务流（与当前代码对齐）

### 关键实体
| 实体 | 关键字段 | 说明 |
|---|---|---|
| `WorkOrder` | status, extraData(jsonb), modificationRound | 主工单 |
| `DispatchedOrder` | moduleCode, status, handlerId, visibleFields, voidAt, flowRound, completionRemark | 子工单 |
| `WorkOrderFieldDirtyMark` | fieldCode, oldValue/newValue, flowRound, isActive, clearedAt | 公共字段变更脏标 |
| `DispatchedOrderReturnRecord` | beforeStatus, afterStatus, returnReason, payload | 后道退回审计 |
| `FieldSupplementRule` | fieldCode, supplementerModule, syncToModules | 谁能补充哪个字段 + 同步到哪些子工单 |
| `DispatchRule` | triggerConditions(jsonb AST), targetModule, customerId, subModule, assigneeUserId, fallbackUserId, dispatchStrategy, priority, isActive | 派发规则（含 A/B 角 fallback、按客户/部门精细化） |
| `ModuleHandler` | moduleCode, handlerId, weight, isBackup, rrCursorVersion | 模块固定办理人池（含主备区分） |
| `ModuleSupervisor` | moduleCode, supervisorId | 模块主管（用于撤回审批权限判定） |
| `WorkflowDefinition` | orderType, definitionJson, status | 可视化流程 v2，目前与 DispatchRule 并存 |
| `ExportTemplate` | moduleCode, fieldList(jsonb), isShared | 模板与子工单 moduleCode 绑定 ✅ |
| `OperationLog` | entityType, entityId, actionType, beforeData/afterData(jsonb) | 含定时清理（默认按 SystemSetting 配置） |
| `SystemSetting` | key, value, isEncrypted | 含 `operation_log.retention_days` 等键 |

### 主要业务流（当前实现）
- **导入 / 一拆四**：`POST /work-orders/import/preview` → `POST /work-orders/import/confirm`；`onboarding-dispatch.helper#buildOnboardingChildren` 决定哪些子工单生成、`getModuleSortOrder` 排序；`DispatchEngineService` 评估 AST、按策略选择 handler。
- **撤回（withdraw）**：业务员发起 → 主工单 `WITHDRAW_PENDING`；后道审批方法是 `WorkOrder.approveWithdraw`（**整张主工单一次审批**）；旧 `withdraw_requests / withdraw_approvals` 表已被 `1716100000000-DropWithdrawTables` 标记，但记忆里仍写"按子工单挨个审批"——这部分**已不再准确**。
- **作废（void）**：`VoidWorkOrderDto` → `VOID_PENDING` → `approveVoid`，作废通过后子工单 `voidAt` 标记并主工单 `VOID`。
- **公共字段同步**：业务员侧通过 `WorkOrder#update` 写入 `extraData` 时同步派发脏标；后道侧通过 `FieldSupplementService#supplement` + `FieldSupplementRule.syncToModules` 同步并通知；`WorkOrderFieldDirtyMark` 记录每条变更，未读标记驱动子工单页 "有字段变更" Tag。
- **重新提交（resubmit）**：`RETURNED` 后合并新 extraData，重跑派发引擎，upsert 子工单。
- **批量办理**：`POST /api/dispatched-orders/batch-complete`、`POST /api/dispatched-orders/social-insurance/batch-complete`（社保备注必填）。**目前没有批量退回 / 批量导入更新状态 / 批量导入修改字段三类接口。**
- **操作日志**：`OperationLogCleanupService` Cron `0 0 3 * * *` 按 `system_settings.operation_log.retention_days` 清理；前端 `Admin/Logs` 列表查看。

### 当前状态枚举（实际值）
```
WorkOrderStatus = DRAFT | PENDING | PROCESSING | COMPLETED | RETURNED |
                  WITHDRAW_PENDING | WITHDRAWN | VOID_PENDING | VOID
DispatchedOrderStatus = PENDING | PROCESSING | COMPLETED | RETURNED
```
> 注意：会议要求"草稿+待派发合并"、保留 7 个状态。当前后端有 9 个状态（多了 `DRAFT / PENDING`），需要做"状态展示层映射"或在后端裁剪。详见第 3 节 §F。

## 3. 会议需求 → 现有架构影响面映射

> 标记：🟢 改动小（仅前端 / 配置） · 🟡 中等（前后端联动） · 🔴 影响面大（实体/迁移/语义变更）

### A. 业务员操作下沉到子工单 🔴
- **现状**：业务员在主工单页有"修改 / 撤回 / 作废 / 催办"全部入口；`WorkOrderController` 上的 `update / withdraw / void / urge` 都是按主工单作用。
- **目标**：主工单仅查看，所有写操作搬到子工单。
- **影响**：
  - 后端：新增子工单粒度的 `update / withdraw / void / urge` 接口（建议：`POST /api/dispatched-orders/:id/withdraw|void|urge`，业务员可调用，受字段权限和状态约束）；写入 `extraData` 时仍走主工单（同 1 条数据），但仅同步到当前模块 + `FieldSupplementRule.syncToModules` 包含的其他模块，不强制全量。
  - 主工单的撤回/作废需要"从全单审批"改为"对单个 `DispatchedOrder` 的审批"。这是核心语义变更，会牵动 `WorkOrderStatus` 的 `WITHDRAW_PENDING/VOID_PENDING` 是否还应该是主工单状态，还是仅放在子工单上。建议的过渡方案：**子工单加 `WITHDRAW_PENDING / VOID_PENDING / WITHDRAWN / VOIDED` 自身状态**，主工单状态由所有子工单状态聚合得出。
  - 前端：`WorkOrderDetail` 去掉操作区，所有按钮迁到 `MyDispatched/Detail` 与 `OnboardingModule` 列表行内；保留主工单的"子工单进度展示"模块（中文化）。

### B. 公共字段双向同步语义补齐 🟡
- **现状**：业务员改 `extraData` → 写主工单 + 通过 `FieldChangeHook / DirtyMark` 通知后道；后道补充 → `FieldSupplementService` + `syncToModules` 推到其他子工单。机制存在，**但目前业务员侧的写路径在主工单上**。
- **目标**：业务员在子工单页修改公共字段也走"主工单 + 同步到其他相关子工单 + 通知"。
- **影响**：把 A 里的子工单 `update` 接口接到现有 `FieldChangeHook`，复用脏标 + 通知；不需要重写同步引擎，但要扩展"何时只同步部分子工单"——按 `FieldSupplementRule` 决定（与会议提到的"如果字段对某模块无意义就不同步"完全吻合）。

### C. 业务员菜单与团队权限收敛 🟢
- **现状**：`BasicLayout.tsx` 菜单含「我的代办 / 我的已办 / 我发起的 / 团队工单」；`MyDispatched` 区分 mode；`TeamDispatched` 已有。
- **目标**：业务员仅保留「我的代办」（仅展示后道退回的待处理），团队工单仅业务组长 / 业务负责人可见。
- **影响**：
  - 前端：调整 `RAW_MENU` 的 roles，把「我的已办 / 我发起的」对业务员隐藏；`/my-work/team` 收敛到 `BUSINESS_GROUP_LEADER + BUSINESS_OWNER`。
  - 后端：`/api/dispatched-orders` 在业务员视角下默认只返回 RETURNED 给该业务员发起的工单。

### D. 历史工单页面 🟡
- **现状**：列表无显式"历史"页；按月切片需要自己加。
- **目标**：新增独立"历史工单"页，按月份筛选，默认仅显示最近 N 条，避免全量加载卡顿。
- **影响**：
  - 前端：新建 `pages/HistoryWorkOrders` 路由 `/history`，月份多选 + 默认 limit。
  - 后端：`/api/work-orders` 增加 `monthList[]` 与 `latestN` 参数（不破坏现有列表查询），后续如需淘汰旧数据可借用现成的 Cron 框架。

### E. 派发配置与 A/B 角 🟢
- **现状**：`DispatchRule` 已支持 `assigneeUserId + fallbackUserId + dispatchStrategy + customerId + 触发 AST`；`ModuleHandler` 支持 `weight + isBackup`；前端 `Admin/DispatchConfig` 已经在用。会议结论是"90% 固定派发 + 后续按客户/参保地扩展 + A/B 角直接显示姓名 + 不要公共池概念"——**当前实体已能覆盖**。
- **影响**：移除"公共池"展示概念。`DispatchStrategy.POOL` 不再下发新规则，前端列表里出现 handler_name 为空时改为"该模块所有备选人"姓名联展（不显示"公共池"标签）；`OnboardingModule/index.tsx:57` 的 `<Tag color="orange">公共池</Tag>` 需要替换为"备选 N 人"或全部显示。

### F. 工单状态合并到 7 个 🔴
- **会议约定**：保留 `处理中 / 已完成 / 已退回 / 已撤回 / 已作废 / 撤回审批中 / 作废审批中`，删除 `草稿 / 待派发`。
- **现状**：枚举里仍有 `DRAFT / PENDING`。
- **影响**：
  - 短期（前端）：在 `constants/dictionaries.ts` 的 `getStatusText/getStatusColor` 里把 `DRAFT/PENDING` 都展示为"待派发"或直接归入"已撤回"派系。
  - 中期（后端）：`WorkOrder.createDraft` 是否仍保留 DRAFT，会议倾向"撤回 / 退回后重新提交即变 PROCESSING，没有独立的待派发态"。建议保留 DRAFT 作为"未点击提交"的内部态，但前端不展示；`PENDING` 这个用得很少的态可以并入 `RETURNED/WITHDRAWN`（取决于来源）。
  - 子工单 4 状态满足要求，不动。
  - 撤回/作废审批中是否仍由主工单承担？受 §A 决定，倾向于挪到子工单粒度。

### G. 界面细节优化 🟢
- 仪表盘：删除周期选择、备注、视角提示；右上角顶栏只保留「我的消息」+ 退出按钮（去掉左上重复用户名块）。前端纯改动。
- 左侧导航：按子工单划分（`BasicLayout.tsx` 已经是这种结构 ✅）；离职管理类似拆分（当前 `OFFBOARDING_ROLES` 仅有 `ResignationList`，需新增对应子工单菜单）。
- 子工单进度英文 → 中文（`getStatusText` 已在用）。

### H. 子工单查询改表头筛选 🟢
- 现状：`OnboardingModule/index.tsx` 用 ProTable 默认顶部 search；改为表头列筛选（filters/filterDropdown）即可，与主工单字段保持一致：客户代码 / 客户名称 / 员工姓名 / 编号 / 状态 / 派发时间 / 完成时间。

### I. 导出模板与子工单绑定 🟢
- 现状：`ExportTemplate.moduleCode` 已绑定模块；`exportTemplatesService` 已被 `DispatchedOrderService` 注入并用于 `POST /api/dispatched-orders/:id/export`。
- 影响：业务员侧不暴露字段选择，仅展示当前模块的固定模板；导入模板与导出模板字段集保持一致 → 在 `Admin/ExportTemplates` 增加"作为该模块默认导出模板"开关，并在子工单页直接调用，不弹字段选择 UI。

### J. 后道批量操作扩展 🔴（新增功能）
1. **批量退回**：`POST /api/dispatched-orders/batch-return`，复用 `returnOrder` 的逻辑 + `DispatchedOrderReturnRecord`，参数 `{ ids[], reason, returnedFields? }`；前端 OnboardingModule 行选中后弹窗。
2. **导入批量更新状态**（complete / return）：新接口 `POST /api/dispatched-orders/import/status-update`，参数 `{ moduleCode, file, decision: 'complete'|'return', remark? }`，按 `身份证` 与 `moduleCode` 匹配代办子工单，仅更新状态。**禁止改字段值**——前端 hint + 后端忽略其他列。
3. **导入批量修改字段**（仅 onboarding_contact 模块开放银行卡相关字段）：新接口 `POST /api/dispatched-orders/import/field-update`，配置项 `allowedFields = ['bank_card_no', 'bank_account', ...]`，**修改后仅写 extraData + dirty mark + 通知，不改子工单状态**（即"暂存"语义）。
4. 三个新接口都建议复用 `import/preview` 的 ImportJob 持久化框架，但 mapping 固定不需要 AI；建议在 `imports/` 里新增 `import-job-mode.ts` 用枚举区分 `CREATE | STATUS_UPDATE | FIELD_UPDATE`。

### K. 操作权限规则明确 🟡
- 业务员：单条新增 / 单条修改 / 批量导入；仅未办理工单可修改/撤回；催办可单条/批量。
- 后道：单条/系统勾选/导入 三种办理 + 三种退回；修改仅单条 + 导入；不可系统勾选批量修改（"修改的内容都不一样"是会议明确的反约束）。
- 撤回 → 后道审批通过 → 业务员可直接作废，不再走第二轮审批：**关键语义补丁**，需要在 `assertCanRequestVoid` 中放行"已撤回回到待派发"的工单直接走作废→无审批→直接 VOID 终态（建议加新方法 `voidWithdrawn`，避免污染原 void 流程）。

### L. 操作日志保留 30 天 🟢
- 当前默认保留天数已通过 SystemSetting 可配，会议提到"按 30 天周期"。改默认值或设置 setting 即可。

## 4. 推荐实施顺序

> 设计原则：先动数据语义和接口，再动 UI 联动；高耦合的"操作下沉 + 状态聚合"放最后做整合，避免回滚。

| 阶段 | 范围 | 说明 |
|---|---|---|
| **P0 准备** | 设计评审 + 接口契约文档 | 架构师产出本文 + API 契约（建议下一篇）→ 后端、前端、QA 一起 review |
| **P1（独立可上线）** | §I 导出模板默认绑定、§G 仪表盘清理、§H 表头筛选、§C 菜单收敛、§E 移除"公共池"展示、§L 日志保留 30 天 | 全部低风险、可单独 PR |
| **P2** | §J1 批量退回 + §J2 导入批量更新状态 | 复用现有 `returnOrder` / `batchComplete`，对系统语义影响小 |
| **P3** | §J3 导入批量修改字段（仅 onboarding_contact 银行卡）+ §K 业务员/后道权限规则补全 | 涉及字段白名单 + 暂存态，需要 QA 重点验证 |
| **P4** | §F 状态合并 + §A 操作下沉 + §B 同步语义补齐 + §D 历史页 | 一起做：撤回/作废从主工单挪到子工单 = 状态语义变更 = UI 入口迁移；分多个 PR 串行合并 |
| **P5 收尾** | 回归测试 + 文档同步 | QA 用配置好的前后道账号串测，业务确认 |

## 5. 风险点与待确认项

### 风险
1. **撤回/作废挪到子工单后，主工单的状态如何聚合？** —— 当前主工单 `WITHDRAW_PENDING / VOID_PENDING / WITHDRAWN / VOID` 是单值；若每个子工单独立审批，主工单状态需要按子工单的最弱态聚合。建议主工单状态变成"派生"，由 service 计算而非 DB 字段；或保留 DB 字段但只表达"任一/全部子工单已撤回"的简化语义。**这是 P4 阶段的核心设计点，需要单独评审。**
2. **删除/合并 DRAFT、PENDING 状态的兼容性**：旧数据需要迁移；前端筛选下拉、Dashboard 卡片、报表口径都依赖现状态值。改动需要 migration + 历史数据清洗 SQL。
3. **导入批量修改字段的并发**：可能与同一子工单的 `supplement` 流程冲突。需要复用 `supplement` 的乐观锁（`workOrderUpdatedAt`），并把 ImportJob 的执行做成单工单串行。
4. **历史工单按月查询的索引**：`work_orders` 当前主键 + `created_at` 应足够，但如果数据量大需在 `created_at` 上确认有索引。
5. **`dispatch/` 与 `dispatch-engine/`、`upload/` 与 `uploads/` 双目录并存**：会议没提及，但本次重构中容易踩到老代码——P1 中记录、P5 清理。
6. **`workflows/` 与 `dispatch-rules/` 并存**：会议结论是"先用基础派发"，所以 P1-P4 不引入 workflows，但要确保两套配置在管理员页面互不污染。

### 待确认项（建议任务分配前先和 Leader / 测试负责人确认）
1. **§F 主工单 DRAFT 是否保留**：业务员"暂存草稿"是否仍然是产品功能？会议没明确。
