# 业务规则回归清单

> 目的：把已经确认过的业务规则固化在项目内，避免后续修改时反复破坏旧规则。AI 或开发人员每次改动前必须先阅读本文件。

## 0. 规则优先级

本清单用于保护用户本次没有要求改变的旧规则，不用于压过用户最新明确要求。

优先级：

1. 用户当前最新明确要求。
2. 本清单中未被本次要求改变的既有规则。
3. Git commit、测试和历史文档。
4. AI 对话记忆或推断。

如果用户最新要求与本清单冲突，必须：

1. 明确指出冲突点。
2. 确认或判断用户是否明确要求覆盖旧规则。
3. 同步更新代码、测试、本清单。
4. 追加记录到 `docs/AI修改记录.md`。
5. 跑固定回归测试，确保未被覆盖的规则不被误伤。

## 1. 工单状态口径

系统统一使用以下 9 个子工单状态，页面筛选项不得随意新增、合并或改名：

1. 未接单：`pending`
2. 已接单：`processing`
3. 修改审批中：`modify_pending`
4. 撤回审批中：`withdraw_pending`
5. 作废审批中：`void_pending`
6. 已完成：`completed`
7. 已作废：`void`
8. 已撤回：`withdrawn`
9. 已退回：`returned`

注意：
- 页面筛选中不得再显示“未接单/已接单”这种合并选项。
- 单独筛选“未接单”只查 `pending`；单独筛选“已接单”只查 `processing`。
- 旧参数 `pending,processing` 可兼容，但不能作为页面显示选项。

## 2. 月份统计口径

工单流转统计按工单流转月份计算，不按完成时间计算。

当前列表/统计月份口径：
- 子工单列表的 `orderMonth`：按 `dispatched_at`，没有派发时间时按 `created_at`。
- 我的已办：按 `orderMonth`，不默认按 `completed_at`。
- 历史工单：按 `orderMonth`。
- 工单列表（入职/离职主工单、我的工单各子页、团队工单、历史工单、入职/离职子工单页）：默认月份为空、显示全部月份，按时间倒序；不传 `orderMonth`（子工单）或 `createdAfter`/`createdBefore`（主工单）。选择某月份只筛该月，清空月份恢复全部月份。
- 仪表盘：默认仍为当前月；用户切换月份后会被记住（缓存），离开再回来仍显示上次选择的月份；清空月份恢复当前月（仪表盘不做“全部月份”，保留 `allowClear={false}`）。

禁止事项：
- 不得把“我的已办”默认改回按完成时间 `completed_at`。
- 不得让 5 月派发/创建、6 月完成的工单默认归到 6 月已办统计。

## 3. 仪表盘口径

仪表盘体现工单最终流转状态：

- 未办结包含：未接单、已接单、修改审批中、撤回审批中、作废审批中、已撤回、已退回。
- 已完成：`completed`。
- 已作废：`void`。
- 当月工单总数 = 未办结 + 已完成 + 已作废。

后道仪表盘五项名称需与业务员仪表盘一致：
- 本月工单总数
- 单月待处理 / 本月待处理（按页面当前约定展示）
- 总待处理
- 本月已完成
- 本月已作废

## 4. 角色菜单矩阵

菜单可见性以 `frontend/src/config/routeVisibility.ts` 和 `frontend/src/layouts/BasicLayout.tsx` 为准。

### 管理员
- 可看全局数据和管理后台。
- 主工单列表默认 100 条/页，避免分页导致看不全。

### 业务负责人
- 只保留团队和历史相关入口。
- 不显示：我发起的、我的退回、我的待办、我的已办。
- 具体入职/离职模块不作为团队数据入口。

### 业务组长
- 入职/离职主工单、子工单普通模块：只看本人发起的数据。
- 团队数据只能在“我的工单 → 团队工单”查看。
- 仪表盘允许切换本人/团队。
- 不显示“我的待办”。

### 业务员
- 可看本人发起、我的退回、我的已办、历史工单。
- 不显示“我的待办”。
- 不显示团队工单。

### 后道人员
- 可看我的待办、我的已办、历史工单。
- 不显示：我发起的、我的退回。
- 普通模块列表按后道授权模块和处理范围展示。

## 5. 数据范围规则

- 业务组长在具体入职/离职模块（主工单 + 子工单）只看本人发起数据。
- 团队数据只在“团队工单”和仪表盘团队视角展示。
- 历史工单显示业务员有权限看到的全量子工单数据，不限状态。
- 后道普通模块列表需显示“发起人”列。
- 历史工单需显示“发起人”列。
- 子工单详情页需显示工单发起人。

## 6. 我的工单规则

### 我的待办
默认包含：
- 未接单 `pending`
- 已接单 `processing`
- 修改审批中 `modify_pending`
- 撤回审批中 `withdraw_pending`
- 作废审批中 `void_pending`

原因：审批中的单据仍需要后道处理，不能从我的待办消失。

### 我的已办
- 只显示已完成 `completed`。
- 月份按 `orderMonth`，不默认按 `completed_at`。
- 后道用户仍需按当前处理人过滤。
- 业务侧用户按本人/权限范围展示，不强制 `handlerId=current`。

### 我发起的 / 我的退回
- 显示子工单行，不再回退到主工单行。
- 保留月份筛选，默认月份为空（显示全部月份）。
- 表头字段筛选应生效。

### 团队工单
- 配置风格需和我的工单子页面一致：无顶部大搜索栏，保留月份筛选，表头字段筛选生效。
- 必须传 `scope=team`。

## 7. 表格筛选规则

以下页面必须支持表头字段筛选：
- 我的工单所有子页面
- 团队工单
- 历史工单
- 入职/离职子工单页面
- 入职/离职主工单页面

主工单筛选字段至少包含：
- 工单编号
- 客户代码
- 客户名称
- 员工姓名
- 员工证件号
- 发起人
- 订单类型

子工单筛选字段至少包含：
- 工单编号
- 子工单类型 / 工单类型
- 客户代码
- 客户名称
- 员工姓名
- 员工证件号
- 发起人
- 状态
- 实际操作人 / 配置负责人

## 8. 子工单详情页规则

- 必填字段用红色 `*` 标识。
- 选填字段不显示“选填”。
- 不要在字段旁显示“必填”文字。
- 子工单详情必须显示工单发起人。
- 我的工单、历史工单、团队工单入口进入详情后都应可按权限操作。
- 子工单详情“返回列表”应优先回到进入详情时的来源页面；来源缺失、非法或当前角色不可访问时，才回到该详情类型的默认安全列表。

## 9. 正式上线账号与首次改密规则

- 登录后主布局顶部必须有可见的“修改密码”入口；该入口是账号安全操作，不得通过新增业务菜单项或修改 `routeVisibility`/菜单矩阵实现。
- 默认密码首次登录后必须进入修改密码链路；前端修改密码请求必须向后端 `/auth/change-password` 传 `oldPassword` / `newPassword`，不得只传 `old_password` / `new_password`。
- 登录响应、`/auth/me` 刷新恢复和 mock refresh 必须同步 `mustChangePassword`/`must_change_password` 到 `userStore.mustChangePassword`；改密成功和退出登录后必须清除该标记，避免继续被路由守卫拦截。

## 10. 审批规则

- 未接单：业务员修改 / 撤回 / 作废无需后道审批，只通知后道。
- 已接单：业务员修改 / 撤回 / 作废必须提交后道审批。
- 已接单后业务员修改应进入 `modify_pending`，并保存修改记录。
- 后道审批通过修改后，应用业务员提交的字段修改。

## 11. 批量操作规则

- 后道待办需要支持批量接单。
- 我的工单相关子页面需要支持批量操作，不能只能单条处理。
- 入职/离职子工单页默认月份为空（显示全部月份），也可筛某个历史月份。
- 批量导入完成、批量改指定字段、批量退回需保持既有业务规则。

## 12. 消息提醒规则

- 消息“已读”功能保留：点击已读后提醒可消失。
- “处理”类提醒不能仅点击处理就消失；需工单办结或以其他方式结束（已完成、已作废、管理员删除等）后消失。

## 13. 显示文案规则

- 入职主工单列表按钮显示“入职批量导入”。
- 离职主工单列表按钮显示“离职批量导入”。
- 主工单页面不显示主工单状态列，只保留子工单进度。
- 子工单进度后缀需与子工单状态一致。
- “实际操作人/配置负责人”显示优先级：实际操作人 > 配置负责人 > 负责人未配置。

## 14. 全系统导航状态记忆与列表状态保留

- 菜单点击默认进入该菜单上次停留的合法**列表**路径，而不是总是回到初始列表。详情页/编辑页（工单详情、子工单详情、离职详情等）不写入菜单最近路径，点菜单回到对应列表页而不是进入详情；页面内的“返回列表”逻辑保持不变。
- 最近路径机制应尽量覆盖全系统菜单，不只覆盖“我的工单”。同一菜单下的列表、详情和带查询参数的合法路径应保持归属关系。
- 登录、改密、403、404、新建、导入等临时动作页默认不写入菜单最近路径；如后续新增临时动作页，需要同步加入排除项。
- 最近路径不能绕过权限：点击菜单前必须校验当前角色仍可访问该 lastPath；无权限、不合法、无路由匹配或当前阶段隐藏时，必须回退到该菜单默认 path。
- 入职/离职主工单共用 `/work-orders?orderType=onboarding` / `/work-orders?orderType=resignation` 时，菜单高亮、展开、跳转和最近路径必须按完整 pathname + search 区分，不能互相串扰。
- 列表状态应尽量保留筛选、月份、页码、pageSize、视图模式、表头筛选等状态；状态缓存需按列表/菜单作用域隔离，避免 A 列表状态污染 B 列表。
- 临时动作完成后返回列表时，应优先恢复原列表状态；但如果 URL 明确携带新查询条件，以 URL/用户最新操作为准。
- 该规则调整后至少覆盖 `BasicLayout.test.tsx`、`routeVisibility.test.ts`、`MultiViewTable/index.test.tsx`；涉及子工单详情返回来源时，还需覆盖 `MyDispatched/Detail/index.test.tsx`、各入口列表页测试和 `dispatchedDetailNavigation.test.ts`，并尽量运行 `./回归测试.ps1 -FrontendOnly`。
- 后台对当前用户的重校验（`visibilitychange`、`storage`、切菜单触发的 `/auth/me`）不得卸载主布局：`PrivateRoute` 只在「尚无用户的首次阻塞加载」时显示全屏 Loading，已有用户时即便 `loading=true` 也必须继续渲染 `BasicLayout`，否则会销毁 `KeepAliveOutlet` 缓存，导致批量导入等页面在窗口最小化/恢复后状态被清空。

## 15. 每次改动后的最低回归要求

至少运行：

```powershell
.\回归测试.ps1
```

如果只改前端，可运行：

```powershell
.\回归测试.ps1 -FrontendOnly
```

如果只改后端，可运行：

```powershell
.\回归测试.ps1 -BackendOnly
```

## 16. 禁止事项

- 禁止只按当前截图局部修，不检查影响面。
- 禁止改状态名称但不更新筛选、测试和后端枚举。
- 禁止改权限但不跑角色菜单测试。
- 禁止改月份口径但不跑我的工单/历史工单/仪表盘相关测试。
- 禁止提交 `.spectrai/`、上传 Excel、`frontend/tsconfig.tsbuildinfo` 等无关文件。

## 17. 电子签平台路由 / 离职三拆 / 入职 63 字段对齐 / 下拉选项集覆盖 / 三套导出模板

- 入职导入表以会议 Excel「杭州」sheet 标注行为权威口径（63 字段）：是否必填看 R3、下拉选项看 R4、条件必填看 R6、涉及工单看 R7。任何字段口径调整必须回到该表核对，不得凭印象改。
- 下拉选项集为表格全量覆盖口径：外包类型=全风险/风险后置；户籍性质=本地城镇/本地农村/外地城市/外地农村；证件类型 6 项；学历 6 项；婚姻状况=已婚/未婚；合同期限形式=固定期限/无固定期限/任务期限；工时制仅「标准工时制」；人员类型=全日制/非全日制/劳务合同/退休返聘（无实习生）；电子签平台=速创/E签宝。改动选项必须同步 5 处别名字典（seed-fields / field-validation HEADER_ALIASES / ai-mapping FIELD_ALIASES / excel-parser KNOWN_FIELD_LABELS / 前端 fields.ts + workOrders.ts）。
- 条件必填：need_company_contract=是 → need_esign/esign_platform/contract_subject/company_address/project_name/work_arrangement/need_contract_urge 必填；need_company_payroll=是 → payroll_location 必填；need_onboarding_contact 必填；need_onboarding_contact=是 → feedback_deadline/is_common_template 必填；template_name 仅在 need_onboarding_contact=是 且 is_common_template=是 时必填。`contract_template` 不再作为业务员入职导入模板/导入校验必填项，但不得全局停用，后道反馈、详情、导出等非入职导入场景仍可使用。前后端两套机制（seed conditionalRequired AST + 前端 CONDITIONAL_REQUIRED_BY_TYPE）必须同时改。
- 离职减员表 10 字段口径（全必填，sheet「社保公积金减员」）：前 7 字段（employee_name/id_card_no/social_pay_region/social_stop_month/resignation_reason/resignation_date/need_resignation_share）流转至「离职材料收集 + 数据录入 + 社保公积金减员」三单；后 3 字段（feedback_deadline/is_common_template/template_name）仅流转离职材料收集。离职派发必须三拆，缺一即回归不通过。
- 导出模板平台路由：仅 contract 模块按主工单 extraData['esign_platform']（速创/E签宝）匹配 export_templates.sign_platform 选模板；无平台值时回落到同模块共享模板。
- 三套种子导出模板（seed-export-templates.ts，is_shared=true，按 templateName+moduleCode(+signPlatform) 幂等）：
  - 入职联系 onboarding_contact = 8 列单行表头（姓名/联系电话/证件号码/需要反馈截止日期/是否为通用模板/模板名称/邮箱（选填）/发起人）。
  - 劳动合同-速创 contract/速创 = 38 列，表头两行（字段名行 + 填写说明行），列序与会议「劳动合同签订批导出模板-速创」一致，并在末尾增加「发起人」；无数据源列走 const（空或表注默认值，如签订方式=新签、版本=013.2021版、工资支付方=甲方）。
  - 劳动合同-e签宝 contract/E签宝 = 31 列、4 行表头（R1 文件名 / R2 字段名 / R3 绑定串 / R4 填写说明），R1/R2/R3 含绑定串必须原样逐字复刻（含部分列尾随空格），数据从第 5 行起，并在末尾增加「发起人」；派生列用 sameAs（姓名/证件号码/联系电话/居住地址同对应签署方2 或 L/F 列）、固定列用 const（合同名称空、工时制=1）。换正式 e签宝 模板时需替换 R3 绑定串行。
- 列模型扩展：export-templates.service.ts 的 field_list 每列支持 { fieldCode | const | sameAs, header: string|string[] }；header 为数组即多行表头（数组分支不 trim，保留尾随空格逐行写出）。管理后台导出模板页面允许配置三类列：业务字段列（从工单/extraData 取值）、空值字段列（`const: ''`，导出固定空白）、默认值字段列（`const: '默认值'`，导出固定值）；sameAs/公式/多行表头仍作为后端种子模板能力保留，普通页面暂不开放复杂编辑。改导出引擎或导出模板页面需跑 `npx jest --config ./test/jest-unit.json --runInBand export-template` 与前端导出模板相关测试。
- 导出系统字段规则（按 2026-06-10 最新用户要求覆盖旧身份列前置规则）：不管模板如何配置，导出时一律不得输出「工单编号(order_no)」和「员工证件号(employee_id_card)」两个系统身份列；批量回填匹配可使用导出表中的「证件号码(id_card_no)」等别名匹配，不依赖这两个系统字段，后端匹配需同时兼容主表 `employee_id_card` 与 `extra_data.id_card_no`/旧别名字段。所有导出模板（共享模板、手选模板、fallback 动态模板、三套平台模板）都必须在末尾增加「发起人(created_by_name)」列；如模板已配置发起人则不重复追加。回归点：导出三套平台模板和普通模块默认导出时均确认无「工单编号/员工证件号」，且存在「发起人」。
