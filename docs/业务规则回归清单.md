# 业务规则回归清单

> 目的：把已经确认过的业务规则固化在项目内，避免后续修改时反复破坏旧规则。AI 或开发人员每次改动前必须先阅读本文件。

## 0. 规则优先级

本清单用于保护用户本次没有要求改变的旧规则，不用于压过用户最新明确要求。

优先级：

1. 用户当前最新明确要求。
2. 本清单中未被本次要求改变的既有规则。
3. Git commit、测试和历史文档。
4. AI 对话记忆或推断。

如果用户最新要求与本清单冲突，必须：

1. 明确指出冲突点。
2. 确认或判断用户是否明确要求覆盖旧规则。
3. 同步更新代码、测试、本清单。
4. 追加记录到 `docs/AI修改记录.md`。
5. 跑固定回归测试，确保未被覆盖的规则不被误伤。

## 1. 工单状态口径

系统统一使用以下 9 个子工单状态，页面筛选项不得随意新增、合并或改名：

1. 未接单：`pending`
2. 已接单：`processing`
3. 修改审批中：`modify_pending`
4. 撤回审批中：`withdraw_pending`
5. 作废审批中：`void_pending`
6. 已完成：`completed`
7. 已作废：`void`
8. 已撤回：`withdrawn`
9. 已退回：`returned`

注意：
- 页面筛选中不得再显示“未接单/已接单”这种合并选项。
- 单独筛选“未接单”只查 `pending`；单独筛选“已接单”只查 `processing`。
- 旧参数 `pending,processing` 可兼容，但不能作为页面显示选项。

## 2. 月份统计口径

工单流转统计按工单流转月份计算，不按完成时间计算。

当前列表/统计月份口径：
- 子工单列表的 `orderMonth`：按 `dispatched_at`，没有派发时间时按 `created_at`。
- 我的已办：按 `orderMonth`，不默认按 `completed_at`。
- 历史工单：按 `orderMonth`。
- 入职/离职主工单列表：默认当前月，可切换历史月份。
- 入职/离职子工单页面：默认当前月，可切换历史月份。

禁止事项：
- 不得把“我的已办”默认改回按完成时间 `completed_at`。
- 不得让 5 月派发/创建、6 月完成的工单默认归到 6 月已办统计。

## 3. 仪表盘口径

仪表盘体现工单最终流转状态：

- 未办结包含：未接单、已接单、修改审批中、撤回审批中、作废审批中、已撤回、已退回。
- 已完成：`completed`。
- 已作废：`void`。
- 当月工单总数 = 未办结 + 已完成 + 已作废。

后道仪表盘五项名称需与业务员仪表盘一致：
- 本月工单总数
- 单月待处理 / 本月待处理（按页面当前约定展示）
- 总待处理
- 本月已完成
- 本月已作废

## 4. 角色菜单矩阵

菜单可见性以 `frontend/src/config/routeVisibility.ts` 和 `frontend/src/layouts/BasicLayout.tsx` 为准。

### 管理员
- 可看全局数据和管理后台。
- 主工单列表默认 100 条/页，避免分页导致看不全。

### 业务负责人
- 只保留团队和历史相关入口。
- 不显示：我发起的、我的退回、我的待办、我的已办。
- 具体入职/离职模块不作为团队数据入口。

### 业务组长
- 入职/离职主工单、子工单普通模块：只看本人发起的数据。
- 团队数据只能在“我的工单 → 团队工单”查看。
- 仪表盘允许切换本人/团队。
- 不显示“我的待办”。

### 业务员
- 可看本人发起、我的退回、我的已办、历史工单。
- 不显示“我的待办”。
- 不显示团队工单。

### 后道人员
- 可看我的待办、我的已办、历史工单。
- 不显示：我发起的、我的退回。
- 普通模块列表按后道授权模块和处理范围展示。

## 5. 数据范围规则

- 业务组长在具体入职/离职模块（主工单 + 子工单）只看本人发起数据。
- 团队数据只在“团队工单”和仪表盘团队视角展示。
- 历史工单显示业务员有权限看到的全量子工单数据，不限状态。
- 后道普通模块列表需显示“发起人”列。
- 历史工单需显示“发起人”列。
- 子工单详情页需显示工单发起人。

## 6. 我的工单规则

### 我的待办
默认包含：
- 未接单 `pending`
- 已接单 `processing`
- 修改审批中 `modify_pending`
- 撤回审批中 `withdraw_pending`
- 作废审批中 `void_pending`

原因：审批中的单据仍需要后道处理，不能从我的待办消失。

### 我的已办
- 只显示已完成 `completed`。
- 月份按 `orderMonth`，不默认按 `completed_at`。
- 后道用户仍需按当前处理人过滤。
- 业务侧用户按本人/权限范围展示，不强制 `handlerId=current`。

### 我发起的 / 我的退回
- 显示子工单行，不再回退到主工单行。
- 保留月份筛选，默认当前月。
- 表头字段筛选应生效。

### 团队工单
- 配置风格需和我的工单子页面一致：无顶部大搜索栏，保留月份筛选，表头字段筛选生效。
- 必须传 `scope=team`。

## 7. 表格筛选规则

以下页面必须支持表头字段筛选：
- 我的工单所有子页面
- 团队工单
- 历史工单
- 入职/离职子工单页面
- 入职/离职主工单页面

主工单筛选字段至少包含：
- 工单编号
- 客户代码
- 客户名称
- 员工姓名
- 员工证件号
- 发起人
- 订单类型

子工单筛选字段至少包含：
- 工单编号
- 子工单类型 / 工单类型
- 客户代码
- 客户名称
- 员工姓名
- 员工证件号
- 发起人
- 状态
- 实际操作人 / 配置负责人

## 8. 子工单详情页规则

- 必填字段用红色 `*` 标识。
- 选填字段不显示“选填”。
- 不要在字段旁显示“必填”文字。
- 子工单详情必须显示工单发起人。
- 我的工单、历史工单、团队工单入口进入详情后都应可按权限操作。
- 子工单详情“返回列表”应优先回到进入详情时的来源页面；来源缺失、非法或当前角色不可访问时，才回到该详情类型的默认安全列表。
- 劳动合同新签子工单详情字段以管理后台最新启用的“详情页字段配置”为准，不得使用速创/E签宝批导出模板字段并集替代。
- `business_group_member` / `biz_member` 可编辑劳动合同新签活动详情配置内的全部字段，配置外字段隐藏；已接单或已完成工单仍走 `modify_pending` 修改审批，不获得管理员流程豁免。

## 9. 正式上线账号与首次改密规则

- 登录后主布局顶部必须有可见的“修改密码”入口；该入口是账号安全操作，不得通过新增业务菜单项或修改 `routeVisibility`/菜单矩阵实现。
- 默认密码首次登录后必须进入修改密码链路；前端修改密码请求必须向后端 `/auth/change-password` 传 `oldPassword` / `newPassword`，不得只传 `old_password` / `new_password`。
- 登录响应、`/auth/me` 刷新恢复和 mock refresh 必须同步 `mustChangePassword`/`must_change_password` 到 `userStore.mustChangePassword`；改密成功和退出登录后必须清除该标记，避免继续被路由守卫拦截。

## 10. 审批规则

- 未接单：业务员修改 / 撤回 / 作废无需后道审批，只通知后道。
- 已接单：业务员修改 / 撤回 / 作废必须提交后道审批。
- 已接单后业务员修改应进入 `modify_pending`，并保存修改记录。
- 后道审批通过修改后，应用业务员提交的字段修改。
- 已完成：业务员修改 / 撤回 / 作废必须进入对应审批状态，原数据在审批通过前不生效；修改审批通过或拒绝后恢复 `completed` 时保留原办结时间。
- 已完成子工单可由当前办理人、模块主管或管理员填写原因后退回；业务员不能直接执行退回。
- 修改字段若会影响其他已完成兄弟子工单，仍需阻止一次审批跨模块生效，必须分别处理。

## 11. 批量操作规则

- 后道待办需要支持批量接单。
- 我的工单相关子页面需要支持批量操作，不能只能单条处理。
- 入职/离职子工单页默认当前月，也可筛历史月份。
- 批量导入完成、批量改指定字段、批量退回需保持既有业务规则。

## 12. 消息提醒规则

- 消息“已读”功能保留：点击已读后提醒可消失。
- “处理”类提醒不能仅点击处理就消失；需工单办结或以其他方式结束（已完成、已作废、管理员删除等）后消失。

## 13. 显示文案规则

- 入职主工单列表按钮显示“入职批量导入”。
- 离职主工单列表按钮显示“离职批量导入”。
- 主工单页面不显示主工单状态列，只保留子工单进度。
- 子工单进度后缀需与子工单状态一致。
- “实际操作人/配置负责人”显示优先级：实际操作人 > 配置负责人 > 负责人未配置。

## 13.1 入职批量导入字段必填规则

- **合同终止日期条件必填**：
  - 当“合同期限形式”为“无固定期限”时，“合同终止日期”非必填。
  - 当“合同期限形式”为“固定期限”或“任务期限”时，“合同终止日期”必填。
  - 该规则同样适用于单条入职工单新建和编辑。

## 14. 全系统导航状态记忆与列表状态保留

- 菜单点击默认进入该菜单上次停留的合法路径，而不是总是回到初始列表；详情页可以作为菜单最近路径。例如从“我的工单 -> 我发起的”进入 `/my-dispatched/:id`，切到“我的退回”后再点“我发起的”，应回到刚才详情页。
- 最近路径机制应尽量覆盖全系统菜单，不只覆盖“我的工单”。同一菜单下的列表、详情和带查询参数的合法路径应保持归属关系。
- 登录、改密、403、404、新建、导入等临时动作页默认不写入菜单最近路径；如后续新增临时动作页，需要同步加入排除项。
- 最近路径不能绕过权限：点击菜单前必须校验当前角色仍可访问该 lastPath；无权限、不合法、无路由匹配或当前阶段隐藏时，必须回退到该菜单默认 path。
- 入职/离职主工单共用 `/work-orders?orderType=onboarding` / `/work-orders?orderType=resignation` 时，菜单高亮、展开、跳转和最近路径必须按完整 pathname + search 区分，不能互相串扰。
- 列表状态应尽量保留筛选、月份、页码、pageSize、视图模式、表头筛选等状态；状态缓存需按列表/菜单作用域隔离，避免 A 列表状态污染 B 列表。
- 临时动作完成后返回列表时，应优先恢复原列表状态；但如果 URL 明确携带新查询条件，以 URL/用户最新操作为准。
- 该规则调整后至少覆盖 `BasicLayout.test.tsx`、`routeVisibility.test.ts`、`MultiViewTable/index.test.tsx`；涉及子工单详情返回来源时，还需覆盖 `MyDispatched/Detail/index.test.tsx`、各入口列表页测试和 `dispatchedDetailNavigation.test.ts`，并尽量运行 `./回归测试.ps1 -FrontendOnly`。

```

```

## 16. 禁止事项

- 禁止只按当前截图局部修，不检查影响面。
- 禁止改状态名称但不更新筛选、测试和后端枚举。
- 禁止改权限但不跑角色菜单测试。
- 禁止改月份口径但不跑我的工单/历史工单/仪表盘相关测试。
- 禁止提交 `.spectrai/`、上传 Excel、`frontend/tsconfig.tsbuildinfo` 等无关文件。

## 17. 电子签平台路由 / 离职三拆 / 入职 63 字段对齐 / 下拉选项集覆盖 / 三套导出模板

- 入职导入表以会议 Excel「杭州」sheet 标注行为权威口径（63 字段）：是否必填看 R3、下拉选项看 R4、条件必填看 R6、涉及工单看 R7。任何字段口径调整必须回到该表核对，不得凭印象改。
- 下拉选项口径：所有「是否」类字段下拉一律为「是 / 否」，**唯一例外**是「是否电子签」(need_esign) 为「1.是 / 2.否」（含其条件必填表达式 need_esign=1.是、esign_platform 依赖 need_esign=1.是）。导出/导入模板对 need_esign 渲染 1.是/2.否、对其余是否字段渲染 是/否。不得再把全部是否字段统一改成 1.是/2.否。
- 条件必填：need_company_contract=是 → contract_subject/need_contract_urge 必填；need_company_payroll=是 → payroll_location 必填；need_onboarding_contact 必填；need_onboarding_contact=是 → feedback_deadline/is_common_template 必填；template_name 仅在 need_onboarding_contact=是 且 is_common_template=否 时必填（方案A翻转：通用模板=是→非必填，通用模板=否→必填；2026-06-25 覆盖原“通用模板=是时必填”口径）。另：后台“导入模板配置”对 feedback_deadline/is_common_template/template_name 等条件字段显式设置导入必填覆盖（isRequiredOverride 非 null）时，以后台配置为准并清掉内置条件必填，使导出模板与后台页面显示一致。`contract_template`（劳动合同模板（标准模板/特殊模板））仍出现在业务员入职导入模板中，但在导入下载/校验阶段不作必填（导入阶段清空其条件必填），导入不强制填写；其在单条新增页面仍按 need_company_contract=是 条件必填。
- 现住地址条件必填：`need_onboarding_contact=否` 时 `current_address` 必填；其他情况保持非必填。单条新建、子工单修改/重提、导入预览和正式导入必须执行同一规则。
- 试用期条件必填：`probation_start_date` 非必填；其有值时 `probation_months`、`probation_end_date`、`probation_salary` 必填。导入根据开始日期和月数自动生成的结束日期视为已填写。
- 入职工资文本口径：`base_salary`（基本工资）与 `probation_salary`（试用期工资）均为文本字段，允许数字、货币格式或文字说明并按原文保存；`base_salary` 继续必填，`probation_salary` 继续遵循上述试用期条件必填。该口径不扩展到续签工资、社保基数、公积金基数等仍为数字的字段。
- 业务员入职导入模板不输出后道反馈/处理字段：`contract_feedback`（劳动合同新签反馈）、`onboarding_feedback`（入职联系反馈）、`data_entry_feedback`（增员报岗录入反馈）。`contract_template`（劳动合同模板）属业务员发起阶段字段，必须保留在入职导入模板与单条新增页面，不再从导入模板排除。该排除仅限入职导入模板和入职导入校验，不得影响后道详情、反馈、字段权限、导出等业务。
- 导入模板字段必须以 `import_template_fields` 配置表为优先来源；无配置时才回退系统默认规则（入职排除上述四字段，离职按减员表默认字段白名单）。后台“导入模板配置”页面应能保存字段出现与否、顺序、Excel 表头别名和导入必填覆盖；导入模板下载、导入预览候选字段、导入确认校验必须同源读取该配置，不能只影响下载。
- 劳动合同新签子工单导出必须按主工单 `extraData.esign_platform` 自动匹配共享模板：`速创` 使用速创模板，`E签宝` 使用 E签宝模板。批量导出混合勾选速创/E签宝时，必须按 `moduleCode + esign_platform` 拆分生成不同模板 sheet，不得用第一条工单的平台套用全部数据；非劳动合同模块不使用电子签平台参与导出模板路由。劳动合同缺少电子签平台或平台没有对应模板时必须明确报错，不得兜底到任意一套劳动合同共享模板。劳动合同两套固定导出必须以用户提供的标准 Excel 文件为底板填充数据，保留原工作表结构、表头行、隐藏行、合并单元格、隐藏选项 sheet 和样式；后台导出模板配置中也必须能看到“劳动合同签订批导出模板-速创”和“劳动合同签订批导出模板-e签宝”两套共享模板，手写字段配置的列名、列序、绑定串、默认值/公式映射必须与标准 Excel 一致，作为管理员可编辑/查看的模板元数据；因 ExcelJS 兼容限制导致无法写出的数据验证规则可清理，但不得改变可见模板结构和字段列序。

## 18. 在职单项业务与省外派单映射

- 在职单项业务使用模块码 `in_service_single_business` 与 `mappingSource=sheet4`，省外增减员共用模块码 `out_of_province_dispatch` 与 `mappingSource=sheet5`；运行时仅查询 `<moduleCode>__<province>` 对应的现有 `module_handlers` 行，同一省份不得跨 Sheet 兜底或混用处理人。
- 双人省份按配置原文首个 `/` 的顺序落库：排前者为 `isBackup=false, weight=100` 的默认接单人，排后者为 `isBackup=true, weight=1` 的转派备选，首次派单不轮询也不在主办停用时自动使用备选。Sheet4 双人省份为湖北、江苏、山西、山东、福建；Sheet5 双人省份仅福建。
- 新模块省份缺失、非法、无映射或无活动主办时返回空 handler，进入待指派/模块池，不读取另一张 Sheet，也不回落新模块的无省份默认人；无 mappingSource 的入职、续签、离职等旧派单继续走原有 `ModuleHandler` 团队、权重和策略链路。
- 省份源严格使用配置表的 27 省：包含新疆、宁夏，不包含浙江、青海；Sheet4/Sheet5 均按这 27 省生成完整活动映射。配置姓名在系统 `users` 表中没有正式账号时，只记录 warn 并保留空 handler，禁止创建猜测账号、跨表兜底或虚构处理人。
- `dispatch_rules.assignee_user_id` 与 `fallback_user_id` 为保留死字段：不删除，但新派单逻辑禁止读取。真实专员名册缺失时不得臆造处理人；占位账号查找失败需 warn 并跳过单个候选，不阻断整批 seed。

## 19. 在职单项业务后端状态机与表单

- 在职单项业务固定使用 `OrderType.IN_SERVICE` 与模块码 `in_service_single_business`。新建表单以《在职模块-工单系统配置表（派单+单项业务）》为权威源，必须包含客户全称、发起部门、期望完成日期、办理事由、一级/二级/三级分类、缴纳省/市/区、客户支付服务费、最多 5 个附件和订单内容；配置表外的联系电话、优先级不得强制填写，办理渠道由办理人在材料确认后选择。
- 分类树固定为 4 个一级、19 个二级、6 个三级项；只有补缴、退费、信息变更存在三级分类，其余二级分类的三级字段不必填。省份固定使用同表映射的 27 省简称，包含新疆、宁夏，不包含浙江、青海。
- 三个在职工单均不经过业务组长审批。单项业务创建时直接读取 Sheet4 同省主办并进入 `dispatched`（待受理）；映射账号缺失时 handler 可为空并显示“待配置”，不得恢复审批草稿或开放 `/in-service/:id/audit`。
- 单项业务节点为：待受理 `dispatched` -> 已受理待初审 `accepted` -> 完成材料初审 `ready` -> 线上/线下办理 `processing` -> 办理成功 `completed` 或办理失败 `failed`。发起人可在非终态取消订单进入 `cancelled`；受理人可在待受理/已受理节点转派，转派后回待受理并记录历史。
- 两类补料回环必须区分：材料初审退回从 `accepted -> pending_info`，发起人重提后回 `dispatched` 重新受理；办理阶段补料从 `processing -> pending_info`，发起人重提后直接回 `processing` 并保留原办理人和渠道。两种回环均可重复，非法流转返回 HTTP 400。
- 列表必须显示工单号、客户、办理事由、分类、缴纳地、期望完成日期、状态、办理渠道、配置负责人、发起人和创建时间；空列表提供“新建单项业务”入口。详情按状态只展示合法动作按钮，并显示五阶段进度、完整业务字段、办理结果和流转记录。
- CRUD 与动作端点沿用 JWT、发起人、当前办理人和管理角色边界；不改变既有入职、续签、离职、待遇申报派单与九种子工单状态规则。劳动合同续签、待遇申报占位路由及 `/renewal`、`/benefit` 旧别名继续冻结。

## 21. 2026-07-29 会议口径：直单业务、证明和省外增减员

### 21.1 工单结构

- 入职管理、离职管理继续保留既有“主工单发起后拆分子工单”结构。
- 在职管理的劳动合同续签、证明开具、单项业务办理均为分别发起的独立工单，不创建在职主工单，也不自动拆分子工单。
- 离职管理新增独立“离职证明”子页面；离职证明由业务员从该页面单独发起，不由离职材料完成钩子自动创建。
- 历史 `resignation_cert` 离职材料收集子工单仅作数据兼容，不得与新的 `resignation_certificate` 独立工单混用。

### 21.2 在职与离职证明

- 证明开具使用独立直单：在职证明、收入证明已启用，并使用用户提供的北仑通用 DOCX 模板导出。
- 社保证明类型保留，但模板为空且入口禁用；未取得标准模板前不得用其他证明模板代替。
- 离职证明使用独立列表与发起页，归属离职管理；没有离职证明标准模板时只保留工单办理，不虚构导出模板。
- 独立离职证明列表入口仅对管理员、业务侧发起角色及办理人杨纯/江璐对应角色开放；社保岗不得显示该菜单，直接访问 `/resignation-certificates` 必须进入 403。业务侧仍可从独立页面发起并查看本人创建的离职证明。
- 历史 `resignation_cert` 子工单仅杨纯（`yangchun`）、江璐（`jianglu`）和管理员可读取；父工单创建人、社保岗及其他后道角色不得通过主工单列表、主工单详情或子工单详情旁路访问。
- 劳动合同续签默认签订方式为“续签”，复用新签合同字段与输出口径；试用期字段保留但非必填、默认留空。

### 21.3 北仑单项业务

- 分类以 Excel Sheet4 为权威源，固定保留 4 个一级、19 个二级、6 个三级分类。
- 每张单项业务工单独立发起，按 Sheet4 的省份主办配置直接派单；真实账号不存在时显示“待配置”，不得创建猜测账号。
- 发起人可在非终态作废；已接单后的材料修改使用独立申请和审批，审批前不覆盖原字段。
- 材料修改申请仅允许从 `accepted` / `processing` 发起，由原办理人或管理角色审批；通过或拒绝后恢复原状态和原办理人。

### 21.4 省外增减员

- 浙江自签省外业务仅保留增员、减员和单项业务，不包含北仑入职、劳动合同签订等模块。
