## 2) 测试数据来源

`dispatched_orders` 表里出现「大量测试数据」可能来自以下三条路径，按数量影响排序：

### 2.1 seed 脚本 — 不直接写 `dispatched_orders`

`backend/src/database/seeds/*` 共 11 个 seed：

| 文件 | 写哪些表 |
|---|---|
| seed-customers.ts / seed-roles.ts / seed-departments.ts / seed-users.ts / seed-fields.ts / seed-field-permissions.ts / seed-dispatch-rules.ts / seed-module-configs.ts / seed-module-handlers.ts / seed-notification-templates.ts | 基础字典/角色/用户/模块/字段权限/派发规则 |
| seed-on-bootstrap.service.ts | 应用启动时按需注入上述 seed |

**grep 结果**：`dispatched|DispatchedOrder` 关键字在 seed 目录下只命中 `seed-notification-templates.ts`（用作通知模板里的链接占位）和 `seed-field-permissions.ts`（字段权限场景常量），**没有任何 seed 会向 `dispatched_orders` 写入数据**。

结论：每次 `npm run seed` 重启并**不会**新增「部门子工单」测试数据。

### 2.2 `tests/phase6-seed-data.sql` —— 看板验收预热脚本（高嫌疑头号）

`tests/phase6-seed-data.sql` 是项目里唯一直接 `INSERT INTO dispatched_orders ...` 的 SQL：

- 路径：`tests/phase6-seed-data.sql`（170 行）
- 用法注释：`psql -h 127.0.0.1 -p 5432 -U ticket -d ticket_system -f tests/phase6-seed-data.sql`
- 预期数据量：**30 条 work_orders + 60 条 dispatched_orders**，分布在 6 个 module、4 种状态、含 SLA 超期样本。
- 关键标记：work_order.extra_data.source = `'phase6_seed'`，订单号前缀 `PH6-YYYYMMDD-NNN`。
- `ON CONFLICT (parent_order_id, module_code) DO UPDATE` —— 反复跑会刷新但不会无限增量。
- **每次 PH6-{今天} 都会重置 30/60 条**，跨日期跑过几次的话 `PH6-` 前缀的工单数 = 跑过的"日期数 × 30"。

> 这是「测试数据」里**最可识别**、**最易批量清理**的部分：`WHERE order_no LIKE 'PH6-%'` 即可定位。

`Glob backend/scripts/**/*` 返回 **0 文件**。也没有 `seed-onboarding-test-data` 之类的脚本。即 backend 端没有「reset + 一键 seed dispatched_orders」工具脚本。

```
admin/module-handlers、admin/departments、admin/customers、

```

### 3.4 「关闭/退回/作废」状态是否能替代删除

| 状态 | 来源 | 能用来「删」吗 |
|---|---|---|
| `returned`（dispatched） | `:id/return` 接口 | 否，业务语义是「材料缺失退回补充」，仍要继续处理 |
| `completed`（dispatched） | `:id/complete` 接口 | 否，业务语义是办结，列表默认仍展示 |
| `withdrawn`（work_order，**仅主单**） | 代码中**没有**调用方在写它（仅 enum 声明） | 实际上属于「保留 enum 占位」，未接通 |
| 无 cancelled / voided / archived | — | — |

**结论**：现有任何状态都**无法**替代「删除」。「批量完成」会把测试数据混进真实订单的 KPI / 看板，**绝不能**用它去清测试数据。

### 3.5 软删 vs 硬删 vs 级联

`backend/src/entities/dispatched-order.entity.ts`：

- `parentOrder` 关系：`@ManyToOne(() => WorkOrder, ..., { onDelete: 'CASCADE' })` —— **主工单 DELETE 时数据库会自动级联删除其全部子单**。
- 没有 `@DeleteDateColumn` / `deleted_at` 字段 → 当前不支持 TypeORM 软删。

`backend/src/entities/work-order.entity.ts`：

- 没有 `deleted_at` / `is_deleted` / `archived_at` 字段。
- `created_by` / `department_id` / `customer_id` / `branch_id` 关系都是 `onDelete: 'RESTRICT'` —— **删除主工单本身没问题**，但删除用户/部门/客户时会因有未删工单引用而被拒绝（这意味着我们删主工单的方向是被允许的）。

### 3.6 权限边界建议

| 角色 | 删除权 | 理由 |
|---|---|---|
| `admin` | 可硬删任意子单 + 主单 | 测试数据清理是 admin 的常规职责 |
| `business_owner`（业务负责人） | 可建议软删本业务条线下的工单 | 跨业务线易出事，先不放开 |
| `business_group_leader` / `shared_team_owner` / `data_entry_leader` | **不放开** | 业务规则里这几个角色「重分派」即可，删除超出他们职责 |
| 业务员 / 处理人 | **不放开** | 仅能撤回（withdraw）草稿，已派发的不允许删 |

## 4) Hotfix 方案建议（路线图）

> 提供 A、B、C 三种路线供 Leader 拍板。建议**A + B 叠加**，由 B 立即止血，A 提供长期能力。

### 方案 A：补「删除子工单」接口 + 前端按钮（推荐主路线）

#### 范围

1. 后端
   - 在 `dispatched-order.controller.ts` 新增 `@Delete(':id')` + `@Delete('batch')` 接口；
   - 在 `work-order.controller.ts` 新增 `@Delete(':id')`（依赖 entity 已有 `onDelete:'CASCADE'`，主单 DELETE 会自动级联清子单）；
   - 用 `@Roles('admin')` + `@Audit('dispatched_orders','delete')` 守护；
   - 写 `operation_log`（after=null + before 快照）。
2. 前端
   - 在 `TeamDispatched/index.tsx` 操作列加「删除」按钮（admin 可见）；
   - `tableAlertRender` 加「批量删除」+ `Popconfirm` 二次确认；
   - 顶部为 admin 加「清理测试数据」入口（按下文 D 选项可选）。
3. QA
   - 验证：不可越权（非 admin 删返回 403）；删除子单不影响兄弟子单；删除主单级联清子单。
   - 验证：操作日志写入 + ProTable 重新拉取。

#### 软删 or 硬删

**推荐：硬删主工单 + 子工单（CASCADE）**，理由：

- 当前没有 `deleted_at` 列，加列就要 migration；
- 真实场景下测试数据要清的就是物理空间；
- 误删风险用「Popconfirm + 二次确认 + Audit Log」覆盖即可；
- 如果未来需要回收站，可在第二期再补软删 + Trash 列表。

#### 人时估算

| 角色 | 工时 | 任务 |
|---|---|---|
| 后端 | 4 h | 2 个 DELETE 接口 + DTO + Roles/Audit + 单测（覆盖 admin 通过 / 非 admin 403 / 主单级联） |
| 前端 | 3 h | 操作列删除按钮 + 批量删除 + Popconfirm + service.ts 新增方法 + admin 角色判断 |
| QA | 2 h | 用例：单删 / 批删 / 越权 / 级联 / 已完成单是否允许删（建议允许）+ UI 截图 |

**合计：9 h（约 1.5 人日）**

### 方案 B：临时清理脚本一键清测试数据（紧急止血路线）

> 立刻能跑、零代码改动、零接口。**仅在 Leader 同意时手工执行。**

写一份 SQL（建议放 `tests/cleanup-phase6-and-e2e-data.sql`）：

```sql
-- 1) 仅清 phase6 看板预热数据（最稳）
DELETE FROM work_orders WHERE extra_data->>'source' = 'phase6_seed';
-- 通过 CASCADE 会同时清掉对应的 dispatched_orders

-- 2) （可选 — 需 Leader 拍板）清 PH6- 前缀的全部主单
DELETE FROM work_orders WHERE order_no LIKE 'PH6-%';

-- 3) （高风险，最后再考虑）清测试员工名/客户名匹配的工单
-- DELETE FROM work_orders WHERE employee_name LIKE '看板员工%' OR employee_name LIKE '测试%';
```

#### 人时估算

| 角色 | 工时 | 任务 |
|---|---|---|
| 后端 / 架构师 | 1 h | 写 SQL + Dry-run（`SELECT COUNT(*) ...`）确认条数 + Leader 拍板范围 |
| QA | 0.5 h | 在 staging 跑一次，截图清前/清后条数对比 |

**合计：1.5 h**

**致命局限**：只解决「现存数据」，**不解决未来又被 e2e/QA 脚本灌进来的问题**。所以建议必须配合 A 使用。

### 方案 C：用 `archived` 列做软删（次推荐）

> 如果 Leader 顾虑「硬删怕不可逆」，可走这条。

- 加一个 `archived_at TIMESTAMPTZ` 列 + migration；
- 列表接口默认 `WHERE archived_at IS NULL`；
- 「删除」按钮改为「归档」；
- 加 admin 专属「回收站」页查 `WHERE archived_at IS NOT NULL`。

#### 人时估算

| 角色 | 工时 |
|---|---|
| 后端 | 8 h（migration + 实体 + 列表 where + 归档/恢复接口） |
| 前端 | 6 h（删除 + 回收站列表页 + 恢复按钮） |
| QA | 4 h |

**合计：18 h（约 2.5 人日）**

### 方案 D（可选附加项）：标记测试数据

新增列 `data_source TEXT NULL`（值如 `phase6_seed` / `e2e_test` / `import` / `manual`），让 e2e 脚本和 phase6 SQL 主动打标。配合 admin 列表加「仅显示测试数据」筛选，删除时就能"只清测试不动真实"。

人时：后端 2 h + 前端 1 h + QA 1 h = **4 h**。可与 A 合并到第二期再做。

### 推荐组合

> **A + B 叠加，第一期落地。**

- B 当晚跑掉存量（约 1.5 h）；
- A 同步排上（9 h，约 1.5 人日 = 2 个工作日内完成）；
- D 留作第二期（带筛选 + 清理路径会更优雅）。

## 5) 风险与边界

| 风险点 | 现状 | 建议 |
|---|---|---|
| 子工单删了主工单怎么办 | 没规定 | 删子工单**不**反向删主单（避免一删全删）；保留主单可让业务员看到「拆了 N 子单，其中一个被 admin 清掉」 |
| 主工单删了子工单怎么办 | entity 已声明 `onDelete:'CASCADE'` | 主单删，子单自动 CASCADE 删 — 这是数据库行为，但要在 UI 提示 admin |
| 是否软删 + 回收站 | 当前无 `deleted_at` 列 | 推荐**先硬删 + Audit Log**，第二期再决定是否补软删 |
| operation_log 是否记录 | 现有 admin 删用 `@Audit('xxx','delete')` 装饰器 | 强制 `@Audit('dispatched_orders','delete')` + before 快照 JSON，after=null |
| 关联表是否要清 | `field_supplement_logs` 关联 `dispatchedOrderId` 外键约束 | 检查 entity 上是否有 CASCADE / SET NULL；如果没有需要先清子表 |
| 通知 `notifications`、`operation_logs` 里的 link 是否会变死链 | 会有死链 | 死链可接受，列表层做空值兜底即可 |
| 业务员 / 主管 已经"接单"的子单能删吗 | 业务上不应该 | UI 层在 `record.status === 'processing'` 且**非 admin** 时按钮禁用；admin 不限制（admin 是上帝） |
| 是否需要支持「按 employee_name / 测试客户」批量删 | 高风险 | **不开放**，仅按 ID 单删 + 批选删；批量按 source 标记是方案 D 才做 |
| e2e 脚本以后还会再灌测试数据 | 是 | 建议同步要求 QA 脚本：① 每个 .mjs 写 `cleanup()` 在 `finally` 里调 DELETE 接口；② 或统一打 `extra_data.source = 'e2e_test'` 后用 SQL 清理。该建议作为 QA 后续行动项 |
