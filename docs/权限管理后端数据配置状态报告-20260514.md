### `GET /api/admin/roles`

实测请求：`GET /api/admin/roles?page=1&pageSize=5`

后端全局响应结构：

```json
{
  "code": 0,
  "data": {
    "page": 1,
    "pageSize": 5,
    "total": 20,
    "totalPages": 4,
    "list": []
  },
  "message": "ok",
  "traceId": "req_xxx"
}
```

前端 axios 响应拦截器会返回内层 `data`，因此前端服务层实际收到的是：

```json
{
  "page": 1,
  "pageSize": 5,
  "total": 20,
  "totalPages": 4,
  "list": []
}
```

这不是数组。调用方如果直接执行 `allRoles.filter(...)` 就会出现 `allRoles.filter is not a function`。

当前 `frontend/src/services/roles.ts` 已经把分页对象归一为数组：

```ts
const list = Array.isArray(result) ? result : (result?.list || []);
return Array.isArray(list) ? list : [];
```

所以角色列表接口本身是有数据且结构稳定的，前端应统一通过 `getRoles()` 获取数组，不能直接把 `/admin/roles` 的返回值当数组。

实测返回成功，结构为：

```json
{
  "code": 0,
  "data": {
    "scenarios": ["main", "dispatched:contract"],
```

注意：当前后端矩阵接口只返回 `scenarios` 和按 `roleId -> scenario -> fieldCode` 组织的 `matrix`，不返回 `roles` 和 `fields` 数组。如果前端字段权限页面期望 `data.roles.map(...)` 或 `data.fields.map(...)`，还需要前端适配或后端扩展接口。这是与 `allRoles.filter` 不同的另一个接口契约风险。

## 风险与建议

1. **角色列表契约**：`/api/admin/roles` 是分页对象，不是数组。前端必须统一通过 `getRoles()` 或读取 `result.list`。
2. **字段命名兼容**：后端实体返回 `isActive`，部分前端类型仍使用 `is_active`；页面如果只读 `is_active` 会导致启用状态显示异常。
3. **字段权限矩阵契约**：后端 `matrix` 接口不返回 `roles/fields` 列表，而当前字段权限页面类型定义看起来期望 `roles/fields/matrix rows`。建议前端组合 `getRoles()` + `getFields()` + 后端 `matrix`，或后端扩展接口返回完整视图。
4. **源码中文显示**：部分 seed 源码文件中的中文在读取时出现乱码，但数据库内当前中文数据正常。后续如重新 seed，应确认文件编码为 UTF-8，避免覆盖成乱码。
5. **重复 admin 角色关系**：当前 `admin` 用户查询到两个 `admin` 角色关系，JWT 最终去重后只返回一个 `admin`，不影响鉴权；可后续清理重复 `user_roles` 数据。

## 最终判断

真实权限数据已经配置成功，数据库不是空的；管理页面报错的主要原因是前端消费 `/api/admin/roles` 返回结构时没有按分页对象处理。后端权限基础数据、迁移、种子脚本和 admin 鉴权均已验证可用。
