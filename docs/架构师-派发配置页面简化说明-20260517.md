## 0. 一句话给用户看的解释

> **这一页只决定一件事：每种工单提交后，每个子模块默认派给谁；如果某个客户要换人，再加一行"客户例外"。**
>
> - 你在表格里看到的每一行，要么是「**默认**」（绿标签，全部客户都生效），要么是「**客户例外**」（橙标签，只对某个客户生效）。
> - 例外永远盖过默认。除此之外没有第三种规则。

如果只看这一句话能用起来，就够了。下面是给后台管理员/我们自己看的细节。

## 1. 你在页面上看到的两种行，分别是什么

页面顶部的提示语写得是对的——但表格里有些标签混进了"高级字段"的列，让人误以为业务很复杂。其实只有两种行：

### 1.1 默认派发（绿色 Tag「默认」）

- **意思**：「以后所有客户的『某个子模块』，**默认**就派给这位主负责人；TA 不在了走备选 1，再不在走备选 2。」
- **数据来源**：后端 `module_handlers` 表（一个模块，一行一个候选人，加 `weight` 权重和 `isBackup` 主备标记）。
- **覆盖范围**：「全部客户」（页面上展示为绿色 Tag「全部客户」）。
- **典型例子**：合同模块默认主=杨纯、备1=江璐；数据录入默认主=安娜祯。

### 1.2 客户例外（橙色 Tag「客户例外」）

- **意思**：「**只针对某个具体客户**，在某子模块上换一个负责人。例外优先级高于默认。」
- **数据来源**：后端 `dispatch_rules` 表里 `customerId IS NOT NULL` 的行。
- **覆盖范围**：选定的那个客户（页面上展示为橙色 Tag «客户名»）。
- **典型例子**：「腾讯的合同子单走张三，不走默认的杨纯」。

> ⚠️ 实际后端 `dispatch_rules` 表还能承担更复杂的事情（按工单字段 AST 触发、按部门维度、按工单类型路由），但**这些都是系统内部逻辑，普通管理员不需要在这一页直接配置**——它们在 seed 启动时由系统建好，不应该作为日常管理操作暴露给用户。所以这一页只暴露「客户例外」这一个用法。

## 2. 主负责人 / 备选 1 / 备选 2 实际是怎么参与派发的

这是用户最容易看不懂的地方。**关键事实：备选不是按"备1再备2"顺序循环挑，是「主有人就走主，主全员不在/停用了才轮到备」。**

### 2.1 默认派发行（来自 module_handlers）

派发引擎的真实顺序（核对 `backend/src/modules/dispatch-engine/handler-picker.service.ts:71-92` `pickFixed`）：

1. 主岗（`isBackup=false`）按 `weight` 降序挑第一个；如果找到就用 TA。
2. 主岗都没人/全停用，才到备岗（`isBackup=true`）按 `weight` 降序挑。
3. 备岗里如果有多个人，**也只挑一个**——按权重，不是「先备 1 再备 2」轮流派。

> **「备选 1 / 备选 2」是 UI 概念，不是数据库概念**。后端表只有 `isBackup` 布尔。前端把同一个模块里 isBackup=true 的人，按权重排序后第一行叫「备选 1」、第二行叫「备选 2」——只为了好看，**派发时不会按「备 1 → 备 2」顺序回落**。

**给用户的简单说法**：
> 主负责人是默认接单的人。备选只在主负责人离职/停用/账号失效时才接到单。备 1 和备 2 没有顺序差别，谁权重高谁先接。

### 2.2 客户例外行（来自 dispatch_rules）

例外只用 `assigneeUserId`（主）和 `fallbackUserId`（备 1），**没有备 2**（核对 `dispatch-rules.service.ts:120-141` 与 `dispatch-engine.service.ts:137-146`）。顺序：

1. 例外里写的「主负责人」可用 → 用 TA。
2. 不可用 → 用例外里写的「备选 1」。
3. 还不行 → **回落到该模块默认派发**（也就是 module_handlers 的主→备）。

所以页面在新增「客户例外」时正确禁用了备 2 字段——这部分前端目前已对（`DispatchConfig/index.tsx:401-405` 的条件渲染）。

## 3. 哪些字段是「系统高级配置」，不该出现在普通管理员视野里

当前页面**新增/编辑**弹窗在选择「客户例外」时会暴露下面这些字段。它们要么是后端 seed 自动写好的、要么是非常 dispatched-rules 内部细节，对实际工作没意义，建议默认折叠或隐藏：

| 字段（代码字段名） | 现在哪里出现 | 业务上是什么 | 普通管理员是否要管 | 建议 |
|---|---|---|---|---|
| `priority` 优先级 | 例外行编辑表单 | 多条规则在同一模块上时谁先生效。客户例外永远 > 默认，部门例外 > 全局，其余靠 priority。 | 99% 的场景不用调 | **隐藏在「高级设置」折叠区**，默认值 10，提示「无并存规则时不必修改」 |
| `allow_manual_override` 允许手动调整 | 例外行编辑表单 | 派发后是否允许在工单详情页手动改派 | 当前没有 UI 把这个开关接到工单详情，等于摆设 | **隐藏**直到改派功能上线 |
| `trigger_conditions` 触发条件 AST | 例外行编辑表单（JSON 文本框） | 按工单字段值动态触发的 AST 条件（如「需要入职联系=是 时才生成入职联系子单」） | 这是 seed 启动时就配好的系统级路由，不是「客户例外」要操心的事 | **从这一页彻底拿掉**。需要时另开一个「高级派发规则」页，由开发/架构师维护 |
| `dispatch_strategy` 分派策略（pool/fixed/round_robin） | 例外行编辑表单 | 主备都不在时怎么从候选池挑人。客户例外里 99% 用 fixed | 一般用不上 | **隐藏**，默认 `fixed`；高级模式才显示 |
| `weight` 权重（默认行） | 默认行编辑表单 | 同一模块多个主时按权重挑高的；多个备时按权重挑高的 | 现在系统里基本一个模块只有一主一备，权重区分意义不大 | **隐藏**，默认 1；只在「同一岗多人」场景显示 |
| `order_type` 模块 / `sub_module` 子模块 | 必填字段 | order_type=入职/续签/离职/待遇申报；sub_module=数据录入/合同/入职联系… | 每条配置都要选，但当前页面把"模块"列显示为 orderType（入职、续签…），把"子模块"列显示成实际模块——业务侧通常关心的就是后者 | **改名**：把「模块」列改名为「工单类型」，「子模块」列改名为「派发模块」，并且默认隐藏「工单类型」（在子模块名旁用浅色括号显示） |
| `rule_name` 规则名称 | 例外行编辑（不填自动生成） | 后台调试用的字符串标识 | 普通管理员不需要 | **隐藏**，自动生成 `客户名-子模块例外` 即可 |

## 4. 推荐的页面改版（文案 + 分组 + 表格列 + 操作流程）

> 原则：**保留全部能力**（后端表结构、API、派发引擎一行不动），只改前端展示和表单分层。**不引入新功能**。

### 4.1 顶部说明（替换现在那条 Alert）

```
派发配置 = 工单提交后自动派给谁。
- 默认：所有客户共用的主/备负责人。
- 客户例外：某个客户单独换人。例外永远优先于默认。
```

### 4.2 表格列（精简到 6 列 + 操作）

| 列名 | 取值 | 说明 |
|---|---|---|
| 类型 | 「默认」/「客户例外」 | 绿/橙标签，仍保留 |
| 派发模块 | 数据录入 / 合同 / 入职联系 / … | 现在的「子模块」列改名而来；后面用灰色括号补一句工单类型 `（入职）` |
| 适用客户 | 「全部客户」/ «客户名» | 现在的「客户范围」列保留 |
| 主负责人 | 姓名 | 必填 |
| 备选 1 | 姓名 / — | 鼠标悬停 tooltip：「主不在/停用时接单」 |
| 备选 2 | 姓名 / — | 仅默认行显示；客户例外行直接显示「—」并 tooltip：「客户例外只支持 1 备」 |
| 操作 | 编辑 / 删除 | 不变 |

**移除当前页面的「模块」「策略」两列**：
- 「模块」列其实就是工单类型，和「子模块」高度重叠，让人困惑——折叠到子模块名后显示。
- 「策略」列对默认行恒为「—」，对客户例外恒为「固定」，没有信息量——彻底拿掉。

### 4.3 新增/编辑弹窗的分层

弹窗顶部仍是「默认 / 客户例外」二选一。下方字段分两区：

**主信息（始终显示）**

- 配置类型（默认 / 客户例外）
- 派发模块（带工单类型自动联动；选完模块后底下自动填工单类型，置灰）
- 适用客户（仅客户例外才显示）
- 主负责人
- 备选 1
- 备选 2（仅默认才显示）
- 是否启用

**高级设置（默认折叠，显示「展开高级设置 ▶」）**

把下面这些都塞进去并配文案说明：

- 权重（默认行）—— 文案：「同一模块同一岗位若配多人，按权重决定接单顺序」
- 优先级（例外行）—— 文案：「同一模块多条例外并存时控制顺序，无需修改」
- 分派策略（例外行）—— 文案：「主备都不在时怎么从候选池挑人，默认固定」
- 允许手动调整（例外行）—— 文案：「保留字段，待手动改派功能上线后启用」
- 规则名（例外行）—— 文案：「不填自动生成」

**触发条件 AST 直接从这一页移除**：它属于「系统级派发规则」，由开发/架构师在另外的页面维护（或者继续靠 seed），日常管理员看不到。

### 4.4 操作流程（用户视角）

1. **看一遍默认表**：每个模块默认派给谁，一目了然。
2. **要给某客户换人**：点新增 → 选「客户例外」→ 选模块 → 选客户 → 选主（可选备 1）→ 保存。
3. **某人离职**：找到 TA 出现的所有行 → 替换成新负责人。
4. **临时停用**：编辑 → 启用关掉。

## 5. 还有没有「假/占位数据」或 seed 复活问题

### 5.1 启动脚本现状

`快速启动.ps1:24,164` 与 `局域网启动.ps1:24,127` **每次启动都强制 `AUTO_SEED=true`**，触发 `backend/src/database/seeds/seed-on-bootstrap.service.ts` 重跑全部 seed。这意味着任何人在数据库里删除的「兼容账号」「seed 出来的默认派发规则」**下次启动会被复活**。

### 5.2 仍然存活的「兼容账号」（seed-users.ts:146-151）

| username | realName | 现在的用途 |
|---|---|---|
| `admin` | 系统管理员（兼容账号） | 早期演示账号，**当前 UI 没人用** |
| `contractsup01` | 合同主管（兼容账号） | 没被任何 module_handlers 引用 |
| `onboardsup01` | 入职联系主管（兼容账号） | 没被任何 module_handlers 引用 |
| `dataentrysup01` | 数据录入主管（兼容账号） | 在 `seed-module-configs.ts` 的 `module_supervisors` 中被引用 |
| `socialsup01` | 社保主管（兼容账号） | **被 `seed-module-handlers.ts:26` 配为 `social_insurance` 模块的备份处理人** |
| `social01` | 社保专员（兼容账号） | **被 `seed-module-handlers.ts:25` 配为 `social_insurance` 模块的主处理人** |

**结论**：`social_insurance`（社保公积金办理）模块**目前没有真实的人**，整套派发依赖 `social01`/`socialsup01` 这两个兼容账号。这就是为什么之前的调研里反复提到「社保模块负责人未确定」——它实际上一直挂在两个虚拟账号上。

### 5.3 仍然存活的 dispatch_rules seed（seed-dispatch-rules.ts:9-81）

启动时会写入/复活 8 条规则（不是用户记的 5 条；过去某个版本可能是 5 条）：

| 规则名 | order_type | 触发条件 | target_module |
|---|---|---|---|
| onboarding-default-data-entry | onboarding | 无（恒触发） | data_entry |
| onboarding-default-social-insurance | onboarding | 无（恒触发） | social_insurance |
| onboarding-contact-when-needed | onboarding | `need_onboarding_contact = 是` | onboarding_contact |
| onboarding-contract-when-needed | onboarding | `need_company_contract = 是` | contract |
| renewal-default-contract | renewal | 无 | renewal_contract |

这些规则是派发引擎运行的**核心路由**，删了系统就不知道入职工单要拆出哪些子单——**不能删**。但它们**不应该出现在「派发配置」页面里给普通管理员看到**，目前页面会把这 8 条作为「客户例外」混进列表（实际上它们 customerId 都是 NULL，按照页面逻辑应当被识别为"全部客户（按条件）"）。

## 6. 三件事，按优先级落地

下面三件事是这一页"看不懂"的根因，按建议顺序：

1. **后端聚合接口（`/admin/dispatch-config`）过滤掉 customerId IS NULL 的 dispatch_rules**——`dispatch-rules.service.ts:88-92` 当前 `find` 没有 customerId 过滤，导致 8 条系统级路由全显示在用户的"客户例外"列表里。这是用户感觉混乱的最大单点原因。
2. **前端表单移除 `trigger_conditions` AST 文本框**——日常配置不该出现 JSON。
3. **前端把「权重 / 优先级 / 策略 / 允许手动调整 / 规则名」收进"高级设置"折叠区**——让普通管理员只看到主/备/客户。

做完这三件事后，用户在这一页看到的就是**两类行（默认 + 客户例外）+ 三个人位（主/备1/备2）+ 一个客户范围**，跟一句话解释完全对得上。
