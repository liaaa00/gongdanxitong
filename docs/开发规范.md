# 开发规范

> 版本：v1.0（Phase 1 定稿）
> 约束对象：后端 / 前端 / 测试工程师
> 关键词：一致性、可读性、可测、可替换

---

## 1. 通用约束

- **语言**：代码中除日志/错误信息/枚举值外，不写中文；注释、DTO 字段含义用英文；面向用户的 `message` / 错误提示用中文。
- **TypeScript 全量类型**：禁止 `any`；必要时用 `unknown` + 类型守卫。
- **单文件上限**：500 行。超过必须按职责拆分。
- **默认不写注释**。只有"非显然的 why"才写（性能权衡、绕过 bug、业务约束）。
- **禁止提交 TODO/FIXME 上主干**：转成 issue，引用到 PR 描述。
- **所有路径在文档中用 Windows 绝对路径或项目相对路径**（如 `backend/src/...`），避免读者混淆。

### 2.3 命名
| 对象 | 规则 | 示例 |
|------|------|------|
| 文件名 | kebab-case，带后缀 | `work-orders.service.ts` |
| 类 | PascalCase | `WorkOrdersService` |
| 方法 / 变量 | camelCase | `submitWorkOrder` |
| 常量 | UPPER_SNAKE | `MAX_IMPORT_ROWS` |
| 枚举 | PascalCase / UPPER_SNAKE | `enum OrderStatus { DRAFT = 'draft' }` |
| DTO | XxxDto | `CreateWorkOrderDto` |
| Entity | Xxx | `WorkOrder`（不加 `Entity` 后缀） |
| Repository | XxxRepository | `WorkOrdersRepository` |

### 2.4 DTO & 校验
- 全部 DTO 使用 `class-validator` + `class-transformer`。
- 请求参数校验挂全局 `ValidationPipe`（`whitelist: true, forbidNonWhitelisted: true, transform: true`）。
- 响应 DTO 建议用 `@Expose/@Exclude` 控制暴露字段，避免泄漏 `password_hash` 等。
- 日期字段用 `@IsDateString()` 接收，Service 内部用 `Date` 操作。

### 2.5 异常与错误码
- 业务异常统一用 `BusinessException(code: number, message: string, httpStatus = 400, details?: unknown)`，在 `common/exceptions/error-code.ts` 维护码表常量。
- 未知异常由 `AllExceptionsFilter` 兜底映射为 `9000`。
- 不要直接 `throw new BadRequestException('xxx')`，除非是 Pipe 级校验异常（由 ValidationPipe 抛出，过滤器会统一处理）。

### 2.6 事务
- 所有涉及多表写入或跨聚合根的 Service 方法必须用 `DataSource.transaction()` 或 `@Transactional` 装饰器封装。
- 事务内不允许调用外部 I/O（邮件、MQ）。外部副作用在事务提交成功后触发（`queueMicrotask` 或事件总线）。

### 2.7 TypeORM
- 实体字段统一用 `@Column({ type: ... })` 明确类型；JSONB 用 `type: 'jsonb'`。
- 不开 `synchronize`；表结构变更一律写迁移。
- Repository 方法按"读 / 写 / 查询" 三类组织；复杂查询用 `QueryBuilder`，避免在 Service 里拼 SQL。
- 分页统一走 `BasePaginationDto` + `findAndCount`。

### 2.8 日志
- 使用 Nest 内置 `Logger`，context 设为类名。
- 重要副作用（派发、撤回审批、字段补充）必须 `logger.log({ action, orderId, ... })` JSON 结构化打点。
- 不打印敏感字段（密码、完整身份证）。

### 2.9 测试
- 单元测试覆盖核心 Service（DispatchEngine、FieldPermissionService、ConditionEvaluator 必须 100%）。
- e2e 测试至少覆盖：登录、工单创建→提交→派发→接单→完成、撤回审批。
- 测试用 `vitest` 或 `jest`（以 NestJS 默认的 Jest 为准）。

### 2.10 Docker / 构建
- `backend/Dockerfile` 采用多阶段：
  - stage `builder`：`node:20-alpine`，`npm ci` + `npm run build`
  - stage `runner`：`node:20-alpine`，只带 `dist`、`package.json`、`node_modules`（production）
- 启动命令：`node dist/main.js`。
- 健康检查端点 `/api/health` 连 DB 探活。

### 3.2 命名
| 对象 | 规则 | 示例 |
|------|------|------|
| 文件 | PascalCase（组件/页面）、camelCase（其它） | `DynamicForm.tsx`, `http.ts` |
| 组件 | PascalCase | `DynamicForm` |
| Hook | `use` 前缀 camelCase | `useFieldPermission` |
| 常量 | UPPER_SNAKE | `ORDER_TYPE_ENUM` |
| CSS 类 | BEM 或 `className + module` | `dynamic-form__item` |

### 3.3 状态管理
- 全局 store 只放"真全局"：登录态、权限、通知未读数、主题。
- 业务数据一律放 React Query（推荐）或路由 loader；不要塞进 Zustand。
- 不使用 Redux / MobX，避免心智分裂。

### 3.4 请求
- 统一 axios 实例 `services/http.ts`；请求/响应拦截器：
  - 请求：注入 `Authorization`、`traceId`。
  - 响应：拆包 `{ code, data, message }`，`code !== 0` 抛 `BizError(code, message, details)`。
  - 401 → 清登录态 → `navigate('/login')`。
- 404/500 由 `errorCode.ts` 映射中文提示；允许业务 try/catch 按需处理。

### 3.5 动态表单
- 字段渲染器注册表：`const renderers: Record<FieldType, FC<FieldProps>>`。新增字段类型只加渲染器，不改调用方。
- 表单 schema 从 `/api/admin/fields?orderType=...` 拉取 + 本地 React Query 缓存。
- 字段权限 `useFieldPermission(fieldCode, scenario)` 返回 `{ visible, editable, masked }`；组件消费即可。

### 3.6 路由
- React Router 6 data router，lazy 加载。
- `errorElement` 全局 fallback。
- 路由 meta 声明权限：`meta: { roles: ['salesperson','manager'] }`；由 `<RouteGuard />` 读取校验。

### 3.7 样式
- Antd 5 design tokens，尽量不写全局 override；局部用 `ConfigProvider` 限定。
- 自定义样式用 Less + CSS Modules 或 Antd 的 `CSS-in-JS`，禁止散落的 `<style>` 内联覆盖。

### 3.8 构建与部署
- 构建产物目标：`dist/`，`Dockerfile` 第二阶段 `nginx:1.27-alpine` 静态托管。
- 前端容器内 nginx 负责 SPA history 兜底（`try_files $uri $uri/ /index.html`），不处理 API 反代（由根 nginx 做）。

### 3.9 测试
- 关键组件用 `@testing-library/react` 写快照 + 交互测试。
- 端到端测试 Phase 6 再上（Playwright），本期可暂略。

## 4. Git / 协作规范

### 4.1 分支
- `main`：稳定分支，Phase 结束合并。
- `phase/<n>-<topic>`：阶段开发分支。
- `feat/<topic>` / `fix/<topic>` / `chore/<topic>`：短生命周期分支，合并到阶段分支后删除。

### 4.2 提交信息（Conventional Commits）
格式：`<type>(<scope>): <subject>`
- `type`：`feat` / `fix` / `refactor` / `docs` / `test` / `chore` / `build` / `perf`
- `scope`：模块或目录（`auth`, `dispatch`, `frontend/login`）
- `subject`：祈使句中文，不超过 50 字

示例：
```
feat(dispatch): 实现基于 JSON AST 的条件求值器
fix(work-orders): 修复提交后 extra_data 冗余列不同步的问题
docs(arch): 补充撤回流程状态机
```

### 4.3 PR 规范
- 标题同 commit 规则。
- 必备内容：变更摘要、测试方式、影响面、是否有 DB 迁移。
- 合并前：CI 必须绿（lint + type check + unit test）。

### 4.4 代码评审
- 架构层面改动（新增模块 / 新增表 / 接口契约变动）必须经架构师 review。
- 对接口有破坏性的改动必须同步更新 `docs/架构设计.md`、`docs/API规范.md`、`docs/数据库ER图.md`。

## 5. 工具链约定

- **Node**：20.x（建议 20.11+）
- **包管理**：`npm`（避免与 Docker 缓存兼容性问题；如要用 pnpm 请架构师确认后再切）
- **Lint**：ESLint + Prettier，规则基线由后端/前端各自落地；CI 不通过 lint 不允许合并。
- **Commit 钩子**：使用 `husky` + `lint-staged` 可选，不硬要求；但 CI 必须执行。
- **环境变量**：严格以 `.env.example` 为准；新增变量需同步更新该文件并在 README 的部署章节说明。

## 6. 安全底线（所有人必须遵守）

- 禁止把 `.env` 提交进 Git。
- 不在日志打印身份证、手机号、银行账号、薪资明文。
- SQL 只能用 TypeORM / QueryBuilder 参数化接口；禁止字符串拼接。
- 前端存储：不得在 `localStorage` 存 refresh token；短期 access token 存 `localStorage` 可接受，须配合登出清理。
- 文件上传必须校验 MIME + 后缀白名单（Excel：`.xlsx`；附件：由后端模块定义）。
- 审批/撤回接口必须做幂等（同一 approval_id 重复审批直接返回当前状态）。

## 7. 验收与交付

- 每个 Phase 结束必须：
  - 提交 Phase 进度 README（本阶段完成项、已知问题、下阶段依赖）
  - 执行一次完整回归测试脚本
  - 架构师 review 后由 Leader 合并到 `main`
- 任何偏离本规范的做法，事先发 `[规范豁免]` 消息说明原因并获得架构师同意，事后在 PR 中注明。
