## 0. 结论摘要

1. **通知页显示“办理人”**不是单一前端文案问题，而是通知写入契约不统一导致的链路问题：部分通知创建路径未把真实操作人写入 `payload.actorUserId`；列表接口只能根据 `payload.actorUserId` 解析 `actorName`；历史 content 中已有“办理人/操作人”占位；legacy 替换逻辑存在行首锚定/匹配范围不足。
2. **子工单表头筛选无响应/不能多选**的主要改造面在前端：`MultiViewTable` 将 `filters` 数组降级为 `value[0]`，`MyDispatched` 的 `normalizeQuery.readString` 把数组转字符串，子工单列表列配置缺少 `mode:'multiple'` / `filterMultiple` / 多选 `filterDropdown`。
3. **修正上一轮偏差**：`dispatched-orders` 后端并非仅支持单值。`ListDispatchedOrderQueryDto` 已有 `MultiQueryValue`，`DispatchedOrderService.applyCommonFilters` 已通过 `normalizeQueryList` + `applySingleOrMultiFilter` 支持模块、状态、处理人、工单类型、部门等多值精确过滤；不应建议对该模块做重复大改。需要区分：`work-orders` 列表 DTO 仍是单值枚举/字符串查询。
4. 验证证据：后端定向单测 `notifications.spec.ts`、`dispatched-order.service.spec.ts` 通过；前端定向 Vitest `MultiViewTable/index.test.tsx`、`Notifications/index.test.tsx` 通过。仍缺少真实浏览器人工点击截图/录像证据。

## 1. 复现路径

### 1.1 通知页显示“办理人”

- 操作步骤：
  1. 使用后道处理人完成/退回/补充/转交子工单，或由业务员发起撤回、作废、催办等会生成通知的动作。
  2. 切换到通知接收人账号。
  3. 打开消息通知页面，查看列表“内容”列和详情弹窗。
- 预期：通知内容显示具体操作者姓名，例如“张三 修改了……”“操作人：张三；……”。
- 实际：部分通知显示“办理人 修改了……”或只能显示占位词，无法追溯真实操作者。
- 触发条件：通知记录的 `payload.actorUserId` 缺失，且 `content` 已写入占位文案；或 legacy 替换正则未命中正文中的占位。

### 1.2 子工单表头筛选无响应/不能多选

- 操作步骤：
  1. 打开“我的待办/我的已办”或“部门子工单管理”。
  2. 点击状态、工单类型、模块等表头筛选入口，尝试选择多个值。
  3. 提交筛选并观察请求参数与列表刷新结果。
- 预期：表头筛选弹层可选择多个值，请求参数保留数组或逗号串，列表按多个条件过滤。
- 实际：部分列没有可点击筛选入口；已有入口只支持单选；多选数组经过公共表格或页面 `normalizeQuery` 后被降级为单值/字符串，表现为筛选无响应或只按第一个值过滤。

## 2. 通知问题数据流与文件级定位

### 2.1 数据流总览

```text
业务动作 user.sub
  -> 通知创建入口（direct save / bulkCreate / send）
  -> notifications.payload.actorUserId ?
  -> NotificationService.resolveActorDisplayNames(payload.actorUserId)
  -> toListItem 输出 actorName/operatorName/content
  -> frontend Notifications.getNotificationDisplayContent()
  -> UI 列表/详情展示
```

核心判断：前端只能根据后端返回的 `actorName` 或 `content` 展示，若写入阶段没有 `payload.actorUserId`，列表接口无法稳定解析真实姓名，只能显示历史 content 中的“办理人/操作人”。

### 2.2 通用通知服务

| 文件 | 行号 | 结论 |
|---|---:|---|
| `backend/src/modules/notifications/notification.service.ts` | 92-109 | `BulkNotificationInput` 与 `SendNotificationInput` 没有顶层 `actorUserId`，只能约定放入 `payload/params`。 |
| 同上 | 266-323 | `bulkCreate` 将 `input.payload` 原样落库；`send` 将 `params` 作为 `payload`，调用方没传 `actorUserId` 就无法补救。 |
| 同上 | 635-705 | 列表阶段通过 `payload.actorUserId` 查 `User.realName/username` 并输出 `actorName/operatorName`；`normalizeLegacyActorContent` 负责 legacy content 替换。 |

### 2.5 通知修复边界

1. 将通知创建契约统一为：凡由用户动作触发的通知，payload 必须包含 `actorUserId`；已有 `urgedBy/changedBy/returnedBy` 等字段可保留，但不能替代 `actorUserId`。
2. 对 `notifyCreator/notifyUsers` 增加 `actorUserId` 参数，调用处显式传 `user.sub`；对 `reassign`、`markAndNotifyAffectedDispatchedOrders`、`field-supplement direct save`、work-order 撤回/作废/审批/催办路径补齐 payload。
3. 保持 `NotificationService.resolveActorDisplayNames` 为唯一列表解析入口，避免前端猜测姓名。
4. 对存量 `notifications` 做一次性回填：优先从 `payload.actorUserId` 关联 `users` 替换 content；对只有 `urgedBy/changedBy/returnedBy` 的历史记录，可先迁移为 `actorUserId` 再回填。
5. legacy 正则不应只匹配行首，应覆盖正文任意位置的“办理人/处理人/操作人 + 动作”组合。

## 3. 子工单筛选问题数据流与文件级定位

### 3.1 数据流总览

```text
AntD/ProTable 列筛选 selectedKeys: string[]
  -> filterDropdown / filters / filterMultiple / mode:'multiple'
  -> ProTable request 第三个参数 tableFilters
  -> MultiViewTable.wrappedRequest 或页面 normalizeQuery
  -> frontend service getDispatchedOrders(params)
  -> backend ListDispatchedOrderQueryDto
  -> DispatchedOrderService.applyCommonFilters
  -> SQL: = / IN (:...values)
```

断点在前端：selectedKeys 原本是数组，但在公共表格和页面 query 归一化中被降级，导致后端即便支持多值也收不到多值。

### 3.2 前端问题定位

| 文件 | 行号 | 问题 | 修复重点 |
|---|---:|---|---|
| `frontend/src/components/MultiViewTable/index.tsx` | 104-118 | `tableFilters` 遍历时只取 `value[0]` 并转字符串。 | 改为保留数组：长度 1 可传单值，长度 >1 传数组或逗号串；不要降级。 |
| `frontend/src/pages/MyDispatched/index.tsx` | 260-328 | 子工单列只有 `valueType/fieldProps`，缺少明确的表头多选 `filterDropdown/filterMultiple`。 | 状态/模块等枚举列补 `mode:'multiple'`、`filterMultiple: true` 或统一多选 header filter。 |
| 同上 | 371-398 | `normalizeQuery.readString` 对数组执行 `String(value)`，破坏多选语义。 | 增加 `readQueryValue`：数组原样过滤空值后返回，单值再 trim。 |
| 同上 | 407-423 | 请求将归一化后的 query 传给 `getDispatchedOrders`；若前一步丢数组，后端无法多选。 | 保证 `status/moduleCode/handlerId` 等多值参数传到 service。 |
| `frontend/src/pages/TeamDispatched/index.tsx` | 242-306 | 状态、处理人等列缺少列级多选筛选配置。 | 补齐列配置，至少状态/模块/负责人支持多选。 |
| 同上 | 313-315 | ProTable request 直接把 params 传 `getDispatchedOrders`。 | 前端列配置和 service 序列化正确即可；可复用 MyDispatched 的 query normalize。 |
| `frontend/src/pages/WorkOrders/index.tsx` | 87-126 | `selectHeaderFilter` 使用 `Radio.Group`，天然单选。 | 改 `Checkbox.Group`，`setSelectedKeys(values)`。 |
| `frontend/src/pages/Notifications/index.tsx` | 145-180 | 通知展示会用 actorName 替换占位；若无 actorName 则尝试去掉行首占位。 | 前端不应硬编码“办理人”，但根因仍是后端 payload/content。 |

### 3.3 后端能力差异：纠正上一轮偏差

| 模块 | 文件 | 行号 | 多值能力 | 结论 |
|---|---|---:|---|---|
| dispatched-orders | `backend/src/modules/dispatched-orders/dto/list-query.dto.ts` | 6-72 | `MultiQueryValue = string | string[]`，`moduleCode/handlerId/statuses/orderType/departmentId` 等支持数组或逗号串。 | 已支持，不应重复大改 DTO。 |
| dispatched-orders | `backend/src/modules/dispatched-orders/dispatched-order.service.ts` | 1049-1065 | `applyCommonFilters` 对模块、处理人、状态、工单类型、部门调用多值过滤。 | 已支持多值精确筛选。 |
| dispatched-orders | 同上 | 1093-1120 | `normalizeQueryList` 支持数组和逗号拆分，`applySingleOrMultiFilter` 单值走 `=`，多值走 `IN (:...param)`。 | 后端契约足够支撑前端多选。 |
| dispatched-orders | 同上 | 1067-1076 | orderNo/customerName/employeeName/idCardNo 等文本模糊字段仍是单值 ILIKE。 | 这类不是本次“状态/模块表头多选”的主阻塞，可后续增强。 |
| work-orders | `backend/src/modules/work-orders/dto/list-query.dto.ts` | 6-17 | `orderType/status` 是单值 enum；其他文本字段也是单值字符串。 | 若主工单页也要多选，需要另行扩展；不要与 dispatched-orders 混淆。 |

### 3.4 筛选修复边界

1. 优先修前端：列配置加 `filterMultiple: true`、`fieldProps.mode = 'multiple'` 或统一 `Checkbox.Group` 型 `filterDropdown`。
2. `MultiViewTable.wrappedRequest` 不得把数组转为 `value[0]`。
3. `MyDispatched.normalizeQuery` 不得通过 `readString` 强制转字符串；多选字段保留数组或转逗号串。
4. `TeamDispatched` 补齐表头多选配置，并保证请求参数与 `dispatched-orders` 后端字段名一致。
5. 后端 `dispatched-orders` 只需回归验证和少量兼容性补充；不要重复重构 `MultiQueryValue/normalizeQueryList/applySingleOrMultiFilter`。
6. `work-orders` 如需多选，是独立增强项，不能作为子工单筛选 bug 的必要后端返工。
