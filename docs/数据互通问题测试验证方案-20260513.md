# 数据互通问题测试验证方案（2026-05-13）

> ⚠️ 当前演示口径（2026-06-03）：所有 seed/演示账号默认密码统一为 `123456`；`admin123` 是历史旧口径，会返回 401，不可用于演示。本文下方如出现 `admin123`，仅为历史记录/旧脚本背景，不代表当前可用密码。

## 1. 问题描述与用户反馈现象

### 1.1 用户反馈原文归纳
- 用户已将自己的本地电脑作为服务器，对同事开放访问。
- 用户登录的是管理员账号，同事登录的也是管理员账号。
- 两台电脑显示的数据不一致，确认不是角色/权限导致。
- 典型判断：同一个系统、同一个 admin 账号，在两台电脑上看到的工单、用户、配置等数据不互通。

### 1.2 需要重点记录的不一致范围
测试时必须逐项记录 A/B 两端当前是否一致：
1. **工单数据**：主工单列表、三个子工单列表、工单详情、状态、撤回/退回记录。
2. **用户与权限数据**：用户管理、角色管理、用户-角色分配、字段权限。
3. **基础配置数据**：部门、客户、字段配置、派发规则、模块负责人。
4. **运营数据**：看板统计、通知中心、我的待办、审批待办。
5. **浏览器本地数据**：localStorage 中是否仍存在 `mock_*` 业务数据。

### 1.3 测试侧初步高风险判断
当前最需要验证的根因是：前端仍处在 Mock 模式，数据写入每台电脑浏览器自己的 `localStorage`，而不是写入电脑 A 上统一的后端数据库。因此 A/B 即使登录同一个 admin 账号，也会天然看到不同数据。

常见本地 mock key 包括但不限于：
- `mock_work_orders_v1`：工单与子工单数据。
- `mock_admin_users_v1`：用户管理。
- `mock_admin_passwords_v1`：用户密码。
- `mock_admin_roles_v1`：角色管理。
- `mock_admin_departments_v1`：部门管理。
- `mock_admin_customers_v1`：客户管理。
- `mock_admin_fields_v1`：字段配置。
- `mock_admin_dispatch_rules_v1`：派发规则。
- `mock_admin_module_handlers_v3`：模块负责人。

> 注意：以上是测试假设，不直接作为最终结论。最终必须用 Network 请求、后端接口、数据库查询三类证据确认。

## 2. 测试目标

1. 复现并记录“两台电脑同账号数据不一致”的真实表现。
2. 确认 A/B 是否访问同一个前端地址、同一个后端 API、同一个 PostgreSQL 数据库。
3. 修复后验证数据已从浏览器 localStorage/mock 模式切换到后端数据库单源模式。
4. 覆盖增、改、删、查和业务流转，确保工单、用户、配置、看板、通知均互通。
5. 为前端/后端修复完成后的实际测试提供可执行步骤和通过标准。

## 3. 测试环境准备

### 3.1 设备
- **电脑 A**：用户本机/服务器，运行前端、后端、PostgreSQL。
- **电脑 B**：同事电脑，通过局域网访问电脑 A。
- **可选电脑 C**：手机或第三台电脑，用于排除 B 电脑缓存/历史 localStorage 影响。

### 3.2 账号
- 主验证账号：`admin / admin123`。
- 业务链路账号：
  - `sales01 / admin123`：业务员。
  - `contract01 / admin123`：合同组。
  - `onboard01 / admin123`：入职联系岗。
  - `dataentry01 / admin123`：数据录入岗。

### 3.3 访问地址要求
A/B 必须访问同一个电脑 A 的地址，例如：
- 前端：`http://<电脑A局域网IP>:5173`
- 后端：`http://<电脑A局域网IP>:3000/api`

禁止 B 端使用：
- `localhost`
- `127.0.0.1`
- B 自己电脑 IP

除非 B 本机也确实运行同一个后端并连接同一个数据库，否则这些地址都会导致“看起来同账号，实际不同服务”。

## 4. 前端切换到真实后端模式后的验证前置

### 4.1 配置检查
修复后，测试开始前需要前端/后端确认：
1. 前端构建或启动环境中已关闭 Mock：
   - `VITE_USE_MOCK=false`
2. 前端 API Base URL 指向电脑 A 后端：
   - 例如 `VITE_API_BASE_URL=http://<电脑A局域网IP>:3000/api`
3. 后端连接的是同一个 PostgreSQL 数据库。
4. 后端 `/api/health` 可从 A/B 两台电脑访问。

### 4.2 浏览器缓存与 localStorage 处理
为避免旧 mock 数据干扰，修复后首次复测建议：
1. A/B 均退出登录。
2. A/B 浏览器控制台执行：
   ```js
   Object.keys(localStorage).filter(k => k.startsWith('mock_'))
   ```
3. 若仍存在历史 mock key，记录截图后清理：
   ```js
   Object.keys(localStorage).filter(k => k.startsWith('mock_')).forEach(k => localStorage.removeItem(k))
   ```
4. 刷新页面后重新登录。

### 4.3 如何确认数据已从 localStorage 迁移到数据库
必须同时满足以下证据：
1. 新建/修改/删除工单、用户、配置时，浏览器 Network 中出现真实 `/api/*` 请求。
2. 操作完成后，对应数据可在 PostgreSQL 中查询到。
3. 清空浏览器 localStorage 后刷新，业务数据不丢失。
4. B 端不做任何 localStorage 导入，也能看到 A 端新建的数据。
5. 重启前端服务后数据不丢失；重启后端后数据仍可从数据库恢复。

## 5. 核心测试场景与用例

### TC-SYNC-001：确认 A/B 访问同一前端与后端
**目的**：排除 A/B 实际访问不同服务。

步骤：
1. A、B 同时打开同一个 URL：`http://<电脑A局域网IP>:5173`。
2. A、B 分别访问 `http://<电脑A局域网IP>:3000/api/health`。
3. A、B 打开开发者工具 Network，刷新页面。
4. 记录所有 `/api/*` 请求的 host、端口、状态码。

预期结果：
- A/B 页面 URL 一致。
- A/B API 请求都指向电脑 A 的后端。
- `/api/health` 均返回正常状态。

失败判定：
- B 的请求指向 `localhost:3000`、`127.0.0.1` 或 B 自己电脑。
- B 端只访问前端静态资源，没有任何后端 API 请求。

---

### TC-SYNC-002：电脑 A 创建工单，电脑 B 应该能看到
**目的**：验证主工单和自动拆分子工单是否互通。

步骤：
1. A 使用 `admin` 或 `sales01` 登录。
2. 进入“入职管理 > 主工单列表”。
3. 新建或导入一条唯一工单，员工姓名填写：`互通创建_<时间戳>`。
4. 确认该工单按规则自动拆分为：
   - 数据录入子工单：必拆。
   - 劳动合同签订子工单：`是否企服发起劳动合同=是` 时生成。
   - 入职联系子工单：`入职材料是否需要集约收集=是` 时生成。
5. B 使用同一账号登录同一地址，刷新“主工单列表”。
6. B 分别进入三个子工单页面检查该员工是否出现。

预期结果：
- B 能看到 A 创建的主工单。
- B 能看到对应自动拆分出的子工单。
- B 打开详情页后字段信息与 A 一致。
- 看板统计中的总数/待处理数同步变化。

证据：
- A/B 主工单列表截图。
- A/B 子工单列表截图。
- Network 新建工单接口响应。
- 数据库中该工单记录。

---

### TC-SYNC-003：电脑 A 修改工单，电脑 B 应该能看到更新
**目的**：验证修改、状态流转、字段回流互通。

步骤：
1. 继续使用 TC-SYNC-002 创建的工单。
2. A 打开主工单详情，修改一个明显字段，例如“特殊备注”：`A端修改_<时间戳>`。
3. B 刷新该工单详情。
4. B 使用对应后道账号执行一次业务动作：
   - 合同组接单/填写合同反馈；或
   - 入职联系岗补充手机号/邮箱/反馈；或
   - 数据录入岗填写数据录入反馈。
5. A 刷新主工单详情、对应子工单详情、看板。

预期结果：
- B 能看到 A 修改的字段。
- A 能看到 B 的后道处理结果。
- 主工单与子工单状态一致，不出现 A/B 状态不一致。
- 操作日志中能看到对应修改记录。

证据：
- 修改前后字段截图。
- 对应 API 请求与响应。
- 数据库更新时间/操作日志记录。

---

### TC-SYNC-004：电脑 A 删除工单，电脑 B 应该看到删除
**目的**：验证删除动作及关联子工单清理是否互通。

步骤：
1. A 创建测试工单：`互通删除_<时间戳>`，确保生成至少一个子工单。
2. B 先刷新确认能看到该主工单及子工单。
3. A 在主工单列表执行删除。
4. B 刷新主工单列表、三个子工单列表、看板。
5. B 尝试通过旧详情 URL 打开该工单。

预期结果：
- B 主工单列表不再显示该工单。
- B 三个子工单列表不再显示该工单派生的子工单。
- 看板统计同步减少。
- 旧详情 URL 返回不存在或友好提示，不显示脏数据。
- 数据库中主工单和关联子工单应按设计软删或硬删一致。

证据：
- 删除接口响应。
- B 端刷新后截图。
- 数据库记录状态。

---

### TC-SYNC-005：admin 用户/角色/部门/客户配置互通
**目的**：验证管理后台配置数据不再只存在本机浏览器。

步骤：
1. A 使用 admin 进入用户管理，新增用户：`sync_user_<时间戳>`。
2. B 使用 admin 刷新用户管理并搜索该用户名。
3. B 修改该用户手机号或角色。
4. A 刷新确认修改结果。
5. 对以下页面重复“新增/修改/删除或禁用”验证：
   - 角色管理。
   - 部门管理。
   - 客户管理。
   - 字段配置。
   - 字段权限。
   - 派发规则。
   - 模块负责人。

预期结果：
- 所有配置数据 A/B 双向可见。
- 删除按钮按角色权限显示，但 admin 应具备完整删除权限。
- 配置修改后，新建工单/派发/字段展示能按新配置生效。

证据：
- 每个配置项唯一名称截图。
- 数据库表查询或接口响应。

---

### TC-SYNC-006：撤回、退回、待办和通知互通
**目的**：验证流程事件不是本地假数据。

步骤：
1. A 创建一条工单并派发子工单。
2. B 使用后道账号打开子工单，执行“退回”，填写原因：`B端退回_<时间戳>`。
3. A 使用业务员账号或 admin 刷新主工单、我的待办、通知中心。
4. A 对另一条未完成工单发起撤回。
5. B 使用对应审批/处理账号查看待审批撤回申请和通知。

预期结果：
- A 能看到 B 发起的退回结果与通知。
- B 能看到 A 发起的撤回审批待办。
- 清空 localStorage 后重新登录，待办/通知仍来自后端，不出现历史假数据。

证据：
- 我的待办截图。
- 通知中心截图。
- 撤回/退回接口响应。

---

### TC-SYNC-007：localStorage/mock 证据采集
**目的**：判断修复前后是否仍依赖浏览器本地数据。

步骤：
1. A/B 控制台执行：
   ```js
   Object.keys(localStorage).filter(k => k.startsWith('mock_')).sort()
   ```
2. 分别记录以下 key 的长度：
   ```js
   ['mock_work_orders_v1','mock_admin_users_v1','mock_admin_customers_v1','mock_admin_fields_v1','mock_admin_dispatch_rules_v1'].map(k => [k, localStorage.getItem(k)?.length || 0])
   ```
3. A 新增数据后，观察 B 端这些 key 是否自动变化。
4. 同时检查 Network 是否有真实 `/api/*` 写请求。

预期结果：
- 修复前：可能发现 A/B 的 `mock_*` 内容不同，且无真实写接口。
- 修复后：核心业务不依赖 `mock_*`；即使清理 `mock_*`，数据库数据仍存在且 A/B 一致。

---

### TC-SYNC-008：数据库单源验证
**目的**：确认最终数据存储在同一 PostgreSQL。

步骤：
1. 后端确认当前 DB 配置，例如 `DATABASE_URL`、数据库名、schema。
2. A 创建唯一测试数据。
3. 在 PostgreSQL 中查询该测试数据。
4. B 修改该数据。
5. 再次查询数据库，确认记录更新时间或字段值变化。
6. 重启前端，必要时重启后端，再次查询页面与数据库。

预期结果：
- 页面显示与数据库一致。
- A/B 操作更新同一条数据库记录。
- 重启服务不丢数据。

## 6. 修复后通过标准

### 6.1 必须全部通过
- A/B 同地址、同账号登录后，工单、用户、角色、部门、客户、字段、派发规则、模块负责人数据一致。
- A 创建工单，B 刷新能看到。
- A 修改工单，B 刷新能看到更新。
- A 删除工单，B 刷新后主工单和子工单都消失。
- admin 在涉及数据的页面具备完整删除权限；非 admin 删除按钮按角色隐藏。
- 业务操作均走真实 `/api/*` 接口，而不是只修改 localStorage。
- 数据库中能查到新建/修改后的业务数据。
- 清空 localStorage 后重新登录，业务数据不丢失。

### 6.2 建议通过
- 无痕窗口/第三台电脑/手机访问同一地址，数据一致。
- `sales01` 创建工单后，`contract01`、`onboard01`、`dataentry01` 能看到各自子工单。
- 后道接单、完成、退回后，业务员/admin 端状态同步。
- 看板统计、通知中心、我的待办与真实数据一致。

## 10. 当前待前后端完成后的测试动作

等前端和后端完成诊断/修复后，测试工程师需要立即执行：
1. 确认 `VITE_USE_MOCK=false` 生效。
2. 清理 A/B 两端历史 `mock_*` localStorage 并截图留证。
3. 执行 TC-SYNC-001 至 TC-SYNC-008。
4. 重点验证四个用户指定场景：
   - A 创建工单，B 能看到。
   - A 修改工单，B 能看到更新。
   - A 删除工单，B 能看到删除。
   - admin 用户管理、角色管理、部门管理、客户管理等配置数据互通。
5. 输出实际复测报告，并将失败项反馈给前端/后端继续修复。
