# P1 一拆四产品确认清单与实施优先级

> 文档日期：2026-05-15  
> 来源方案：`docs/入职一拆四-架构方案-20260515.md`  
> 用途：给用户 / 产品在开发前快速确认关键口径，避免后端、前端、QA 进入实施后反复返工。  
> 范围：只做 P1 入职一拆四方案收口，不改代码。

---

## 0. 结论先行

### 0.1 建议产品优先确认的 5 个问题

| 优先级 | 确认项 | 默认建议答案 | 是否阻塞代码实施 |
|---|---|---|---|
| P0 | 入职联系、劳动合同签订是否仍按字段条件生成 | 继续按原字段条件生成；数据录入、社保公积金固定生成 | **阻塞派发逻辑实施** |
| P0 | 社保公积金办理是否所有入职都必须生成 | 一期所有已提交入职主工单都生成 | **阻塞派发逻辑与迁移脚本实施** |
| P0 | 社保公积金负责人账号与权限 | 使用“杨杰”为默认负责人；如后续换人走后台配置 | **阻塞联调与上线验证** |
| P1 | 历史已完成入职主工单补社保子单后的展示口径 | 补出子单但在业务员侧标记为“历史补充，待社保确认”，不直接把主单改成异常 | **阻塞历史数据展示细节，不阻塞迁移预研** |
| P1 | Dirty 标记什么时候清除 | 当前轮相关子单全部完成后自动取消红色活跃提示，审计记录永久保留 | **不阻塞后端表结构，影响前端提示细节** |

### 0.2 建议开发启动策略

1. **可以立即启动技术预研**：数据表迁移草案、一拆四派发服务改造、dirty 标记表设计、前端四模块展示兼容、QA 用例整理。
2. **必须等产品确认后再写死代码的点**：联系 / 合同是否条件生成、社保是否全量生成、历史已完成单展示口径、默认社保负责人账号。
3. **不建议等所有细节都确认才动手**：后端可以先按默认建议做可配置实现，前端可以先按中文文案和四模块容器做兼容开发。

## 1. 必须确认项清单

### 1.1 入职联系、劳动合同签订是否仍按字段条件生成

| 项目 | 内容 |
|---|---|
| 问题 | 入职主工单升级为“一拆四”后，入职联系、劳动合同签订两个子单是否仍沿用旧字段条件生成？ |
| 默认建议答案 | **继续按原字段条件生成**：`是否需要入职联系=是` 才生成“入职联系”；`是否企服发起劳动合同=是` 才生成“劳动合同签订”；“数据录入”和“社保公积金办理”固定生成。 |
| 原因 | 这样兼容已完成的一拆三逻辑，不会突然给不需要联系/合同的工单增加无效待办。 |
| 影响范围 | 后端派发引擎、历史迁移筛选条件、前端四模块状态展示、QA 新建工单用例。 |
| 是否阻塞技术预研 | 不阻塞。后端可以先把生成规则做成配置或函数。 |
| 是否阻塞代码实施 | **阻塞派发逻辑最终落地**。如果产品改为“四个子单全部固定生成”，后端派发和前端空状态都要调整。 |
| 建议确认截止 | 2026-05-18 上午。 |

---

### 1.2 社保公积金办理是否所有入职都必须生成

| 项目 | 内容 |
|---|---|
| 问题 | 是否所有已提交入职主工单都必须生成“社保公积金办理”子单？是否存在客户、项目、用工形式不需要办理社保公积金？ |
| 默认建议答案 | **一期全部生成**。如果业务上确实存在“不需要社保公积金”的特殊情况，先由杨杰/社保负责人在子单里线下判断并标记完成，不在 P1 做复杂规则。 |
| 原因 | 会议已明确社保公积金子模块一期简化，且不做省份自动派单；全量生成最稳，能避免漏办。 |
| 影响范围 | 一拆四派发、历史一拆三迁移 SQL、社保待办列表、业务员侧状态展示、批量完成入口。 |
| 是否阻塞技术预研 | 不阻塞。可以先按全量生成设计表和接口。 |
| 是否阻塞代码实施 | **阻塞派发逻辑和迁移脚本最终条件**。如果不是全量生成，需要新增字段或规则。 |
| 建议确认截止 | 2026-05-18 上午。 |

---

### 1.3 社保公积金默认负责人是谁、账号是否已存在

| 项目 | 内容 |
|---|---|
| 问题 | 北仑项目社保公积金办理默认负责人是否固定为“杨杰”？系统中是否已有启用账号？需要赋予哪个角色/权限？ |
| 默认建议答案 | 默认负责人为**杨杰**；后台保留“当前社保负责人”配置，后续换人不改代码。上线前确认杨杰账号存在、可登录、有社保公积金办理列表和批量完成权限。 |
| 原因 | 会议明确北仑项目由杨杰统一接单，内部拆分线下完成。 |
| 影响范围 | 派发规则、module_handlers 种子数据、社保列表权限、批量完成权限、站内通知接收人。 |
| 是否阻塞技术预研 | 不阻塞。可以先按“负责人配置项 + 杨杰兜底”设计。 |
| 是否阻塞代码实施 | **阻塞联调与上线验证**。没有账号/权限会导致社保子单无人可见或无法批量完成。 |
| 建议确认截止 | 2026-05-18 下班前。 |

### 1.4 历史已完成入职主工单补社保子单后如何展示

| 项目 | 内容 |
|---|---|
| 问题 | 旧的一拆三入职主工单如果原本已经完成，迁移补出“社保公积金办理”子单且默认未完成后，业务员侧是否显示未完成？是否影响主工单已完成状态？ |
| 默认建议答案 | **补子单但不粗暴打断历史主单状态**：业务员侧展示“社保公积金办理：历史补充，待社保确认”；后台/社保负责人列表显示为“待办理”。主工单可保留原已完成状态，并增加“历史补充子单未确认”提示。 |
| 原因 | 既满足“不能丢数据、补出第四子单”的要求，又避免用户突然看到大量历史已完成工单变成未完成，引发误解。 |
| 影响范围 | 历史迁移脚本、主工单状态计算、前端状态标签、社保待办列表、QA 历史数据用例。 |
| 是否阻塞技术预研 | 不阻塞。迁移脚本可以先按批次号补数据。 |
| 是否阻塞代码实施 | **阻塞前端展示和主单状态计算**。如果产品要求主单也回到处理中，影响会更大。 |
| 建议确认截止 | 2026-05-19 内部跑流程前。 |

### 1.5 Dirty 标记什么时候清除

| 项目 | 内容 |
|---|---|
| 问题 | 业务员修改字段后，下游详情页红色标记和顶部蓝色提示条何时消失？ |
| 默认建议答案 | **当前轮相关子单全部完成后自动取消活跃提示**，但 dirty 审计记录永久保留在日志/历史记录里。 |
| 原因 | 自动清除能减少办理人重复看到过期提示；永久审计能满足追溯。 |
| 影响范围 | Dirty 标记表 `is_active` / `cleared_at` 字段、前端标红展示、通知已读与审计查询。 |
| 是否阻塞技术预研 | 不阻塞。表结构已经支持自动清除和手动清除。 |
| 是否阻塞代码实施 | 不阻塞核心流程，但会影响前端提示消失时机和 QA 断言。 |
| 建议确认截止 | 2026-05-19 内部跑流程前。 |

### 1.6 已完成节点退回是否必须由原办理人操作

| 项目 | 内容 |
|---|---|
| 问题 | 任一子单已完成后，业务员想修改，已完成节点退回必须由原办理人本人操作，还是模块负责人/admin 可以代退？ |
| 默认建议答案 | **原办理人、模块负责人、admin 都可退回**，但必须填写退回原因；操作日志记录实际退回人。 |
| 原因 | 避免原办理人请假或离职导致流程卡住，同时保留审计。 |
| 影响范围 | 子工单退回接口权限、前端按钮显示、操作日志、QA 权限用例。 |
| 是否阻塞技术预研 | 不阻塞。 |
| 是否阻塞代码实施 | 阻塞退回接口权限判断细节，但不阻塞一拆四派发。 |
| 建议确认截止 | 2026-05-19。 |

### 1.7 社保公积金批量完成是否需要填写备注

| 项目 | 内容 |
|---|---|
| 问题 | 福宝团队批量勾选“社保公积金办理完成”时，是否必须填写办理备注或完成日期？ |
| 默认建议答案 | **完成日期自动取当前日期，备注非必填**；如果业务有异常说明，可选填备注。 |
| 原因 | 会议要求平台只提供批量标记完成入口，不能把一期做复杂。 |
| 影响范围 | 批量完成接口 DTO、前端确认弹窗、QA 批量完成用例。 |
| 是否阻塞技术预研 | 不阻塞。 |
| 是否阻塞代码实施 | 不阻塞核心代码；只影响弹窗字段和接口参数必填性。 |
| 建议确认截止 | 2026-05-19。 |

## 2. 阻塞等级划分

### 2.1 会阻塞代码实施的事项

| 编号 | 事项 | 阻塞对象 | 如果不确认的风险 |
|---|---|---|---|
| B1 | 联系 / 合同是否条件生成 | 后端派发引擎、QA 用例 | 生成子单数量错误，返工派发逻辑 |
| B2 | 社保是否所有入职必生成 | 后端派发、历史迁移 SQL | 漏生成或多生成社保子单 |
| B3 | 杨杰账号与权限 | 联调、上线试运行 | 子单无人可见、无法批量完成 |
| B4 | 历史已完成单补社保后的主单展示口径 | 前端状态展示、主单状态计算 | 历史已完成工单突然变未完成，引发用户质疑 |
| B5 | 已完成节点退回权限 | 后端权限、前端按钮 | 退回卡死或权限过宽 |

### 2.2 不阻塞技术预研但需尽快确认的事项

| 编号 | 事项 | 可先做什么 | 后续确认后怎么收口 |
|---|---|---|---|
| N1 | Dirty 标记清除时机 | 先建 dirty 表并返回 `dirty=true/false` | 调整自动清除策略或增加“已知悉”按钮 |
| N2 | 批量完成是否备注必填 | 先按备注选填设计 | 如产品要求必填，只改前端校验和 DTO |
| N3 | 站内通知正文具体措辞 | 先按中文模板开发 | 产品确认后替换文案 |
| N4 | 历史异常数据处理人 | 先输出异常清单 | 确认后由管理员人工处理 |
| N5 | 社保负责人未来换人机制 | 先做配置项 | 后续后台页面优化 |

## 4. 实施优先级建议

### 4.1 后端实施优先级

| 优先级 | 任务 | 是否需要等产品确认 |
|---|---|---|

| 后端 5 | 业务员修改规则 A/B、dirty 标记、退回后重走 | 不需要等全部确认，可按默认规则做 |
| 后端 6 | 社保批量完成接口 | 不需要等全部确认，备注是否必填可后改 |
| 后端 7 | 站内通知触发 | 不需要等全部确认，文案可配置 |

### 4.2 前端实施优先级

| 优先级 | 任务 | 是否需要等产品确认 |
|---|---|---|
| 前端 1 | 入职详情支持四模块容器，旧三模块数据不崩 | 不需要 |

| 前端 6 | 历史已完成主单补社保后的状态展示 | 需要产品确认展示口径 |

### 4.3 QA 实施优先级

| 优先级 | 任务 | 说明 |
|---|---|---|
| QA 1 | 新提交入职工单一拆四验证 | 覆盖联系/合同需要和不需要两类场景 |
| QA 2 | 社保不按省份分流验证 | 不同参保省份均派给杨杰/当前负责人 |
| QA 3 | 业务员修改规则 A | 所有子单未完成时可改、下游标红、站内通知 |
| QA 4 | 业务员修改规则 B | 任一子单完成后不可直接改，退回原因必填，重走流程 |
| QA 5 | 历史一拆三迁移 | 补社保子单、不丢旧三子单、可回滚 |
| QA 6 | 中文展示回归 | 不出现 visible/readonly/pending 等英文枚举 |
| QA 7 | 社保批量完成 | 多选完成、重复完成、部分失败提示 |

## 6. 架构师建议

1. **请优先确认 P0 阻塞项**：联系/合同生成规则、社保是否全量生成、杨杰账号权限、历史已完成单展示口径。
2. **开发建议先按默认答案推进**：默认答案均以减少返工、兼容旧一拆三、满足会议简化方案为原则。
3. **前端必须坚持中文展示**：页面上只出现“社保公积金办理、待办理、已完成、可编辑、仅可见、隐藏、脱敏”等中文，不向用户暴露英文 code 或枚举。
4. **历史数据必须可回滚**：迁移生成的社保子单必须带批次号，回滚只删除本批次补出的子单，不动原三类子单。
5. **本轮不要扩范围**：省份自动派单、流程可视化配置、邮件/短信通知均不进入 P1。
