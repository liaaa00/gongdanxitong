# P1 入职一拆四架构最终方案（2026-05-15）

> 文档定位：本文件是 P1「入职一拆四 + 轻流式模块化表格/字段配置」的架构总方案，作为后续后端、前端、QA 拆任务与验收的统一依据。  
> 依据来源：用户本轮最终确认口径、`docs/P1-一拆四后端最终实施方案-20260515.md`、`docs/P1-一拆四前端最终交互方案-20260515.md`、`tests/P1-QA最终规则与模块化配置验收方案-20260515.md`，并修订旧版 `docs/入职一拆四-架构方案-20260515.md` 中已不适用的历史迁移口径。  
> 本文只做架构设计，不包含业务代码修改。

## 0. 最终结论摘要

### 0.1 入职一拆四最终生成规则

新提交的入职主工单，从本版本开始按「一拆四」执行，四类子单如下：

| 序号 | 内部模块编码 | 中文模块名 | 是否生成 | 最终规则 |
|---:|---|---|---|---|
| 1 | `onboarding_contact` | 入职联系 | 条件生成 | **仍按原来的条件生成**，例如 `need_onboarding_contact = 是` 时生成；条件不满足不生成。 |
| 2 | `contract` | 劳动合同签订 | 条件生成 | **仍按原来的条件生成**，例如 `need_company_contract = 是` / 企服发起劳动合同为是时生成；条件不满足不生成。 |
| 3 | `data_entry` | 数据录入 | 必生成 | 所有入职工单都必须生成。 |
| 4 | `social_insurance` | 社保公积金办理 | 必生成 | **所有入职工单都必须生成**，不再按参保省份、客户或其他条件决定是否生成。 |

关键要求：

1. `data_entry` 和 `social_insurance` 是入职工单的硬性必拆子模块。
2. `onboarding_contact` 和 `contract` 只保留原条件生成，不改成必生成。
3. 新数据可统一使用 `contract` 作为劳动合同模块编码；如旧代码存在 `contract_signing`，仅在查询/展示字典层兼容，不做数据迁移。
4. 前端所有页面必须显示中文模块名，不向业务用户裸露 `social_insurance`、`data_entry` 等内部编码。

### 0.2 用户最终确认口径固化

| 编号 | 事项 | 最终口径 |
|---:|---|---|
| 1 | 入职联系 | 仍按原条件生成。 |
| 2 | 劳动合同 | 仍按原条件生成。 |
| 3 | 社保公积金办理 | 所有入职工单必须生成。 |
| 4 | 杨杰账号 | 目前还不存在，后续可以添加；本阶段不能假设系统已有杨杰账号。 |
| 5 | 历史数据 | 当前没有历史数据，直接从现在开始一拆四；不做历史一拆三迁移、补社保子单、迁移回滚。 |
| 6 | dirty 清除 | 下游负责人打开子工单详情，或点击「确认已阅」后，清除该子工单的所有 active dirty 标记。 |
| 7 | 已完成子单退回 | 由该节点模块主管或系统管理员操作；普通办理人完成子单后没有退回权限；退回原因必填。 |
| 8 | 社保批量完成备注 | 必填，用于记录月份、基数、操作类型等追溯信息。 |
| 9 | 模块化搭建 | 参考轻流，支持模块、子模块、字段库、字段分组、字段权限、拆分规则、模块负责人/主管、导出模板、办理动作配置。 |

### 0.3 本方案的边界

本方案包含：

- 入职一拆四最终规则。
- Dirty 标记、通知、已阅清除机制。
- 已完成子单退回权限、原因必填、重走影响。
- 社保批量完成备注必填。
- 轻流式模块化配置模型。
- 后端、前端、QA 可直接拆分的实施清单。

本方案明确不包含：

- 历史一拆三数据迁移。
- 历史主单补社保子单。
- `migration_batch_no` 回滚方案。
- 假设或强制初始化杨杰账号。
- 邮件、短信、企业微信等站外通知；本轮只要求站内通知和操作日志。

## 2. 业务域与模块层级设计

参考轻流的「应用 / 表单 / 流程 / 节点 / 权限 / 动作」思想，本系统按三级结构组织：

```text
业务域（domain）
  └── 业务模块（module / app）
        └── 子模块（sub_module / node）
              └── 字段、权限、负责人、动作、导出模板、拆分规则
```

### 2.1 三大业务模块

| 业务模块 | 建议编码 | 说明 | 典型子模块 |
|---|---|---|---|
| 入职管理 | `onboarding_management` | 入职主工单及其下游办理 | 入职联系、劳动合同签订、数据录入、社保公积金办理 |
| 在职管理 | `employment_management` | 续签、待遇申报等在职事项 | 合同续签、待遇申报、其他在职服务 |
| 离职管理 | `resignation_management` | 离职、离职证明等事项 | 离职办理、离职证明、停保/减员等可扩展事项 |

说明：

1. 三大业务模块用于菜单、权限归类和后台配置入口。
2. 子模块用于实际子工单派发、办理、退回、字段权限和导出模板。
3. P1 本轮重点落地「入职管理」的一拆四；在职/离职只要求模型能承载，不强制一次性完成所有后台搭建能力。

### 2.2 入职管理子模块清单

| 子模块编码 | 中文名 | 生成规则 | 默认处理方式 | 主管/退回权限来源 |
|---|---|---|---|---|
| `onboarding_contact` | 入职联系 | 原条件生成 | 可分派给入职联系办理人，如毛雅妮 | 模块主管，如江璐，或 admin |
| `contract` | 劳动合同签订 | 原条件生成 | 可分派给合同办理人，如杨纯 | 合同组主管，如江璐，或 admin |
| `data_entry` | 数据录入 | 必生成 | 分派给数据录入负责人/池 | 数据录入组长，如安娜祯，或 admin |
| `social_insurance` | 社保公积金办理 | 必生成 | 分派给社保负责人/池；杨杰账号后续添加后再绑定 | 社保负责人/主管，如杨杰后续账号，或 admin |

## 3. 入职一拆四派发规则

### 3.1 规则矩阵

新建入职主工单提交时，按以下规则生成子工单：

| 条件组合 | 入职联系 | 劳动合同 | 数据录入 | 社保公积金办理 | 子单数量 |
|---|---:|---:|---:|---:|---:|
| 联系=否，合同=否 | 不生成 | 不生成 | 生成 | 生成 | 2 |
| 联系=是，合同=否 | 生成 | 不生成 | 生成 | 生成 | 3 |
| 联系=否，合同=是 | 不生成 | 生成 | 生成 | 生成 | 3 |
| 联系=是，合同=是 | 生成 | 生成 | 生成 | 生成 | 4 |

后端必须有服务级兜底：

1. `order_type='onboarding'` 提交后结果中必须包含 `data_entry`。
2. `order_type='onboarding'` 提交后结果中必须包含 `social_insurance`。
3. `onboarding_contact`、`contract` 只按规则生成，不因兜底变成必生成。
4. 派发结果必须在同一事务中完成，避免主工单提交成功但必生成子单缺失。

### 3.2 派发规则配置建议

短期可复用现有 `dispatch_rules`，长期抽象为 `module_split_rules`。

| 规则名建议 | 主工单类型 | 目标子模块 | 规则类型 | 条件 |
|---|---|---|---|---|
| `onboarding-default-data-entry` | `onboarding` | `data_entry` | 固定生成 | 恒真 |
| `onboarding-default-social-insurance` | `onboarding` | `social_insurance` | 固定生成 | 恒真 |
| `onboarding-contact-when-needed` | `onboarding` | `onboarding_contact` | 条件生成 | 是否需要入职联系 = 是 |
| `onboarding-contract-when-needed` | `onboarding` | `contract` | 条件生成 | 是否需要劳动合同/企服发起劳动合同 = 是 |

配置后台必须用中文表达规则，例如「固定生成」「满足条件时生成」，不向管理员裸露 `always`、`conditional` 等技术枚举。

### 3.3 杨杰账号暂不存在时的社保负责人处理

本轮不能假设杨杰账号已存在，系统应支持以下处理：

1. **优先读取配置**：从 `module_handlers` / `module_supervisors` 找 `social_insurance` 的负责人或主管。
2. **无负责人时不创建假账号**：不在 seed 中硬造“杨杰”。
3. **允许待配置/池模式**：若没有具体负责人，可将社保子单进入「社保模块池」或 `handler_id=null` 的待指派状态。
4. **给管理员提示**：生成站内通知或配置页告警：「社保公积金办理模块未配置负责人，请配置后处理」。
5. **后续补账号**：杨杰账号创建后，通过后台配置绑定为社保负责人/主管即可，不需要数据迁移。

## 4. 状态机与业务员修改规则

### 4.1 主工单状态

| 中文状态 | 内部状态建议 | 进入条件 | 关键操作 |
|---|---|---|---|
| 草稿 | `draft` | 尚未提交 | 发起人编辑、提交 |
| 流转中 | `processing` | 已提交且至少一个当前轮子单未完成 | 下游办理；符合条件时业务员修改并产生 dirty |
| 待业务员修改 | `returned` | 已完成子单被主管/admin 退回，需要发起人处理 | 发起人修改并重新提交 |
| 已完成 | `completed` | 当前轮所有已生成子单均完成 | 只读；如需改，先由主管/admin 退回完成子单 |
| 已作废 | `cancelled` | 业务作废 | 全部只读 |

### 4.2 子工单状态

| 中文状态 | 内部状态建议 | 说明 |
|---|---|---|
| 待办理 | `pending` | 已生成，等待负责人办理或认领 |
| 办理中 | `processing` | 已接单或正在处理 |
| 已完成 | `completed` | 办理完成；普通办理人此后无退回权限 |
| 已退回 | `returned` | 被主管/admin 退回，必须有退回原因 |

### 4.3 业务员修改规则

业务员只允许修改「业务员发起字段」，不能修改下游办理字段。

| 场景 | 是否允许业务员直接修改 | 处理方式 |
|---|---:|---|
| 草稿未提交 | 允许 | 正常编辑，不产生 dirty。 |
| 已提交且当前轮所有子单都未完成 | 允许 | 保存主单字段，刷新相关子单快照，生成 dirty 标记并通知下游。 |
| 当前轮存在任一已完成子单 | 不允许 | 前端置灰，后端强拦截；必须由对应模块主管/admin 退回已完成子单并填写原因。 |
| 全部已完成节点均已退回后 | 允许 | 业务员修改并重新提交，主工单进入新一轮流转。 |
| 已作废 | 不允许 | 全部只读。 |

### 4.4 重新提交与重走流程

当存在已完成节点且确需修改时：

1. 对应已完成子单由模块主管或 admin 退回，并填写退回原因。
2. 当前轮不再存在 `completed` 子单后，业务员才可编辑业务员发起字段。
3. 业务员保存并「重新提交」后：
   - `work_orders.modification_round + 1`；
   - 重新计算四类子单生成规则；
   - `data_entry` 与 `social_insurance` 继续必生成；
   - `onboarding_contact` 与 `contract` 按新字段值重新判断；
   - 当前轮相关子单 `flow_round` 更新为新轮次或生成新轮子单记录；
   - 当前轮 active dirty 标记结束，新轮按新快照办理；
   - 发送「重新流转」站内通知。

## 5. Dirty 标记、通知与清除机制

### 5.1 Dirty 产生时机

当业务员在「已提交且当前轮所有子单都未完成」的场景下修改业务员发起字段时，后端必须：

1. 比对 `work_orders.extra_data` 修改前后差异。
2. 校验变更字段属于业务员可编辑字段。
3. 根据字段归属、模块字段绑定、字段权限，计算受影响子模块。
4. 写入字段级 dirty 标记。
5. 刷新受影响子工单字段快照。
6. 给受影响子模块负责人/主管发送站内通知。
7. 写操作日志。

### 5.2 Dirty 表设计

建议新增 `work_order_field_dirty_marks`。

| 字段 | 类型建议 | 说明 |
|---|---|---|
| `id` | uuid | 主键。 |
| `work_order_id` | uuid | 主工单 ID。 |
| `dispatched_order_id` | uuid nullable | 受影响子工单 ID；能精确到子单时建议写入。 |
| `module_code` | varchar(64) | 受影响模块编码。 |
| `field_code` | varchar(128) | 字段编码。 |
| `field_label` | varchar(128) | 字段中文名快照。 |
| `old_value` | jsonb nullable | 修改前值；敏感字段按权限脱敏或仅审计可见。 |
| `new_value` | jsonb nullable | 修改后值。 |
| `changed_by` | uuid | 修改人。 |
| `changed_at` | timestamptz | 修改时间。 |
| `flow_round` | int | 所属流转轮次。 |
| `is_active` | boolean | 是否仍需下游确认。 |
| `cleared_at` | timestamptz nullable | 清除时间。 |
| `cleared_by` | uuid nullable | 清除人。 |
| `clear_reason` | varchar(64) nullable | `owner_open_detail` / `confirm_read` / `new_round` 等。 |

索引建议：

- `(dispatched_order_id, is_active)`：子单详情清除和查询。
- `(work_order_id, module_code, flow_round, is_active)`：按模块查询。
- `(work_order_id, field_code, flow_round)`：字段修改历史查询。

### 5.3 Dirty 返回与前端表现

子工单详情字段返回建议：

```json
{
  "fieldCode": "employee_name",
  "fieldLabel": "员工姓名",
  "value": "张三",
  "permissionText": "仅可见",
  "dirty": true,
  "dirtyInfo": {
    "changedAt": "2026-05-15 15:20:00",
    "changedByName": "业务员A",
    "oldValueText": "张三三",
    "newValueText": "张三"
  }
}
```

前端要求：

1. dirty 字段用红色或醒目标识展示。
2. 子单详情顶部展示中文提示条，如「业务员已修改 3 个字段，请核对红色标记字段」。
3. 敏感字段旧值/新值按当前角色字段权限展示；无权查看时显示「按权限隐藏」。
4. 页面不得显示 `dirtyMarks`、`field_code`、`visible` 等内部字段。

### 5.4 Dirty 清除最终规则

用户最终确认：**下游节点查看后自动清除**。

清除入口：

| 触发入口 | 推荐接口/行为 | 清除范围 |
|---|---|---|
| 负责人打开子工单详情 | `GET /api/dispatched-orders/:id` 内部自动调用清除服务 | 清除该子工单所有 active dirty 标记。 |
| 点击「确认已阅」 | `POST /api/dispatched-orders/:id/dirty/confirm-read` 或等价接口 | 清除该子工单所有 active dirty 标记。 |

清除权限：

1. 当前子工单负责人/当前认领人。
2. 该模块主管。
3. 系统管理员。
4. 其他只读查看者打开详情不应自动清除，避免误清。

清除要求：

- 只将 dirty 标记置为 `is_active=false`，写 `cleared_at`、`cleared_by`、`clear_reason`，不物理删除。
- 自动打开详情清除时，`clear_reason='owner_open_detail'`。
- 点击确认已阅时，`clear_reason='confirm_read'`。
- 清除操作写入 `operation_logs`，摘要包含清除字段数量。
- 清除 UI 活跃标记不等于删除审计历史；修改历史仍可追溯。

## 6. 已完成子单退回权限与重走影响

### 6.1 最终权限模型

已完成子单退回必须同时满足：

1. 子单当前状态为 `completed`。
2. 操作者是该子模块的模块主管，或系统管理员。
3. 退回原因必填，去空白后不能为空；建议不少于 5 个汉字或 10 个字符。
4. 普通办理人完成子单后不再拥有退回权限。

| 子模块 | 普通办理人示例 | 模块主管/负责人示例 | 退回权限 |
|---|---|---|---|
| 劳动合同签订 | 杨纯 | 江璐 | 江璐或 admin 可退回；杨纯完成后不可退回。 |
| 入职联系 | 毛雅妮 | 江璐 | 江璐或 admin 可退回；毛雅妮完成后不可退回。 |
| 数据录入 | 数据录入办理人 | 安娜祯 | 安娜祯或 admin 可退回。 |
| 社保公积金办理 | 社保办理人 | 杨杰后续账号/当前配置社保主管 | 绑定主管后可退回；未绑定前仅 admin。 |

### 6.2 权限实现建议

新增或扩展 `ModulePermissionService.canReturnCompletedDispatchedOrder(user, dispatchedOrder)`：

```text
if user has admin role -> allow
else if user is active supervisor of dispatchedOrder.module_code -> allow
else -> deny with message: 已完成子单只能由模块主管或系统管理员退回
```

主管来源建议：

1. 优先使用新增 `module_supervisors`。
2. 短期也可在 `module_handlers` 中通过 `handler_type='supervisor'` 或 `is_supervisor=true` 表达。
3. 不建议通过姓名硬编码判断江璐、安娜祯、杨杰。

### 6.3 退回记录表

建议新增 `dispatched_order_return_records`。

| 字段 | 类型建议 | 说明 |
|---|---|---|
| `id` | uuid | 主键。 |
| `dispatched_order_id` | uuid | 子工单 ID。 |
| `work_order_id` | uuid | 主工单 ID。 |
| `module_code` | varchar(64) | 模块编码快照。 |
| `module_name` | varchar(64) | 中文模块名快照。 |
| `from_status` | varchar(32) | 退回前状态。 |
| `to_status` | varchar(32) | 退回后状态。 |
| `return_reason` | text | 退回原因，必填。 |
| `returned_by` | uuid | 退回人。 |
| `returned_at` | timestamptz | 退回时间。 |
| `flow_round` | int | 当前流转轮次。 |

### 6.4 退回后的同步影响

主管/admin 退回已完成子单后：

1. 子单状态改为 `returned` 或回到待办理态，具体以现有状态机为准，但页面中文显示必须明确「已退回」。
2. 主工单若仍存在其他 completed 子单，业务员仍不能编辑。
3. 当前轮所有 completed 子单都不再 completed 后，主工单进入「待业务员修改」。
4. 业务员修改并重新提交后，整单进入新轮次，重新按一拆四规则拆分。
5. 退回原因、退回人、退回时间必须在详情、操作日志或历史记录中可追溯。
6. 通知业务员和相关模块主管/办理人。

## 7. 社保批量完成备注必填

### 7.1 业务原则

社保公积金办理涉及月份、基数、操作类型、客户确认口径等关键信息。批量完成如果没有备注，后续无法追溯，因此本轮统一设为必填。

### 7.2 接口建议

`POST /api/dispatched-orders/social-insurance/batch-complete`

```json
{
  "ids": ["子工单ID1", "子工单ID2"],
  "remark": "2026年5月社保公积金新增，基数已按客户确认表办理完成"
}
```

后端强校验：

1. `remark` 必填，去空白后不能为空；建议不少于 10 个字符。
2. 仅允许处理 `module_code='social_insurance'` 的子工单。
3. 操作者必须是社保模块负责人/主管或 admin。
4. 已完成子单幂等跳过并返回 skipped，不重复写脏数据。
5. 每条完成记录写操作日志，日志摘要包含批量备注。
6. 备注必须能在子单详情、完成记录或操作日志中追溯。

### 7.3 前端交互

1. 只有社保模块授权角色和 admin 可见批量完成入口。
2. 弹窗中备注项标红星必填，提示文案建议：「请填写办理备注，如月份、基数、操作类型等」。
3. 空备注、纯空格不可提交；前端拦截，后端也要拒绝。
4. 批量完成后展示成功、跳过、失败数量及中文原因。

## 8. 轻流式模块化配置模型

### 8.1 设计目标

参考轻流的模块化搭建形式，系统应逐步从硬编码表单/流程转为配置驱动：

- 管理员可以配置业务模块和子模块。
- 管理员可以配置字段库、字段分组、模块字段、字段权限。
- 管理员可以配置拆分规则，决定主工单提交后生成哪些子模块。
- 管理员可以配置模块负责人、模块主管、备用人、处理人池。
- 管理员可以配置办理动作，如完成、退回、确认已阅、批量完成。
- 管理员可以配置导出模板，决定不同模块导出哪些字段。

### 8.2 模块化配置对象总览

| 配置对象 | 建议表/复用表 | 解决的问题 | P1 建议 |
|---|---|---|---|
| 业务模块/子模块 | `work_order_modules` | 模块中文名、归属业务域、启用状态、排序 | 建议新增，作为模块配置入口。 |
| 字段库 | `field_configs` 或 `field_definitions` | 字段编码、中文名、控件类型、校验、选项 | 短期复用现有字段配置。 |
| 字段分组 | `field_groups` | 表单分段、展示顺序、折叠配置 | 建议新增或扩展现有配置。 |
| 模块字段 | `module_fields` | 每个子模块展示哪些字段、顺序、是否必填、是否参与 dirty | 建议新增。 |
| 字段权限 | `field_permissions` / `module_field_permissions` | 角色在不同模块对字段可编辑/仅可见/隐藏 | 短期复用，长期模块化。 |
| 拆分规则 | `dispatch_rules` / `module_split_rules` | 条件生成、固定生成、规则版本 | 短期复用，长期独立。 |
| 模块负责人 | `module_handlers` | 处理人、处理池、轮询、备份 | 继续复用并扩展。 |
| 模块主管 | `module_supervisors` | 已完成子单退回权限、模块看板 | 建议新增。 |
| 办理动作 | `action_configs` | 完成、退回、确认已阅、批量完成的权限和表单 | 建议新增。 |
| 导出模板 | `export_templates` | 模块/角色导出字段与格式 | 继续复用并按模块扩展。 |
| 配置版本 | `module_config_versions` | 配置发布、回滚、老单稳定快照 | 可选，后台配置复杂后再做。 |

### 8.3 `work_order_modules`：模块定义

建议字段：

| 字段 | 说明 |
|---|---|
| `id` | UUID 主键。 |
| `domain_code` | 业务域：入职管理、在职管理、离职管理。 |
| `order_type` | 主工单类型，如 `onboarding`、`renewal`、`resignation`。 |
| `module_code` | 子模块编码，如 `social_insurance`。 |
| `module_name` | 中文名，如「社保公积金办理」。 |
| `module_type` | 子模块类型：办理节点、信息页、导出节点等。 |
| `is_required` | 是否默认必生成；入职数据录入/社保为 true。 |
| `is_active` | 是否启用。 |
| `sort_order` | 展示顺序。 |
| `description` | 管理端说明。 |

### 8.4 字段库与字段分组

字段库只定义字段本身，不直接决定在哪个模块出现。

字段库建议包含：

- `field_code`：唯一字段编码。
- `field_label`：中文字段名。
- `field_type`：控件类型，如文本、日期、单选、多选、金额、附件。
- `options`：下拉/单选选项。
- `validation_rules`：长度、格式、正则、必填条件。
- `data_owner`：字段归属，如业务员发起字段、合同办理字段、社保办理字段。
- `is_sensitive`：是否敏感字段。

字段分组建议支持：

- 分组中文名，如「员工基础信息」「合同信息」「社保公积金信息」「银行与发薪信息」。
- 分组排序。
- 是否默认展开。
- 适用业务模块/子模块。

### 8.5 模块字段 `module_fields`

用于解决「表格拆分」和「字段处理」：主表单字段可以按模块拆成不同子工单视图，不同模块看到不同字段、顺序和必填规则。

建议字段：

| 字段 | 说明 |
|---|---|
| `module_code` | 子模块编码。 |
| `field_code` | 字段编码。 |
| `group_code` | 所属字段分组。 |
| `display_order` | 展示顺序。 |
| `required_mode` | 必填策略：继承字段库、模块内必填、模块内非必填、条件必填。 |
| `visible_in_list` | 是否在列表展示。 |
| `visible_in_detail` | 是否在详情展示。 |
| `editable_in_module` | 是否允许该模块办理人编辑。 |
| `snapshot_enabled` | 是否写入子单快照。 |
| `dirty_tracked` | 业务员修改时是否产生 dirty。 |
| `exportable` | 是否可用于导出模板。 |

示例：

| 子模块 | 典型字段 |
|---|---|
| 入职联系 | 员工姓名、手机号、入职日期、联系备注、材料收集状态 |
| 劳动合同 | 员工姓名、身份证、合同开始/结束日期、合同类型、合同办理备注 |
| 数据录入 | 员工基础信息、客户/商社、岗位、薪资、银行信息、录入反馈 |
| 社保公积金 | 员工姓名、身份证、参保城市、参保月份、社保基数、公积金基数、办理备注 |

### 8.6 字段权限

权限三态面向业务用户必须中文化：

| 中文权限 | 内部值建议 | 含义 |
|---|---|---|
| 可编辑 | `editable` | 可见且可修改。 |
| 仅可见 | `readonly` | 可见但不可修改。 |
| 隐藏 | `hidden` | 不返回或不展示。 |
| 脱敏（可选） | `masked` | 可见脱敏值，不显示完整敏感信息。 |

权限维度建议：

```text
角色/用户 × 业务模块 × 子模块 × 场景 × 字段
```

典型场景：

- 新建主工单。
- 主工单详情。
- 子工单详情。
- 子工单办理。
- 批量完成。
- 导出。

### 8.7 拆分规则 `module_split_rules`

长期建议用独立规则表表达拆分逻辑。

| 字段 | 说明 |
|---|---|
| `order_type` | 主工单类型。 |
| `module_code` | 目标子模块。 |
| `rule_type` | 固定生成、条件生成、手动生成。 |
| `condition_expr` | JSON 条件表达式，如字段等于某值。 |
| `priority` | 规则优先级。 |
| `is_required` | 是否服务级必生成。 |
| `version` | 规则版本。 |
| `is_active` | 是否启用。 |

入职一拆四规则必须预置：

- 数据录入：固定生成，必生成。
- 社保公积金办理：固定生成，必生成。
- 入职联系：条件生成。
- 劳动合同：条件生成。

### 8.8 模块负责人/主管

`module_handlers` 用于「谁办理」，`module_supervisors` 用于「谁负责/谁可退回已完成子单」。两者可以是同一个人，但职责不同。

模块负责人配置能力：

- 固定处理人。
- 处理人池。
- 轮询分派。
- 备份处理人。
- 未配置负责人时进入模块池或待指派。

模块主管配置能力：

- 查看本模块团队子单。
- 退回本模块已完成子单。
- 查看模块统计。
- 管理模块处理人（如产品允许）。

### 8.9 办理动作配置 `action_configs`

动作配置用于把「完成」「退回」「确认已阅」「批量完成」等操作从页面硬编码中抽象出来。

| 动作 | 适用模块 | 权限 | 表单要求 |
|---|---|---|---|
| 完成 | 所有子模块 | 办理人/主管/admin | 可配置完成备注是否必填。 |
| 确认已阅 | 有 dirty 的子模块 | 办理人/主管/admin | 无额外必填；清除 dirty。 |
| 退回已完成子单 | 所有子模块 | 模块主管/admin | 退回原因必填。 |
| 社保批量完成 | 社保公积金办理 | 社保负责人/主管/admin | 完成备注必填。 |

### 8.10 导出模板

导出模板应绑定到业务模块/子模块/角色：

- 模板名称、适用模块、适用角色。
- 导出字段列表、字段顺序、表头中文名。
- 数据权限范围。
- 是否包含 dirty 历史、退回历史、办理备注。

本轮建议至少预留社保公积金办理导出模板能力，便于后续按月份/基数/办理状态导出。

## 10. 前端交互与中文化要求

### 10.1 拆分预览

入职主工单提交前应展示中文拆分预览：

- 数据录入：必生成。
- 社保公积金办理：必生成。
- 入职联系：根据条件显示「将生成」或「不生成」。
- 劳动合同签订：根据条件显示「将生成」或「不生成」。

提交成功弹窗中也应展示本次实际生成的子单中文列表。

### 10.2 Dirty 交互

- 子单列表显示「有业务员修改待确认」等中文标签。
- 子单详情顶部展示提示条。
- 打开详情后如本次自动清除，可展示「本次打开已自动确认 3 个修改标记」或在历史记录中体现。
- 「确认已阅」按钮可作为显式入口；重复点击应幂等。

### 10.3 退回交互

- 普通办理人完成子单后不显示退回按钮。
- 模块主管/admin 在已完成子单详情中显示退回按钮。
- 退回弹窗中退回原因必填。
- 空白、纯空格、过短原因不可提交。
- 成功后展示退回人、退回时间、退回原因。

### 10.4 社保批量完成交互

- 仅社保授权角色/admin 可见批量完成入口。
- 批量完成弹窗备注必填。
- 备注提示应引导填写月份、基数、操作类型。
- 结果反馈区分成功、跳过、失败。

### 10.5 中文映射禁止裸露

业务用户页面禁止裸露：

- 模块编码：`social_insurance`、`onboarding_contact`、`data_entry`、`contract`。
- 状态值：`pending`、`processing`、`completed`、`returned`、`dirty`。
- 权限值：`visible`、`readonly`、`editable`、`hidden`、`masked`。
- 技术字段：`module_code`、`field_code`、`handler_id`、`dirtyMarks`。

## 13. 最低验收标准

本 P1 方案进入业务验收前必须满足：

1. 新提交入职工单按最终一拆四规则生成：`data_entry` 必生成、`social_insurance` 必生成、`onboarding_contact` 按原条件、`contract` 按原条件。

5. 已完成子单退回只允许模块主管/admin，普通办理人完成后无退回权限。
6. 退回原因必填且可追溯。
7. 社保批量完成备注必填且可追溯。
8. 轻流式模块化配置至少打通模块、字段、字段权限、拆分规则、负责人/主管、导出模板的配置闭环。

10. P0 既有入职/续签/离职、字段权限、菜单、详情等核心能力不回归。
