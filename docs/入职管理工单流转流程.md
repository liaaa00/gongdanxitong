# 入职管理工单流转流程文档

## 1. 流程概述

入职管理工单系统是一个多角色协作的业务流程管理平台，支持从工单创建、派发、处理到完成的全生命周期管理。系统通过主工单和子工单的两层结构，实现业务流程的并行处理和精细化管理。

## 2. 角色说明

### 2.1 业务员（Salesperson）
**职责**：
- 创建和管理主工单
- 填写员工基本信息（姓名、身份证号等）
- 提交工单触发派发流程
- 处理后道退回的工单
- 发起撤回/修改申请

**权限**：
- 只能查看和操作自己创建的工单
- 可以修改草稿状态和退回状态的工单
- 可以查看所有子工单的处理状态

### 2.2 数据录入岗（Data Entry）
**职责**：
- 接收并处理数据录入类子工单
- 补充和完善员工详细信息
- 完成后标记子工单为已完成
- 必要时可退回给业务员

**权限**：
- 查看分配给自己的子工单
- 查看和编辑可见字段范围内的数据
- 可以补充字段信息
- 可以退回工单

### 2.3 入职联系岗（Onboarding Contact）
**职责**：
- 联系新员工安排入职事宜
- 记录联系结果和入职时间
- 完成联系后标记子工单为已完成
- 必要时可退回给业务员

**权限**：
- 查看分配给自己的子工单
- 查看和编辑可见字段范围内的数据
- 可以补充字段信息
- 可以退回工单

### 2.4 合同组（Contract Team）
**职责**：
- 处理合同相关事务
- 准备和审核入职合同
- 完成后标记子工单为已完成
- 必要时可退回给业务员

**权限**：
- 查看分配给自己的子工单
- 查看和编辑可见字段范围内的数据
- 可以补充字段信息
- 可以退回工单

### 2.5 主管/管理员（Supervisor/Admin）
**职责**：
- 查看团队所有工单
- 重新分配子工单
- 审批撤回申请
- 监控工单处理进度

**权限**：
- 查看所有工单和子工单
- 可以重新分配子工单处理人
- 可以审批撤回/修改申请

## 3. 详细流程步骤

### 3.1 业务员创建/导入工单

#### 3.1.1 手动创建工单
**操作步骤**：
1. 业务员登录系统
2. 点击"创建工单"按钮
3. 选择工单类型（入职管理：`onboarding`）
4. 填写必填字段：
   - 客户信息（`customerId`）
   - 部门信息（`departmentId`）
   - 员工姓名（`employee_name`）
   - 身份证号（`id_card_no`）
   - 其他业务字段（存储在 `extraData` 中）
5. 保存为草稿（状态：`DRAFT`）

**系统行为**：
- 自动生成唯一工单号（`orderNo`）
- 记录创建人（`createdBy`）
- 记录创建时间（`createdAt`）
- 工单状态设置为 `DRAFT`

#### 3.1.2 批量导入工单
**操作步骤**：
1. 业务员上传 Excel 文件
2. 系统预览并智能匹配字段映射
3. 业务员确认字段映射关系
4. 系统批量创建草稿工单

**系统行为**：
- 创建导入任务（`ImportJob`）
- 逐行解析并创建工单
- 记录成功和失败数量
- 生成错误报告（如有）

### 3.2 系统自动派发子工单

#### 3.2.1 派发触发条件
业务员提交主工单时（调用 `submit` 接口），系统自动触发派发流程。

#### 3.2.2 派发规则引擎
**规则评估流程**：
1. 系统读取所有激活的派发规则（`DispatchRule`）
2. 按优先级（`priority`）从高到低评估
3. 对每条规则：
   - 解析条件表达式（AST 语法树）
   - 评估条件是否满足（基于工单数据）
   - 如果满足，记录该规则命中
4. 根据命中的规则生成子工单列表

**派发策略**：
- `FIXED`：固定分配给指定处理人
- `ROUND_ROBIN`：轮询分配
- `LOAD_BALANCE`：负载均衡分配
- `POOL`：放入公共池，不指定处理人

#### 3.2.3 子工单创建
**系统行为**：
1. 为每个命中的模块创建子工单（`DispatchedOrder`）
2. 设置子工单属性：
   - `parentOrderId`：关联主工单
   - `moduleCode`：模块代码（如 `data_entry`、`onboarding_contact`、`contract`）
   - `status`：初始状态为 `PENDING`
   - `handlerId`：根据派发策略分配处理人（可能为空）
   - `visibleFields`：该模块可见的字段列表
   - `dispatchedAt`：派发时间
3. 主工单状态更新：
   - `DRAFT` → `PENDING` → `PROCESSING`
   - 记录 `submittedAt` 时间

**通知机制**：
- 如果子工单已分配处理人（`handlerId` 不为空）
- 系统创建通知（`Notification`）
- 通知内容：`新子工单待处理：主工单 {orderNo} 分派到 {moduleCode}`
- 通知链接：`/dispatched-orders/{dispatchedOrderId}`

### 3.3 后道接单和完成流程

#### 3.3.1 接单（Accept）
**操作步骤**：
1. 后道人员登录系统
2. 查看待处理子工单列表
3. 点击"接单"按钮

**系统行为**：
- 子工单状态：`PENDING` → `PROCESSING`
- 记录接单人（`handlerId`）
- 记录接单时间（`acceptedAt`）
- 使用乐观锁防止并发接单冲突

**权限控制**：
- 如果子工单已分配处理人，只有该处理人可以接单
- 如果子工单在公共池（`handlerId` 为空），任何有该模块权限的人都可以接单
- 管理员可以代替已分配的处理人接单

#### 3.3.2 补充字段（Supplement）
**操作步骤**：
1. 后道人员在子工单详情页查看字段
2. 填写或修改可编辑字段
3. 提交字段补充

**系统行为**：
- 创建字段补充日志（`FieldSupplementLog`）
- 记录字段代码、旧值、新值
- 记录补充人和补充时间
- 更新主工单的 `extraData`
- 使用乐观锁（基于 `workOrderUpdatedAt`）防止并发冲突

**字段权限**：
- 根据 `FieldPermission` 配置控制字段可见性和可编辑性
- 权限模式：
  - `VISIBLE`：可见可编辑
  - `READONLY`：可见不可编辑
  - `HIDDEN`：不可见
  - `MASKED`：脱敏显示

#### 3.3.3 完成子工单（Complete）
**操作步骤**：
1. 后道人员完成所有必要工作
2. 点击"完成"按钮
3. 可选：提交额外的字段数据

**系统行为**：
- 子工单状态：`PROCESSING` → `COMPLETED`
- 记录完成时间（`completedAt`）
- 如果提交了 `extraData`，更新主工单数据
- 检查主工单是否所有子工单都已完成

**主工单自动完成**：
- 系统检查所有子工单状态
- 如果所有子工单都是 `COMPLETED` 状态
- 主工单状态自动更新：`PROCESSING` → `COMPLETED`
- 记录主工单完成时间（`completedAt`）

### 3.4 退回流程（后道 → 业务员）

#### 3.4.1 后道发起退回
**操作步骤**：
1. 后道人员发现工单信息有误或不完整
2. 点击"退回"按钮
3. 填写退回原因（必填）
4. 可选：指定需要补充的字段列表

**系统行为**：
- 子工单状态：`PROCESSING` → `RETURNED`
- 记录退回原因（`returnReason`）
- 主工单状态：`PROCESSING` → `RETURNED`
- 创建通知给业务员

**通知内容**：
- 标题：`子工单已退回`
- 内容：退回原因
- 链接：`/work-orders/{workOrderId}`

#### 3.4.2 业务员处理退回
**操作步骤**：
1. 业务员收到退回通知
2. 查看退回原因
3. 修改工单数据（只能修改 `extraData`）
4. 重新提交工单

**系统行为**：
- 业务员只能修改 `extraData`，不能修改 `customerId` 和 `departmentId`
- 重新提交时，系统重置所有 `RETURNED` 状态的子工单
- 子工单状态：`RETURNED` → `PENDING`
- 主工单状态：`RETURNED` → `PROCESSING`
- 清空子工单的 `returnReason`
- 更新 `dispatchedAt` 为当前时间
- 不会创建新的子工单，使用原有子工单

### 3.5 撤回流程（业务员发起 → 多方审批）

#### 3.5.1 业务员发起撤回申请
**操作步骤**：
1. 业务员发现工单需要撤回或修改
2. 点击"撤回"或"修改"按钮
3. 选择申请类型：
   - `WITHDRAW`：撤回工单
   - `MODIFY`：修改工单数据
4. 填写申请原因（必填）
5. 如果是修改申请，填写 `modifyData`（要修改的字段）
6. 提交申请

**系统行为**：
- 创建撤回申请（`WithdrawRequest`）
- 申请状态：`PENDING`
- 查找所有未完成的子工单（状态不是 `COMPLETED`）
- 为每个未完成的子工单创建审批记录（`WithdrawApproval`）
- 审批人（`approverId`）为子工单的处理人（`handlerId`）
- 如果子工单未分配处理人，审批人为业务员自己
- 发送通知给所有审批人

**通知内容**：
- 模板：`withdraw_requested`
- 标题：`撤回/修改申请待审批`
- 内容：工单号、申请人、申请类型、申请原因

#### 3.5.2 后道人员审批
**操作步骤**：
1. 后道人员收到审批通知
2. 查看撤回申请详情
3. 选择审批结果：
   - `AGREE`：同意
   - `REJECT`：拒绝（需填写拒绝原因）
4. 提交审批

**系统行为**：
- 更新审批记录状态：`PENDING` → `AGREE` 或 `REJECT`
- 记录审批时间（`resolvedAt`）
- 如果是拒绝，记录拒绝原因（`rejectReason`）
- 检查申请是否可以结算

#### 3.5.3 申请结算逻辑
**结算规则**：
1. **全部拒绝**：任何一个审批人拒绝
   - 申请状态：`PENDING` → `REJECTED`
   - 记录 `resolvedAt`
   - 通知业务员：申请被拒绝

2. **全部同意**：所有审批人都同意
   - 申请状态：`PENDING` → `APPROVED`
   - 执行撤回或修改操作
   - 记录 `resolvedAt`
   - 通知业务员：申请已通过

3. **部分同意**：有人同意，有人未审批
   - 申请状态：`PENDING` → `PARTIAL`
   - 等待其他人审批

4. **无需审批**：没有未完成的子工单
   - 申请状态：直接 `APPROVED`
   - 立即执行撤回或修改操作

#### 3.5.4 执行撤回操作
**撤回申请（WITHDRAW）**：
- 主工单状态：`PROCESSING` → `WITHDRAWN`
- 记录主工单完成时间（`completedAt`）
- 所有未完成的子工单状态：→ `COMPLETED`
- 子工单 `returnReason` 设置为：`主工单已撤回`
- 记录子工单完成时间（`completedAt`）

**修改申请（MODIFY）**：
- 更新主工单 `extraData`（合并 `modifyData`）
- 如果修改了 `employee_name`，更新 `employeeName`
- 如果修改了 `id_card_no`，更新 `employeeIdCard`
- 如果主工单是 `RETURNED` 状态，更新为 `PROCESSING`
- 子工单状态不变，继续处理

#### 3.5.5 取消撤回申请
**操作步骤**：
1. 业务员在审批完成前可以取消申请
2. 点击"取消申请"按钮

**系统行为**：
- 申请状态：`PENDING` 或 `PARTIAL` → `CANCELLED`
- 记录 `resolvedAt`
- 通知所有审批人：申请已取消

## 4. 通知机制

### 4.1 通知触发场景

| 场景 | 触发时机 | 接收人 | 通知类型 | 通知内容 |
|------|---------|--------|---------|---------|
| 子工单派发 | 主工单提交后 | 子工单处理人 | `dispatch` | 新子工单待处理：主工单 {orderNo} 分派到 {moduleCode} |
| 子工单退回 | 后道退回工单 | 业务员（主工单创建人） | `dispatched_returned` | 子工单已退回：{returnReason} |
| 撤回申请创建 | 业务员发起撤回 | 所有未完成子工单的处理人 | `withdraw_requested` | 撤回/修改申请待审批：工单 {orderNo} |
| 撤回申请通过 | 所有审批人同意 | 业务员（申请人） | `withdraw_resolved` | 撤回/修改申请已通过 |
| 撤回申请拒绝 | 任一审批人拒绝 | 业务员（申请人） | `withdraw_resolved` | 撤回/修改申请被拒：{rejectReason} |
| 撤回申请取消 | 业务员取消申请 | 所有审批人 | `withdraw_cancelled` | 撤回/修改申请已取消 |

### 4.2 通知数据结构

```typescript
interface Notification {
  id: string;
  userId: string;              // 接收人 ID
  bizType: string;             // 业务类型
  title: string;               // 通知标题
  content: string;             // 通知内容
  link: string;                // 跳转链接
  payload: Record<string, any>; // 附加数据
  isRead: boolean;             // 是否已读
  readAt: Date | null;         // 阅读时间
  createdAt: Date;             // 创建时间
}
```

### 4.3 通知模板

系统使用 `NotificationService` 统一管理通知模板，支持参数化内容生成。

**示例**：
```typescript
// 撤回申请通知
{
  templateCode: 'withdraw_requested',
  recipients: ['user-id-1', 'user-id-2'],
  bizType: 'withdraw_requested',
  params: {
    requestId: 'req-123',
    orderNo: 'WO-2024-001',
    requesterName: '张三',
    requestType: 'withdraw',
    reason: '客户取消订单'
  }
}
```

## 5. 权限控制

### 5.1 角色权限矩阵

| 操作 | 业务员 | 后道人员 | 主管 | 管理员 |
|------|--------|---------|------|--------|
| 创建工单 | ✅ | ❌ | ✅ | ✅ |
| 查看自己的工单 | ✅ | ✅ | ✅ | ✅ |
| 查看团队工单 | ❌ | ❌ | ✅ | ✅ |
| 查看所有工单 | ❌ | ❌ | ❌ | ✅ |
| 修改工单 | ✅（仅自己的） | ❌ | ✅ | ✅ |
| 提交工单 | ✅（仅自己的） | ❌ | ✅ | ✅ |
| 接单 | ❌ | ✅ | ✅ | ✅ |
| 完成子工单 | ❌ | ✅（仅自己的） | ✅ | ✅ |
| 退回子工单 | ❌ | ✅（仅自己的） | ✅ | ✅ |
| 补充字段 | ❌ | ✅（仅自己的） | ✅ | ✅ |
| 发起撤回 | ✅（仅自己的） | ❌ | ✅ | ✅ |
| 审批撤回 | ❌ | ✅（仅自己负责的） | ✅ | ✅ |
| 重新分配子工单 | ❌ | ❌ | ✅ | ✅ |

### 5.2 字段权限控制

字段权限通过 `FieldPermission` 实体配置，支持按角色、模块、工单类型细粒度控制。

**权限模式**：
- `VISIBLE`：可见可编辑
- `READONLY`：可见但只读
- `HIDDEN`：完全不可见
- `MASKED`：脱敏显示（如身份证号显示为 `320***********1234`）

**配置示例**：
```json
{
  "roleCode": "data_entry",
  "moduleCode": "data_entry",
  "orderType": "onboarding",
  "fieldCode": "id_card_no",
  "permissionMode": "VISIBLE"
}
```

### 5.3 数据可见性规则

**业务员**：
- 只能查看自己创建的主工单
- 可以查看主工单下所有子工单的状态
- 不能查看子工单的详细处理过程

**后道人员**：
- 只能查看分配给自己的子工单
- 可以查看公共池中自己有权限的模块的子工单
- 只能看到 `visibleFields` 配置的字段

**主管**：
- 可以查看本部门所有工单
- 可以查看团队成员的子工单
- 可以重新分配子工单

**管理员**：
- 可以查看所有工单和子工单
- 可以执行所有操作
- 不受字段权限限制

## 6. 状态流转图

### 6.1 主工单状态流转

```
┌─────────┐
│  DRAFT  │ 草稿
└────┬────┘
     │ submit()
     ▼
┌─────────┐
│ PENDING │ 待派发（瞬态）
└────┬────┘
     │ 自动派发子工单
     ▼
┌────────────┐
│ PROCESSING │ 处理中
└─────┬──────┘
      │
      ├─────────────────┐
      │                 │
      │ 后道退回         │ 所有子工单完成
      ▼                 ▼
┌──────────┐      ┌───────────┐
│ RETURNED │      │ COMPLETED │ 已完成
└────┬─────┘      └───────────┘
     │
     │ 业务员重新提交
     ▼
┌────────────┐
│ PROCESSING │
└─────┬──────┘
      │
      │ 撤回申请通过
      ▼
┌───────────┐
│ WITHDRAWN │ 已撤回
└───────────┘
```

**状态说明**：
- `DRAFT`：草稿，业务员创建但未提交
- `PENDING`：待派发，提交后等待系统派发子工单（瞬态）
- `PROCESSING`：处理中，子工单已派发，正在处理
- `RETURNED`：已退回，后道退回给业务员修改
- `COMPLETED`：已完成，所有子工单都已完成
- `WITHDRAWN`：已撤回，撤回申请通过后的终态

### 6.2 子工单状态流转

```
┌─────────┐
│ PENDING │ 待接单
└────┬────┘
     │ accept()
     ▼
┌────────────┐
│ PROCESSING │ 处理中
└─────┬──────┘
      │
      ├──────────────┬──────────────┐
      │              │              │
      │ complete()   │ return()     │ 主工单撤回
      ▼              ▼              ▼
┌───────────┐  ┌──────────┐  ┌───────────┐
│ COMPLETED │  │ RETURNED │  │ COMPLETED │
└───────────┘  └────┬─────┘  └───────────┘
                    │
                    │ 业务员重新提交
                    ▼
               ┌─────────┐
               │ PENDING │
               └─────────┘
```

**状态说明**：
- `PENDING`：待接单，等待后道人员接单
- `PROCESSING`：处理中，已接单正在处理
- `COMPLETED`：已完成，后道人员完成处理
- `RETURNED`：已退回，后道退回给业务员

### 6.3 撤回申请状态流转

```
┌─────────┐
│ PENDING │ 待审批
└────┬────┘
     │
     ├──────────────┬──────────────┬──────────────┐
     │              │              │              │
     │ 部分同意      │ 全部同意      │ 任一拒绝      │ 业务员取消
     ▼              ▼              ▼              ▼
┌─────────┐  ┌──────────┐  ┌──────────┐  ┌───────────┐
│ PARTIAL │  │ APPROVED │  │ REJECTED │  │ CANCELLED │
└────┬────┘  └──────────┘  └──────────┘  └───────────┘
     │
     │ 继续审批
     ▼
┌──────────┐
│ APPROVED │ 或 REJECTED
└──────────┘
```

**状态说明**：
- `PENDING`：待审批，等待所有审批人审批
- `PARTIAL`：部分同意，有人同意但未全部审批
- `APPROVED`：已通过，所有审批人都同意
- `REJECTED`：已拒绝，任一审批人拒绝
- `CANCELLED`：已取消，业务员取消申请

### 6.4 审批记录状态

```
┌─────────┐
│ PENDING │ 待审批
└────┬────┘
     │
     ├──────────────┐
     │              │
     │ approve()    │ reject()
     ▼              ▼
┌────────┐    ┌────────┐
│ AGREE  │    │ REJECT │
└────────┘    └────────┘
```

**状态说明**：
- `PENDING`：待审批
- `AGREE`：同意
- `REJECT`：拒绝

## 7. 异常处理

### 7.1 退回场景

#### 7.1.1 后道退回给业务员
**触发条件**：
- 工单信息不完整
- 工单信息有误
- 需要业务员补充特定字段

**处理流程**：
1. 后道人员点击"退回"，填写退回原因
2. 子工单状态变为 `RETURNED`
3. 主工单状态变为 `RETURNED`
4. 系统通知业务员
5. 业务员修改工单数据
6. 业务员重新提交
7. 系统重置退回的子工单为 `PENDING`
8. 主工单状态恢复为 `PROCESSING`

**注意事项**：
- 退回后，业务员只能修改 `extraData`，不能修改客户和部门
- 重新提交不会创建新的子工单，使用原有子工单
- 已完成的子工单不受影响

#### 7.1.2 多个子工单同时退回
**处理逻辑**：
- 只要有一个子工单退回，主工单就变为 `RETURNED`
- 其他未退回的子工单状态不变
- 业务员重新提交后，只重置 `RETURNED` 状态的子工单

### 7.2 撤回场景

#### 7.2.1 撤回申请被拒绝
**触发条件**：
- 任一审批人拒绝申请

**处理流程**：
1. 审批人点击"拒绝"，填写拒绝原因
2. 申请状态立即变为 `REJECTED`
3. 系统通知业务员申请被拒
4. 业务员可以查看拒绝原因
5. 业务员可以重新发起新的撤回申请

**注意事项**：
- 一票否决制，任何一个审批人拒绝即失败
- 拒绝后不能再次审批
- 业务员需要重新发起申请

#### 7.2.2 撤回申请部分同意
**触发条件**：
- 有审批人同意，但还有审批人未审批

**处理流程**：
1. 申请状态变为 `PARTIAL`
2. 等待其他审批人审批
3. 如果后续有人拒绝，申请变为 `REJECTED`
4. 如果所有人都同意，申请变为 `APPROVED`

#### 7.2.3 无需审批的撤回
**触发条件**：
- 所有子工单都已完成
- 没有未完成的子工单需要审批

**处理流程**：
1. 申请创建后立即变为 `APPROVED`
2. 立即执行撤回或修改操作
3. 通知业务员申请已通过

### 7.3 并发冲突处理

#### 7.3.1 接单冲突
**场景**：多个后道人员同时接同一个公共池工单

**解决方案**：
- 使用数据库乐观锁
- SQL 条件：`WHERE status = 'PENDING' AND (handler_id IS NULL OR handler_id = :userId)`
- 只有一个人能成功接单
- 其他人收到错误提示：`接单失败：状态已变化`

#### 7.3.2 字段补充冲突
**场景**：多个后道人员同时修改同一个工单的字段

**解决方案**：
- 使用乐观锁（基于 `workOrderUpdatedAt`）
- 前端提交时携带工单的 `updatedAt` 时间戳
- 后端检查时间戳是否匹配
- 如果不匹配，返回错误：`工单已被他人修改，请刷新后重试`

#### 7.3.3 撤回审批冲突
**场景**：多个审批人同时审批同一个撤回申请

**解决方案**：
- 使用数据库悲观锁（`SELECT FOR UPDATE`）
- 事务内锁定申请记录和审批记录
- 按顺序处理审批
- 确保状态流转的一致性

### 7.4 数据一致性保障

#### 7.4.1 事务保护
**关键操作使用事务**：
- 提交工单并派发子工单
- 完成子工单并检查主工单完成
- 撤回申请的创建和审批
- 退回工单并更新主工单状态

**事务隔离级别**：
- 使用 PostgreSQL 默认的 `READ COMMITTED`
- 关键操作使用 `SELECT FOR UPDATE` 行锁

#### 7.4.2 分布式锁
**使用场景**：
- 工单提交：`pg_advisory_xact_lock(hashtext('work_order:submit:{id}'))`
- 防止重复提交
- 确保派发流程的原子性

#### 7.4.3 操作日志
**所有关键操作记录日志**：
- 实体类型（`entityType`）：`work_order`、`dispatched_order`、`withdraw_request`
- 实体 ID（`entityId`）
- 操作人（`userId`）
- 操作类型（`actionType`）：`create_draft`、`submit`、`accept`、`complete`、`return`、`approve`、`reject`
- 操作前数据（`beforeData`）
- 操作后数据（`afterData`）
- 操作时间（`createdAt`）

**日志用途**：
- 审计追踪
- 问题排查
- 数据恢复

### 9.3 字段权限计算

**权限计算逻辑**：
```typescript
function calculateFieldPermission(
  fieldCode: string,
  roleCode: string,
  moduleCode: string,
  orderType: string
): FieldPermissionMode {
  // 1. 查找精确匹配的权限配置
  const exact = findPermission({
    fieldCode,
    roleCode,
    moduleCode,
    orderType
  });
  if (exact) return exact.permissionMode;
  
  // 2. 查找模块级默认权限
  const moduleDefault = findPermission({
    fieldCode,
    roleCode,
    moduleCode,
    orderType: null
  });
  if (moduleDefault) return moduleDefault.permissionMode;
  
  // 3. 查找角色级默认权限
  const roleDefault = findPermission({
    fieldCode,
    roleCode,
    moduleCode: null,
    orderType: null
  });
  if (roleDefault) return roleDefault.permissionMode;
  
  // 4. 默认隐藏
  return FieldPermissionMode.HIDDEN;
}
```

if (result.affected === 0) {

## 10. 总结

入职管理工单系统通过主工单和子工单的两层结构，实现了复杂业务流程的并行处理和精细化管理。系统的核心特点包括：

1. **灵活的派发机制**：基于规则引擎的自动派发，支持多种派发策略
2. **完善的权限控制**：细粒度的字段权限和角色权限管理
3. **健壮的异常处理**：支持退回、撤回等异常流程
4. **强大的并发控制**：乐观锁、悲观锁、分布式锁保障数据一致性
5. **完整的审计追踪**：操作日志记录所有关键操作

系统适用于需要多角色协作、流程复杂、权限要求严格的业务场景。
