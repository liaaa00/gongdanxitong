## 1) 「入职·数据录入三个人」是不是主+备1+备2 平铺？

### 1.1 贴 seed 原始代码（`backend/src/database/seeds/seed-module-handlers.ts:33`）

```ts
// 数据录入模块：安娜珍。
{ moduleCode: 'data_entry', username: 'annazhen', weight: 10, isBackup: false },
```

**注意**：seed 里 `data_entry` **只配置了 1 行 1 个人**（安娜珍 / annazhen / 主岗 / weight=10）。**没有备1，没有备2。**

### 1.2 对比同文件其他模块（`seed-module-handlers.ts:11-32`）

```ts
// 合同模块：1 主 + 1 备
{ moduleCode: 'contract', username: 'yangchun', weight: 10, isBackup: false },
{ moduleCode: 'contract', username: 'jianglu',  weight: 1,  isBackup: true  },

// 入离职联系：1 主 + 1 备
{ moduleCode: 'onboarding_contact', username: 'maoyani',  weight: 10, isBackup: false },
{ moduleCode: 'onboarding_contact', username: 'jianglu',  weight: 1,  isBackup: true  },

// 社保办理：1 主 + 1 备
{ moduleCode: 'social_insurance', username: 'social01',    weight: 10, isBackup: false },
{ moduleCode: 'social_insurance', username: 'socialsup01', weight: 1,  isBackup: true  },
```

### 1.3 表结构（`backend/src/entities/module-handler.entity.ts`）

```ts
@Entity({ name: 'module_handlers' })
export class ModuleHandler {
  id: string;                  // 主键
  moduleCode: string;          // 模块代码
  handlerId: string;           // 用户 ID
  weight: number;              // 权重（数字越大越优先）
  isBackup: boolean;           // false=主岗 / true=备用
  isActive: boolean;           // 启用/停用
  rrCursorVersion: number;     // 轮询游标
}
```

**关键判断：表结构是「1 行 = 1 个人」的扁平结构**。区分主备只有一个布尔字段 `isBackup`，**没有「备1/备2」的层级概念**——多个 `isBackup=true` 的行会同时被视为备份候选，由 `pickFromCandidates` 按 `weight` 降序排序后挑第一个。

### 1.4 用户为什么会看到「数据录入三个人」？

**原因**：seed 中 `data_entry` 仅配置 annazhen 一人。如果用户实际看到 3 行，**只能是数据库里被手动追加了 2 行**（管理后台 → 模块负责人 → 添加，参考 `frontend/src/pages/Admin/ModuleHandlers/index.tsx:107-124` 的 `createModuleHandlersBatch`）。

候选人选项池里至少存在以下 2 个相关账号（`backend/src/database/seeds/seed-users.ts:149,151`）：

```ts
{ username: 'dataentrysup01', realName: '数据录入主管（兼容账号）', ... },
{ username: 'social01',       realName: '社保专员（兼容账号）',     ... },
```

另外 `seed-module-configs.ts:65` 把 `dataentrysup01` 配进了**模块主管表**（`module_supervisors`，与 `module_handlers` 不是同一张表）：

```ts
{ moduleCode: 'data_entry', usernames: ['annazhen', 'dataentrysup01'] }, // 主管表，不是负责人表
```

> **结论**：代码侧 seed 里数据录入**只有 1 主（无备）**，不是「主+备1+备2 平铺」。用户看到 3 行，是管理员后期通过 UI 手动添加。表结构本身就是「1 人 1 行」的扁平存储——所以即便要展示「主+备1+备2 三列」，**也是同一个 module_code 的 N 行记录**，不存在原生「3 列」结构。

## 2) module_handlers vs dispatch_rules 字段对比

### 2.1 实体字段对比表

| 维度 | `module_handlers` (8 字段) | `dispatch_rules` (16 字段) |
|---|---|---|
| 主键 | `id` ✅ | `id` ✅ |
| 模块定位 | `moduleCode` ✅ | `targetModule` + `subModule` ✅ |
| 关联人 | `handlerId` ✅ | `assigneeUserId` + `fallbackUserId` ✅ |
| 权重 | `weight` ✅ | ❌ |
| 主/备 | `isBackup` ✅ | ❌（用 assignee/fallback 两字段） |
| 启停 | `isActive` ✅ | `isActive` ✅ |
| 轮询游标 | `rrCursorVersion` ✅ | ❌ |
| 工单类型 | ❌ | `orderType` ✅ |
| 触发条件 (AST) | ❌ | `triggerConditions` (jsonb) ✅ |
| 客户范围 | ❌ | `customerId` ✅ |
| 部门范围 | ❌ | `departmentId` ✅ |
| 派发策略 | ❌ | `dispatchStrategy` ✅ |
| 优先级 | ❌ | `priority` ✅ |
| 允许手动改派 | ❌ | `allowManualOverride` ✅ |
| 规则名 | ❌ | `ruleName` ✅ |
| 创建时间 | ❌ | `createdAt` ✅ |

### 2.2 重叠 vs 独占

**真正重叠的字段**（语义上）：

| 含义 | module_handlers | dispatch_rules |
|---|---|---|
| 「这个工单交给谁处理」 | `handlerId`（候选池） | `assigneeUserId` + `fallbackUserId`（指定人） |
| 「指向哪个模块」 | `moduleCode` | `targetModule` (+ `subModule`) |
| 「是否启用」 | `isActive` | `isActive` |

**只在 `module_handlers` 有的**（候选池语义）：
- `weight`、`isBackup`、`rrCursorVersion` — 多人候选时按权重/主备/轮询挑一个

**只在 `dispatch_rules` 有的**（路由规则语义）：
- `orderType`、`triggerConditions`、`customerId`、`departmentId`、`dispatchStrategy`、`priority` — 决定「在什么条件下走这个规则」

### 2.3 所谓「重合」的本质

**两表语义不同，不是真重合**：

- `dispatch_rules` 回答 **「何时把工单分到哪个模块（再可选指定具体人）」**——这是**路由层**。
- `module_handlers` 回答 **「这个模块的候选人池有哪些」**——这是**候选池层**。

唯一有 overlap 的情况：当 `dispatch_rules.assigneeUserId` 不为空时，它直接绕过 `module_handlers` 的候选池逻辑（见第 3 节代码）。**这种 overlap 是设计上的「指定优先级 > 候选池」短路**，不是冗余。

## 3) HandlerPicker 实际逻辑 + 优先顺序

### 3.1 真正的入口：`DispatchEngineService.resolveRuleHandler()`

**`backend/src/modules/dispatch-engine/dispatch-engine.service.ts:137-146`**

```ts
private async resolveRuleHandler(rule: DispatchRule, moduleCode: string, manager?: EntityManager): Promise<string | null> {
  const userRepository = manager?.getRepository(User);
  if (rule.assigneeUserId && await this.isUserAvailable(rule.assigneeUserId, userRepository)) {
    return rule.assigneeUserId;                          // ① 第一优先
  }
  if (rule.fallbackUserId && await this.isUserAvailable(rule.fallbackUserId, userRepository)) {
    return rule.fallbackUserId;                          // ② 第二优先
  }
  return this.handlerPicker.pick(rule.dispatchStrategy, moduleCode, manager);  // ③ 兜底
}
```

### 3.2 兜底层：`HandlerPickerService.pick()`

**`backend/src/modules/dispatch-engine/handler-picker.service.ts:19-43`**

```ts
async pick(strategy: DispatchStrategy, moduleCode: string, manager?: EntityManager): Promise<string | null> {
  // ...
  if (strategy === DispatchStrategy.POOL)         return null;                  // 进池等领取
  if (strategy === DispatchStrategy.FIXED)        return this.pickFixed(...);   // 主岗优先 → 备岗兜底
  if (strategy === DispatchStrategy.LOAD_BALANCE) return this.pickLoadBalance(...);
  return this.pickRoundRobin(...);                                              // 加权轮询
}
```

`pickFixed` 的内部顺序（`handler-picker.service.ts:71-92`）：

```ts
// ① 先在 isBackup=false 的主岗里按 weight 降序挑
const primary = this.pickFixedFromList(candidates.filter(c => !c.isBackup));
if (primary) return primary;
// ② 主岗都没人/全停用，再到 isBackup=true 的备岗里挑
const backup = this.pickFixedFromList(candidates.filter(c => c.isBackup));
return backup ?? null;
```

### 3.3 完整优先顺序总结

```
工单提交
  └─ DispatchEngine.evaluateDetailed()
       └─ 遍历 dispatch_rules（按 priority/createdAt 排序）
            └─ AST 命中 + 客户/部门 scope 匹配 → 选 winner
                 └─ resolveRuleHandler(winner)
                      ① rule.assigneeUserId （指定人，直接返回）
                      ② rule.fallbackUserId （指定备份人）
                      ③ handlerPicker.pick(rule.dispatchStrategy, moduleCode)
                           └─ 查 module_handlers 表
                                ├─ 主岗（isBackup=false）按 weight 挑
                                └─ 备岗（isBackup=true）兜底
```

> **回答用户原问题**：现在**不是**「先查 dispatch_rules、没匹配回落 module_handlers」的简单二级回落。
>
> 实际是：**dispatch_rules 永远是入口（决定哪些子单生成 + 走哪个模块）**，只有当规则没指定具体人时，才落到 module_handlers 候选池里挑人。两者**不是替代关系，而是「路由 → 候选池」的串联关系**。

### 3.4 一个隐藏的兜底：入职 ensure 兜底（重要）

`dispatch-engine.service.ts:186-201`：入职工单即使没有任何规则命中，也会强制确保 `data_entry`、`social_insurance` 两个子单存在；如果 `need_onboarding_contact=是` 强制确保 `onboarding_contact` 子单——这部分**完全绕过 dispatch_rules**，直接走 `handlerPicker.pick(FIXED, moduleCode)`，所以即便管理员把入职相关的 dispatch_rules 全停了，子单依然会按 module_handlers 的候选人生成。**这是用户感觉「两表重合」最关键的来源**。

## 4) 方案 A 合并可行性（前端一页 UI 合并）

### 4.1 用户的合并意图（重述以确认理解）

将「派发规则 + 模块负责人」两张管理页合并为一张「派发配置」表格：
- 表头：模块 / 客户 / 主处理人 / 备1 / 备2 / 优先级 / 启停 / 操作
- 「全部客户默认」一行（数据来源 = module_handlers + dispatch_rules 的 customer_id IS NULL 的部分）
- 「具体客户」例外行（数据来源 = dispatch_rules 的 customer_id IS NOT NULL 的部分）

### 4.2 可行性结论：✅ 可行

后端两表保留不动，前端在视图层做合并。理由：

1. **「全部客户默认」这一行的数据本就在 module_handlers**：每个 moduleCode 的若干行（主+备1+备2）→ 前端透视成一行多列即可。
2. **「具体客户例外」这一行的数据就是 dispatch_rules.customerId IS NOT NULL 的行**：本身就是 1 行 1 客户 1 模块，直接平铺。
3. **派发引擎的优先级解析逻辑已经内建在 `ruleScopeRank()`**（`dispatch-engine.service.ts:131-135`，customerId > departmentId > 全局），UI 合并不会改变运行时行为。

### 4.3 合并后用户看到的表是怎么拼的

**示例（用户视角）**：

| 模块 | 客户 | 主 | 备1 | 备2 | 来源 |
|---|---|---|---|---|---|
| 数据录入 | （全部） | 安娜珍 | — | — | module_handlers |
| 合同 | （全部） | 杨纯 | 江璐 | — | module_handlers |
| 合同 | 客户A | 张三 | — | — | dispatch_rules（customerId=A，assigneeUserId=张三）|
| 入职联系 | （全部） | 毛雅妮 | 江璐 | — | module_handlers |

**拼接方式**：**前端拼接**（不需要 SQL UNION）。后端可以保留两个独立接口（已存在 `GET /admin/module-handlers` 和 `GET /admin/dispatch-rules`），前端取回后在内存里 reduce 成一张表。也可以新增一个聚合接口（A1 方案），减少前端 join 复杂度。

### 4.4 合并后的写操作如何路由

| 用户操作 | 后端路由 |
|---|---|
| 编辑「数据录入 / 全部客户 / 主」 | PUT `/admin/module-handlers/:id` |
| 添加「合同 / 客户A / 主=张三」例外行 | POST `/admin/dispatch-rules` |
| 删除「具体客户」例外行 | DELETE `/admin/dispatch-rules/:id` |

前端在 row 对象里挂 `_source: 'module_handler' | 'dispatch_rule'` 和原始 `id`，操作时按来源路由即可。

## 5) 主+备1+备2 三行 → 三列展示的设计

### 5.1 当前是 1 行 1 人 还是 1 行 主+备？

**1 行 1 人**（见第 1.3 节实体）。区分是 `isBackup` 布尔 + `weight` 数值。

### 5.2 三列展示需要后端调整吗？

**前端聚合即可，不必改后端**：

```ts
// 前端按 moduleCode 分组 + 排序
const grouped = handlers.groupBy('moduleCode');
const row = {
  moduleCode,
  primary:   grouped[moduleCode].filter(h => !h.isBackup).sort(byWeightDesc)[0],
  backup1:   grouped[moduleCode].filter(h =>  h.isBackup).sort(byWeightDesc)[0],
  backup2:   grouped[moduleCode].filter(h =>  h.isBackup).sort(byWeightDesc)[1],
};
```

**约定**：
- **主**：`isBackup=false`，按 weight 降序取第 1 个（业务上一般只有 1 个主）。
- **备1**：`isBackup=true`，按 weight 降序取第 1 个。
- **备2**：`isBackup=true`，按 weight 降序取第 2 个。

> 派发引擎运行时**不依赖「备1/备2」这种序号概念**——它只关心 `isBackup` 布尔。所以「备1/备2」**纯 UI 概念**，仅用于展示和编辑入口，不需要新建数据库列。

### 5.3 需要新增 aggregate 接口吗？

**不强制，但推荐**（见第 6 节 A1）。原因：

- 不加也行：前端并行 `GET /admin/module-handlers` + `GET /admin/dispatch-rules`，本地拼。
- 加一个 `GET /admin/dispatch-config` 的好处：
  - 一次请求拿到完整表数据（含模块名、客户名、用户姓名 join 后的展示文本），减少前端两次接口 + 两次 join。
  - 后端可以稳定排序（先按 module_code，再按 customer），UI 直接渲染。
  - 后续要加分页/搜索/导出更顺手。

## 6) 推荐路线 + 工时

### 路线对比

| 路线 | 后端改动 | 前端改动 | 数据迁移 | 风险 | 用户感受 |
|---|---|---|---|---|---|
| **A1**：后端加聚合接口 + 前端 UI 合并 | 新增 1 个只读聚合接口 | 重写 1 个页面 | 无 | 低 | ⭐⭐⭐⭐⭐ |
| **A2**：后端表结构合并 | 改 entity + 写 migration + 改 dispatch-engine | 重写 1 个页面 | 是 | **高**（动派发核心） | ⭐⭐⭐ |
| **A3**：纯前端拉两接口拼 | 0 | 重写 1 个页面 + 双接口编排 | 无 | 中（前端复杂度高） | ⭐⭐⭐⭐ |

### 强烈推荐：**A1**

**理由**：

1. **派发引擎核心逻辑（`dispatch-engine.service.ts`、`handler-picker.service.ts`）一行不动**——风险可控。
2. 现有 16 张相关测试（`backend/test/dispatch-engine-p7.spec.ts`、`onboarding-split-and-users.spec.ts` 等）**全部仍然有效**，无需重跑改造。
3. 后端聚合接口对前端友好，未来扩展（导出/搜索/分页）成本低。
4. 数据库零迁移，回滚极简。

### A1 工时拆分（推荐 1.5–2 人天）

| 任务 | 角色 | 工时 |
|---|---|---|
| 后端：新增 `GET /admin/dispatch-config` 聚合接口（join 两表 + 用户姓名 + 客户名） | 后端 | 0.5 天 |
| 后端：补 1 个 e2e 测试覆盖 customer/全局两类行 | 后端 | 0.25 天 |
| 前端：重写 `Admin/DispatchRules` 或新建 `Admin/DispatchConfig` 页面 | 前端 | 0.75 天 |
| 前端：编辑/添加/删除按 row 来源路由到既有 API | 前端 | 0.25 天 |
| QA：手测三类操作 + 派发实际验证 | QA | 0.25 天 |

### 不推荐 A2 的关键原因

合表后必须改派发核心路径（resolveRuleHandler、ensureOnboardingSplitChildren、ruleScopeMatches），等于把整个派发引擎拆开重做，在没有性能或正确性问题的前提下，纯为了 UI 而动核心模块，**收益/风险比极差**。

## 7) 是否可以直接丢 `dispatch_rules`，只留 `module_handlers`？

### 7.1 如果用户公司「根本不存在按客户分人」

**不能直接丢**，原因：

`dispatch_rules` 不只承担「按客户/部门指定人」，还承担：

1. **决定生成哪些子单**：`triggerConditions` (AST) 是入职工单按字段判断要不要生成「劳动合同」「入职联系」等子单的条件。例如 `seed-dispatch-rules.ts:34-48`：

   ```ts
   { name: 'onboarding-contact-when-needed', triggerConditions: yesCondition('need_onboarding_contact'), targetModule: 'onboarding_contact', priority: 30 },
   { name: 'onboarding-contract-when-needed', triggerConditions: yesCondition('need_company_contract'),  targetModule: 'contract',           priority: 40 },
   ```

   去掉这些规则，AST 触发条件就丢了，入职工单要么全生成所有子单（噪音）、要么少生成（漏单）。

2. **`orderType` 路由**：dispatch_rules 决定「续签工单 → renewal_contract」「离职工单 → resignation_contact」这种 orderType→module 的映射，module_handlers 表里没有 orderType 字段。

3. **派发策略**：FIXED / LOAD_BALANCE / ROUND_ROBIN / POOL 写在 `dispatch_rules.dispatchStrategy`，不在 module_handlers。

### 7.2 真正能丢的部分

可以**「逻辑上不用」但表保留**：

- 如果用户确认「永远不会按客户分人」，那 `dispatch_rules` 里**永远不会出现 `customerId IS NOT NULL` 的行**。
- 此时管理 UI 可以**只显示 module_handlers 一张表**（隐藏 dispatch_rules 编辑入口），但后端 dispatch_rules 表必须保留，因为 AST 触发条件、orderType 路由、策略字段都还在用。
- 入职工单的「需要入职联系？/ 需要合同？」这类 AST 触发也必须保留——这是业务条件分流，不是「按客户分人」。

### 7.3 推荐方案

**保留 dispatch_rules 表 + 默认 UI 隐藏 customer 维度的编辑入口**：

- 默认管理 UI 只暴露「模块负责人」（来自 module_handlers）。
- 如果将来需要按客户分人，开关一打，UI 就显示「具体客户例外行」编辑区。
- 后端 dispatch_rules 表完全不动，AST 触发、orderType 路由、策略选择都正常工作。

这正是**方案 A1 的天然形态**——前端做合并，后端两表分工不变，UI 自由控制显隐。
