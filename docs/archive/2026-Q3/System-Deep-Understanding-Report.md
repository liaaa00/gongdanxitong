## 一、系统全景理解

### 1.1 系统定位与价值

**系统名称**：工单系统（Ticket System）  
**核心定位**：人力资源外包服务的数字化协作平台

**业务价值**：
- 标准化员工入职/在职/离职全生命周期管理
- 实现业务侧与后道专业岗位的高效协作
- 提供完整的权限控制和数据安全保障
- 支持大规模员工办理（批量导入、并发处理）

**使用场景**：
- HR外包公司为企业客户办理员工入转调离
- 涉及社保、公积金、劳动合同、证明开具等业务
- 业务员发起 → 专业岗位处理 → 完成闭环

### 1.2 技术栈全景

**后端**：
- NestJS 10.4.2 + TypeScript 5.5.4（strict模式）
- TypeORM 0.3.20 + PostgreSQL 16
- Passport JWT认证（access + refresh token）
- 41张数据库表，18个迁移文件

**前端**：
- React 18.3.1 + Vite 5.4.11
- Ant Design 5.22.0 + Pro Components
- Zustand状态管理
- Vitest + Playwright测试

**基础设施**：
- Docker Compose（4个服务）
- Nginx反向代理
- SSE实时通知

### 1.3 核心业务模型

**两层工单结构**：
```
主工单 (WorkOrder)
  ├─ 入职类型 → 4个子工单模块
  ├─ 在职类型 → 2个子工单模块  
  └─ 离职类型 → 3个子工单模块

子工单 (DispatchedOrder)
  ├─ 根据模块自动派发给专业岗位
  ├─ 处理人接单 → 处理 → 完成
  └─ 支持退回、撤回、作废
```

**9个核心角色**：
1. admin - 系统管理员（全部权限）
2. biz_manager - 业务负责人（只读，看全局）
3. biz_leader - 业务组长（发起工单，查看本组）
4. biz_member - 业务员（发起工单，只看自己）
5. data_entry_leader - 数据录入组长
6. shared_leader - 共享团队负责人
7. contract_specialist - 合同专员
8. onboarding_specialist - 入离职专员
9. social_insurance_specialist - 福保负责人

**权限控制架构**：
- 后端：4层守卫（JWT → 密码变更 → 角色 → 业务权限）
- 前端：路由守卫 + 组件权限 + 按钮显隐
- 字段：三维权限（角色 × 字段 × 场景）
- 数据：基于角色的数据范围过滤

## 三、代码质量审查

### 3.1 🔴 严重问题（3个，需立即修复）

#### 问题1：SQL注入风险

**位置**：`backend/src/modules/dashboard/dashboard.service.ts`

**描述**：
仪表盘使用原生SQL查询，虽然当前使用了参数化查询，但存在维护风险。如果后续开发者不注意，可能引入SQL注入。

**风险**：
- 当前代码安全，但容易被破坏
- 代码审查难以发现潜在注入点
- 维护者可能不理解参数化的重要性

**修复方案**：
```typescript
// 方案1：迁移到QueryBuilder
const count = await this.notificationRepository
  .createQueryBuilder('n')
  .where('n.user_id = :userId', { userId })
  .andWhere('n.is_read = false')
  .getCount();

// 方案2：如必须用原生SQL，添加注释
// ⚠️ SQL注入风险：必须使用参数化查询，禁止字符串拼接
const rows = await this.dataSource.query(
  `SELECT COUNT(*)::int AS count FROM notifications WHERE user_id = $1`,
  [userId]
);
```

**优先级**：🔴 P0（高风险维护漏洞）

---

#### 问题2：管理员绕过字段权限

**位置**：`backend/src/modules/field-permissions/field-permission.interceptor.ts:31`

**描述**：
字段权限拦截器对管理员完全跳过：
```typescript
if (request.user.roles.includes('admin')) {
  return next.handle(); // 管理员直接放行
}
```

**风险**：
- 管理员可访问所有敏感数据（身份证、手机号）
- 违反最小权限原则
- 不满足数据隐私合规要求（GDPR、个人信息保护法）
- 管理员账号泄露后果严重

**修复方案**：
```typescript
// 短期：为管理员配置特殊字段权限
const fieldPermissions = await this.fieldPermissionService
  .resolveFieldPermissions({
    roleCode: userRole,
    scenarioCode,
    // 移除 admin 的特殊逻辑
  });

// 长期：引入敏感数据访问审批流程
@UseGuards(SensitiveDataAccessGuard)
async getWorkOrderDetail(@Param('id') id: string) {
  // 敏感字段需要临时权限申请
}
```

**优先级**：🔴 P0（数据安全与合规风险）

#### 问题3：子工单并发控制缺失

**位置**：`backend/src/modules/dispatched-orders/dispatched-order.service.ts`

**描述**：
子工单状态变更无乐观锁保护：
```typescript
const order = await this.dispatchedOrderRepository.findOne({...});
order.status = DispatchedOrderStatus.PROCESSING;
await this.dispatchedOrderRepository.save(order);
```

**风险场景**：
1. 用户A和B同时对同一子工单执行"完成"操作
2. A读取状态=`processing`
3. B也读取状态=`processing`
4. A提交，状态变为`completed`
5. B提交，覆盖A的结果 → 丢失A的办结备注

**修复方案**：
```typescript
// 方案1：乐观锁（推荐）
// 1. 在实体中添加 @VersionColumn
@VersionColumn()
version: number;

// 2. 更新时TypeORM自动检查版本
await this.dispatchedOrderRepository.save(order); 
// 版本不匹配会抛出 OptimisticLockVersionMismatchError

// 方案2：悲观锁（财务相关操作）
const order = await this.dispatchedOrderRepository.findOne({
  where: { id },
  lock: { mode: 'pessimistic_write' }
});
```

**优先级**：🔴 P0（数据不一致风险）

### 3.2 🟡 重要问题（8个，需优先处理）

#### 1. 密码哈希强度不足
- **位置**：`auth.service.ts:264`
- **问题**：bcrypt rounds=10偏低，OWASP建议≥12
- **修复**：提升到12或使用环境变量配置

#### 2. JWT密钥硬编码默认值
- **位置**：`auth.service.ts:140`
- **问题**：默认密钥`'change-me-jwt-refresh-secret'`容易被遗忘
- **修复**：启动时强制检查，无有效密钥则拒绝启动

#### 3. 外键级联删除不一致
- **位置**：多个实体
- **问题**：部分实体用`CASCADE`，部分用`SET NULL`，不一致
- **修复**：统一级联策略，文档化决策

#### 4. N+1查询问题
- **位置**：`work-order.service.ts`
- **问题**：查询工单列表时未eager加载关联实体
- **修复**：使用`relations`或`leftJoinAndSelect`

#### 5. Token存储不安全
- **位置**：前端localStorage
- **问题**：XSS可窃取token
- **修复**：使用httpOnly cookie或内存存储

#### 6. 文件上传缺少类型校验
- **位置**：`file-upload.controller.ts`
- **问题**：只检查扩展名，未验证文件内容
- **修复**：使用file-type库验证Magic Number

#### 7. 缺少请求频率限制
- **位置**：全局
- **问题**：无API限流，易被DDoS
- **修复**：使用@nestjs/throttler

#### 8. 敏感数据日志泄露风险
- **位置**：全局日志
- **问题**：可能记录身份证、手机号等敏感信息
- **修复**：脱敏中间件

## 四、业务流程深度理解

### 4.1 核心业务场景

#### 场景1：入职员工全流程

```
业务员发起入职主工单
  ↓
系统自动派发4个子工单：
  ├─ 入职联系（onboarding_contact）→ 入离职专员
  ├─ 劳动合同新签（contract）→ 合同专员
  ├─ 增员报岗录入（data_entry）→ 数据录入组长
  └─ 社保公积金增员（social_insurance）→ 福保负责人
  ↓
各专业岗位并行处理
  ├─ 接单 → 处理中 → 完成
  ├─ 可退回给业务员补充信息
  └─ 业务员可撤回工单
  ↓
所有子工单完成后，主工单自动标记完成
```

#### 场景2：退回流程

```
专业岗位发现信息不全
  ↓
点击"退回"按钮 → 填写退回原因
  ↓
子工单状态变为 RETURNED
  ↓
业务员收到通知 → 在"我的退回"中看到
  ↓
补充信息后重新提交
  ↓
子工单重新派发给原处理人
```

### 4.2 派发引擎规则

**派发优先级**：
1. 省份匹配（省内/省外）
2. 模块匹配（合同/入职/数据录入/福保）
3. 团队分配（共享团队/数据录入组/福保组）
4. 负载均衡（同组内轮询）

**特殊规则**：
- 省外工单：单独的派单流程
- 在职直单：不通过主工单，直接创建子工单
- 批量导入：分批派发，避免雪崩

### 4.3 权限矩阵

| 角色 | 主工单 | 子工单 | 系统管理 | 数据范围 |
|-----|-------|--------|---------|---------|
| admin | 全部 | 全部 | ✅ | 全部 |
| biz_manager | 查看 | 查看 | ❌ | 全部（只读） |
| biz_leader | 创建/查看/撤回 | 查看 | ❌ | 本组 |
| biz_member | 创建/查看/撤回 | 查看 | ❌ | 自己 |
| data_entry_leader | 查看 | 处理（数据录入） | ❌ | 本模块 |
| contract_specialist | 查看 | 处理（合同） | ❌ | 本模块 |
| onboarding_specialist | 查看 | 处理（入离职） | ❌ | 本模块 |
| social_insurance_specialist | 查看 | 处理（福保） | ❌ | 本模块 |
| shared_leader | 查看 | 处理（多模块） | ❌ | 本团队 |

## 五、关键技术决策分析

### 5.1 三维字段权限模型

**设计思路**：
```
字段权限 = f(角色, 场景, 字段)

场景：
- create:onboarding - 创建入职工单
- dispatched:contract - 处理合同子工单
- dispatched:data_entry - 处理数据录入子工单

字段权限级别：
- invisible - 不可见（前端不渲染）
- readonly - 只读（显示但禁用）
- visible - 可编辑
```

**优点**：
- 精细到字段级别的控制
- 同一字段在不同场景下权限不同
- 配置灵活，支持运行时调整

**缺点**：
- 配置复杂度高（角色 × 场景 × 字段 = 组合爆炸）
- 维护成本高
- 性能开销（每次请求都要计算）

### 5.2 角色归一化机制

**设计思路**：
```typescript
// 后端可能返回新旧任一种代码
后端：biz_manager / business_owner
       ↓
前端归一化：BACKEND_TO_CANONICAL
       ↓
统一为：business_owner
       ↓
路由配置、权限判断都使用统一代码
```

**优点**：
- 前后端解耦
- 支持平滑迁移（新旧角色代码都能用）
- 前端只需维护一套配置

**缺点**：
- 新人理解成本高
- 映射表需要手动维护

### 5.3 表驱动配置

**设计思路**：
- module_configs表：定义子工单模块
- dispatch_configs表：定义派发规则
- field_configs表：定义字段元数据
- system_settings表：运行时配置

**优点**：
- 配置变更无需重启
- 支持多租户（不同客户不同配置）
- 便于后台管理

**缺点**：
- 配置错误难以在编译期发现
- 调试困难（配置在数据库里）
- 缺少Schema验证
