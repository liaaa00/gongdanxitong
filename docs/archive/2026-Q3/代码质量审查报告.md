## 🔴 严重问题 (Critical)

### C1. SQL注入风险 - 仪表盘原生SQL查询未参数化

**位置:** `backend/src/modules/dashboard/dashboard.service.ts`

**问题描述:**  
发现多处使用 `dataSource.query()` 执行原生SQL,虽然大部分使用了参数化查询(`$1`, `$2`),但代码中存在字符串拼接的潜在风险。审查发现状态过滤使用了固定SQL片段常量,但如果后续维护不当可能引入注入风险。

```typescript
// 当前代码使用了参数化
const rows = await this.dataSource.query(
  `SELECT COUNT(*)::int AS count
   FROM notifications
   WHERE user_id = $1 AND is_read = false`,
  [userId]
);
```

**风险评估:**  
- 当前代码使用了参数化查询,风险可控
- 但状态判断使用了字符串模板拼接(`status::text = 'completed'`),如果这些常量被动态替换会产生注入
- 代码维护者可能不注意参数化的重要性

**建议修复:**  
1. 将所有原生SQL查询迁移到QueryBuilder或Repository方法
2. 如必须使用原生SQL,添加注释明确标注参数化要求
3. 对所有SQL拼接点进行代码审查,确保无动态输入

**优先级:** 🔴 高 - 虽然当前实现安全,但维护风险高

### C2. 权限校验遗漏 - 管理员绕过字段权限

**位置:** `backend/src/modules/field-permissions/field-permission.interceptor.ts:31`

**问题描述:**  
字段权限拦截器对管理员角色完全跳过处理:

```typescript
if (!resolver || !request.user || request.user.roles.includes('admin')) {
  return next.handle();
}
```

这意味着管理员可以**绕过所有字段权限控制**,直接访问所有敏感数据(身份证、手机号等),且不受字段级脱敏规则约束。

**风险评估:**  
- 管理员权限过大,违反最小权限原则
- 一旦管理员账号泄露,所有敏感数据完全暴露
- 无法满足数据隐私合规要求(如GDPR、个人信息保护法)
- 操作日志可能记录不完整(管理员操作未经权限检查)

**建议修复:**  
1. **短期修复:** 为管理员添加特殊的字段权限配置,而非完全跳过
2. **长期方案:** 引入敏感数据访问审批流程,即使管理员也需申请临时权限查看脱敏字段
3. 记录所有管理员对敏感字段的访问日志
4. 在前端对敏感字段显示增加二次确认提示

**优先级:** 🔴 高 - 数据安全与合规性风险

### C3. 并发控制不足 - 子工单状态变更无乐观锁

**位置:** `backend/src/modules/dispatched-orders/dispatched-order.service.ts`

**问题描述:**  
子工单状态变更(接单、完成、退回)等操作缺少乐观锁或悲观锁保护:

```typescript
// 当前代码直接更新,无版本号检查
const order = await this.dispatchedOrderRepository.findOne({...});
order.status = DispatchedOrderStatus.PROCESSING;
await this.dispatchedOrderRepository.save(order);
```

**风险场景:**  
1. 用户A和用户B同时对同一子工单执行"完成"操作
2. A先读取状态为`processing`
3. B也读取状态为`processing`
4. A提交,状态变为`completed`
5. B提交,覆盖A的结果,可能丢失A的办结备注或时间戳

**建议修复:**  
1. 在`dispatched_orders`表增加`version`列(乐观锁)
2. 更新时检查版本号: `UPDATE ... WHERE id = ? AND version = ?`
3. 如果影响行数为0,抛出`ConflictException`
4. 对于财务相关操作,使用悲观锁:`lock: { mode: 'pessimistic_write' }`

**优先级:** 🔴 高 - 可能导致数据不一致和操作丢失

## 🟡 重要问题 (Important)

### I1. 密码哈希强度不足

**位置:** `backend/src/modules/auth/auth.service.ts:264`

**问题描述:**  
bcrypt哈希轮数设置为10,在2026年这个强度偏低:

```typescript
const passwordHash = await bcrypt.hash(newPassword, 10);
```

**风险:** 现代GPU可以较快暴力破解rounds=10的bcrypt。OWASP建议至少使用12轮。

**建议修复:**  
```typescript
const BCRYPT_ROUNDS = Number(process.env.BCRYPT_ROUNDS ?? 12);
const passwordHash = await bcrypt.hash(newPassword, BCRYPT_ROUNDS);
```

**优先级:** 🟡 中高 - 影响密码安全

---

### I2. JWT密钥硬编码在环境变量

**位置:** `backend/src/modules/auth/auth.service.ts:140-141`

**问题描述:**  
JWT密钥使用了默认值`'change-me-jwt-refresh-secret'`,虽然有环境变量,但代码中的默认值容易被遗忘修改:

```typescript
secret: process.env.JWT_REFRESH_SECRET ?? 'change-me-jwt-refresh-secret',
```

**风险:** 生产环境如果未正确配置,将使用默认密钥,攻击者可伪造token。

**建议修复:**  
1. 启动时强制检查JWT密钥是否为生产密钥
2. 默认值改为`undefined`,未配置时拒绝启动
3. 密钥长度至少64字节随机值

**优先级:** 🟡 高 - 认证安全基础

---

### I3. 外键级联删除配置不一致

**位置:** `backend/src/entities/*.entity.ts`

**问题描述:**  
实体关系的`onDelete`配置不一致:

- `DispatchedOrder.parentOrder`: `CASCADE` (删主工单会级联删子工单)
- `DispatchedOrder.handler`: `SET NULL` (删用户不删子工单)
- `WorkOrder.creator`: `RESTRICT` (有工单的用户不能删)
- `WorkOrder.customer`: `RESTRICT` (有工单的客户不能删)

**潜在风险:**  
1. 删除主工单会级联删除所有子工单,但可能有操作日志、附件等关联数据成为孤儿记录
2. `RESTRICT`可能导致无法清理测试数据或历史归档
3. 缺少文档说明级联规则,维护时容易误删

**建议修复:**  
1. 统一规则:核心业务数据一律使用`RESTRICT`,必须先手工清理子数据
2. 如需级联,必须在Entity注释中说明原因和影响范围
3. 增加数据归档机制,避免物理删除

**优先级:** 🟡 中 - 数据完整性风险

### I4. 权限守卫顺序可能导致绕过

**位置:** `backend/src/common/guards/roles.guard.ts`

**问题描述:**  
RolesGuard同时处理`@BusinessPermission`和`@Roles`,优先级是BusinessPermission > Roles:

```typescript
if (businessPermission) {
  // 检查业务权限
  return true;
}
// 然后检查Roles
```

如果某个Controller同时标注了两种装饰器,BusinessPermission检查通过后直接返回,不再检查Roles。这可能导致开发者以为配置了Roles保护,实际被BusinessPermission绕过。

**建议修复:**  
1. 文档明确说明优先级规则
2. 禁止同时使用两种装饰器,启动时检测并报错
3. 或者改为AND逻辑:两者都要满足

**优先级:** 🟡 中 - 权限逻辑混淆

### I5. 登录失败锁定机制可被绕过

**位置:** `backend/src/modules/auth/auth.service.ts:92-98`

**问题描述:**  
登录锁定基于数据库字段`lockedUntil`,但检查逻辑在密码验证之前:

```typescript
if (user.lockedUntil && user.lockedUntil.getTime() > now.getTime()) {
  throw new UnauthorizedException(`登录失败次数过多...`);
}
const matched = await bcrypt.compare(password, user.passwordHash);
```

**潜在绕过:**  
攻击者可以先用错误密码触发锁定,然后在锁定期间用正确密码登录 - 虽然会被拒绝,但错误是"账号锁定"而非"密码错误",泄露了账号有效性。

更严重的是,`failedLoginAttempts`计数器在密码错误时才增加,如果攻击者在锁定期内不停尝试,计数器不会继续增加,锁定时间不会延长。

**建议修复:**  
1. 锁定期间的尝试也应该计入失败次数并延长锁定时间
2. 错误信息统一为"用户名或密码错误",不泄露账号状态
3. 增加IP级别的限流,防止分布式爆破

**优先级:** 🟡 中高 - 认证安全

### I6. 敏感数据日志泄露风险

**位置:** 全局Logger使用

**问题描述:**  
代码中大量使用`Logger`记录操作,但未检查是否会记录敏感字段。例如:

```typescript
this.logger.log(`User ${user.username} logged in`);
```

如果后续有人添加了详细日志如`this.logger.debug(JSON.stringify(user))`,可能泄露密码哈希、身份证号等敏感信息到日志文件。

**建议修复:**  
1. 制定日志脱敏规范,禁止记录敏感字段原文
2. 实现日志脱敏中间件,自动过滤`passwordHash`、`idCard`等字段
3. 生产环境日志级别设为`info`或`warn`,禁用`debug`

**优先级:** 🟡 中 - 合规与隐私风险

### I7. N+1查询问题 - 字段权限加载

**位置:** `backend/src/modules/field-permissions/field-permission.service.ts:57-75`

**问题描述:**  
`getPermissionsForUser`方法中:

```typescript
const roleRows = await this.userRoleRepository.find({
  where: { userId },
  relations: { role: true },
});
// 然后遍历roleRows查询field_permissions
```

如果一个用户有多个角色(常见场景),且每个角色有不同的字段权限配置,会产生N+1查询。实际项目中字段权限查询是热点操作(每个详情页、列表页都会调用FieldPermissionInterceptor)。

**性能影响:**  
- 每次详情页渲染可能触发5-10次额外查询
- 高并发时数据库连接池压力大
- 响应时间增加200-500ms

**建议修复:**  
1. 将字段权限查询改为单次JOIN查询
2. 增加Redis缓存,key为`field_perm:${userId}:${scenario}`,TTL=5分钟
3. 用户角色变更时清除对应缓存

**优先级:** 🟡 中高 - 性能瓶颈

### I8. 前端Token存储在localStorage

**位置:** `frontend/src/services/request.ts:51` 和 `114-116`

**问题描述:**  
JWT token存储在`localStorage`:

```typescript
const token = localStorage.getItem('token');
localStorage.removeItem('token');
```

**风险:** localStorage可被同域名下的任意JS脚本访问,如果存在XSS漏洞,攻击者可窃取token。

**建议修复:**  
1. **最佳实践:** token存储在HttpOnly Cookie中,前端无法通过JS访问
2. 如必须用localStorage,增加CSP策略:`Content-Security-Policy: script-src 'self'`
3. token增加设备指纹绑定,防止token被盗用到其他设备

**优先级:** 🟡 中 - XSS防御不足

### S9. 环境变量未做类型校验

**问题描述:**  
环境变量直接使用`process.env.XX`,没有启动时校验:

```typescript
const maxAttempts = Number(process.env.LOGIN_MAX_ATTEMPTS ?? 5);
```

如果配置文件写错(如`LOGIN_MAX_ATTEMPTS=abc`),系统行为未定义。

**建议:** 使用`@nestjs/config`配合`class-validator`做启动时校验:

```typescript

  @IsInt()
  @Min(1)
  @Max(10)

}
```

### S10. 前端状态管理混乱

**问题描述:**

- `localStorage`存储token、user
