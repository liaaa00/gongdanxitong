# 工单系统权限体系综合分析报告

生成时间：2026-08-01  
分析团队：后端架构分析师 + 数据库权限分析师 + 前端权限分析师

---

## 📊 整体架构概览

系统采用**三层权限控制架构**，从数据库到后端再到前端形成完整的防御链：

```
数据库层（三维权限模型）
    ↓
后端层（四层守卫）
    ↓
前端层（三层防御）
```

---

## 🗄️ 一、数据库层权限设计

### 核心特点
- **三维复合主键**：UserRole 表使用 `(user_id, role_id, department_id)` 组合主键
- **三层权限控制**：
  1. 角色层级（RoleLevel：执行层/主管层/管理层/全局层）
  2. 字段级权限（角色×字段×场景 三维矩阵）
  3. 数据权限（部门+业务范围）

### 关键表结构
- `users` - 用户基础信息
- `roles` - 角色定义
- `user_roles` - 用户-角色-部门关联（复合主键）
- `departments` - 部门组织架构
- `field_permissions` - 字段权限矩阵（支持 visible/readonly/hidden/masked）

### 设计亮点 ✅
- 字段级权限粒度非常细，灵活性高
- 部门维度天然支持数据隔离
- 级联删除配置完整

### 存在问题 ⚠️
1. **复合主键复杂**：查询逻辑需明确部门上下文
2. **新旧角色混杂**：历史角色代码未完全清理
3. **历史遗留场景**：LEGACY_SCENARIOS 仍在引用
4. **逻辑分散**：权限判断分散在种子文件和业务代码中

## 🔐 二、后端权限体系

### 四层守卫架构
```
请求进入
  ↓
① JwtAuthGuard - JWT 身份验证（检查 @Public 跳过）
  ↓
② PasswordChangeGuard - 强制改密验证（检查 @AllowBeforePasswordChange 跳过）
  ↓
③ RolesGuard - 角色/业务权限验证（@Roles/@BusinessPermission）
  ↓
④ FieldPermissionInterceptor - 字段权限过滤
  ↓
业务逻辑
```

### 业务操作权限
- **54 个业务操作权限**（RoleActionCode）
- 包括：工单操作、路由访问、模块管理、批量操作等

### 核心装饰器
- `@Public()` - 公开接口
- `@Roles(...roles)` - 角色要求
- `@BusinessPermission(action)` - 业务操作权限
- `@FieldPermissionScenario(scenario)` - 字段权限场景

### 设计优点 ✅
- 层次清晰，职责明确
- 灵活度高，支持三层权限控制
- 默认安全，除非明确 @Public

### 存在问题 ⚠️
1. **AdminOnlyGuard 重复**：与 @Roles('admin') 功能重复，使用不一致
2. **优先级不直观**：@BusinessPermission 会覆盖 @Roles 的检查
3. **验证时机割裂**：RolesGuard（请求阶段）vs FieldPermissionInterceptor（响应阶段）
4. **性能瓶颈风险**：角色权限矩阵每次查库，无缓存

## 🖥️ 三、前端权限体系

### 三层防御结构
1. **路由层**：RoleRoute 守卫 + canAccessPath() 判断
2. **菜单层**：filterMenuByRoles() 动态过滤
3. **组件层**：useAuth() Hook + 按钮/字段级控制

### 权限数据流
```
登录 POST /auth/login
  ↓ 返回 {token, user: {roles, permissions}}
userStore 缓存 + localStorage 持久化
  ↓
路由守卫: canAccessPath(pathname, roles, permissions)
  ↓
菜单过滤: filterMenuByRoles()
  ↓
组件判断: hasRole() / hasPermission()
```

### 核心文件（12个）
- `config/routeVisibility.ts` (408行) - 路由×角色矩阵
- `constants/roles.ts` (69行) - 9个规范角色+归一化
- `utils/moduleAccess.ts` (170行) - 模块访问控制
- `hooks/useAuth.ts` - 权限判断Hook
- `hooks/useFieldPermissions.ts` - 字段权限
- `stores/userStore.ts` - Zustand状态管理

### 存在问题 ⚠️（7个关键问题）

#### 🔴 严重问题
1. **双重权限系统并存**
   - 静态 ROUTE_VISIBILITY（基于角色）vs 动态 allowedActions（基于权限码）
   - 路由守卫优先角色，按钮显示优先权限码
   - 后台修改权限可能部分生效

2. **角色硬编码泛滥**
   - 87个文件直接写 hasRole()
   - 业务规则分散在组件中
   - 角色调整需全局搜索

#### 🟡 中等问题
3. **权限判断入口分散**
   - 5种不同判断函数：canAccessPath / canAccessModuleCode / hasRole / hasPermission / allowedActions.includes()

4. **字段权限可能失效**
   - 登录返回 role.code 无 role.id 时
   - 非 admin 角色字段权限配置失效

5. **模块白名单与路由权限不同步**
   - moduleAccess.ts 隐藏 benefit_apply
   - 但 routeVisibility.ts 允许访问
   - 导致空白页面

#### 🟢 低风险问题
6. **权限缓存失效风险** - 跨标签页登出不同步
7. **菜单与路由配置重复维护** - RAW_MENU vs ROUTE_VISIBILITY

---

## 💡 核心混乱点总结

### 1. **新旧权限体系混杂**（最核心的问题）
- **前端**：静态角色配置 vs 动态权限码，两套系统并行
- **后端**：@Roles vs @BusinessPermission，优先级不明确
- **数据库**：新旧角色代码混杂，历史遗留未清理

### 2. **权限判断逻辑分散**
- 前端：5种不同的权限判断函数
- 后端：装饰器、守卫、业务层多处判断
- 数据库：种子文件和业务代码都有权限逻辑

### 3. **前后端同步机制不完善**
- 字段权限依赖 role.id 但有时只返回 role.code
- 模块白名单与路由权限配置不一致
- 权限缓存跨标签页不同步

### 4. **性能隐患**
- 后端角色权限矩阵每次查库，无缓存
- 前端字段权限重复请求

---

## 🎯 改进建议（优先级排序）

### 高优先级
1. **明确新旧权限系统迁移路径**
   - 选择一套作为主体（建议：基于权限码的动态系统）
   - 制定迁移计划，逐步淘汰旧系统

2. **统一权限判断入口**
   - 前端：封装统一的权限判断服务
   - 后端：明确装饰器使用规范，禁止混用

3. **修复字段权限 role.id 缺失问题**
   - 确保登录接口返回完整的 role 信息

### 中优先级
4. **同步模块白名单与路由权限**
   - 建立一致性检查机制

5. **增加后端权限缓存**
   - Redis 或内存缓存角色权限矩阵

6. **清理历史角色代码**
   - 统一角色命名和定义

### 低优先级
7. **优化跨标签页权限同步**
8. **减少菜单与路由的重复配置**
