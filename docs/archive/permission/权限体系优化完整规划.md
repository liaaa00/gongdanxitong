# 工单系统权限体系优化完整规划

> 生成时间：2026-08-01
> 规划依据：三份权限基线清单 + 系统架构分析
> 目标：在不破坏现有功能的前提下，逐步优化权限体系的可维护性和一致性

---

## 📊 现状评估

### 当前权限配置规模
- **后端**：54个业务操作权限 × 18个角色（含停用）
- **前端**：72个路由 × 9个规范角色
- **字段**：13个场景 × 多维度权限矩阵

### 核心问题分类

#### 🔴 架构层问题（影响可维护性）
1. **新旧权限体系并存**
   - 前端：静态 ROUTE_VISIBILITY vs 动态权限码
   - 后端：@Roles vs @BusinessPermission
   - 数据库：新旧角色代码混杂

2. **权限判断入口分散**
   - 前端：5种不同的权限判断函数
   - 后端：装饰器、守卫、业务层多处判断

3. **前后端权限配置不同步**
   - 角色命名差异（business_group_leader vs biz_leader）
   - 权限粒度不一致

#### 🟡 配置层问题（需要验证）
1. **business_owner 路由权限疑似不足**（需确认是否为业务设计）
2. **业务角色无 /onboarding 入口访问权**（需确认是否为业务设计）
3. **历史遗留场景未清理**（LEGACY_SCENARIOS）

#### 🟢 性能优化点
1. 后端角色权限矩阵每次查库，无缓存
2. 前端字段权限重复请求

---

## 🎯 优化目标与原则

### 优化目标
1. **保持功能稳定**：不破坏任何现有正常工作的权限逻辑
2. **提升可维护性**：统一权限判断入口，减少重复配置
3. **建立安全网**：完整的测试覆盖，确保改动安全
4. **逐步演进**：分阶段实施，每步可验证可回滚

### 优化原则
- **先测试后改动**：任何代码改动前先建立测试覆盖
- **小步快跑**：每次改动范围小、影响可控
- **数据驱动**：基于实际使用情况决定优化方向，而非理论最优
- **向后兼容**：保留历史配置的兼容性，逐步迁移

### Phase 4：架构层面优化（可选，2-4周）

**前置条件**：Phase 3 完成 + 团队决定进行架构升级

**目标**：解决新旧权限体系并存的问题，统一为一套清晰的权限系统

#### 4.1 选择主体权限系统

**方案A：基于权限码的动态系统（推荐）**
- 优点：灵活、可运行时配置、细粒度控制
- 缺点：需要完整迁移前端 ROUTE_VISIBILITY

**方案B：基于角色的静态系统**
- 优点：简单、直观
- 缺点：灵活性不足，难以支持复杂业务

**决策依据**：
- 业务复杂度
- 运维需求（是否需要运行时调整权限）
- 团队技术栈偏好

#### 4.2 迁移路径（如果选择方案A）

1. **建立权限码到路由的映射**
   ```typescript
   // 新增：路由权限配置
   const ROUTE_PERMISSIONS = {
     '/work-orders': ['route.work_orders'],
     '/work-orders/create': ['work_order.create'],
     // ...
   }
   ```

2. **双轨运行**
   - 同时保留 ROUTE_VISIBILITY 和新的权限码系统
   - 逐步迁移路由判断逻辑

3. **逐步废弃旧系统**
   - 迁移完成后，移除 ROUTE_VISIBILITY
   - 更新文档和规范

**交付物**：
- 新权限系统设计文档
- 迁移脚本和工具
- 迁移后的完整测试覆盖

## 📊 风险评估与应对

### 高风险点

1. **测试覆盖不完整导致回归bug**
   - 应对：Phase 1 重点投入，确保核心场景100%覆盖
   
2. **前后端权限不一致导致安全漏洞**
   - 应对：Phase 0 详细对比，Phase 2 优先修复

3. **大规模重构导致项目进度延误**
   - 应对：Phase 4 标记为可选，仅在前3个阶段完成后评估

### 回滚策略

- **Phase 1**：纯测试代码，可随时回滚
- **Phase 2**：小步修复，每个修复独立可回滚
- **Phase 3**：保留旧代码兼容性，逐步切换
- **Phase 4**：双轨运行，确保新系统稳定后再废弃旧系统
