## 1. 入职拆四 + 主工单只读 + 业务员操作迁移到子工单

### 1.1 现状要点

| 项 | 现状 | 文件 |
|---|---|---|
| 入职一拆四派发 | 已实装。`buildOnboardingChildren` 必拆 `data_entry`/`social_insurance`，按 `need_onboarding_contact`/`need_company_contract` 条件拆 `onboarding_contact`/`contract` | `backend/src/modules/work-orders/onboarding-dispatch.helper.ts:115-142`；`dispatch-engine.service.ts:186-201` 兜底 |
| 主单业务员修改 | 通过 `WorkOrderService.update` 走规则 A/B 校验 + dirty 标记 + `fieldChangeHook` | `work-order.service.ts:1224-1318` |
| 业务员撤回 | `POST /work-orders/:id/withdraw` 在主单上写 `WITHDRAW_PENDING`；通知所有未完成子单 handler | `work-order.service.ts:414-483` |
| 业务员作废 | `POST /work-orders/:id/void` 同上但写 `VOID_PENDING` + 必填 reason | `work-order.service.ts:634-712` |
| 业务员催办 | `POST /work-orders/:id/urge?moduleCode=…` 30 分钟节流 + 通知子单 handler | `work-order.service.ts:565-632` |

### 1.2 会议口径补齐

会议明确：**"一拆四后主工单只读（业务员视角），所有的修改、撤回、作废、催办都迁移到对应的子工单上发起"**。

> 含义：业务员**不再在主单详情页看到这些操作按钮**；进入子单详情页（按模块）后，按子单粒度发起：
> - 修改：只能改"业务员发起字段"，且当前模块未办结时才允许；规则 A/B 仍生效，但**入口在子单**。
> - 撤回：以子单粒度撤回，需求约束『撤回后，所有子单回到 pending；主单聚合为 `WITHDRAW_PENDING`』。
> - 作废：作废行为针对**整张工单**，但入口在任意子单详情页；后端必须把『子单作废』理解为整单作废。
> - 催办：以子单粒度催办（已支持 `moduleCode`，进一步要求**子单详情页是唯一入口**）。

### 1.3 实施设计

#### 后端
1. **新增子单代理接口**（不改主单语义，纯 controller 层路由）：
   - `POST /dispatched-orders/:id/withdraw`：定位到 `parentOrderId`，再调 `WorkOrderService.withdraw(parentOrderId, dto, user)`。
   - `POST /dispatched-orders/:id/void`：同上，调 `WorkOrderService.void`。
   - `POST /dispatched-orders/:id/urge`：自动以 `child.moduleCode` 作为 `moduleCode` 入参；30 分钟节流键改为 `${parentId}:${moduleCode}`。
   - `PATCH /dispatched-orders/:id/extra-data`：业务员修改公共字段时，子单代理调 `WorkOrderService.update(parentOrderId, partialExtra)`。注意：`partialExtra` 必须先经过『当前模块可见 + 业务员发起字段』白名单校验。
2. **主单接口加 deprecation 注释**（不下线）：保留 `/work-orders/:id/{withdraw,void,urge}` 给 admin 工具与历史脚本用，前端业务员不再调用。
3. **业务员发起字段 = `module_fields(moduleCode='salesperson_fields')` 一份元数据**（推荐）；或 `field_configs` 上加 `is_salesperson_initiated boolean` 列（性价比更高）。本期选**字段配置**方案：
   - DDL: `ALTER TABLE field_configs ADD COLUMN is_salesperson_initiated boolean DEFAULT false;`
   - Seed: 入职业务员发起字段 ≈ 22 个（员工姓名、身份证、手机、客户、入职日、合同条件、社保省份等），由 `seed-fields.ts` 标记。
   - Service: `WorkOrderService.assertSalesEditableFields` 改为读 `field_configs.is_salesperson_initiated=true`。
4. **状态联动**：`WORK_ORDER_TERMINAL_STATUSES` 不变；`WITHDRAW_PENDING/VOID_PENDING/RETURNED` 仍是主单状态，子单不持有这三个值。

#### 前端
1. `pages/WorkOrders/Detail/index.tsx`（业务员视图）：
   - 顶部不再渲染 `撤回 / 作废 / 催办` 按钮；改为 `<Alert type="info">`：『此页面只读，请进入对应子工单办理。』
   - 子工单 Tabs 增加每个子单的 `[修改 / 撤回 / 作废 / 催办]` 4 按钮。
   - 子单按钮 disabled 规则：
     - 修改：`childStatus IN (pending,processing) && !hasOtherCompletedSibling`
     - 撤回：`childStatus IN (pending,processing,returned) && parent.status NOT IN (terminal)`
     - 作废：`parent.status NOT IN (terminal)`，**任何**子单的按钮都打开整单作废对话框
     - 催办：30 分钟节流由前端读 `lastUrgedAt` 临时禁用 + 后端兜底
2. `pages/MyDispatched/Detail/index.tsx`（后道视图）：保留模块视角的字段操作；**业务员入口和后道入口共享 `/dispatched-orders/:id` 页面**，按 `useUserStore().user.roles` 切换按钮组。
3. `services/dispatchedOrders.ts` 新增 4 个 client 方法：`withdrawDispatched / voidDispatched / urgeDispatched / patchDispatchedExtraData`。
4. **撤回/作废范围确认弹窗**：业务员点击子单"撤回"时弹窗：『撤回会让所有子单回到 pending，已办结字段保留；继续？』。

### 1.4 风险点

- **R1.1 路由切换不彻底**：仍有部分页面（`Onboarding/Detail`、`WorkOrders/Detail` 旧版）调用主单接口；必须在 PR 前 grep 全量替换。
- **R1.2 模块粒度催办与已存在的"全单催办"冲突**：30 分钟节流 key 改为 `${parentId}:${moduleCode}`；admin 全单催办（不带 moduleCode）使用 `${parentId}:__all__` 共享 throttle，避免业务员通过『分别催 4 个子单』绕过节流。
- **R1.3 字段白名单**：`is_salesperson_initiated` 漏标会导致业务员改不到字段；上线前 QA 必须按入职 56 字段对照表校验。

## 2. 公共字段双向同步与通知

### 2.1 现状要点

| 项 | 现状 | 文件 |
|---|---|---|
| 业务员→后道方向 | `WorkOrderService.update` 写 `extraData` → `createDirtyMarksForSalesUpdate` 写 `work_order_field_dirty_marks` → `fieldChangeHook.onWorkOrderUpdated` 发通知 | `work-order.service.ts:1232-1290`；`field-change.hook.ts:35-66` |
| 后道→业务员方向 | `dispatched-order.service.complete` / `supplement` 写后再触发 `fieldChangeHook`（可选） | `dispatched-order.service.ts:253-264` |
| 通知 payload | 当前 `diff` 结构 `{field, before, after}`，缺 `field_name` 中文 | `notification.service.ts:NotificationListItem.diff_fields` 已预留新字段 |
| 字段值多份 | 主单 `extraData` 是唯一源；子单只持有 `visibleFields` 白名单，不冗余值 | `dispatched-order.entity.ts:50` |

### 2.2 会议口径补齐

『公共字段双向同步』需求 = ①子单 A 改了公共字段（如 `mobile_phone`），子单 B 详情页打开时该字段必须是新值且**带『已修改』高亮**；②业务员改公共字段时，**所有**接收侧子单都要收到通知。

### 2.3 实施设计

#### 后端
1. **`field_configs.is_common_field boolean` 标识公共字段**（已隐含：复用 `is_salesperson_initiated` 的字段大多是公共字段；但有些字段是后道也可改的『流转中字段』，例如 `bank_account`，需要单独标）。
   - DDL: `ALTER TABLE field_configs ADD COLUMN is_common_field boolean DEFAULT false;`
   - Seed: 公共字段 ≈ 入职 28 字段（基础信息 + 银行 + 社保省份 + 反馈类除外）。
2. **后道侧反向 dirty hook**：`DispatchedOrderService.supplement` / `complete` 中，对 `extraData` patch 调一次 `createDirtyMarksForBackendUpdate(parentOrderId, dispatchedOrderId, diff)`：
   - 写 `work_order_field_dirty_marks`，`affected_module_codes` = 其他**未办结**子单的 module_code 集合 ∪ `['main']`。
   - `is_active=true`，`changed_by = user.sub`，`flow_round = parent.modificationRound`。
3. **`fieldChangeHook.payload.diff_fields[]` 升级**（与上轮 0521 设计文档一致，本期落实）：
   ```ts
   diff_fields: meaningful.map(d => ({
     field_code: d.field,
     field_name: lookupFieldName(d.field),  // 来自 field_configs.fieldName
     old_value: d.before,
     new_value: d.after,
   }))
   link: `/work-orders/${order.id}?focus=${meaningful[0].field}`
   // 后道侧推送时，link 改为：`/dispatched-orders/${dispatchedOrderId}?focus=...`
   ```
4. **字段名查找避开热路径开销**：在 `FieldChangeHook` 启动时一次性加载 `field_configs.fieldName` 入内存 Map，并在 `field_configs` 写操作 emit 事件后失效缓存。

#### 前端
1. `pages/WorkOrders/Detail/index.tsx` 与 `pages/MyDispatched/Detail/index.tsx`：
   - 解析 `?focus=fieldCode`：组件挂载完毕后 `scrollIntoView` + 2s 黄色 keyframes。
   - 调 `GET /work-orders/:id` (业务员) 或 `GET /dispatched-orders/:id` (后道)，从响应中拿 `dirty_marks[]`，按 `field_code` 给所有命中字段加 `className="field-dirty-highlight"`。
2. `components/DynamicForm/index.tsx` 新增 `highlightFields?: string[]` 与 `dirtyTooltips?: Record<fieldCode, {oldVal, newVal, changedAt, changedByName}>`。
3. **"已查看"按钮**：详情页 `Affix` 一个 `<Button>已知悉</Button>`，调 `POST /dispatched-orders/:id/dirty/confirm-read`（已存在 `confirmDirtyRead`）。

### 2.4 风险点

- **R2.1 后道→业务员的反向通知量过大**：每次后道做 `supplement`（一个字段一改）会通知主单创建人；考虑**节流批合并**：5 分钟内多次后道改同一子单的字段，合并成一条『N 个字段已被后道更新'。
- **R2.2 dirty 标记互相覆盖**：业务员/后道同字段同轮次再改，必须在 `work_order_field_dirty_marks` 上加 `unique_active(work_order_id, field_code, flow_round, is_active=true)`；现状已建（`P1-一拆四架构最终方案` §3.2.3）。

## 4. 派发引擎：固定负责人 + 条件派发 + AB 角

### 4.1 现状要点

`dispatch_rules` 表（`backend/src/entities/dispatch-rule.entity.ts`）已有：

| 字段 | 用途 |
|---|---|
| `target_module` / `sub_module` | 命中目标模块 |
| `trigger_conditions` jsonb | AST 条件（AND/OR/EQ/NEQ/GT 等）→ `AstEvaluator` |
| `customer_id` / `department_id` | 范围匹配 (`ruleScopeRank` 决定优先级) |
| `assignee_user_id` | **固定负责人**（命中后直接派给该人）|
| `fallback_user_id` | **B 角**（assignee 不可用时回退） |
| `dispatch_strategy` enum | `fixed/round_robin/load_balance/pool` |
| `is_active` / `priority` | 启用/优先级 |

`DispatchEngineService.resolveRuleHandler` 已实现：assignee → fallback → handlerPicker(strategy)。

### 4.2 会议口径补齐

『AB 角』在 HR 业务里有两种语义：
1. **B 角作为 A 角不在岗时的兜底**（现状已支持，`fallback_user_id` + `User.isActive=false` 时回退）。
2. **AB 角并行派发，谁先认领谁处理**（pool 模式 + 两人都是 handler 的子集）—— 当前 `DispatchStrategy.POOL` 只产生 `handler_id=null` 的池子单，认领靠 `claim`；不能限制只让 A/B 两个人看到。

### 4.3 实施设计

#### 后端
1. **DDL: 扩 `dispatch_rules` 一列存『AB 角并行成员名单』**（不重做 strategy）：
   ```sql
   ALTER TABLE dispatch_rules
     ADD COLUMN ab_member_ids jsonb NULL;  -- ["userA-uuid", "userB-uuid"]
   ```
2. **派发逻辑**（`HandlerPickerService` + `DispatchEngineService.resolveRuleHandler`）：
   ```ts
   if (rule.dispatchStrategy === DispatchStrategy.POOL && rule.abMemberIds?.length) {
     // 拆出"限定可见池"：handler_id=null，但 visibleFields 之外，记录 ab_pool_members 到 dispatched_orders 新增字段
     return { handlerId: null, abPoolMembers: rule.abMemberIds };
   }
   ```
3. **DDL: 扩 `dispatched_orders` 一列**：
   ```sql
   ALTER TABLE dispatched_orders ADD COLUMN ab_pool_members jsonb NULL;
   ```
4. **认领校验**：`DispatchedOrderService.claim` 中如 `ab_pool_members != null`，必须满足 `user.sub IN ab_pool_members`，否则 4220。
5. **池可见性**：`applyUserScope` 在 `onlyPool=true` 分支增加 `OR (handler_id IS NULL AND ab_pool_members @> jsonb_build_array(:userId))`。
6. **admin 页面（派发配置）**新增 AB 角下拉多选（最多 2 人）。

#### 前端
- `admin/dispatch-config` 表单增 AB 角字段（多选 user，限 2 人）；
- `pages/MyDispatched/index.tsx` 池视图加『AB 角池』筛选 chip。

### 4.4 风险点

- **R4.1 AB 池既不是 fixed 也不是纯 pool**：必须 admin 严格校验：『AB 角时强制 strategy=pool；ab_member_ids ⊆ active users；不能超 2 人』。
- **R4.2 历史规则升级**：未填 `ab_member_ids` 的规则，行为不变（普通 pool / fixed），不需要数据迁移。
