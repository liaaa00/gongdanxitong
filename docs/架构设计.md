# 工单系统架构设计

> 版本：v1.0（Phase 1 定稿）
> 维护：架构组
> 目标：本期交付"入职工单"完整闭环，架构需为"续签 / 离职 / 待遇申报 / 月度批量业务"预留扩展点，不得为入职工单写死。

---

## 1. 总体目标与架构原则

### 1.1 业务目标
- 打通前台业务员 → 后道交付团队的信息流转。
- 所有派发规则、字段、字段权限、导出模板 **全部表驱动**，由后台可视化配置。
- 角色与业务解耦；一人多角色；完整操作审计。

### 1.2 架构原则（强约束）
| 编号 | 原则 | 落地方式 |
|------|------|----------|
| P-1 | 表驱动（不写死业务规则） | 字段、派发规则、字段权限、模板均存 DB；核心 Service 读取配置执行 |
| P-2 | 扩展优先于完美 | `work_orders.order_type` 枚举可扩；`extra_data` JSONB 承载任意字段 |
| P-3 | 角色与业务解耦 | 通过 `role × scenario × field` 三维矩阵控制权限 |
| P-4 | 前后端双重权限 | 后端是真权威（SQL 层过滤 + 字段级脱敏），前端只是体验优化 |
| P-5 | 事件而非过程 | 子工单完成 → 触发事件 → 主工单聚合；降低耦合 |
| P-6 | 幂等 & 可重放 | 派发、撤回、回流均以数据库事务 + 唯一键保障 |

## 2. 系统分层与部署拓扑

### 2.1 部署拓扑
```
          ┌──────────────────────────────┐
          │           浏览器              │
          └──────────────┬───────────────┘
                         │ 8080
                  ┌──────▼──────┐
                  │   Nginx     │  反向代理 / 静态资源 / 附件直出
                  └──┬───────┬──┘
                     │       │
         /api/*      │       │   /*
                     ▼       ▼
              ┌──────────┐ ┌──────────┐
              │ Backend  │ │ Frontend │   node:20-alpine / nginx:alpine
              │ NestJS   │ │ Vite SPA │
              └────┬─────┘ └──────────┘
                   │
                   ▼
              ┌──────────┐

              └──────────┘
```

所有容器位于同一 `ticket_net` bridge 网络，仅 nginx 对外暴露 `HTTP_PORT`。附件目录 `backend_uploads` 同时挂载到 backend（读写）和 nginx（只读），支持 `X-Accel-Redirect` 模式下载。

### 2.2 运行形态
- 开发态：`docker compose up -d postgres`，backend/frontend 各自 `npm run dev`。
- 生产态：`docker compose up -d`，四容器编排。
- 后期可将 `backend_uploads` 卷换为 MinIO / S3（仅需实现 `StorageAdapter` 接口，见 §4.6）。

## 3. 后端架构（NestJS + TypeORM）

### 3.1 分层职责

```
HTTP 请求
   │
   ▼
┌───────────────┐
│ Guards        │ JwtGuard → RolesGuard → ScenarioGuard
├───────────────┤
│ Pipes         │ ValidationPipe（class-validator）+ 业务 DTO
├───────────────┤
│ Controller    │ 路由声明、DTO 绑定、调 Service
├───────────────┤
│ Service       │ 业务用例编排，调用 Repository、DispatchEngine、FieldPermission
├───────────────┤
│ Repository    │ TypeORM 封装，复杂查询用 QueryBuilder；禁止在 Controller 里写 SQL
├───────────────┤
│ Entities      │ 与 DB 表一一对应，字段带装饰器；JSONB 用 `type: 'jsonb'`
├───────────────┤
│ Interceptors  │ ResponseInterceptor（统一 { code,data,message }） / AuditInterceptor
├───────────────┤
│ Filters       │ AllExceptionsFilter（统一错误码映射）
└───────────────┘
```

### 3.2 模块划分（`src/modules/`）

| 模块 | 职责 | 关键 Provider |
|------|------|---------------|
| `auth` | 登录 / 登出 / refresh / change-password | JwtStrategy、AuthService |
| `users` | 用户 CRUD、`user_roles` 多绑定 | UsersService |
| `roles` | 角色 CRUD | RolesService |
| `departments` | 树形部门 | DepartmentsService |
| `customers` | 客户档案 | CustomersService |
| `fields` | `field_configs` / `field_permissions` | FieldConfigService、**FieldPermissionService**（被其他模块注入） |
| `dispatch-rules` | `dispatch_rules` / `module_handlers` / `field_supplement_rules` | DispatchRuleService |
| `work-orders` | 主工单：手动单条、导入、提交、撤回、详情 | WorkOrdersService、**DispatchEngine** |
| `dispatched-orders` | 子工单：接单、完成、退回、补充、重分派、导出 | DispatchedOrdersService |
| `withdraw` | 撤回申请 & 审批 | WithdrawService |
| `uploads` | Excel / 附件上传 & 文件下发签名 | StorageService（抽象） |
| `ai` | Excel 表头 → field_code 映射 | AIMappingService（OpenAI Compatible Client） |
| `dashboard` | 三类看板聚合 | DashboardService |
| `admin` | 统一管理后台门面，聚合各配置模块的管理端点 | — |
| `common` | DTO 基类 / 装饰器 / 拦截器 / 过滤器 / 工具 | — |

> 所有业务模块依赖 `fields` 模块，用来做字段渲染/过滤；依赖 `dispatch-rules` 来解读派发配置。

### 3.3 核心组件抽象

#### 3.3.1 DispatchEngine（派发引擎）
> 单一职责：基于配置，把主工单转换为若干子工单。纯函数 + 配置查询，不持久化（由调用方事务内落库）。

```ts
// src/modules/work-orders/dispatch/dispatch-engine.ts
export interface DispatchContext {
  workOrder: WorkOrderSnapshot;   // 主工单（含 extra_data、order_type、department、customer）
  rules: DispatchRule[];          // 当前 order_type 启用的规则（按 priority 升序）
  moduleHandlers: ModuleHandler[];// 各模块可用处理人及权重
}

export interface DispatchResult {
  childrenToCreate: Array<{
    moduleCode: string;
    handlerId: number | null;     // null = 公共池
    visibleFields: string[];      // 该子工单可见字段快照
    reason: string;               // 命中的规则名（审计）
  }>;
}

export interface DispatchEngine {
  evaluate(ctx: DispatchContext): DispatchResult;
}
```

- **规则条件求值器** `ConditionEvaluator.evaluate(conditions, extraData)`：
  - `conditions` 为 JSON AST：`{ op: 'AND'|'OR'|'EQ'|'NE'|'IN'|'GT'|'LT'|'EXISTS', ... }`
  - 叶子节点：`{ op: 'EQ', field: 'need_onboarding_contact', value: '是' }`
  - 组合节点：`{ op: 'AND', children: [...] }`
  - 必须支持空条件 = 恒真（实现"无条件派发"）。
- **分派策略器** `HandlerPicker`：
  - `fixed`：`module_handlers.is_backup=false` 的第一个可用人
  - `round_robin`：按 `module_handlers.weight` 轮询，状态保存在 `module_handlers` 的游标字段（或 Redis 后期扩展）
  - `load_balance`：SQL 查 `dispatched_orders` 中该模块每人未完成数，取最小
  - `pool`：直接返回 null

> 将来新增策略只需实现 `HandlerStrategy` 接口并在 `DispatchStrategyFactory` 注册，不改 Engine 主流程。

#### 3.3.2 FieldPermissionService（字段权限过滤）
> 单一入口，所有涉及字段可见性的 Controller 都必须经它过滤，不允许自行裸返 `extra_data`。

```ts
export type FieldPermission = 'visible' | 'hidden' | 'readonly' | 'masked';
export type Scenario =
  | { kind: 'main' }
  | { kind: 'dispatched'; moduleCode: string };

export interface FieldPermissionService {
  /** 根据用户角色 + 场景，返回字段 code → 权限的 map */
  resolve(userId: number, scenario: Scenario): Promise<Record<string, FieldPermission>>;

  /** 对 extra_data 应用权限：hidden 丢弃 / masked 脱敏 / readonly 标记 */
  apply(
    extraData: Record<string, unknown>,
    permMap: Record<string, FieldPermission>,
  ): { data: Record<string, unknown>; readonlyFields: string[] };
}
```

脱敏规则表（`MaskingStrategy` 注册表）：
- `id_card_no`：保留前 6 后 4
- `mobile`：保留前 3 后 4
- `bank_account`：保留后 4
- `base_salary` / `other_salary` / `probation_salary`：一律 `***`

实现方式二选一，推荐 **Interceptor 模式**：
- 在 Controller 返回工单详情时，`@UseInterceptors(FieldPermissionInterceptor)`
- Interceptor 从请求上下文取 `user + scenario`，调用 Service 完成过滤后再进入统一 Response 包装。

> 一个用户可能有多个角色。合并策略：**取最宽松的**（visible > readonly > masked > hidden）。唯一例外：如果任一角色显式 `hidden`，且其它角色未显式声明，按"未声明视为 hidden"（白名单策略）。在 §4.2 的 `resolve` 里落实。

#### 3.3.3 AuditInterceptor（操作日志）
- 在 `@Audit(entityType, actionType)` 装饰过的路由上：
  - 请求进入时快照 `beforeData`（需要时 Service 写入 `request.audit.beforeData`）
  - 响应完成后快照 `afterData`
  - 异步写 `operation_logs`
- 失败不阻塞主流程，打 warn 日志。

### 3.4 路由与鉴权

- 统一前缀 `/api`。
- `JwtAuthGuard` 放在 `APP_GUARD` 里默认全开；个别开放路由（如 `/api/health`、`/api/auth/login`）用 `@Public()` 跳过。
- `RolesGuard` 支持 `@Roles('admin')` 单角色、`@AnyRoles('contract_team','contract_supervisor')` 任一匹配。
- `ScenarioGuard` 仅用于 `/api/dispatched-orders/*`：校验当前用户在此子工单的模块中是否有角色（或是主管 / admin）。

### 3.5 错误与响应
- 所有正常响应由 `ResponseInterceptor` 包装成：`{ code: 0, data, message: 'ok' }`
- 业务异常抛 `BusinessException(code, message, httpStatus = 400)`，由 `AllExceptionsFilter` 映射。错误码表见 `docs/API规范.md`。

### 3.6 配置与环境
- `ConfigModule.forRoot({ isGlobal: true, envFilePath: ['.env'] })`
- 关键配置通过 `ConfigService.get<T>(key)` 读取：`DATABASE_URL`、`JWT_SECRET`、`OPENAI_*`、`UPLOAD_DIR`、`MAX_UPLOAD_SIZE_MB`。
- 永远不从环境变量读业务规则，业务规则只读数据库。

## 4. 关键流程的架构映射

### 4.1 工单提交 → 派发
```
Controller.submit(id)
  → WorkOrdersService.submit(id)
     ├─ 事务开始
     ├─ 1. 取主工单 + 字段配置 + 校验必填（FieldConfigService）
     ├─ 2. 查询 order_type 的 dispatch_rules（按 priority 升）
     ├─ 3. DispatchEngine.evaluate(...) → DispatchResult
     ├─ 4. 去重 moduleCode（同一模块多规则命中只落一次，reason 合并）
     ├─ 5. 批量 insert dispatched_orders，visible_fields 冗余写入
     ├─ 6. 主工单 status = processing
     ├─ 7. 发站内通知（NotificationService，异步/事务外）
     └─ 事务提交
```
> "去重"是本架构的默认实现：**同一模块由多条规则命中 → 取最高优先级规则，其它规则只在审计日志中记录命中**。避免客户端看到两张"合同子工单"。

### 4.2 子工单完成 → 主工单聚合
- `DispatchedOrdersService.complete()` 事务中更新子工单状态，并调用 `MainOrderCompleteChecker.check(parentId)`。
- Checker 只看 `count(*) where status != 'completed'`，为 0 即置主工单 `completed`。

### 4.3 字段补充回流
```
POST /api/dispatched-orders/:id/supplement
  → Service.supplement
     ├─ 校验：当前用户角色 × 当前模块 对该 field_code 的权限 ≥ readonly? 否则拒绝
     ├─ 查 field_supplement_rules：该 field_code 允许由该模块补充？
     ├─ 写 field_supplement_logs
     ├─ 更新 work_orders.extra_data[field_code]
     └─ 对 sync_to_modules 中的 dispatched_orders，更新其冗余字段 & 推通知
```

### 4.4 撤回/修改审批
- 创建 `withdraw_requests` + 对未完成子工单生成 `withdraw_approvals`。
- 每次审批刷新状态机：
  - 全部 agree → request=approved / 主工单=withdrawn / 未完成子工单关闭
  - 出现 reject → request=rejected，通知业务员
  - `request_type=modify` 同意后，Service 将 `modify_data` 合并回 `work_orders.extra_data`，并按字段 `sync_to_modules` 同步。

### 4.5 Excel 导入 + AI 映射
```
POST /api/work-orders/import/preview
  → UploadsService 存 Excel → 解析表头
  → AIMappingService.suggest({ headers, availableFields })
  → 返回 { headers, suggestion: { header → fieldCode } }
POST /api/work-orders/import/confirm
  → 启动 import_jobs（异步 Worker Task）
  → 逐行验证（FieldConfigService.validate(row)）
  → 合规 → 新建 work_order(draft)
  → 最后批量 submit（或由用户在预览页决定是否一键提交）
  → 生成错误报表 xlsx，写入 import_jobs.error_report_url
```
> AI 仅做"表头映射建议"，不参与数据清洗，**不触及用户 PII**（只把表头字符串传给模型）。

### 4.6 文件存储抽象

```ts
export interface StorageAdapter {
  save(buffer: Buffer, ext: string, meta: FileMeta): Promise<StoredFile>;
  signUrl(fileId: string, ttlSec: number): Promise<string>;
  read(fileId: string): NodeJS.ReadableStream;
}
```
Phase 1 用 `LocalStorageAdapter`（写 `UPLOAD_DIR`，返回 `/files/:id`，由 nginx `X-Accel-Redirect` 直出）。后期切 MinIO 只换实现。

## 5. 前端架构（Vite + React 18 + TS）

### 5.1 技术选型

| 用途 | 选型 | 说明 |
|------|------|------|
| 构建 | Vite 5 | HMR、`import.meta.env` |
| UI | Ant Design 5 + Ant Design Pro Components | 用 `ProTable` / `ProForm` / `ProLayout` 减少样板 |

| Excel 预览 | `xlsx` | 预览 + 前端轻量校验 |

### 5.3 动态表单渲染
- 进入"新建 / 编辑 / 详情"页前，根据当前 `order_type` + `scenario` 一次性拉取：
  - `GET /api/admin/fields?orderType=xxx&active=true`
  - `GET /api/auth/me` 得到角色列表
- 由 `<DynamicForm />` 基于 `field_configs` 渲染控件；`<FieldPermissionProvider />` 注入权限 map，决定 hidden / readonly / masked。
- `masked` 字段在详情页只渲染脱敏字符串；编辑页直接禁用编辑并提示"无权修改"。

### 5.4 权限路由
- 路由 `meta.roles` 声明可访问角色；`meta.requires` 支持组合条件（如"主管 OR admin"）。
- 守卫组件 `<RouteGuard />` 从 `useAuthStore` 取 `roles`，不符合则跳 `/403`。

## 6. 数据库设计关键点（详见《数据库ER图.md》）

- 19 张表，**`work_orders.order_type` 枚举为扩展点**，本期实现 `onboarding`，表结构天然支持 `renewal` / `resignation` / `benefit` / `monthly` 等。
- `work_orders.extra_data` 为 `JSONB`，所有业务字段以 `field_code` 为键存入；后续新业务只需在 `field_configs` 加行，不改表结构。
- `field_configs.order_type` 支持 null = 通用字段（姓名、身份证等），非 null = 业务专属字段。
- `dispatched_orders.module_code` 不硬编码枚举，用字符串 + `module_handlers.module_code` 索引；新业务/新模块只需在 `module_handlers` 加配置。
- `dispatch_rules.trigger_conditions` 为 JSON AST，无需改代码即可新增条件；条件求值器独立。
- 所有历史数据不硬删除，统一用 `is_active` 软标记；`operation_logs` 保留完整 before/after。

## 7. 安全与合规

- 密码：`bcrypt`，盐轮数由 `BCRYPT_SALT_ROUNDS` 控制（默认 10）。
- JWT：`HS256` + 32 位以上随机 secret；支持 refresh（刷新令牌与访问令牌分开 TTL，Phase 1 可用单令牌 + 续期接口）。
- 敏感字段脱敏统一由 `FieldPermissionService` 兜底，禁止在 Controller 中直接吐 `extra_data`。
- 所有写接口上 `@Audit`；越权请求一律返回 403 + 错误码 `AUTH_FORBIDDEN`。
- 文件下载必须经 `/files/:id` 路由校验后再出内容（`X-Accel-Redirect`），不把原始 URL 暴露给前端。

## 8. 可观测性

- 日志：Nest 内置 Logger + JSON 结构化输出（生产）。
- 健康检查：`GET /api/health` 连 Postgres 探活；Docker healthcheck 消费之。
- 慢 SQL：TypeORM 开启 `logging: ['warn','error','schema']`；> 500ms 的查询记 warn。
- 前端错误：`react-error-boundary` 兜底，暂不接 APM（后期接入 Sentry）。

## 9. 扩展预留清单

| 扩展点 | 如何接入 |
|--------|----------|
| 续签 / 离职 / 待遇申报 | 新增 `order_type` 枚举值；在 `field_configs` 维护该类型字段；在 `dispatch_rules` 加派发规则；无需改代码 |
| 新后道模块（如税务） | 加 `module_handlers` 行 + 写字段权限矩阵 + 加派发规则；前端"我的子工单"列表自动识别 |

| 多租户 | 预留 `tenant_id`（本期不建列，但 Service 签名统一带 `ctx` 参数；未来加列只需数据库迁移 + 查询加过滤） |

## 10. 交付约束对后端 / 前端的硬性要求

- **后端**：
  - 使用本文件第 3.2 节的模块划分；不允许随意新增顶层模块，公共逻辑放 `common/`。
  - 所有响应走 `ResponseInterceptor`；所有异常走 `AllExceptionsFilter`。
  - 字段权限过滤强制走 `FieldPermissionService`，严禁 Controller 直接 `return workOrder`。
  - TypeORM 迁移脚本必须可重跑；初始数据写在 `src/database/seeds/`，通过 `npm run seed` 执行。
  - 单文件 ≤ 500 行，超了拆。

- **前端**：
  - 所有表单使用 `<DynamicForm />` 渲染，不允许硬编码字段列表。
  - 权限判断统一走 `useFieldPermission(fieldCode, scenario)` hook，不允许在业务组件里直接 `if (role === 'xxx')`。
  - 路由 lazy 加载 + 路由守卫；公共数据（字段配置、角色树）使用 React Query 缓存 + stale-while-revalidate。
  - i18n：本期不接，但所有写死的中文文案集中在 `constants/messages.ts`，方便未来抽取。
