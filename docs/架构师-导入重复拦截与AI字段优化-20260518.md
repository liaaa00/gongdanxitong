## 0. 用户原话与本期定位

> 「这是最新的导入情况，这是怎么回事呀，一直出现这个错误……上一轮表态是『全部兼容，不要拦截，错误可以在导入后修改』。」
>
> 「使用 AI 去进行字段匹配，我觉得只有没有识别到的才需要进行字段匹配吧，识别到的就不需要重复去匹配消耗算力了，现在的逻辑是不是重复匹配的，我觉得是这样的。」

**两件事不是同一性质**：
- **问题 1（同月身份证重复）**：这是一条业务唯一性约束（B+ 类），不是字段级"必填/格式"问题。前一期"宽进严出"明确说「身份证缺值无法定位重复 → 仍属 A 类硬必填」，**没有承诺去掉同月重复**。所以这不属于上轮"全部兼容"的覆盖范围。
- **问题 2（AI 字段匹配重复消耗）**：用户的直觉**完全正确**。当前实现是**先调 LLM、失败才退回本地模糊匹配**，并不是"本地命中的不发给 LLM"。这是一个真实的优化点。

下文 §1–§2 分别交付决策表与代码点。§3 给出清理 SQL。

### 1.1 链路梳理（grep 实测）

### 1.3 业务规则的设计意图

| 设计动机 | 来源 |
| --- | --- |
| **同一员工同月不重复入职** | `findDuplicateIdCardInMonth` 仅作用于 `OrderType.ONBOARDING`、仅按月、排除 `WITHDRAWN`。续签/离职/福利单都不查。 |
| **避免分支机构同时为同一员工开重复入职单** | 调用链发生在 `createDraft`，比"提交"更早，立即阻断录入。 |

**这是 HR 主数据完整性约束**（同一身份证号在同一月份只允许 1 张有效入职单），不是"严格录入校验"，撤销改 warning 会带来下游脏数据（薪资/合同/社保都按工单 1:1 关联）。

## 2. 问题 2：AI 字段匹配是否重复消耗算力

### 2.1 现状代码点（`backend/src/modules/ai/ai-mapping.service.ts`）

**入口函数** `suggest(orderType, headers, candidateFields)` —— L85–L128：

```ts
// L96
const prompt = this.buildPrompt(orderType, headers, candidateFields);
//                                            ↑ 全表头，没有过滤

for (const provider of this.providers()) {   // L97
  if (!(await provider.isAvailable())) continue;
  try {
    const result = await provider.call(prompt);     // ← LLM 请求
    const normalized = await this.normalizeLlmResult(result.content, ...);
    ...
    return normalized;
  } catch (error) {
    ...
    const fallback = this.fallbackFuzzy(headers, candidateFields, ...);   // ← 仅在 LLM 失败时才用本地
    return fallback;
  }
}
```

**`buildPrompt`** —— L170–L179：

```ts
return {
  system: '你是字段映射助手，只能输出严格 JSON。...',
  user: JSON.stringify({ orderType, candidateFields, headers }),  // ← 整个 headers 数组进 prompt
};
```

**`fallbackFuzzy`（本地匹配）** —— L130–L164：基于 `FIELD_ALIASES`（L14–L70 写死的别名表）+ bigram Jaccard + Levenshtein，输出 `suggestion / confidence / unmatched`，**质量已经相当好**——本期 v1.1 报告中"户籍归一化、姓名/身份证/客户名识别"绝大多数就是它能搞定的。

### 2.2 现状流程图（用户的判断完全正确）

```
                ┌── 当前实现 ──┐
[parsed.headers] ─┬─→ provider.call(prompt with ALL headers)
                  │     ↓ 成功
                  │   LLM result  (一次性返回全部映射)
                  │     ↓ 失败
                  └─→ fallbackFuzzy(ALL headers) ── 本地兜底
```

- **没有"先本地、再 LLM"的阶段拆分**。
- 一旦 LLM provider 可用（本仓库 `.env` 配的是 qwen-plus），**整个表头每次都丢给 LLM**，不管里头多少列已经能被 `FIELD_ALIASES` 精确命中。
- 用户的直觉 100% 正确：**当前逻辑就是「重复匹配」**——本地的能力被白白当兜底用了。

### 2.3 优化建议（不改代码，仅给出代码点）

**目标流程**：

```
                ┌── 建议实现 ──┐
[parsed.headers]
   ↓
Step 1: localExactAndFuzzy(headers, candidateFields)
   ↓  返回 { suggestion: {...已命中}, unmatched: [仅剩疑难列] }
   ↓
Step 2:  if (unmatched.length === 0) return localResult;     ← 零 LLM 调用
         else {
           llmResult = provider.call(buildPrompt(unmatched, candidateFields));
           merged = merge(localResult, llmResult);
           return merged;
         }
         若 LLM 失败：fallback 也只对 unmatched 跑，但本地段已经命中，无需重做
```

**具体落点（建议给后端去改）**：

| 代码点 | 当前行为 | 建议改动 |
| --- | --- | --- |
| `ai-mapping.service.ts:96` `buildPrompt(orderType, headers, candidateFields)` | 用整个 `headers` 构造 prompt | 拆出 Step 1：先调一个**与 `fallbackFuzzy` 同一打分函数**的本地匹配，**但门槛降到 ≥ 0.85（高置信度）才直接采纳**；剩余的列才进入 `buildPrompt(orderType, unmatchedHeaders, ...)`。 |
| `ai-mapping.service.ts:130–164` `fallbackFuzzy` | 既负责 LLM 失败兜底，也是唯一本地实现 | **抽取共享内核** `localMatch(headers, candidateFields, threshold)`：返回 `{ suggestion, confidence, unmatched }`。供 Step 1 与 fallback 复用。 |
| `ai-mapping.service.ts:85–128` `suggest(...)` | 一次 try/catch 串到底 | 改为两阶段：先 `localMatch(headers, fields, 0.85)`；若 `unmatched.length === 0` → 直接返回（不调 LLM）；否则 `provider.call(buildPrompt(orderType, unmatched, fields))`，再 `merge`。 |
| `buildPrompt(orderType, unmatched, fields)` | 当前传完整 headers | 仅传 unmatched headers；candidate 字段池可同步过滤掉已被 Step 1 占用的 `fieldCode`，减少 token。 |
| `ImportPreviewResult.modelUsed`、`fallbackReason` | 单一来源（LLM 或 fallback） | 加 `localMatchedCount` / `llmMatchedCount` 两个字段，前端可见地告诉用户"本地命中 N 列、AI 命中 M 列、未匹配 K 列"，与用户原话"识别到的就不需要重复匹配"对账。 |

**门槛 0.85 选择依据**：
- 现 `fallbackFuzzy` 的接受门槛是 `< 0.6` 才丢到 unmatched（L146）——这个门槛是"宁可错配也要给个结果"。
- 用作 Step 1 时门槛应**更严**（避免错配后 LLM 没机会纠错），建议 0.85。`FIELD_ALIASES` 命中的列在 `score()` 中通常拿到 0.95+（包含关系分支）或精确匹配 1.0，都能稳过；纯靠 bigram+Levenshtein 的弱匹配会被卡到 0.6–0.84，留给 LLM 复核。
- 这种"先本地高门槛、剩余给 LLM、LLM 失败再本地兜底（任何门槛）"是常规 hybrid 字段映射的成熟模式。

**预期收益**：
- **典型用例**（已有 `FIELD_ALIASES` 覆盖的入职模板）：**0 次 LLM 调用**，preview 接口响应从原来的 1.5–3s（qwen-plus 的 round-trip）降到本地几十 ms。
- **新模板/陌生表头**：LLM 仍参与，但只接收 3~5 个 unmatched 列（而非 60+ 全部），prompt token 数减少 80%+ 且 LLM 更聚焦（系统提示词不变，user 部分变短），上下文窗口压力小且更不易跑偏。
- **安全性**：候选字段池可同步剪枝（去掉已被 Step 1 占用的 `fieldCode`），LLM 不会把同一个目标字段又分配给另一个 header。

### 2.4 安全隐患评估

| 问题 | 现状 | 改造后 |
| --- | --- | --- |
| 本地匹配错配（false-positive） | 不存在（LLM 主导） | 门槛 0.85 + `FIELD_ALIASES` 显式表，错配概率可接受 |
| LLM 复核机会 | 总会有 | 只对 unmatched 列有；但 Step 1 的列若错配，**LLM 看不到原表头，发现不了** → 风险点 |
| 边界场景：同义但不在 `FIELD_ALIASES` 里 | LLM 能识别 | 若本地评分 ≥ 0.85，会直接采纳；建议保留"前端用户可手动改"的能力（preview 接口已经返回 `mapping[]`，前端可以让用户调整） |
| LLM 调用失败 | 退回 fallbackFuzzy | 改造后：Step 1 已命中部分不丢，只 fallback 处理剩余的 unmatched |

> 建议在改造同时保留 `AI_FORCE_LLM=true` 开关，让 QA/性能场景可以强制走全表头 LLM（用于诊断）。

### 2.5 验证手段（不需要改代码）

打开后端日志（`backend/.env` `DB_LOGGING=false` 不影响 ai 日志），重跑 36a19098 同一 fixture 的 preview，可以在日志里看到 `LLM provider qwen ...` 的 round-trip 调用——再对比 `previewResult.modelUsed: 'qwen:qwen-plus'`，就能证明当前**每次 preview 都会真的发 LLM 请求**。

### 3.3 软删除选项（更保守）
