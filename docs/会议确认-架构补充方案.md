## 1. 客户(Customer) + 商社(Branch) 数据模型

### 决策
- 一个 **客户主体(Customer)** 可拆出多个 **商社(Branch)**；员工 / 工单挂在 Branch 上，但视图聚合到 Customer。
- `branch_code` 全局唯一，是业务员上传 Excel 的核心匹配键。
- 业务员↔客户 是**多对一 + 可动态调整**：用独立绑定表 `customer_assignees`，不写死在 `customers.assignee_user_id`。

### 表结构

```sql
-- 商社（新增）
CREATE TABLE branches (
  id            uuid PK,
  customer_id   uuid FK -> customers.id,
  branch_code   varchar(64) UNIQUE NOT NULL,     -- 全局唯一，对应"商社代码"
  branch_name   varchar(128) NOT NULL,
  city          varchar(64),                     -- 杭州/深圳/...
  is_active     boolean default true,
  created_at    timestamptz default now()
);
CREATE INDEX idx_branches_customer ON branches(customer_id);

-- 业务员↔客户 动态绑定（新增）
CREATE TABLE customer_assignees (
  id            uuid PK,
  customer_id   uuid FK -> customers.id,
  user_id       uuid FK -> users.id,             -- 业务员
  group_code    varchar(32),                     -- 业务一组~五组（冗余便于按组查）
  is_active     boolean default true,
  assigned_at   timestamptz default now(),
  UNIQUE(customer_id, user_id)                   -- 当前会议口径：一个客户对应一个业务员
);
CREATE INDEX idx_customer_assignees_user ON customer_assignees(user_id) WHERE is_active;
```

### 现有表改造
- `work_orders` 增加 `branch_id uuid NOT NULL` + 索引 `(branch_id, created_at)`。`customer_id` 保留为冗余（性能 + 兼容旧数据）。
- `work_orders.extra_data` 内的 `customer_code / branch_code / customer_name` 三个字段从 JSONB **升级为列**，建联合索引便于按组/客户筛选与批办。
- `users` 增加 `group_code` 业务组冗余（用于后台派单规则按组匹配）。
- `departments` 表保留，**业务一~五组** 用 department 实现（`type=business_group`）；后道职能岗（合同签订 / 入离职联系 / 数据录入）用 department `type=back_office`。

### 兼容
- 旧工单：迁移脚本根据 `extra_data->>'customer_code'` 反查 customer，再按 customer 默认主商社回填 branch_id。无法回填的标记 `branch_id IS NULL` 并由后台批量补录。

## 2. 重复值校验：身份证 × 当月 唯一

### 决策
- **DB 层兜底**：在 `work_orders` 上加部分唯一索引（PostgreSQL 支持表达式索引）。
- **服务层**：单条提交 → 命中即 409 `DUPLICATE_ID_CARD_IN_MONTH`；批量导入 → 该行进失败队列，其他行继续，最终返回行级错误清单。

### 索引

```sql
-- 仅对入职工单 + 非作废状态 + 按月维度生效
CREATE UNIQUE INDEX uq_work_orders_idcard_month
  ON work_orders (
    employee_id_card,
    date_trunc('month', created_at)
  )
  WHERE order_type = 'onboarding'
    AND status NOT IN ('withdrawn');
```

### 接口契约
- 单条：`POST /api/work-orders` → 422，body：`{ code: 'DUPLICATE_ID_CARD_IN_MONTH', message, conflictOrderNo }`。
- 批量：`POST /api/import-jobs` 行级错误项：`{ row: 12, code: 'DUPLICATE_ID_CARD_IN_MONTH', existedOrderNo }`，整体导入返回 `partial`。

### 影响范围
- backend：`WorkOrdersService.create / ImportJobsService.processRow`
- frontend：批量导入结果页加 `重复行` 分组展示，复制 + 跳转到原工单。
- qa：补 3 组用例（同月重复、跨月不重复、作废后再传放行）。

## 3. 派发规则表 `dispatch_rules`（重构）

### 决策
- 现有 `dispatch_rules` 用 `trigger_conditions jsonb` 表达条件过于松散，**改为强类型字段**，避免后台配错。
- 维度：`customer_id` 或 `department_id (业务组)`，至少一个。
- 子工单类型：固定三个 `sub_module ∈ {contact, contract, data_entry}`。

### 表结构（增量字段，不破坏旧列）

```sql
ALTER TABLE dispatch_rules
  ADD COLUMN customer_id        uuid NULL FK -> customers.id,
  ADD COLUMN department_id      uuid NULL FK -> departments.id,         -- 业务一组~五组
  ADD COLUMN sub_module         varchar(32) NULL,                       -- contact|contract|data_entry
  ADD COLUMN assignee_user_id   uuid NULL FK -> users.id,
  ADD COLUMN fallback_user_id   uuid NULL FK -> users.id,               -- AB 角
  ADD COLUMN allow_manual_override boolean default true;

CREATE INDEX idx_dispatch_rules_lookup
  ON dispatch_rules(order_type, sub_module, customer_id, department_id, is_active);
```

### 匹配优先级（高→低）
1. `customer_id` 精确匹配
2. `department_id`（业务组）匹配
3. 全局默认（customer_id IS NULL AND department_id IS NULL）

匹配后取 `assignee_user_id`，若该 user 当前不可用（停用/请假），落到 `fallback_user_id`，再不可用 → 进入未派单池由 supervisor 手动指派。

### 手动调整
- 一拆三完成后，每个 `dispatched_orders` 行允许 `manager` / `supervisor` 调用 `PATCH /admin/dispatched-orders/:id/reassign`，操作写 `operation_logs`。

## 4. 变更通知中心（field-change hook）

### 决策
- **复用现有 `notifications` 表**，新增 `biz_type` 取值：`order.field_changed`、`order.completed_modified`、`order.supplement_filled`。
- 新增**字段变更钩子层** `FieldChangeHook`：拦截 `WorkOrder.update / DispatchedOrder.complete` 的 diff，按规则扇出消息。
- 站内消息**必做**；扩展通道（短信 / 飞书）**预留** `notification_channels` 表与 `payload.channels[]`，本期不实现发送器。

### 钩子伪代码

```ts
// backend/src/modules/notifications/field-change.hook.ts
@Injectable()
export class FieldChangeHook {
  async onWorkOrderUpdated(orderId, diff, actorUserId) {
    if (!hasMeaningfulDiff(diff)) return;
    const downstream = await this.getDownstreamAssignees(orderId);
    // 扇出：3 个下游办理人 + 创始人（创始人本人除外）
    const targets = uniq([...downstream, order.createdBy]).filter(id => id !== actorUserId);
    await this.notify.bulkCreate(targets.map(uid => ({
      userId: uid,
      bizType: 'order.field_changed',
      title: `工单 ${order.orderNo} 被 ${actor.realName} 修改`,
      content: renderDiffSummary(diff),
      link: `/work-orders/${orderId}`,
      payload: { diff, actorUserId, channels: ['in_app'] },
    })));
  }
}
```

### 触发点
| 事件 | 触发动作 | 接收人 |
|---|---|---|
| 工单任意字段修改 | `WorkOrdersService.update` afterUpdate | 三个下游办理人 + 创始人 |
| 入职联系补字段（银行卡等） | `FieldSupplementService.fill` | 创始人 + 另外两个下游（合同签订 / 数据录入） |
| 已办结工单修改 | `WorkOrdersService.update` 且 status=completed | 同上 + biz_type=order.completed_modified |

### 接口
- `GET /api/notifications?unreadOnly=true&limit=20`（已有，补 `bizType` 过滤）
- `POST /api/notifications/mark-read`（已有）
- 站内右上角铃铛 + 未读小红点 + 列表跳转。

## 5. 已办结工单修改方案二落地

### 决策
- **方案二**：发起人可直接改任意 **业务员字段**；保存时：① 写回总单 ② 自动同步到三个 `dispatched_orders` 的字段快照 ③ 触发 §4 通知 ④ 不触发审批流。
- **不允许**改"办理人字段"（如银行卡是由入职联系补的）→ 用 `field_ownership` 元数据 + `FieldPermission` 双重拦截。
- 已办结状态保持 `completed`，新增 `last_modified_at / last_modified_by` 列用于看板提示"⚠️ 此工单已办结后被修改"。

### 权限边界
| 用户角色 | 可改字段 | 可改的工单状态 |
|---|---|---|
| 业务员（创始人） | 自己发起的 + 业务员字段集合（41 个）| 任意状态（draft / pending / processing / completed） |
| 入职联系办理人 | 银行卡相关 2 字段 | 自己池中的 dispatched_order |
| 合同签订办理人 | 合同字段 | 自己池中的 dispatched_order |
| 数据录入办理人 | 录入相关字段 | 自己池中的 dispatched_order |
| 领导(郝总等) | 不可改 | 只读 |

### 同步策略
- 总单是 single source of truth；三个 dispatched_orders 仅保存"快照视图"。修改总单 → 强制同步覆盖快照对应字段 → 通知。
- 后续若业务要求"已办结回滚"，再考虑加版本表 `work_order_revisions`，本期不做。

## 6. 字段权限三态（仅可见 / 可编辑 / 隐藏）

### 决策
- 现有 `FieldPermissionMode` 已有 4 态（visible/hidden/readonly/masked）。本次会议要求的"三态" 直接映射：

| 会议口径 | 系统取值 |
|---|---|
| 仅可见 | `readonly` |
| 可编辑 | `visible` |
| 隐藏 | `hidden` |
| 脱敏（保留） | `masked`（身份证、手机号默认） |

- 不新增枚举，**改前端命名**为"可编辑 / 仅可见 / 隐藏 / 脱敏"，保持表存量数据兼容。
- `field_permissions.scenario` 现有支持 `view/create/edit/approve`，本次再加 `supplement`（入职联系补字段场景）和 `completed_modify`（已办结修改场景），用于差异化授权。

### 兼容业务组动态权限
- 业务组动态权限当前在 `department + role` 维度生效；字段权限作用于 `role`。两者通过 `(role, scenario)` 组合解析，命中 hidden / readonly 优先级最高。
- 解析顺序：`hidden > masked > readonly > visible`。

## 7. AB 角任务池

### 决策
- 江璐同时持有 **合同签订**、**入离职联系** 两个角色 → 通过 `user_roles` 多行实现（已支持）。
- "工单池"概念落地为**视图**：

```sql
CREATE VIEW v_dispatch_pool AS
SELECT d.*, mh.module_code AS pool_code, mh.handler_id AS pool_member_id
FROM dispatched_orders d
JOIN module_handlers mh ON mh.module_code = d.sub_module
WHERE mh.is_active = true;
```

### 池可见性 / 认领规则
- 合同池：`module_code='contract'` 的 handlers = { 杨纯, 江璐 } → 这两人都能看；任一人点击"认领"将 `dispatched_orders.handler_id` 锁定到自己。
- 入离职联系池：`module_code='contact'` 的 handlers = { 毛雅妮, 江璐 } → 同上。
- 数据录入池：handlers = { 安娜 }（后续可加人）。
- **互斥**：池视图按 `handler_id IS NULL` 过滤显示"未认领"；认领后从对方列表消失。

### 接口
- `GET /api/dispatched-orders?pool=contract&onlyUnclaimed=true`
- `POST /api/dispatched-orders/:id/claim` → 原子 update 防并发（`UPDATE ... WHERE handler_id IS NULL`）

## 8. 默认密码 + 首次登录强制改密

### 决策
- 默认密码：`123456`（bcrypt 加盐入库，不明文存）。
- 不发短信，不做手机验证（内网使用，会议明确）。
- 首次登录拦截：登录成功 → 检查 `must_change_password=true` → 强制弹出改密页 → 提交后清除标志。

### 表改造

```sql
ALTER TABLE users
  ADD COLUMN must_change_password boolean default true,
  ADD COLUMN password_updated_at  timestamptz NULL;
```

种子脚本：所有现有用户 `must_change_password=true`，`password_hash=bcrypt('123456')`。

### 接口
- `POST /auth/login` 返回体增加 `mustChangePassword: boolean`。
- `POST /auth/change-password` 校验旧密码 → 写新 hash → 置 `must_change_password=false` + `password_updated_at=now()`。
- 前端 axios 拦截器：响应里检测到 `mustChangePassword` → 跳转 `/change-password` 并拦截其他路由。

### 9.4 关键风险

1. **历史数据回填 branch_id**：现有 customer 若已有多商社差异，自动回填可能错。→ 提供"未匹配工单清单"页让后台手工补。
2. **身份证唯一索引与历史脏数据冲突**：建索引前必须先跑去重 / 标作废脚本。
3. **字段变更钩子事务边界**：通知发送必须在主事务提交后异步，避免事务回滚误发。
4. **AB 角池并发认领**：必须用 `UPDATE ... WHERE handler_id IS NULL RETURNING` 保证原子性，禁止先 SELECT 再 UPDATE。
5. **方案二的"已办结后修改"会破坏对账**：建议数据看板加"已办结后被修改"标签 + 操作日志可追溯，业务方确认能接受再上线。
