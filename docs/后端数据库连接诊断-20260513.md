## 4. 会话管理机制分析

### 4.1 JWT Payload

`backend/src/modules/auth/auth.types.ts`：

```ts
export interface JwtUserPayload {
  sub: string;
  username: string;
  roles: string[];
}
```

JWT 只包含：

- `sub`：用户 ID
- `username`：用户名
- `roles`：角色码数组

没有包含：

- 设备 ID
- 浏览器 ID
- IP 地址
- sessionId
- tenantId
- localStorage key

### 4.2 JWT 验证逻辑

`JwtStrategy` 从 Authorization Bearer Token 提取 JWT，验证签名和过期时间后直接返回 payload。没有按设备隔离会话的逻辑。

### 4.3 双会话 API 验证

```text

me equal user id: True
```

前 5 条工单 ID 完全一致：


## 5. 数据查询和同步逻辑分析

### 5.1 主工单查询

`work-order.service.ts` 中主工单列表逻辑：

```ts
if (!user.roles.includes('admin')) {
  if (user.roles.includes('manager')) {
    qb.andWhere('w.department_id IN (:...departmentIds)', { departmentIds });
  } else {
    qb.andWhere('w.created_by = :userId', { userId: user.sub });
  }
}
```

说明：

- admin 不进入过滤分支，所以能看到所有工单。
- 非 admin 才按部门或创建人过滤。

### 5.2 子工单查询

`dispatched-order.service.ts` 中 admin 通过 `isAdmin(user)` 跳过处理人或模块池限制。

说明：子工单后端也没有设备级隔离。

### 5.3 缓存层

后端没有 Redis、分布式缓存或按设备缓存工单列表。只有 AI 字段映射服务存在内存 Map 缓存，但它只缓存字段映射建议，不缓存工单数据。

### 5.4 高风险前端本地数据源

前端仍保留大量 Mock/localStorage 逻辑，例如：

```ts
// frontend/src/services/mock.ts
export const isMockMode = import.meta.env.VITE_USE_MOCK !== 'false';
```

这意味着：只要前端构建或运行时没有明确设置：

```env
VITE_USE_MOCK=false
```

就会进入 Mock 模式。

Mock 模式下工单存在浏览器本地：

```text
localStorage['mock_work_orders_v1']
```

这会造成：

- A 电脑浏览器有一份 localStorage
- B 电脑浏览器有另一份 localStorage
- 即使登录同一个 admin 账号，看到的数据也不一样
- 刷新、导入、删除只影响当前浏览器，不影响服务器数据库

当前服务器本地 `frontend/.env` 内容是：

```env
VITE_USE_MOCK=false
VITE_API_BASE_URL=http://localhost:3000
```

但是这里仍有一个部署风险：如果同事电脑访问的是自己电脑启动的前端，或者前端构建产物是在 `VITE_USE_MOCK` 未关闭时生成的，则仍会数据不互通。

## 6. 根因判断

从后端证据看，后端数据库、JWT、工单查询都没有设备隔离问题。

最可能根因是以下二选一或同时存在：

### 根因 A：同事电脑访问了自己的前端或 Mock 前端

如果同事电脑打开的是：

```text
http://localhost:5173
```

这在同事电脑上代表“同事自己的本机”，不是服务器电脑。如果同事电脑也启动了前端 dev server，且仍是 Mock 模式，就会读写同事电脑浏览器 localStorage。

正确访问方式应该是：

```text
http://192.168.26.66:5173
```

或部署后的 Nginx 地址。

### 根因 B：前端 API 地址仍指向 localhost

当前 `frontend/.env`：

```env
VITE_API_BASE_URL=http://localhost:3000
```

在 Vite dev server 的 proxy 场景下，如果同事访问服务器的 `5173`，请求 `/api` 会由服务器的 Vite 代理到服务器本机 `localhost:3000`，这是可以的。

但如果同事电脑运行了自己的前端，则 `localhost:3000` 就变成同事电脑自己的 3000，可能连不到真正后端，或回退到 Mock/其他服务。

### 根因 C：浏览器残留 Mock localStorage

即使现在 `.env` 已是 `VITE_USE_MOCK=false`，用户浏览器之前可能已有：

- `mock_work_orders_v1`
- `mock_admin_users_v1`
- `mock_session_user_v1`
- `token`
- `refresh_token`

如果页面仍加载了旧构建包或旧 dev server，这些缓存会继续制造“数据不互通”的假象。

## 7. 修复方案和操作步骤

### 7.1 用户/同事电脑统一访问服务器地址

服务器电脑 IP：

```text
192.168.26.66
```

同事电脑请访问：

```text
http://192.168.26.66:5173
```

不要访问同事电脑自己的：

```text
http://localhost:5173
```

### 7.2 后端 API 访问验证

在同事电脑浏览器打开：

```text
http://192.168.26.66:3000/api/health
```

预期看到：

```json
{"code":0,"data":{"status":"ok"},"message":"ok"}
```

如果打不开，优先检查 Windows 防火墙是否放行 3000 端口。

### 7.3 前端必须关闭 Mock

确认前端 `.env`：

```env
VITE_USE_MOCK=false
VITE_API_BASE_URL=http://localhost:3000
```

如果改过 `.env`，必须重启前端 dev server：

```powershell
cd D:\AI\SpeceAppDate\工单系统\frontend
npm run dev -- --host 0.0.0.0 --port 5173
```

### 7.4 清理浏览器旧 Mock 缓存

在两台电脑浏览器中执行一次：

1. 打开工单系统页面
2. 按 F12
3. Console 执行：

```js
[
  'mock_work_orders_v1',
  'mock_admin_users_v1',
  'mock_admin_roles_v1',
  'mock_admin_departments_v1',
  'mock_admin_customers_v1',
  'mock_admin_fields_v1',
  'mock_admin_dispatch_rules_v1',
  'mock_admin_module_handlers_v2',
  'mock_session_user_v1'
].forEach(k => localStorage.removeItem(k));
localStorage.removeItem('token');
localStorage.removeItem('refresh_token');
localStorage.removeItem('user');
location.reload();
```

然后重新登录 admin。

### 7.5 防火墙放行 3000/5173

如同事电脑打不开服务器地址，以管理员身份执行：

```powershell
New-NetFirewallRule -DisplayName "Ticket Backend 3000" -Direction Inbound -Protocol TCP -LocalPort 3000 -Action Allow
New-NetFirewallRule -DisplayName "Ticket Frontend 5173" -Direction Inbound -Protocol TCP -LocalPort 5173 -Action Allow
```

### 7.6 推荐最终部署方式

为避免 dev server、localhost、Mock 环境混乱，建议使用统一生产地址：

- 前端由 Nginx 或 Vite preview 统一提供
- 前端构建时 `VITE_USE_MOCK=false`
- API 统一反代到后端 `3000`
- 所有员工只访问同一个服务器地址，不在各自电脑启动前端

## 9. 最终判断

后端数据库连接、JWT 会话、工单查询逻辑本身未发现导致“两台电脑同 admin 数据不同”的隔离问题。

当前最高概率根因是：其中一台或两台电脑没有真正访问同一个后端真实 API，而是在访问本机前端/旧构建/Mock localStorage 数据。

下一步需要前端同事配合确认：

1. 两台电脑地址栏是否都为 `http://192.168.26.66:5173` 或同一个生产域名。
2. 浏览器 Network 中 `/api/work-orders` 是否请求到 `192.168.26.66`，而不是本机 localhost 或没有请求 API。
3. 前端运行环境变量是否确认为 `VITE_USE_MOCK=false`。
