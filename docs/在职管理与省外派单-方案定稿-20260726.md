## 一、总体规划（大模块视角）

系统现处 Phase1（仅入职、离职）。本轮扩展按**两个大模块 + 一个共用底座**规划：

```
工单系统
├─ 【共用底座】派单引擎改造（规则级指定专员）—— 两大模块都依赖，必须先做
│
├─ 大模块一：在职管理模块（北仑福保在职员工）
│   ├─ 单项业务办理        ← 本期
│   ├─ 劳动合同续签        ← 后续（去试用期字段）
│   ├─ 证明开具            ← 后续（动态字段随证明类型变化）
│   └─ 工伤提醒            ← 后续
│
└─ 大模块二：省外派单模块（浙江自签团队，双系统架构）
    ├─ 业务范围切换器 + 数据隔离   ← 本期（模块级基建）
    ├─ 省外增员 / 减员             ← 本期（复用入职/离职状态机）
    └─ 省外单项业务                ← 后续（复用在职模块状态机 + 换省外映射）
```

**本期范围**：底座 + 在职管理·单项业务办理 + 省外派单·增减员。续签/证明/工伤提醒延后，后台管理页本期不做。

## 二、共用底座（先摆代码事实，再谈方案）

### 2.1 派单：匹配层 vs 执行层（关键纠正）

| 层 | 表/代码 | 职责 | 证据 |
|---|---|---|---|
| 匹配层 | `dispatch_rules` | 什么条件（省份/客户/部门）→ 拆出哪些 `targetModule` 子工单 | `dispatch-engine.service.ts:55-108 evaluateDetailed` 只读 triggerConditions/targetModule/scope |
| 执行层 | `module_handlers` | 规则命中后，按"团队+权重+策略"选人，写 `dispatched_orders.handler_id` | `resolveModuleTeamHandler():182-192` + `HandlerPickerService.pick():27`，落地 `:283-284` |

**死字段**：`dispatch_rules.assignee_user_id / fallback_user_id` 在实际派单引擎里从不被读取（全目录 grep 仅出现在 entity/DTO/migration/预览 service）。
→ **上一版"备选人复用 fallback_user_id、派单复用现有规则"是错的。** "省份→指定某专员"需在执行层新补一条**规则级指定专员**的选人链路，这是本期真正的开发量。

### 2.2 派单引擎改造方案（本期核心工作量，两大模块共用）

- `dispatch_rules.trigger_conditions` 加 `{ province, businessType }` 做匹配（无 schema jsonb，不改表）。businessType 取值：`single_business`（在职单项业务）/ `provincial_dispatch`（省外派单），决定加载哪套映射。
- 执行层新增分支：命中规则携带的指定专员 → 直接选该 handler；未指定才回落现有"团队+权重+策略"。
- 双人省份：默认派映射表排前者，排后者作转派备选。**不做轮询**。
- 验证：按省分流 + 转派可用。

### 2.3 状态机：硬编码，非配置驱动

- 状态机硬编码在 `dispatched-order.service.ts`（2900+ 行）+ `handling-feedback.ts`；`WorkflowDefinition.definition_json`(jsonb) 可视化流程**不驱动**实际流转。
- 子工单状态枚举：`enums.ts:56-66`（pending/processing/modify_pending/completed/returned/withdraw_pending/withdrawn/void_pending/void）。
- **没有独立"增减员"工单类型，也没有"北仑"专属状态机**（`enums.ts:16-21` 仅 ONBOARDING/RENEWAL/RESIGNATION/BENEFIT）。增员=入职子工单、减员=离职子工单，共用同一套硬编码状态机。

### 2.4 配置表各 Sheet 的角色

| Sheet | 角色 | 本期怎么用 |
|---|---|---|
| Sheet1 | 单项业务字段清单（11 必填） | 在职·单项业务表单层依据 |
| Sheet2 | 流转动作及节点 | **需求规格**，非可导入配置；按其逻辑硬编码进单项业务状态机 |
| Sheet3 | 单项业务 省份→专员 映射 | 在职·单项业务派单映射（single_business），湖北/江苏/山西/山东/福建双人 |
| Sheet5 | 省外非北仑 派单映射 | 省外派单映射（provincial_dispatch），同省与 Sheet3 派不同人、多数退化为单人 |

**Sheet3 与 Sheet5 同省派不同人** → 两大模块是两套独立映射数据（结构复用、数据两份，用 `businessType` 区分）。

### 2.5 省份数据源

27 省简称以后端 seed 写入统一字典（`province_dict` 或常量），前端下拉与派单映射读同一份，源头保证一致（配置表用简称：广东/安徽，无"省"字）。

## 三、大模块一：在职管理模块

在职模块骨架已建但被禁用（menuVisible）。本期只做第一个子工单**单项业务办理**，其余子工单沿用同一模块框架后续接入。

### 3.1 本期子工单：单项业务办理

#### 3.1.1 状态机（还原自 Sheet2 往返流程）

```
创建 → 待受理 → 受理中 ─┬─ 订单确认 → 办理中(线上/线下) ─┬─ 办理成功(终态)
                        │                              ├─ 办理失败(终态)
                        │                              ├─ 订单取消(终态)
                        │                              └─ 需补充材料 → 发起人补充 → 重新提交 ┐
                        │                                                    (直接回办理中)┘
                        ├─ 退回(材料缺失) → 发起人补充 → 重新提交 → 待受理
                        └─ 转派 → 待受理(标注"由XX转派")
```

**两个回环不要混淆：**
- **材料缺失退回**（受理阶段）：主办发现材料不全 → 退回 → 重提**回到待受理**（需重新受理/接单）。
- **需补充材料**（办理阶段）：办理到一半要补料 → 退回 → 重提**直接回办理中**，原办理人继续，**不重新接单**（避免重复派单）。

#### 3.1.2 字段清单（Sheet1 的 11 必填 + 补充）

| 字段 | 口径 | 说明 |
|---|---|---|
| 附件 | 放宽到 **5 个** | 入职工单已支持多附件，零成本 |
| 客户支付服务费 serviceFee | **金额**（数字 2 位小数） | 已拍板 |
| 办理渠道 handleChannel | 线上/线下，**可切换不改状态** | 渠道是属性非节点 |
| 一二三级分类 | 联动下拉（Sheet2：4 一级/22 末级） | seed 初始化，**本期不做管理页** |
| 省份 | **27 省简称常量表** | 见 2.5；不走通用省市字典，避免"广东/广东省"不一致 |

#### 3.1.3 角色与动作

- **两层角色**：主办负责人（受理/转派）→ 最终办理人（处理）。
- **转派 TRANSFER**：当前受理人可转，不限次数，每次写日志，转派后回待受理。
- **取消**：仅发起人可操作，不可恢复，办理人线下通知引导发起人操作。

#### 3.1.4 后台可配 —— **本期不做**（ponytail：留口子不建页）

映射数据本期走 seed/DB 直接录入。管理后台页（前端页 + 接口 + 权限）列为**后续迭代**。业务若频繁改人，届时再建。

### 3.2 后续子工单（本期不做，仅占位）

| 子工单 | 要点 |
|---|---|
| 劳动合同续签 | 复用续签框架，去试用期字段 |
| 证明开具 | 动态字段随证明类型变化（extraData jsonb 已支持） |

## 四、大模块二：省外派单模块

### 4.1 顶部业务范围切换器（模块级基建，类租户切换）

- 位置：`BasicLayout.tsx` 顶部常驻下拉（北仑 / 省外）。
- **不是加个下拉就完**：选中值作为**全局业务范围上下文**，需贯穿列表查询、派单、字段权限。

### 4.2 全局上下文如何贯穿（技术方案）

- 前端：存 Zustand（本项目技术栈），切换即写入。
- 传递：接口请求统一带 `businessScope`（header 或 query）。
- 后端：拦截器/中间件统一读取，作为数据过滤 + 派单规则匹配的默认条件。
- → 前端存一下不够，后端必须配合过滤与匹配。

### 4.3 本期子工单：省外增员 / 减员

- 表单：字段按省外口径新增（moduleCode 区分省外）。
- 状态机：**复用北仑增减员（即入职/离职子工单）状态机，完全一致**——接单→办理→完成/退回/转派/作废（社保类多"三项结果全办结"反馈机制，见 2.3）。**不是** Sheet2 那套单项业务往返流程。零新写，只新增 moduleCode + 配派单规则。
- 派单：读 Sheet5 映射（`businessType: "provincial_dispatch"`），与 Sheet3 数据独立。

### 4.4 后续子工单：省外单项业务

届时复用在职管理模块·单项业务的状态机 + 换省外映射数据，不新写流程。
