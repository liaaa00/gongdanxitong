# 工单系统权限审计清单

> ⚠️ 当前演示口径（2026-06-03）：所有 seed/演示账号默认密码统一为 `123456`；`admin123` 是历史旧口径，会返回 401，不可用于演示。本文下方如出现 `admin123`，仅为历史记录/旧脚本背景，不代表当前可用密码。

> **版本**: v1.0  
> **生成日期**: 2026-05-12  
> **审计范围**: 入职/续签/离职/待遇申报四类工单的完整权限配置  
> **审计目的**: 梳理当前系统所有角色、权限配置、用户关联关系，识别潜在风险点

## 1. 执行摘要

本次审计覆盖工单系统的完整权限体系，包括：
- **9个激活角色** + 2个软下线角色
- **11个默认用户**，通过 `user_roles` 表实现用户-角色-部门三元绑定
- **字段权限矩阵**：9场景 × 9角色 × 119字段 = 理论9,639条权限记录
- **7条派发规则**：覆盖4类工单的自动派发逻辑
- **8个模块负责人配置**：定义子工单的默认处理人

### 关键发现
✅ **优势**：
1. 权限配置完全表驱动，支持运行时动态调整
2. 字段级权限控制细粒度到场景×角色×字段三维
3. 用户支持一人多角色，权限取最宽松策略
4. 社保模块已软下线（`isActive=false`），历史数据保留

⚠️ **风险点**：
1. **admin角色权限过大**：绕过所有字段权限检查，可见所有数据
2. **用户-角色关联缺少审计日志**：`user_roles`表无`created_at`/`created_by`字段
3. **字段权限默认策略不明确**：未配置的字段×角色组合行为依赖代码逻辑
4. **模块负责人单点**：8个模块各只配置1个处理人，无备用机制
5. **派发规则无版本控制**：`dispatch_rules`表修改无历史记录

### 3.2 用户-角色关联机制

**数据模型**：`user_roles`表（多对多关联）
```sql
CREATE TABLE user_roles (
  user_id UUID REFERENCES users(id),
  role_id UUID REFERENCES roles(id),
  department_id UUID REFERENCES departments(id),
  is_primary BOOLEAN DEFAULT true,
  created_at TIMESTAMP DEFAULT NOW(),
  PRIMARY KEY (user_id, role_id, department_id)
);
```

**关联规则**：
- 一个用户可以绑定多个角色（不同部门）
- `is_primary`标记主要角色（用于默认看板）
- 权限合并策略：取所有角色的**最宽松权限**（visible > readonly > masked > hidden）

**⚠️ 审计发现**：
- ❌ `user_roles`表缺少`created_by`字段，无法追溯谁分配的角色
- ❌ 无角色变更历史表，无法审计权限变更轨迹
- ✅ 通过`operation_logs`表可间接追溯（需要Controller层主动记录）

### 4.2 字段权限模式（4种）

| 权限模式 | 代码 | 说明 | 前端行为 | 后端行为 |
|---------|------|------|---------|---------|
| 可见可编辑 | `VISIBLE` | 完全访问 | 显示输入框，可修改 | 返回原值，接受更新 |
| 只读 | `READONLY` | 可见但不可改 | 显示文本，禁用输入 | 返回原值，拒绝更新 |
| 脱敏 | `MASKED` | 部分隐藏 | 显示`***`或部分字符 | 返回脱敏值（如身份证前6后4） |
| 隐藏 | `HIDDEN` | 完全不可见 | 不渲染该字段 | 不返回该字段 |

**脱敏规则**：
- `id_card_no`：保留前6后4，中间`****`
- `mobile`：保留前3后4，中间`****`
- `bank_account`：保留后4，前面`****`
- `base_salary`/`other_salary`/`probation_salary`：一律`***`

## 5. 派发规则配置

### 5.1 派发规则清单（7条）

| 规则名称 | 工单类型 | 触发条件 | 目标模块 | 派发策略 | 优先级 |
|---------|---------|---------|---------|---------|-------|
| onboarding-default-data-entry | 入职 | 无条件（必拆） | data_entry | FIXED | 10 |
| onboarding-contact-when-needed | 入职 | `need_onboarding_contact='是'` | onboarding_contact | FIXED | 30 |
| onboarding-contract-when-needed | 入职 | `need_company_contract='是'` | contract | FIXED | 40 |
| renewal-default-contract | 续签 | 无条件（必拆） | renewal_contract | FIXED | 10 |
| resignation-default-contact | 离职 | 无条件（必拆） | resignation_contact | FIXED | 10 |
| resignation-cert-when-needed | 离职 | `need_resignation_cert='是'` | resignation_cert | FIXED | 20 |
| benefit-default-apply | 待遇申报 | 无条件（必拆） | benefit_apply | FIXED | 10 |

### 5.2 派发策略说明

| 策略代码 | 策略名称 | 说明 | 当前使用情况 |
|---------|---------|------|------------|
| `FIXED` | 固定分派 | 从`module_handlers`取第一个`is_backup=false`的处理人 | 所有7条规则 |
| `ROUND_ROBIN` | 轮询分派 | 按权重轮询分配 | 未使用 |
| `LOAD_BALANCE` | 负载均衡 | 取当前未完成工单最少的处理人 | 未使用 |
| `POOL` | 公共池 | 不指定处理人，`handler_id=null` | 未使用 |

**⚠️ 审计发现**：
- ❌ 所有规则均使用`FIXED`策略，无负载均衡机制
- ❌ 派发规则无版本控制，修改无历史记录
- ✅ 触发条件使用JSON AST格式，支持复杂逻辑组合（当前仅用简单`EQ`判断）

### 5.3 触发条件JSON AST示例

```json
{
  "op": "AND",
  "children": [
    {
      "op": "EQ",
      "field": "need_onboarding_contact",
      "value": "是"
    }
  ]
}
```

**支持的操作符**：
- 逻辑：`AND`、`OR`
- 比较：`EQ`（等于）、`NE`（不等于）、`IN`（包含）、`GT`（大于）、`LT`（小于）、`EXISTS`（字段存在）

## 8. 潜在风险点与改进建议

### 8.1 高风险项（需立即处理）

#### 风险1：admin角色权限过大
**描述**：`admin`角色绕过所有字段权限检查，可见所有数据，包括薪资、身份证等敏感信息。

**影响**：
- 数据泄露风险
- 无法满足最小权限原则
- 审计合规性问题

**建议**：
1. 拆分`admin`为`system_admin`（系统配置）和`data_admin`（数据管理）
2. `system_admin`仅可管理用户/角色/配置，不可查看业务数据
3. `data_admin`需遵守字段权限，但可查看所有工单

#### 风险2：用户-角色关联缺少审计日志
**描述**：`user_roles`表无`created_by`/`updated_by`/`updated_at`字段。

**影响**：
- 无法追溯谁分配/撤销了角色
- 权限变更无历史记录
- 安全事件无法溯源

**建议**：
1. 增加`created_by`/`updated_by`/`updated_at`字段
2. 新建`user_role_history`表记录所有变更
3. 在管理后台显示角色分配历史

#### 风险3：模块负责人单点故障
**描述**：每个模块仅配置1个处理人，无备用机制。

**影响**：
- 处理人请假/离职导致工单积压
- 无法应对突发流量

**建议**：
1. 每个模块至少配置2个处理人（1主1备）
2. 启用`ROUND_ROBIN`或`LOAD_BALANCE`策略
3. 增加处理人工作量监控告警

### 8.2 中风险项（建议优化）

#### 风险4：字段权限默认策略不明确
**描述**：未配置的字段×角色组合行为依赖代码逻辑（前端默认`visible`，后端可能`hidden`）。

**影响**：
- 新增字段可能意外暴露
- 前后端权限不一致

**建议**：
1. 明确默认策略：未配置=`HIDDEN`（白名单模式）
2. 新增字段时强制配置所有角色权限
3. 增加权限配置完整性检查

#### 风险5：派发规则无版本控制
**描述**：`dispatch_rules`表修改无历史记录。

**影响**：
- 规则变更导致的问题无法回溯
- 无法审计规则变更合理性

**建议**：
1. 新建`dispatch_rule_history`表
2. 规则修改前自动备份旧版本
3. 支持规则回滚功能

#### 风险6：社保字段逻辑断层
**描述**：社保5字段在主工单对业务员`VISIBLE`，但所有子工单`HIDDEN`。

**影响**：
- 业务员可填写但无人处理
- 数据孤岛

**建议**：
1. 短期：在主工单表单隐藏社保字段（前端层面）
2. 长期：社保模块接回后重新启用
3. 增加字段"孤岛检测"工具

### 8.3 低风险项（可接受）

#### 观察点1：数据录入岗可见薪资
**描述**：`data_entry_team`可见`base_salary`等薪资字段。

**当前评估**：业务需要，录入全国数创系统需要完整信息。

**建议**：增加操作日志，记录谁查看了薪资字段。

#### 观察点2：合同组负载集中
**描述**：`contract01`负责5个模块。

**当前评估**：一期可接受，待业务量增长后扩容。

**建议**：监控`contract01`的工单处理时长，超过阈值时增加处理人。

## 12. 附录

### 12.1 权限审计SQL脚本

```sql
-- 1. 查询所有用户及其角色
SELECT 
  u.username,
  u.real_name,
  r.code AS role_code,
  r.name AS role_name,
  d.name AS department_name,
  ur.is_primary
FROM users u
JOIN user_roles ur ON u.id = ur.user_id
JOIN roles r ON ur.role_id = r.id
JOIN departments d ON ur.department_id = d.id
WHERE u.is_active = true
ORDER BY u.username, ur.is_primary DESC;

-- 2. 查询字段权限配置（按角色）
SELECT 
  r.code AS role_code,
  fp.scenario,
  COUNT(*) AS field_count,
  COUNT(CASE WHEN fp.permission = 'visible' THEN 1 END) AS visible_count,
  COUNT(CASE WHEN fp.permission = 'readonly' THEN 1 END) AS readonly_count,
  COUNT(CASE WHEN fp.permission = 'hidden' THEN 1 END) AS hidden_count,
  COUNT(CASE WHEN fp.permission = 'masked' THEN 1 END) AS masked_count
FROM field_permissions fp
JOIN roles r ON fp.role_id = r.id
WHERE r.is_active = true
GROUP BY r.code, fp.scenario
ORDER BY r.code, fp.scenario;

-- 3. 查询派发规则及目标模块
SELECT 
  dr.rule_name,
  dr.order_type,
  dr.target_module,
  dr.dispatch_strategy,
  dr.priority,
  dr.is_active,
  COUNT(mh.id) AS handler_count
FROM dispatch_rules dr
LEFT JOIN module_handlers mh ON dr.target_module = mh.module_code AND mh.is_active = true
GROUP BY dr.id, dr.rule_name, dr.order_type, dr.target_module, dr.dispatch_strategy, dr.priority, dr.is_active
ORDER BY dr.order_type, dr.priority;

-- 4. 查询模块负责人及工作量
SELECT 
  mh.module_code,
  u.username,
  u.real_name,
  mh.weight,
  mh.is_backup,
  COUNT(do.id) AS pending_count
FROM module_handlers mh
JOIN users u ON mh.handler_id = u.id
LEFT JOIN dispatched_orders do ON mh.handler_id = do.handler_id 
  AND do.status IN ('pending', 'processing')
WHERE mh.is_active = true
GROUP BY mh.module_code, u.username, u.real_name, mh.weight, mh.is_backup
ORDER BY mh.module_code, mh.is_backup, pending_count DESC;

-- 5. 查询admin角色用户
SELECT 
  u.username,
  u.real_name,
  u.email,
  u.last_login_at
FROM users u
JOIN user_roles ur ON u.id = ur.user_id
JOIN roles r ON ur.role_id = r.id
WHERE r.code = 'admin'
  AND u.is_active = true;
```

## 13. 审计结论

### 13.1 总体评价

工单系统的权限体系设计**基本合理**，采用表驱动配置、字段级权限控制、角色与业务解耦等先进理念。但在**审计追溯**、**单点故障**、**权限最小化**等方面存在明显不足。

**优势**：
- ✅ 权限配置完全表驱动，灵活可扩展
- ✅ 字段级权限控制细粒度高
- ✅ 支持一人多角色，权限合并策略合理
- ✅ 社保模块软下线处理得当

**不足**：
- ❌ admin权限过大，违反最小权限原则
- ❌ 缺少审计日志，无法追溯权限变更
- ❌ 模块负责人单点故障风险
- ❌ 字段权限默认策略不明确

### 13.2 风险等级

- **高风险**：2项（admin权限、审计日志缺失）
- **中风险**：4项（单点故障、默认策略、版本控制、逻辑断层）
- **低风险**：2项（薪资可见、负载集中）

### 13.3 建议

1. **立即处理**：拆分admin角色、增加审计字段
2. **2周内完成**：模块负责人备用机制、字段权限默认策略
3. **1个月内完成**：派发规则版本控制、权限检查工具
4. **持续改进**：定期权限审查、操作日志完善
