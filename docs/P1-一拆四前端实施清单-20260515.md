## 0. 架构同步后的关键结论

### 0.1 入职一拆四模块定义

入职管理由原「一拆三」升级为「一拆四」。新增第 4 个子工单：

| 业务模块 | 子工单中文名 | 内部 code | 生成规则 | 一期派发口径 |
|---|---|---|---|---|
| 入职管理 | 数据录入 | `data_entry` | 已提交入职主工单默认生成 | 按现有规则 |
| 入职管理 | 入职联系 | `onboarding_contact` | 是否仍按条件生成待产品确认 | 按现有规则 |
| 入职管理 | 劳动合同签订 | `contract` | 是否仍按条件生成待产品确认 | 按现有规则 |
| 入职管理 | 社保公积金办理 | `social_insurance` | 一期默认所有已提交入职主工单必生成 | 不按参保省份自动派单，默认派给杨杰或当前社保负责人 |

**前端硬性要求：**

- 所有页面必须显示中文「社保公积金办理」，不能显示 `social_insurance` 给用户。
- 所有状态必须显示中文，不能裸露 `pending / processing / completed / returned`。
- 所有字段权限必须显示中文，不能裸露 `visible / readonly / hidden / masked`。
- 社保一期只提供批量标记完成；业务员只看社保办理状态，不参与办理操作。

### 0.2 业务员修改规则

业务员修改规则分两类，前端必须区分展示：

#### A. 当前轮所有子单都未完成

业务员可以直接修改「业务员发起字段」。后端会：

1. 生成字段级 dirty 标记；
2. 刷新下游子单快照；
3. 触发站内通知；
4. 下游详情页需要把被修改字段标红/高亮。

前端影响：

- 主工单详情页允许进入编辑态。
- 下游子工单详情页读取 dirty 标记后标红字段。
- 通知中心显示中文变更提醒。

#### B. 任一子单已完成

业务员不能直接修改。必须：

1. 已完成节点逐一退回；
2. 每个退回节点填写退回原因；
3. 全部已完成节点退回后，业务员再修改并重新提交；
4. 整条主工单重新走完整一拆四流程。

前端影响：

- 主工单详情页应禁用直接编辑入口，提示「已有子工单办结，请先联系已完成节点退回」。
- 已完成子工单需要退回入口和退回原因展示。
- 重新提交后，子工单状态、dirty 标记、通知状态需要刷新。

### 0.3 历史一拆三兼容

架构方案要求：

- 已提交且未作废、已有原三类子单但缺少 `social_insurance` 的历史入职主工单，迁移时补生成「社保公积金办理」子单。
- 补生成的社保子单默认未完成，负责人默认杨杰，并写 `migration_batch_no` 便于回滚。
- 草稿、作废、已存在社保子单、异常数据不自动补。

前端影响：

- 历史一拆三数据迁移后会出现第 4 个未完成社保子单，页面必须正常显示。
- 如果存在未迁移的历史一拆三数据，也不能崩溃；子工单数量必须按实际返回动态展示。
- 不得在页面上写死「三个子工单」或「四个子工单」，除非是当前提交结果的实际数量。

### 0.4 仍需产品确认的问题

以下内容前端实施前仍需产品/业务确认：

1. 入职联系、劳动合同签订是否仍按现有条件生成；
2. 社保公积金办理是否所有入职主工单均必生成；
3. 杨杰账号、角色、权限与模块负责人配置；
4. 历史已完成主工单补未完成社保子单时，业务展示口径如何描述；
5. dirty 标记的清除时机：下游查看后清除、办理完成后清除，还是业务员再次提交后清除。
