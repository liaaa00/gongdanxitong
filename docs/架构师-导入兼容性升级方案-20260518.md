## 0. 用户原话与目标

> 「现在这个 Excel 导入还是失败……我希望的是全部兼容，你不要直接拦截，有错误到时候导入之后发现了可以再修改，而不是你现在直接要按照你说的指定模板来进行导入。」

**核心策略**：把导入从「严进严出」改为「宽进严出」。除少数真正落不了库的字段外，缺值一律给出 `safe_default` 或留空，让记录先进系统、warning 留痕、后续在工单详情页补全。

## 1. 现状链路梳理

### 1.1 「必填字段」校验链路

参考代码：`backend/src/modules/imports/field-validation.service.ts:114-148`、`:304-309`。

| 步骤 | 代码位置 | 行为 |
| --- | --- | --- |
| 1. 取字段元数据 | `getActiveFields` → `field_configs` 表 | 读 `is_required` / `default_required` / `conditional_required` |
| 2. 行级校验 | `validateRow`（L114） | 每行遍历 `input.fields`，逐字段判断 |
| 3. 必填判定 | `isRequired`（L304） | `isRequired \|\| defaultRequired` ⇒ 硬必填；否则跑 `astEvaluator.evaluate(conditional_required, normalized)` |
| 4. 缺值生成 error | L129–132 | `errors.push({ reason: 'required', message: "${fieldName}必填" })`，**continue 跳过本字段后续校验** |
| 5. 返回结果 | L147 | `RowValidationResult { ok: errors.length === 0, errors, warnings, normalized }` |
| 6. 调用方处理失败 | `import-job.service.ts:230-234` | `if (!validation.ok)` → `failRows.push(...)`，并 `fail_rows += 1`，**跳过 writeOne，不再尝试落库** |

`contract_template` 在 seed 里是 `required: false, defaultRequired: false`，但带 `conditionalRequired: { op: 'EQ', field: 'need_company_contract', value: '是' }`。本次导入的 12 行 `need_company_contract = "是"`，触发了第 3 步的 `astEvaluator.evaluate` 返回 true → 第 4 步生成 `required` 错误 → 第 6 步 row 标记为 failed。

### 1.2 「行被升级为失败」的代码点

参考代码：`backend/src/modules/imports/import-job.service.ts:209-245`、`:255-282`。

| 升级路径 | 代码位置 | 触发条件 |
| --- | --- | --- |
| 校验失败 | L230–234 | `validation.ok === false`（含 required / regex / enum / conditional / type_convert / relation / field_disabled） |
| 写库失败 | L240–244 | `writeOneRow` 抛错（含身份证月度重复、`requireText` 抛 4400、其他 DB 异常） |
| 全任务失败 | L256–260 | `createdWorkOrderIds.length === 0` ⇒ `ImportJobStatus.FAILED`；部分失败 ⇒ `PARTIAL`；全成功 ⇒ `COMPLETED` |

`success_rows` 仅在 L239 的 `writeOneRow` 成功后才 `+1`。换句话说，**只要 `validation.ok` 为 false，行不会走到 `writeOneRow`，必然计入失败行**。

### 1.3 已走 `safe_default` 兜底的字段

参考代码：`field-validation.service.ts:274-287`。当前 `applySafeDefaults` 只兜底了一个字段：

| 字段 | 触发条件 | 兜底值 | 说明 |
| --- | --- | --- | --- |
| `social_urge` | 字段存在 + dropdown 包含「否」+ 当前值为空 | `"否"` | 业务安全默认值 |

另一个被频繁触发但并非 safe_default 的逻辑是 `normalizeEnumAlias`（L238–272），它把 `城镇户口 → 非农业`、`是/否 → 是/否` 等做了归一化，**仍然算入 `warnings`**，不算 error。

## 2. 字段分类决策表（核心产出）

总览：后端预读实测 `ticket_system` 库 `field_configs` 表，**`is_required=true OR default_required=true OR conditional_required IS NOT NULL` 共 60 行**（ONBOARDING 32 硬 + 4 条件 + RENEWAL 10 硬 + 2 条件 + RESIGNATION 5 硬 + 1 条件 + BENEFIT 6 硬，与 seed-fields.ts 一致）。

> **重要更正**：本期之前讨论过的"`fields` 表"在 `ticket_system` 库不存在，实际表名是 `field_configs`，列名也不同——不是 `default_value/validation_rules`，而是 `is_required/default_required/conditional_required/validation_regex/validation_msg`。本方案以下所有引用以 `field_configs` 为准。

### 2.0 后端实测 DB 输出片段（节选 contract_template 行作为关键证据）

```text
field_code         | is_required | default_required | conditional_required
-------------------+-------------+------------------+-----------------------------------------------------------------
contract_template  | f           | f                | {"op": "EQ", "field": "need_company_contract", "value": "是"}
```

含义：`contract_template` 不是无条件必填，但当 `need_company_contract='是'` 时通过 `astEvaluator` 触发条件必填。本次失败的 8 行就是 `need_company_contract` 均为「是」且 `contract_template` 缺值的结果。

### 2.1 A 类 —— 真正的硬必填（必须保留拦截）

**判定标准**：缺值时**完全无法落库**或**破坏后续匹配/去重**。来源依据：
- `work_orders` 表对 `employee_name`、`employee_id_card`、`customer_id` 字段是 `NOT NULL`（实体定义 `backend/src/entities/work-order.entity.ts:85-93`）。
- `customer_id` 在 `work-order-import.service.ts:46-101` 通过 `customer_code + customer_name` 自动 `INSERT … ON CONFLICT`，缺任一字段 → 无法解析客户 → `customerId` 为 `undefined` → `createDraft` 报 4400。
- `id_card_no` 还要走月度重复 `findDuplicateIdCardInMonth`，缺值无法定位重复。
- 通过 `validationService.requireText` 校验（`work-order.service.ts:89,112`），缺值直接抛 `businessException`。

| 字段 code | 字段名 | 拦截原因 |
| --- | --- | --- |
| `employee_name` | 员工姓名 | `work_orders.employee_name NOT NULL`；`requireText` 强校验 |
| `id_card_no` | 身份证号/护照 | `work_orders.employee_id_card NOT NULL`；月度去重；`requireText` 强校验 |
| `customer_name` | 客户名称 | 自动创建客户时缺 `name` 直接拒绝；`work_orders.customer_id NOT NULL` |
| `customer_code` | 客户代码 | 自动创建/匹配客户的唯一键；缺值无 `customer_id` |

> **结论**：A 类 = 4 个字段。其他「公司业务上必填」但 DB 不强校验的字段都进 B 类。

### 2.2 B 类 —— 软必填（导入时不拦截，留空或 safe_default + warning）

**判定标准**：DB 不强约束（写入 `work_orders.extra_data` JSONB），缺值不影响落库，业务上可以让操作员在工单详情页之后补齐。**B 类是本次升级的主战场**。

## 3. 兜底策略汇总表

| 策略代号 | 含义 | 适用字段 |
| --- | --- | --- |
| `STRICT` | 缺值→error，拦截行 | A 类 4 个（`employee_name`, `id_card_no`, `customer_name`, `customer_code`） |
| `SAFE_DEFAULT` | 缺值→自动填入指定占位值 + warning | `contract_template = "待补充"`、`renewal_contract_template = "待补充"`、`social_urge = "否"` |
| `KEEP_NULL` | 缺值→保留 null + warning | B 类除上述 SAFE_DEFAULT 之外的所有字段（包含条件必填） |
| `RELAX_REGEX` | regex 不匹配→保留原值 + warning（不再 error） | `mobile`、`email`、`id_card_no`* |
| `RELAX_ENUM` | enum 不在范围且别名归一失败→保留原值 + warning | 所有 DROPDOWN 字段 |

> *`id_card_no` 走 STRICT 必填，但其 regex 失败仍建议降级为 warning（防止「写了护照号但格式不一致」导致全行失败）；这样仍要求字段非空，只是不再要求格式合规。

## 4. 最小修改建议

### 4.1 方案选型对比

| 方案 | 改动面 | 复杂度 | 推荐 |
| --- | --- | --- | --- |
| **方案 A**：把 `is_required` 校验整体降级为 warning | 仅 `field-validation.service.ts` 一处分支 | 极小 | ✗ 会让 `employee_name`/`id_card_no` 也跳过 validation，写库时被 `requireText` 抛 4400，错误信息劣化 |
| **方案 B**：新增 `is_strict_required` 元数据 | DB migration + entity + seed-fields + service 共 4 处 | 中 | △ 干净，但需 DB 迁移与 seed 重跑；本期改动收益不抵成本 |
| **方案 C（推荐）**：在 `field-validation.service.ts` 写死 `STRICT_REQUIRED_FIELD_CODES` 常量 + 扩展 `applySafeDefaults` | 仅 `field-validation.service.ts` 一处文件 | 小 | ✓ 零迁移、零 seed 改动、策略集中、可灰度回滚 |

**推荐方案 C**，长期可演化到方案 B（把 STRICT 列表沉淀为字段元数据）。

### 4.2 后端最小修改清单（方案 C）

**文件**：`backend/src/modules/imports/field-validation.service.ts`

1. **顶部加常量**：

   ```ts
   const STRICT_REQUIRED_FIELD_CODES = new Set<string>([
     'employee_name',
     'id_card_no',
     'customer_name',
     'customer_code',
   ]);

   const SOFT_REQUIRED_SAFE_DEFAULTS: Record<string, unknown> = {
     contract_template: '待补充',
     renewal_contract_template: '待补充',
     // social_urge 由现有 applySafeDefaults 处理，保留不变
   };
   ```

2. **改 `validateRow`（L126-145）**：

   ```ts
   for (const field of input.fields) {
     const value = normalized[field.fieldCode];
     const required = await this.isRequired(field, normalized);
     if (!this.hasValue(value)) {
       if (required && STRICT_REQUIRED_FIELD_CODES.has(field.fieldCode)) {
         errors.push({ fieldCode: field.fieldCode, reason: 'required',
           message: `${field.fieldName}必填（核心字段，无法自动补全）` });
       } else if (required) {
         // 软必填降级
         const fallback = SOFT_REQUIRED_SAFE_DEFAULTS[field.fieldCode];
         if (fallback !== undefined) {
           normalized[field.fieldCode] = fallback;
           warnings.push({
             fieldCode: field.fieldCode,
             code: 'safe_default',
             message: `${field.fieldName}未填写，已默认为"${fallback}"，请在工单详情页确认`,
             normalizedValue: fallback,
           });
         } else {
           warnings.push({
             fieldCode: field.fieldCode,
             code: 'soft_required_empty',
             message: `${field.fieldName}未填写，工单已先入库，请在详情页补齐`,
           });
         }
       }
       continue;
     }
     // 以下 enum / regex 校验：把 errors.push 改为 warnings.push（推荐做法）
     if (field.dropdownOptions && !field.dropdownOptions.includes(String(value))) {
       warnings.push({ fieldCode: field.fieldCode, code: 'enum_mismatch',
         message: `${field.fieldName}「${value}」不在标准枚举内，已保留原值，请在详情页确认`,
         originalValue: value });
     }
     if (field.validationRegex) {
       const regex = new RegExp(field.validationRegex);
       if (!regex.test(String(value))) {
         warnings.push({ fieldCode: field.fieldCode, code: 'regex_mismatch',
           message: field.validationMsg ?? `${field.fieldName}格式不规范，已保留原值`,
           originalValue: value });
       }
     }
   }
   ```

3. **`RowValidationError.reason` 联合类型**：可以保持原样，仅 `required` 一种 reason 被用到；其余通过 warning 输出。

**总改动量**：1 个文件、约 30 行代码。无 entity、无 migration、无 seed 改动。

### 4.2.1 warning 对象契约（前端 normalize 兼容性约束）

前端预读发现：`frontend/src/services/workOrders.ts:159-178` 的 `normalizeImportValidationErrors` 只识别 `row.level === 'warning'` 或 `row.severity === 'warning'`，**不识别 `errorLevel` / `isWarning` 字段**。同时 `frontend/src/components/ExcelUploader/index.tsx:665-716` 的「失败原因明细」表数据源 = `validationErrors + topErrors`，**没有按 level 过滤**——若后端把 warning 塞进这两个数组，会泄漏到失败明细表。

因此本方案严格遵守两条契约：

1. **数组分离原则**：B 类软必填/safe_default/enum_mismatch/regex_mismatch 一律推到 `validation.warnings`，**绝不**写入 `errors`。这样 `import-job.service.ts:222-229` 把它流向 `aiMappingRaw.warnings`，`serializeJob` 返回的是 `warnings` 字段，前端独立 Alert（line 651-663）展示，不会污染失败明细。
2. **如必须在 validationErrors 中携带 warning**（例如希望前端表格统一展示），对象必须用 `level: 'warning'`（前端识别此键）：

   ```jsonc
   {
     "row": 3,
     "field": "contract_template",
     "message": "劳动合同模板未填写，已默认为「待补充」",
     "code": "safe_default",
     "level": "warning",
     "originalValue": null,
     "normalizedValue": "待补充"
   }
   ```

> 推荐第 1 条契约（数组分离），实现最简单且前端零改动。

### 4.3 字段权限/派发引擎影响评估

参考代码：`seed-module-configs.ts:32-44`（contract 模块字段清单）、`dispatch-engine` 模块。

- 派发引擎按 **模块归属** 决定生成哪些子工单，不依赖 `contract_template` 等具体字段值是否非空。`contract_template = "待补充"` 不会阻塞合同子工单的派发。
- `seed-field-permissions.ts`（如有 require 权限规则）不影响导入路径，导入用的是 `field-validation.service` 自己的 required 判定。
