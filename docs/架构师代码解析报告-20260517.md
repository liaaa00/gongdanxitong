### 1.2 现状判断

✅ **后端实现整体完整且正确**：
- AI 配置写库 → 加密 → 缓存自动失效；
- 任何 Provider 的 `resolveConfig()` 都会优先读 DB；
- `AiMappingService.suggest()` 在 LLM 失败/无 key 时降级到本地 Jaccard+Levenshtein，并把 `fallbackReason` 透传给前端；
- 前端 `ExcelUploader` 已会展示 `fallbackReason` 中文文案（`no_api_key=未配置 AI_API_KEY...`、`provider_error=AI 服务不可用...`）。

✅ **前端 AISettings 页面已是新版**（`192 行`）：
- 新增 `validateHttpUrl` 客户端校验 + 首次保存强制要求 apiKey + provider 切换时联动默认 baseUrl/model；
- 文案明确告知"首次配置必须填写 API Key，否则导入 Excel 时仍会提示未识别到 AI 配置"。

### 1.3 可能的 Bug 根因

| 可能根因 | 复现条件 | 验证步骤 |
|---|---|---|
| **A. 用户保存时未填 apiKey 且 DB 中 hasApiKey=false** | 第一次配置时 apiKey 留空 | 检查 `system_settings` 中 `ai.config` 解密后的 apiKey 是否为空字符串 |
| **B. provider 切换后 apiKey 仍是旧 provider 的 key** | 例如把 provider 从 qwen 改成 openai 但留空 apiKey 沿用→实际 key 是 sk-xxx 的 qwen key，OpenAI 调用 401 → fallbackReason=`provider_error` | 看导入预览返回的 `fallbackReason` |
| **C. URL 格式不合法但被保存** | DTO 未校验 URL；`baseUrl` 输入诸如 `api.openai.com/v1`（缺协议） | 调用 LLM 时 `${cfg.baseUrl}/chat/completions` 走出形如 `api.openai.com/v1/chat/completions` 失败 |
| **D. AI_SECRET_KEY 与历史值不一致**（新部署/不同 env） | 历史已加密的 `system_settings.value` 用旧 key 解密失败 | `ai-settings.service.ts:99-101` 走入 catch，`logger.error('Failed to load AI config from system_settings: ...')`，导致 GET 返回 `provider:'openai',hasApiKey:false`；用户看到"未配置"；**这条最可疑**。若前端"配置成功"但下次刷新 hasApiKey=false，即此场景。 |
| **E. 旧版本 AISettings 页面被缓存** | 用户浏览器加载旧 `index.tsx`（没有 hasApiKey 必填校验、没有 URL 校验） | 强制刷新或检查 `dist/` 构建版本 |

### 1.4 改造范围（AI 配置）

#### 后端补齐

1. **`update-ai-settings.dto.ts`** 增加 URL 与 model 强校验：
   - 添加 `@Matches(/^https?:\/\//,...)` 给 `baseUrl`，杜绝 root cause C；
   - 添加 `@MinLength(1)` 给 `model`。
2. **`ai-settings.service.ts:83-106`** 解密失败时记录更清晰的 stage 标记（`Failed to decrypt`），并增加一个回归用 `decryptable` 状态返回到 `getConfigPublic`（前端一目了然），杜绝 root cause D。
3. **`AiSettingsController.get()`** 在加密读取失败时不要静默返回默认值，应返回 `{ ..., decryptOk:false, error:'config_corrupted' }`，前端根据该字段提示"AI 配置加密 key 已变更，请重新保存"。
4. **`ai-mapping.service.ts:97-119`** provider 循环逻辑微调：在第一个 `isAvailable()=true` 的 provider 调用失败后，目前直接 break 走 fallback；建议在错误分类是 401/403/404 时打印更明确的 `fallbackReason='auth_invalid'`、`'baseurl_invalid'`，前端给出"key 与 provider 不匹配"提示。

#### 前端补齐

1. **`AISettings/index.tsx`** 已完成 URL 校验和 hasApiKey 必填提示，无需再改；可补充：保存成功后，**主动调用一次 `/ai/field-mapping` 探测 endpoint**，把 `modelUsed`/`fallbackReason` 直接显示在管理页的 Alert 上，让管理员当场知道配置是否生效。
2. **`ExcelUploader/index.tsx:383-389`** 已展示 fallbackReason，无需改动。
3. 若后端返回 `decryptOk=false`，AISettings 页面顶部 Alert 增加 `error` 类型 + 一键"重置 AI 配置"按钮（调用一个新 `DELETE /admin/ai-settings`）。

#### 双端协同

- 后端新增 `POST /admin/ai-settings/test`：用当前保存的配置打一次最小 chat completion 探活，前端"测试连接"按钮；这样能彻底解除"配置成功但导入提示未识别"的疑虑。
