## 1. 问题 1：主工单列表导入后什么都不显示

### 1.1 现象
用户批量导入 Excel 后，回到主工单列表（`/work-orders`）页面，表格区域空白，但 import job 显示 success。

### 1.2 调用链路
1. 前端表格 `frontend/src/pages/WorkOrders/index.tsx:282` 用 `MultiViewTable`，`request={requestFn}`。
2. `requestFn` 见 `WorkOrders/index.tsx:252-255`：
   ```ts
   const result = await getWorkOrders({ ...params, ...quickFilters });
   return { data: result.list, success: true, total: result.total };
   ```
3. `getWorkOrders` 见 `frontend/src/services/workOrders.ts:514-526`：
   ```ts
   export async function getWorkOrders(params: PageParams): Promise<PageResult<WorkOrderItem>> {
     if (isMockMode) { /* mock 返回 { list, total, ... } */ }
     return request.get('/work-orders', { params }) as Promise<PageResult<WorkOrderItem>>;
   }
   ```
4. 后端 `backend/src/modules/work-orders/work-order.controller.ts:24-27` → `WorkOrderService.findAll`。
5. `WorkOrderService.findAll` 返回 `PagedResponse<WorkOrderListItem>`，类型定义 `backend/src/modules/work-orders/work-order.types.ts:3-8`：
   ```ts
   export interface PagedResponse<T> {
     items: T[]; total: number; page: number; pageSize: number;
   }
   ```
   实际实现 `work-order.service.ts:402-403`：`return { items: rows.map(...), total, page, pageSize };`

### 1.3 根因
**后端返回字段是 `items`，前端断言/读取的是 `list`，二者不一致。**

- 响应拦截器（`frontend/src/services/request.ts:69-88`）已剥离 `code/message`，把 `data` 返回给业务层；
- 业务层 `getWorkOrders` 把 `data` 当作 `PageResult<T>`，但 `PageResult` 定义为 `{ list, page, pageSize, total, totalPages, success }`（`frontend/src/services/mock.ts:14-22`）；
- 由于 axios 响应中没有 `list` 字段，`result.list` 为 `undefined`，`MultiViewTable` 收到 `{ data: undefined, total: undefined }`，列表自然空。

**为什么子工单列表不会有同样问题？**
对照 `frontend/src/services/dispatchedOrders.ts:182-202` 的 `normalizePageResult`，**已经做了兼容**：
```ts
const rawList = Array.isArray(result.list) ? result.list
              : Array.isArray(result.items) ? result.items
              : Array.isArray(result.data) ? result.data
              : Array.isArray(raw) ? raw : [];
```
工单服务层 `workOrders.ts` 中**没有等价的兼容层**，所以问题暴露在主工单列表上。

### 1.4 次因（不会单独导致空列表，但可能放大）
**权限范围过滤**：`work-order.service.ts:351-367` 对非 admin 用户用 `created_by = :userId` 或 `department_id IN (:...ids)` 过滤。导入接口 `imports/work-order-import.service.ts:29-37` 走 `workOrderService.createDraft`，`createdBy = user.sub`，理论上导入者自己能看到。

但如果业务员的 `department_id` 未设置或 `resolveUserDepartmentIds` 返回空数组（`work-order.service.ts:354-356, 360-362`），则**直接 return 空列表**。建议同步排查测试账号的部门关联（与导入 bug 无直接关系，但是常见次因）。

### 1.5 推荐修复（前端）
**最小改动方案** —— `getWorkOrders` 复用 `dispatchedOrders.ts:182-202` 的归一化思路：

```ts
// frontend/src/services/workOrders.ts
function normalizeWorkOrderPage(raw: unknown): PageResult<WorkOrderItem> {
  const r = (raw || {}) as Record<string, unknown>;
  const list = Array.isArray(r.list) ? r.list
             : Array.isArray(r.items) ? r.items
             : Array.isArray(r.data) ? r.data : [];
  return {
    list: list.map(normalizeWorkOrderResponse),  // 已存在的归一化函数
    page: Number(r.page ?? 1),
    pageSize: Number(r.pageSize ?? list.length),
    total: Number(r.total ?? list.length),
    totalPages: Number(r.totalPages ?? 1),
    success: true,
  };
}

// 在第 525 行替换：
const raw = await request.get('/work-orders', { params });
return normalizeWorkOrderPage(raw);
```

**注意**：
- 不要改后端字段名，否则会冲击所有调用 `items` 的下游（管理后台、E2E）。
- 由于 `normalizeWorkOrderResponse` 已经能容错 `customer/createdBy` 等嵌套字段，归一化后行内字段（`order_no`、`customer_name`、`created_by`）能正确显示。
- 验证范围：管理员账号、业务员账号、刚导入的工单、空列表态。

### 1.6 验证清单（不在本任务交付内，供 QA）
1. 用导入用户登录 → 进入 `/work-orders` → 表格出现导入的记录。
2. 切换业务负责人/管理员视角 → 数据正确按 department/scope 过滤。
3. 翻页、状态筛选、客户代码/姓名筛选三类参数仍生效。

## 2. 问题 2：前端显示的条件还没有放宽

### 2.1 现象 / 用户语境
用户说"前端显示的条件还是没有放宽"。结合上下文（最近一次后端去掉 enum 拦截）应理解为：**后端已允许字段值超出 `dropdown_options`，但前端表单组件仍强制只能从下拉列表中选**。

### 2.2 后端现状（确实已经放宽）
查 `backend/src/modules/imports/field-validation.service.ts:118-170`（`validateRow`）：
- 只做 `required` 检查（`STRICT_REQUIRED_FIELD_CODES`）和 `validationRegex` 校验；
- **没有** enum/dropdown_options 命中检查；
- 文件中虽有 `normalizeEnumAlias`（L241-275），但已被 `normalizeFieldValue`（L237-239）**短路绕过** —— 当前实现只调 `normalizeValue(value, fieldType)`，不传 options。

也就是说导入侧、提交侧后端已经容忍任意字符串。问题不在后端。

### 2.3 前端现状（仍然锁死）
`frontend/src/components/DynamicForm/index.tsx:197-208`：
```tsx
case 'dropdown':
  return (
    <ProFormSelect key={field.field_code} {...commonProps}
      fieldProps={{ ...commonProps.fieldProps, getPopupContainer: ... }}
      options={field.dropdown_options || []}
    />
  );
```
- `ProFormSelect` 默认不允许自由输入；
- options 完全由 `field.dropdown_options` 决定；
- 没有 `mode="tags"`、没有 `showSearch + allowClear` 的"输入即添加"逻辑；
- 因此用户在新建/编辑工单表单里看到的下拉框，只能在配置的选项里挑，**和"放宽"完全相反**。

### 2.4 根因
**前端 `DynamicForm` 没有跟随后端放宽。** 后端只是把数据闸门打开，前端表单 UI 仍然把用户锁在 enum 集合内。

### 2.5 推荐修复（按可行性排序）

**方案 A（推荐）— 在 `ProFormSelect` 上开放自由输入**

```tsx
case 'dropdown':
  return (
    <ProFormSelect
      key={field.field_code}
      {...commonProps}
      fieldProps={{
        ...commonProps.fieldProps,
        mode: 'tags',          // 允许任意输入新值
        maxTagCount: 1,        // 单值场景保持单选语义
        tokenSeparators: [],
        getPopupContainer: ...,
      }}
      options={field.dropdown_options || []}
    />
  );
```
- 优点：兼容旧数据、不改 schema、用户既能选也能写；
- 风险：`mode='tags'` 会让 ProForm 把值变成数组，需在 `convertDates` 旁边补一段"单值 dropdown 提取第一个 tag"的规则，或对所有 dropdown 切到 `mode='combobox'`（已被 antd 标记 deprecated，须谨慎）。

**方案 B — 把"放宽字段"在 admin/fields 里改 field_type 为 `text`**
- 优点：DynamicForm 不动；
- 缺点：失去 dropdown_options 的提示能力；要逐字段维护。

**方案 C — 给 DynamicForm 加 `freeformDropdown` 开关 prop**
- 默认 `false` 保持现状；新建/导入纠错页面传 `true`；
- 改动比 A 大但语义清晰。

**建议先 A，后续根据业务反馈决定要不要拆 prop。**

### 2.6 涉及范围
所有调用 `DynamicForm` 的页面会同时受影响：
- `frontend/src/pages/WorkOrders/New/index.tsx`
- `frontend/src/pages/WorkOrders/Detail/index.tsx`
- `Renewal/New`、`Resignation/New`、`Benefit/New` 等
- 子工单详情页（`MyDispatched/Detail`）的字段表单

变更前请前端工程师在 `WorkOrders/New` 跑一次烟雾测试。

## 3. 问题 3：除社保子单页外，其他模块页面没有批量功能

### 3.1 现象
用户进入 `/onboarding-modules/social_insurance` 能看到「批量完成」按钮；切到 `data_entry`、`contract`、`onboarding_contact` 等模块，按钮消失。

### 3.2 路由结构
`frontend/src/pages/OnboardingModule/index.tsx:23` 是**所有子单模块共用的页面**，URL 形如 `/onboarding-modules/:moduleCode`，由 `useParams` 取 `moduleCode` 来切换列表过滤。

### 3.3 根因
`OnboardingModule/index.tsx:34-35`：
```ts
const isSocialModule = currentModule === 'social_insurance';
const canBatchComplete = isSocialModule && (hasRole('admin') || hasRole('data_entry_leader') || hasRole('shared_team_owner'));
```
- 批量按钮（L126-136）和 `rowSelection`（L137-141）都用 `canBatchComplete` 控制；
- `canBatchComplete` 强依赖 `isSocialModule`，导致只有社保模块出现 UI；
- `handleBatchOk`（L79-104）写死调用 `batchCompleteSocialInsurance`，调用 `/dispatched-orders/social-insurance/batch-complete` 专属接口。

### 3.4 后端能力盘点
后端**已经具备通用批量接口**，前端没有调用而已：

| 接口 | 路径 | 用途 | 当前前端调用方 |
|---|---|---|---|
| `batchComplete` | `POST /dispatched-orders/batch-complete` | 通用：循环调 `complete`，必填 remark | `TeamDispatched/index.tsx`（团队子单页），但 `OnboardingModule` 没调 |
| `batchCompleteSocialInsurance` | `POST /dispatched-orders/social-insurance/batch-complete` | 仅社保，硬校验 `moduleCode === 'social_insurance'` | `OnboardingModule/index.tsx` |
| `batchDelete` | `POST /dispatched-orders/batch-delete` | admin only | `TeamDispatched`，`OnboardingModule` 未用 |
| `batch-return` / `batch-reassign` | — | 不存在 | — |

源码参考：
- `backend/src/modules/dispatched-orders/dispatched-order.controller.ts:80-96`
- `backend/src/modules/dispatched-orders/dispatched-order.service.ts:312-335`（batchComplete）

### 3.5 推荐实现

**第一步（P1，前端最小改动）：放开 OnboardingModule 的批量完成**

```tsx
// frontend/src/pages/OnboardingModule/index.tsx
const canBatchComplete = (hasRole('admin') || hasRole('data_entry_leader') || hasRole('shared_team_owner'));
const isSocialModule = currentModule === 'social_insurance';

const handleBatchOk = async () => {
  const values = await batchForm.validateFields();
  const remark = String(values.remark || '').trim();
  const ids = selectedRows
    .filter((r) => r.status !== 'completed' && r.module_code === currentModule)
    .map((r) => r.id);
  if (ids.length === 0) { message.warning('请选择未完成的子工单'); return; }
  setBatchLoading(true);
  try {
    const result = isSocialModule
      ? await batchCompleteSocialInsurance(ids, remark)
      : await batchCompleteDispatchedOrders(ids, remark);
    // ... 复用现有结果处理
  } finally { setBatchLoading(false); }
};
```

- 删除 `canBatchComplete = isSocialModule && ...` 的 `isSocialModule` 依赖；
- `rowSelection.getCheckboxProps`（L140）把 `record.module_code !== 'social_insurance'` 改为 `record.module_code !== currentModule`；
- Modal 标题和 Alert 文案根据 `getModuleLabel(currentModule)` 动态显示；
- `Alert` 对社保保留特殊文案（基数/月份提示），其他模块用通用文案。

**第二步（P2，可选）：批量退回 / 批量重派**

后端目前没有 `batch-return` 和 `batch-reassign` 接口。如果业务确实需要，建议：
- 短期：前端在客户端循环串行调用 `:id/return`、`:id/reassign`（性能可接受，子单数量级 < 50）；
- 中期：后端补 `POST /dispatched-orders/batch-return`、`batch-reassign`，复用现有 `returnOrder`、`reassign` 循环执行 + 跳过失败项的模式（和 `batchComplete` 一致）。

**第三步（P3）：权限差异**
不同模块的"批量完成"权限可能不同（如合同模块应允许 `contract_leader`、入职联系允许 `onboarding_leader`）。当前实现写死了 `data_entry_leader / shared_team_owner / admin`。建议把模块 → 允许角色的映射收敛到 `frontend/src/constants/modules.ts` 或后端 `module-handlers`，让前端 `canBatchComplete` 动态判定。
