## 2. OpenAI 兼容 baseUrl `/v1` vs 不带 `/v1` 走通性判断

### 2.1 代码层证据
关键拼接位置：`backend/src/modules/ai/providers/llm-provider.interface.ts:75-117` 中 `OpenAiCompatibleProvider.call()`：

```ts
// :84
`${cfg.baseUrl.replace(/\/$/, '')}/chat/completions`
```

行为分析：
- 该正则仅去掉**末尾单个**斜杠；不会插入也不会删除中间的 `/v1`。
- `baseUrl='https://api.deepseek.com'` → 拼出 `https://api.deepseek.com/chat/completions`
- `baseUrl='https://api.deepseek.com/v1'` → 拼出 `https://api.deepseek.com/v1/chat/completions`
- 测试连接位置同源：`ai-settings.service.ts:150`：`${baseUrl.replace(/\/$/, '')}/models`，规则一致。

### 2.2 服务端兼容性
DeepSeek 官方文档目前对 OpenAI 兼容路径的描述是 `https://api.deepseek.com`（不带 `/v1`），但实测 `https://api.deepseek.com/v1/chat/completions` 这条历史路径**当前仍然 work**（V3 时期上线的兼容路径未下线）。结论：

| baseUrl | 拼出的请求路径 | 当前能否 work |
|---|---|---|
| `https://api.deepseek.com`（官方推荐） | `/chat/completions` | ✅ |
| `https://api.deepseek.com/v1`（V3 时代写法） | `/v1/chat/completions` | ✅（兼容保留） |
| `https://api.deepseek.com/anthropic`（OpenAI 形态调） | `/anthropic/chat/completions` | ❌（要求 Anthropic 形态请求） |

**判断**：拼接逻辑对两种 OpenAI 兼容 baseUrl 都安全。已保存 V3 旧 baseUrl(`/v1`) 的用户在 hotfix 后**不会断**——LLM 调用仍走通；但 model 名若仍是 `deepseek-chat` 且账号是 V4 Key，会被 DeepSeek 服务端按 404/不存在模型驳回。

## 3. Anthropic 兼容 baseUrl 现状与扩 provider 建议

### 3.1 现状
- provider 联合类型：`'openai' | 'qwen' | 'deepseek'`（`backend/src/modules/ai/providers/llm-provider.interface.ts:26,35`）
- DTO 校验：`@IsIn(['openai', 'qwen', 'deepseek'])`（`backend/src/modules/admin/ai-settings/dto/update-ai-settings.dto.ts:46`）
- normalizeConfig 白名单：`['openai', 'qwen', 'deepseek']`（`ai-settings.service.ts:188`）
- 调用形态：`OpenAiCompatibleProvider.call()` 强行 POST `${baseUrl}/chat/completions`，请求头 `Authorization: Bearer ${apiKey}`，body 是 OpenAI ChatCompletions 形态。
- 前端 `PROVIDER_OPTIONS`（`AISettings/index.tsx:15-19`）：仅 OpenAI / Qwen / DeepSeek。

### 3.2 即便用户手填 `https://api.deepseek.com/anthropic` 会怎样？
hotfix 后 tooltip 中已经把 anthropic 兼容 URL 写出来了，所以**会有用户尝试手填**。届时：
- 前端通过：`validateHttpUrl` 只校验 http/https，不限制路径，能保存。
- 后端通过：`assertValidBaseUrl` 同样只查 protocol，能保存到 `system_settings`。
- LLM 实际调用：`OpenAiCompatibleProvider.call()` 仍按 OpenAI 形态发 POST，请求路径变成 `https://api.deepseek.com/anthropic/chat/completions` —— **DeepSeek 必返 404**，前端字段映射降级到本地 fuzzy。

**这相当于在 UI 上挖了个坑：tooltip 引导用户填 anthropic URL，但代码不接 anthropic 形态。**

> **明确结论（应 Leader 要求显式列出）**：后端**不会拒收** `provider='deepseek' + baseUrl='https://api.deepseek.com/anthropic'` 这种组合。
> - DTO 层（`update-ai-settings.dto.ts:46`）：`@IsIn(['openai','qwen','deepseek'])` 只校验 provider 枚举，`baseUrl` 仅 `MaxLength(512)` + 自定义 `IsHttpUrl`（只查 `http:`/`https:` 协议）。
> - 服务层（`ai-settings.service.ts:172-185`）`assertValidBaseUrl` 也只校验 protocol，不限制路径。
> - 因此用户保存这一组合**接口会返 200**，但 LLM 实际调用走 OpenAI 形态打到 `/anthropic/chat/completions` → DeepSeek 必返 404 → 字段映射降级到 fuzzy。
> - 也就是说："能存进去"+"不能 work"——前端 tooltip 暴露选项 + 后端不拒 = 留给用户一条死路。这就是为什么 §5.3 建议前端临时下掉 tooltip 中的 anthropic URL，或加 `（暂未启用）`。

## 4. 风险 / 迁移：已存 V3 配置的用户重启后是否被覆盖？

### 4.1 代码路径走查（`backend/src/modules/admin/ai-settings/ai-settings.service.ts`）

**入口 1：`getConfigInternal()`（:89-92）**
```ts
async getConfigInternal(): Promise<AiConfigStored | null> {
  const read = await this.readStored();
  return read.decryptOk && read.value ? this.normalizeConfig(read.value) : null;
}
```
- `readStored()`（:200-226）：从 `system_settings` 行 `key='ai.config'` 读密文，AES 解密 → JSON.parse → 直接当作 `AiConfigStored` 返回。**不会调默认值**。
- 走到 `normalizeConfig(read.value)` 时：

**`normalizeConfig`（:187-198）逻辑**
```ts
const provider = ['openai','qwen','deepseek'].includes(config.provider) ? config.provider : 'openai';
const defaults = PROVIDER_DEFAULTS[provider];
return {
  provider,
  apiKey: config.apiKey?.trim() ?? '',
  baseUrl: config.baseUrl?.trim() || defaults.baseUrl,  // :195
  model:   config.model?.trim()   || defaults.model,    // :196
};
```
- 关键：`||` 运算符。`'https://api.deepseek.com/v1'.trim()` 是 truthy 字符串 → **不会**走 `defaults.baseUrl`。
- `'deepseek-chat'.trim()` 同理 → **不会**走 `defaults.model`。
- 仅当用户存的 `baseUrl===''` 或 `undefined`（即历史就没填）才会回填新默认值。
- **结论：已保存 V3 旧值的用户重启后字段保持原样，不被 hotfix 覆盖。**

**入口 2：`updateConfig()`（:94-131）**
- `:106-111` `next = normalizeConfig({ baseUrl: incomingBaseUrl ?? existing?.baseUrl ?? '', model: dto.model ?? existing?.model ?? '', ... })`
- 用户在 AISettings 页只点"保存"而没碰任何字段时，前端实际会发 `provider/baseUrl/model` 全量（来自 form 当前值）。如果用户**手动改过 baseUrl/model**——存进去什么是什么；如果用户**只切换 provider 又切回**，会触发前端 `handleProviderChange` 回填新默认（V4 值），保存即生效。
- 这条路径不会"自己"覆盖；要么用户主动改，要么他什么都不改。

### 4.2 三类用户的实际行为
| 场景 | 数据库现存值 | hotfix 重启后 | 后续 LLM 调用 |
|---|---|---|---|
| A. 历史从未存过（空表） | 无 | 进 AISettings 页时表单显示 V4 新默认 | 用户保存后用 V4 默认调，OK |
| B. 已存 V3 旧值（baseUrl 带 /v1，model=deepseek-chat） | `{baseUrl:'.../v1', model:'deepseek-chat'}` | **保留**，不被覆盖 | OpenAI 兼容路径 `/v1/chat/completions` 仍能命中；但 model 在 V4 Key 下被 DeepSeek 拒认 → fuzzy fallback。**用户感知"AI 没识别"** |
| C. hotfix 后用户在页面切了 provider 重新填 | 用户手填 V4 值 | 写库 V4 值 | OK |

### 4.3 迁移建议
- **不需要 DB 迁移**，AES 密钥不变。
- **强烈建议**：前端在 `current.provider==='deepseek' && /^deepseek-(chat|coder|reasoner|v3)/.test(current.model)` 时显示一条 `Alert type="warning"`，引导用户『DeepSeek 已升级至 V4，建议改用 deepseek-v4-flash / deepseek-v4-pro』。这一条 hotfix 评审里若没看见，建议补上。
- 不需要让用户重输 API Key（前端 `apiKey` 留空沿用旧密钥已实现：`AISettings/index.tsx:120-133`）。

## 5. Hotfix 预检（件 2）

### 5.1 后端：`PROVIDER_DEFAULTS` 是否被 `ai-settings.service.ts` 之外引用？
- 全仓 grep `PROVIDER_DEFAULTS|DEFAULT_PROVIDER_CONFIG`（src/）：**唯一定义点**在 `ai-settings.service.ts:17`，唯一引用点在 `ai-settings.service.ts:191`（`normalizeConfig` 内）。
- `getConfigInternal()`、`updateConfig()`、`testConnection()` 均通过 `normalizeConfig` 间接消费默认值，无直接引用。
- AES 加解密分支（`encryptSecret`/`decryptSecret` 在 `aes.util`，`readStored()` 内）与默认值常量**完全无关**：解密失败时 `decryptOk=false`，`getConfigPublic` 返回兜底空值 `{provider:'openai', baseUrl:'', model:'', ...}`（:67-76），完全不读 `PROVIDER_DEFAULTS`。
- **结论**：后端 hotfix 改 `PROVIDER_DEFAULTS.deepseek` 一处 + `configuration.ts` 两处 + 注释 + test fixture **无副作用**。已落地代码已交叉核对，行为符合预期。

### 5.2 前端：`PROVIDER_DEFAULTS` 是否被 `AISettings/index.tsx` 之外引用？
- 全仓 grep `PROVIDER_DEFAULTS|DEFAULT_PROVIDER_CONFIG`（frontend/src）：**唯一定义点**在 `AISettings/index.tsx:21`，唯一引用点在同文件：
  - `:38-39` `normalizeSettings` 兜底（仅 `openai` 默认值，且只在后端返回 baseUrl/model 为空时生效——`||` 短路）
  - `:101-102` `handleResetBrokenConfig`（解密失败一键重置时按当前 provider 回填）
  - `:111` `handleProviderChange`（用户切换 provider 时回填）
- 没有别的页面或服务读 `PROVIDER_DEFAULTS`。
- 后端返回 `provider/baseUrl/model` 时，前端 `normalizeSettings`（:36-43）会优先用后端值（`cfg?.baseUrl || PROVIDER_DEFAULTS.openai.baseUrl` 用 `||`），所以已存 V3 旧值的用户进页面时**显示的是旧值**，不会被前端默认覆盖。这点和后端 normalizeConfig 行为一致——好的对齐。
- **结论**：前端 hotfix 改 `PROVIDER_DEFAULTS.deepseek` 一处 + tooltip + placeholder **无副作用**，已落地代码符合预期。
