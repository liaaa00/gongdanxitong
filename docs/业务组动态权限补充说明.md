# 业务组动态权限补充说明

## 文档信息

- **版本**：v1.0
- **日期**：2026-05-14
- **目的**：修正架构方案中业务组数量假设，明确动态权限设计原则
- **适用对象**：后端工程师、前端工程师、测试工程师

---

## 一、核心修正

### 1.1 业务组数量修正

**原假设**：业务组为 3 个（业务1组、业务2组、业务3组）  
**实际情况**：业务组为 **5 个**（业务1组、业务2组、业务3组、业务4组、业务5组）

**重要原则**：
- ⚠️ **所有权限判断逻辑必须基于 `groupId` / `departmentId`，不得硬编码组数量**
- ⚠️ **种子数据可包含 5 个业务组，但系统必须支持动态增删组织**
- ⚠️ **前端页面筛选、后端查询、测试用例均不得假设固定组数量**

### 1.2 权限规则（不变）

| 角色 | 数据可见范围 | 判断依据 |
|------|-------------|---------|
| 业务员 | 仅本人发起的工单 | `createdBy = currentUserId` |
| 业务组长 | 本组所有工单 | `departmentId IN (用户所属部门列表)` |
| 业务负责人 | 全部业务团队工单 | `orderType = 'onboarding'` 且角色为 `business_owner` |
| 系统管理员 | 全部工单 | 无过滤 |

**关键点**：
- 业务组长的权限判断使用 `departmentId IN (...)` 而非枚举组名
- 支持一个用户属于多个部门（通过 `user_roles` 表的多条记录）

## 二、数据模型与种子数据

### 2.1 组织架构表 `departments`

**设计原则**：
- 使用树形结构，支持任意层级
- 业务组作为"业务团队"的子部门
- 通过 `parent_id` 关联父部门

**示例数据**：
```sql

('dept-sys', 'system', '系统管理', NULL),
('dept-biz', 'business', '业务团队', NULL),
('dept-shared', 'shared', '共享团队', NULL);

-- 业务团队下的 5 个业务组
INSERT INTO departments (id, code, name, parent_id) VALUES
('dept-biz-1', 'business_group_1', '业务1组', 'dept-biz'),
('dept-biz-2', 'business_group_2', '业务2组', 'dept-biz'),
('dept-biz-3', 'business_group_3', '业务3组', 'dept-biz'),
('dept-biz-4', 'business_group_4', '业务4组', 'dept-biz'),
('dept-biz-5', 'business_group_5', '业务5组', 'dept-biz');
```

**扩展性**：
- 新增业务6组：只需插入一条 `departments` 记录，无需修改代码
- 删除业务组：软删除（`is_active = false`）或物理删除（需处理关联数据）

## 三、后端实现检查点

### 3.1 权限过滤逻辑（必须动态）

**文件**：`backend/src/modules/work-orders/work-orders.service.ts`

**错误示例**（硬编码）：
```typescript
// ❌ 错误：硬编码组数量
if (user.groupName === '业务1组' || user.groupName === '业务2组' || user.groupName === '业务3组') {
  // ...
}
```

**正确示例**（动态查询）：
```typescript
// ✅ 正确：基于 departmentId 动态查询
async findAllForUser(userId: string) {
  const userRoles = await this.userRoleRepository.find({
    where: { userId },
    relations: ['role', 'department']
  });
  
  const departmentIds = userRoles.map(ur => ur.departmentId);
  const roleIds = userRoles.map(ur => ur.roleId);
  
  // 判断角色类型
  const isAdmin = roleIds.some(rid => rid === 'role-admin');
  const isBusinessOwner = roleIds.some(rid => rid === 'role-business-owner');
  const isGroupLeader = roleIds.some(rid => rid === 'role-biz-leader');
  
  const qb = this.workOrderRepository.createQueryBuilder('wo');
  
  if (isAdmin) {
    // 系统管理员：无过滤
  } else if (isBusinessOwner) {
    // 业务负责人：全部业务工单
    qb.where('wo.orderType = :type', { type: 'onboarding' });
  } else if (isGroupLeader) {
    // 业务组长：本组所有工单（基于 departmentId）
    qb.where('wo.departmentId IN (:...deptIds)', { deptIds: departmentIds });
  } else {
    // 业务员：仅本人发起
    qb.where('wo.createdBy = :userId', { userId });
  }
  
  return qb.getMany();
}
```

### 3.2 后端落地检查点

**检查点 1**：权限查询不得包含硬编码的组名或组数量
- 搜索关键词：`'业务1组'`, `'业务2组'`, `'业务3组'`
- 确认所有权限判断使用 `departmentId` 或 `roleId`

**检查点 2**：种子数据脚本支持 5 个业务组
- 文件：`backend/src/database/seeds/*.ts`
- 确认插入 5 个业务组的 `departments` 和 `user_roles` 数据

**检查点 3**：API 返回用户所属部门列表（非单一部门）
- 接口：`GET /api/admin/users/:id`
- 返回格式：`{ departments: [{ id, name, code }] }`

**检查点 4**：工单列表查询支持多部门过滤
- 接口：`GET /api/work-orders`
- 查询参数：`departmentIds` 数组（非单一 `departmentId`）

**检查点 5**：组织架构管理接口支持动态增删
- 接口：`POST /api/admin/departments`（新增部门）
- 接口：`DELETE /api/admin/departments/:id`（删除部门）

```typescript
      label: d.name,
      value: d.id

}, []);
```

```typescript
  '共享团队': 'magenta',
```

**更好的方案**（动态颜色）：
```typescript
const getGroupColor = (groupName: string) => {
  if (groupName.startsWith('业务')) {
    const colors = ['blue', 'cyan', 'green', 'purple', 'orange'];
    const match = groupName.match(/业务(\d+)组/);
    if (match) {
      const index = parseInt(match[1]) - 1;
      return colors[index % colors.length];
    }
  }
  const colorMap: Record<string, string> = {
    '系统管理': 'gold', '业务团队': 'purple', '共享团队': 'magenta',
  };
  return colorMap[groupName] || 'default';
};
```

1. **不得硬编码业务组数量**：所有权限判断使用 `departmentId` 或 `roleId`

4. **测试覆盖所有业务组**：每个组的组长和组员都需要测试
