### 1.4 推荐实现形式

**选 A：`backend/scripts/clean-orders.ts` + ts-node + 新增 `db:clean-orders` npm script。**

理由：

1. **复用 TypeORM `DataSource`**（`backend/src/database/data-source.ts`）——自动从 `.env` 拿数据库配置，不需要在脚本里硬编码 host/user/password；上一轮 `generate-cleanup-plan-a.js` 就硬编码了 `ticket/ticket123/127.0.0.1`，环境一变就失效。
2. **事务安全** —— 用 `dataSource.transaction(async manager => { ... })` 包裹，全部成功才提交。
3. **可加交互护栏** —— 检测 `process.env.NODE_ENV === 'production'` 直接 abort；非 prod 要求 `--confirm` 参数或 stdin TTY 输入 `YES` 才执行。
4. **可输出清理报告** —— 删除前 SELECT count，删除后 console.log 每张表行数。
5. **与现有 `npm run seed` 同构** —— 同样是 `ts-node -r tsconfig-paths/register`，开发者认知一致。

对比备选：

- 备选 B：纯 SQL + psql 包装 —— 需要硬编码 psql 路径与连接串，Windows 上还要处理 `chcp 65001` 中文，运维不友好。
- 备选 C：放进 `src/database/seeds/clean-orders.ts` 由 `seeds/index.ts` 调度 —— 会破坏 `npm run seed` 是"幂等 upsert"的语义，不推荐放在同一目录。

#### 1.4.1 推荐脚本骨架（仅供后端实现参考，**不实际写入文件**）

```ts
// backend/scripts/clean-orders.ts
import 'reflect-metadata';
import { dataSource } from 'src/database/data-source';

async function main() {
  const confirm = process.argv.includes('--confirm');
  if (process.env.NODE_ENV === 'production' && !process.argv.includes('--force-production')) {
    throw new Error('Refusing to run db:clean-orders in production');
  }
  if (!confirm) {
    console.log('Dry run. Pass --confirm to actually delete.');
  }

  await dataSource.initialize();
  await dataSource.transaction(async (m) => {
    // 顺序：先清非 CASCADE 的旁路表，再清主表（让 FK CASCADE 链做剩余清理）
    const r1 = await m.query(`DELETE FROM notifications WHERE biz_type IN ('work_order','dispatched_order','onboarding_dispatch','contract_dispatch','dirty_mark') OR payload->>'workOrderId' IS NOT NULL`);
    const r2 = await m.query(`DELETE FROM operation_logs WHERE entity_type IN ('work_order','dispatched_order')`);
    const r3 = await m.query(`DELETE FROM import_jobs`);
    const r4 = await m.query(`DELETE FROM work_orders`); // 级联 dispatched_orders / dirty_marks / attachments
    console.log({ notifications: r1, operation_logs: r2, import_jobs: r3, work_orders: r4 });
    if (!confirm) throw new Error('Rolling back (no --confirm)');
  });
  await dataSource.destroy();
}

main().catch((e) => { console.error(e); process.exit(1); });
```

`package.json` 加：
```json
"db:clean-orders": "ts-node -r tsconfig-paths/register scripts/clean-orders.ts"
```

护栏建议（**强制**）：
- `--confirm` 必填，否则 dry run（事务回滚，仅输出会删多少行）
- `NODE_ENV=production` 拒绝执行，除非额外 `--force-production`
- 启动时 console.log 当前数据库 host / database 名字，让用户看清楚再确认

### 2.4 推荐方案：**A——全面去枚举（保留拆单兜底）**

**结论**：推荐 Plan A，原因如下：

1. **完整满足用户诉求** —— "Excel 写什么就导什么，不要自作聪明"。
2. **结构性安全有保障** —— 拆单/派单的兜底 `isYes` / `isTruthyYes` / `ensureOnboardingSplitChildren` 仍接受宽松 yes 写法；即使用户写"yes"，子工单结构仍正确生成。
3. **条件必填降级是可接受的副作用** —— 用户已经选择"系统不再自作聪明"，那 `contract_subject` 等的条件必填从"系统判定"降级为"详情页人工补全"也是这个原则的一部分。
4. **改动局部、影响面可控** —— 主要改动在 `field-validation.service.ts` 8 处；其他文件零改动。
5. **可逆** —— `field_configs.dropdown_options` 保留，未来若产品改主意只需在 service 里把校验代码恢复。

```
[ ] E2E 抽测：导入"户籍性质=城镇户口、是否企服发起劳动合同=yes" 的样本，全链路通过且拆出合同子单
```

#### 2.4.2 不推荐 B/C/D 的原因（备查）

- **B：保留枚举但去归一化** —— 半吊子方案，校验仍会失败大量行，违背"写什么就是什么"。
- **C：只去 household 不去是/否** —— 用户口径明确说"等"，强暗示扩展到全部枚举，部分改动反而要解释为什么这个去那个不去，体验割裂。
- **D：配置化开关** —— 当前没有这个量级的多客户/多租户场景，引入配置项是 over-engineering。
