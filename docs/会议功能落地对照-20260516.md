## 1. 议题 1 — 登录规则：用户名+密码、默认 123456、首登强改密、不需手机验证

【会议原话】
- *转述（决议六.6.2）*："用户登录仅用「用户名 + 密码」；邮箱/手机号当前是占位虚拟数据，上线后用户可自行更新真实信息。"
- *转述*：默认密码 `123456`，首次登录强制改密。

【现状】
- 默认密码 `123456` 已固化在 `backend/src/database/seeds/seed-users.ts:19`。
- `User.mustChangePassword` 字段存在，seed 时为 `true`（`seed-users.ts:174、184`）。
- 登录返回体含 `must_change_password` 与 `mustChangePassword` 双字段（`backend/src/modules/auth/auth.service.ts:69-70`）。
- 前端登录页根据 `must_change_password` 跳 `/change-password`（`frontend/src/pages/Login/index.tsx:30-37`）。
- 改密接口 `auth.service.ts:145-166`，成功后 `mustChangePassword=false`。
- 没有手机验证码 / OTP 链路。

【差距 / 待实现】
- ✅ 已落地，无差距。
- 注意：seed 中 `email`/`phone` 是占位（`example.com` / `138000000xx`），上线后用户首登强改密但邮箱手机仍是占位 → 需提示用户去"个人资料"页更新（个人资料页是否存在需前端复查）。

【优先级】 P2（已完成，仅做收尾自检）。

【后端动作】 无（保持 seed 默认）。
【前端动作】 复查"个人资料"页是否能让用户改邮箱/手机；若无，本轮不做，上线前给业务员书面流程。
【QA 验收点】
- 新建用户首登 → 强制跳改密页 → 改密后 `mustChangePassword=false` → 再次登录不再跳改密页。
- 登录响应同时含 snake_case 与 camelCase（兼容历史前端）。

## 3. 议题 3 — 字段拆分与字段权限：业务员可空字段后道补全（银行卡）

【会议原话】
- *转述（基线 §4 / 会议）*：业务员发起入职单时，开户银行信息 / 银行借记卡帐号可空；入职联系节点办理时收齐并由系统回灌总单 + 数据录入子单。

【现状】
- 业务员可空字段 = `bank_name`、`bank_account`，基线 §4 明确。当前 seed 中两个字段 `isRequired=false`（基线 §7.2 一致）。
- `FieldSupplementRule` + `FieldSupplementService` 已实现（`backend/src/modules/field-supplement/field-supplement.service.ts`）：
  - 校验补充人 module 是否被允许；
  - 写 `field_supplement_logs`；
  - 更新 `work_orders.extra_data`；
  - 同步到 `syncToModules` 中各子单的 `visibleFields`；
  - 站内通知发起人；
  - 调 `FieldChangeHook.onSupplementFilled` 通知所有子单办理人。
- 前端 `useDispatchedActions` 含 `supplement` 入口。

【差距 / 待实现】
- 是否已经为 `bank_name` / `bank_account` 配置 `FieldSupplementRule`（`supplementerModule=onboarding_contact`、`syncToModules=['data_entry']`），**需后端复查 seed 数据**。如果没有，业务员不填银行卡时，入职联系节点也无法补充。
- 前端业务员侧字段渲染应在 `bank_name`/`bank_account` 上加副标签"由入职联系节点补全"（基线 §4.2.4），**需前端复查实现**。

【优先级】 P0（直接影响业务员能否提交不带银行卡的工单）。

【后端动作】
- 复查/补齐 `field_supplement_rules` 表中两条 seed：`bank_name` 与 `bank_account` 的 `supplementerModule=onboarding_contact`、`syncToModules=['data_entry']`、`isActive=true`。
- 单元测试：业务员空银行卡 → 入职联系节点补 → 总单 `extra_data` + 数据录入子单 `visibleFields` 同步刷新 → 站内通知到位。

【前端动作】
- 业务员新建表单中 `bank_name`/`bank_account` 加 helper "由入职联系节点补全"，且不强校验。
- 入职联系子单详情页的字段补充入口（`useDispatchedActions.supplement`）能直接编辑这两个字段。

【QA 验收点】
- 空银行卡提交 → 工单可走完拆单（`data_entry` 子单不卡校验）。
- 入职联系节点补银行卡 → 总单 + 数据录入子单可见；操作日志 `field_supplement_logs` 落库；通知发起人收到。

- *转述*：业务员可空的字段（如银行卡），由入职联系节点在子单办理过程中补全后，必须回灌总单 `extra_data` 并刷新数据录入子单字段快照。

【现状】
- `FieldSupplementService.supplement()`（同议题 3）已实现：

【QA 验收点】 入职联系补银行卡 → 数据录入岗打开子单详情 → 银行卡字段已可见且值正确。

## 7. 议题 7 — 已办结工单修改：业务员可改"业务员字段"，同步三份快照+提醒

【会议原话】
- *转述（决议二）*："若任一子单节点已标记完成 → 业务员不可直接修改；必须先把所有已完成节点逐一线下沟通后退回（写明退回原因），全部子单回到未完成状态后业务员才能修改，修改后整条主工单重走完整流转流程。"

【现状】
- 当前 `WorkOrderService.update` 在 `status=COMPLETED` 时**仍允许直接修改**（仅在 `assertSalesEditableFields` 拦截"办理人字段"如银行卡 / 合同号 / data_entry_status，`work-order.service.ts:681-697`），通过后写 `actionType='completed_modify'` + `bizType='order.completed_modified'` 通知。
- 这与会议决议二（已完成节点必须先退回再改）**冲突**。会议口径下：
  - 业务员对已完成工单不能直接编辑；
  - 必须先调用退回接口，全部子单退回到非完成状态后才能改，改完后整条重走。
- 但议题 7 的措辞"业务员可改业务员字段，同步三份快照+提醒"暗示存在另一种白名单方案：业务员仅能改一组"业务员字段"（员工姓名、客户、岗位、合同期限等业务员归属字段），且会同步给入职联系/合同/数据录入三份快照 + 通知。
- 当前代码同时具备两种解释的部分能力但不完整。

【差距 / 待实现】
- 与产品确认两种解释中哪一种是最新口径（**Q10 悬挂**：议题 7 与决议二的"已完成必须先退回"在边界上是否冲突？议题 7 的"业务员字段白名单"是否仅适用于一拆四中**未完成节点**的修改？）。
- 如选决议二口径：
  - 后端 `update` 在 `status=COMPLETED` 直接抛业务异常引导走退回；
  - 已完成子单的"退回"流程已存在 `withdraw-requests` 模块，但需确认能否由办理岗主动退回 + 写退回原因（决议二）；当前 `withdraw-requests` 主要是业务员撤回主单方向。**需后端复查**。
- 如选议题 7 的白名单口径：
  - 把 `assertSalesEditableFields` 反转成 allowList（仅允许业务员归属字段如客户名 / 客户代码 / 员工姓名 / 岗位），其他字段在 `completed` 状态下禁改；
  - 所有变更同步到三份子单 `feedback_data` 或 `extraData` 快照 + 三方通知。

【优先级】 P0（行为不一致 + 涉及生产数据完整性）。

【Q10 悬挂】 已完成工单修改：选"必须退回再改"还是"白名单字段直接改+同步"？或两者并存按字段分流？请产品在 05-19 前明确，否则后端按"必须退回再改"实现以贴近决议二。

【后端动作】 等 Q10 决议；本轮先**不动该路径**，挂 P0 标签等产品。
【前端动作】 等后端动作。
【QA 验收点】 待 Q10。
