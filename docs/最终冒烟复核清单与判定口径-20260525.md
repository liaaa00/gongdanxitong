## 5. 总体通过/失败判定口径

### 5.1 可直接判定通过的条件

同时满足以下条件，才建议本轮冒烟通过：

1. 自动化清单 A1-A4 全部通过。
2. 人工清单 M1-M6 至少覆盖一条新产生的真实业务通知和一个 OnboardingModule 子模块。
3. 通知列表与详情均未出现“办理人/处理人/操作人”作为最终操作人名称。
4. OnboardingModule 状态表头多选、清空、单值三条路径均能从 Network 和表格结果双重验证。
5. 验收报告明确记录 S12 范围：其他子工单页面是否属于本轮范围。

### 5.2 任一失败即不通过的红线

| 红线 | 判定 |
| --- | --- |
| 通知列表或详情出现“办理人 修改/办理人：”且无法识别真实姓名 | 不通过 |
| 状态表头点击无响应或确认后不发请求 | 不通过 |
| 多选状态只发送最后一个状态或表格出现未选状态 | 不通过 |
| 清空筛选后仍携带旧 `statuses/status/statusIn` 参数 | 不通过 |
| 单选状态导致后端 400/500 或列表异常为空 | 不通过 |
| 当前模块筛选丢失 `module_code` 导致跨模块数据混入 | 不通过 |
| 验收报告把 OnboardingModule 结论泛化为“所有子工单列表均已表头筛选”，但未验证其他页面 | 不通过/需澄清范围 |
