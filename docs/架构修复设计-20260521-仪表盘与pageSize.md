## 1. pageSize 全局根因与统一治理

### 1.1 前后端约束链路

| 层 | 文件 | 现状 |
|----|------|------|
| 后端 ValidationPipe | `backend/src/main.ts:19-22` | `transform/whitelist/forbidNonWhitelisted` 全量启用 |
| 后端 DTO 基类 | `backend/src/common/dto/pagination-query.dto.ts:6,42` | `MAX_PAGE_SIZE = 100`；`@Max(MAX_PAGE_SIZE)` |
| 后端校验抛错 | `class-validator` 默认错误信息 | 即 `pageSize must not be greater than 100` |
| 前端违规调用 | `frontend/src/services/dashboard.ts:230,235` | `getDispatchedOrders({pageSize:10000})`、`getWorkOrders({pageSize:10000})` |

### 1.2 触发链（导致仪表盘报错）

```
Dashboard mount
  → getOrderTypeMatrix({dimension:'node'})
  → buildMatrixRowsFromListApis(dimension)
  → getDispatchedOrders({pageSize:10000})         ← 立即 400
  → ProTable dataSource 为空 / 节点总表报错气泡
```

后端实际有现成的 `/dashboard/order-type-matrix`（`backend/src/modules/dashboard/dashboard.controller.ts:61-64` + `dashboard.service.ts:484-587`），但前端 `services/dashboard.ts:336-346` 注释为"兼容旧部署"，永远走前端聚合，**绕过了真正的服务端聚合接口**。这是同时引发 #1 和 #2 的关键开关。

### 1.3 全局治理点（推荐 4 处一致改）

#### 后端
1. **保留 `MAX_PAGE_SIZE = 100`** 作为对外契约硬上限（不要为应付前端而放宽到 10000）。
2. **前端常见违规面 + 内部聚合需求** 改用专用服务端接口：
   - `GET /dashboard/cards`（已存在）
   - `GET /dashboard/order-type-matrix?dimension=orderType|node`（已存在，前端要切换到它）
   - `GET /dashboard/leader-trend?orderType=&moduleCode=`（已存在）
3. **错误响应增强**（可选）：在 `ResponseInterceptor`（`backend/src/common/interceptors/response.interceptor.ts`）对 `400 pageSize` 一类校验失败，统一翻译为业务码 `4011 PAGINATION_OUT_OF_RANGE` + 中文提示，避免英文裸串泄漏到 UI。
4. **审计**：搜索后端 DTO 上是否有未继承 `PaginationQueryDto` 的"自建分页"。`grep -rn "Max(\\d" backend/src` 仅发现 `update-operation-log-retention.dto.ts:8` 与 `imports/dto/preview-import.dto.ts:18`（均非分页），其余分页全部走基类。**结论：后端契约一致，无需放宽。**

#### 前端
5. **常量化分页上限**：在 `frontend/src/services/request.ts` 或新增 `frontend/src/constants/pagination.ts` 暴露 `MAX_PAGE_SIZE = 100`，并在 `request.ts` 拦截请求 params：发现 `pageSize > 100` 自动夹紧为 100 + `console.warn` 标记调用栈。这是「最后一道防线」，避免后续业务再写出 10000。
6. **修正业务调用点**：替换以下文件里的"全量取数"模式：
   - `frontend/src/services/dashboard.ts:230,235` → 改用 `request.get('/dashboard/order-type-matrix', { params:{ dimension } })`，本地保留 mock 兼容。
   - 如有"导出全部" 真实需求，应走专用接口（POST 创建导出 job），不要靠 list 大 pageSize 模拟。
7. **测试用例 / mock 数据**：保留 `pageSize:100` 上限。`frontend/src/mocks/handlers/*` 里的 `pageSize:20` 是默认值，无须改。

### 1.4 风险点与回归

- **风险 A**：服务端 `/dashboard/order-type-matrix` 当前 `getOrderTypeMatrix` 仅过滤 `status <> 'draft'`，未排除 `withdrawn/void`，前端 fallback 与之口径不一致。前端切换后需要 QA 在导入后比对四个数字。
- **风险 B**：若 `request.ts` 自动夹紧，可能掩盖真正的逻辑 bug（开发时务必带 warn）。
- **风险 C**：`getWorkOrders/getDispatchedOrders` 在很多 ProTable 调用点已经默认拿 `pageSize:20`，自动夹紧不会影响主线路。

## 3. "共享团队视角" 与 子工单"未派发" 的语义修正

### 3.1 现状根因

#### A. "共享团队视角"出现给业务员
`frontend/src/pages/WorkOrders/index.tsx:61-67`：
```ts
const viewDescription = (() => {
  if (isAdmin) return ...
  if (isBusinessOwner) return ...
  if (isGroupLeader) return ...
  if (isGroupMember) return ...
  return { title: '共享团队视角', desc: '查看派发给你的工单', color: 'green' };
})();
```

`useAuth` 的 `hasRole` 实际上检查的是 canonical role。但**当用户角色映射没命中任何业务角色时（例如登录后 token 里 roles 为空、或角色被映射为 `data_entry_leader`/`shared_team_owner`），这条 fallback 就被命中**——但他们打开的是"主工单列表 `/work-orders`"，不是"我的子工单 `/my-dispatched`"。所以文案"查看派发给你的工单"既不准也不真——后端 `findAll`（`work-order.service.ts:795-816`）对非业务非 admin 用户走 `else qb.andWhere('w.created_by = :userId')` 分支，返回的还是该用户**自己创建**的主工单（一般为 0 条）。

→ 这条兜底文案应当被**移除**或改为"主工单列表（仅显示由你创建的工单）"，并对后道角色直接跳转到 `/my-dispatched`（已有 `pages/MyDispatched/`）。

#### B. 子工单一律"未派发"
`frontend/src/pages/WorkOrders/index.tsx:247`：
```tsx
const children = record.dispatched_orders;
if (!children || children.length === 0) return <Tag>未派发</Tag>;
```

而后端 `toWorkOrderListItem`（`backend/src/modules/work-orders/work-order.mapper.ts:68-91`）**根本不输出 `dispatched_orders` 字段**——只有 `findOne` 详情页通过 `toDetailItem`（`work-order.service.ts:1051-1083`）才返回 `dispatched_orders/sub_orders`。

→ 这是 100% 复现的 bug：列表永远拿不到子工单，于是永远显示"未派发"。

### 3.2 修正设计

#### 后端
1. `backend/src/modules/work-orders/work-order.service.ts:findAll` 改造：
   - 在主查询拿到 `WorkOrder[]` 后批量补一次 `dispatched_orders`：
     ```ts
     const ids = rows.map(r => r.id);
     const children = await this.dispatchedOrderRepository.find({
       where: { parentOrderId: In(ids) },
       relations: { handler: true },
     });
     // 按 parentOrderId 分组并通过 toWorkOrderSubOrderItem 映射
     ```
   - `toWorkOrderListItem` 增加可选 `dispatched_orders?: WorkOrderSubOrderItem[]`，复用现有 `toWorkOrderSubOrderItems`。
2. 性能：单次 `IN (...)` 查询 + 内存分组，避免 N+1。`pageSize` 上限 100，最多 100 主单 × 平均 4 子单 = 400 行，开销可忽略。
3. **不要**把 `dispatched_orders` 加到 `toWorkOrderSubOrderItem` 的复用里——保持"列表用最小子集，详情用全集"。`work-order.types.ts:dispatched_orders` 在 `WorkOrderListItem` 里是可选字段即可。
4. 单测覆盖：在 `tests/work-order-service.list.spec.ts`（按现有命名）加 `should include dispatched_orders summaries in list response`。

#### 前端
1. `frontend/src/pages/WorkOrders/index.tsx:61-67` viewDescription 重写：
   ```ts
   if (isAdmin) ...
   if (isBusinessOwner) ...
   if (isGroupLeader) ...
   if (isGroupMember) ...
   // 不再 fallback 到"共享团队视角"。后道角色不应进此页面。
   return null;
   ```
   配合 `routes/index.tsx` 给后道角色把 `/work-orders` 重定向到 `/my-dispatched`。
2. `frontend/src/pages/WorkOrders/index.tsx:247` 加上"派发中 / 部分派发" 状态标签：
   - `dispatched_orders` 长度为 0 → "待派发"（仅 draft / submitted 短窗口）
   - 任一子单 `handler_id == null && status == 'pending'` → 标"派发池"
   - 其余正常：每个子单 Badge（已实现）。
3. **菜单层兜底**：`frontend/src/layouts/BasicLayout.tsx` 的 `filteredMenu` 已按角色过滤，确认后道角色看不到"主工单列表"菜单项。

### 3.3 风险点

- **B 风险**：`work-order.service.findAll` 关联子工单后，`order by w.created_at DESC + skip/take` 的 SQL 必须保留在主单上，子工单是事后补充的。不要用 TypeORM `relations: { dispatchedOrders: true }` 进 `find`，那会破坏分页（join + offset/limit 行数膨胀）。
- **A 风险**：兜底文案改动若部署到生产前忘了同步重定向，后道用户会看到一个空页面 + 没视角文案，体验不如现状（虽然语义错的）。建议**菜单+视角+重定向**作为同一个 PR。

### 4.2 期望流程

```
[业务员改了字段]
  → work-order.service.update() 调 createDirtyMarksForSalesUpdate
  → 同事务 fieldChangeHook.onWorkOrderUpdated → notification.bulkCreate
     · userIds = [creator] ∪ [所有子单 handler_id] - actor
     · biz_type = 'order.field_changed' (后道侧) 或 'order.completed_modified' (已办结后改)
     · payload.diff_fields = [{field_code, field_name, old_value, new_value}]
     · payload.workOrderId = ..., dispatchedOrderId? = ...
     · link = '/work-orders/:id?focus=field_code' 或 '/my-dispatched/:dispatchedId?focus=field_code'

[后道用户]
  → BasicLayout 顶部铃铛 / 消息中心列表 → 点击
  → 路由跳到详情页
  → 详情页读取 ?focus=fieldCode + 调 GET /dispatched-orders/:id 拿到 dirty_marks
  → DynamicForm 渲染时按 dirty_marks 给字段加 className="field-dirty-highlight"
  → 滚动到该字段 + 短暂闪烁

[查看后]
  → 点击"已查看"按钮 → POST /dispatched-orders/:id/dirty-marks/clear
  → notification 列表自动刷新 unread 数
```

### 4.3 后端必要变更

A. **生成完整定位元数据**：`field-change.hook.ts:58-64` 的 `payload` 中 `diff` 改为 `diff_fields`（已在 `notification.service.ts:NotificationListItem.diff_fields` 中预留），并补 `field_name`：
```ts
payload: {
  workOrderId: order.id,
  orderNo: order.orderNo,
  diff_fields: meaningful.map(d => ({
    field_code: d.field,
    field_name: getFieldNameByCode(d.field), // 来自 module_fields
    old_value: d.before,
    new_value: d.after,
  })),
  ...
}
link: `/work-orders/${order.id}?focus=${meaningful[0].field}`
```

B. **biz_type 颗粒化**（按需求第 4 条）：
| 业务侧 | 后端事件源 | 应使用 biz_type |
|--------|-----------|---------------|
| 数据修改（后道补充/编辑） | dispatched-order supplement / update | `order.field_changed`（业务员收到） |
| 退回 | `returnDispatchedOrder` | `order.returned`（已存在） |
| 后道办理人员侧 | | |
| 业务员催办 | `WorkOrderController.urge` | `work_order.urged` |
| 即将超时 | SLA 调度（cron / setInterval） | `dispatched_order.sla_warning` |
| 已超时 | 同上 | `dispatched_order.sla_breached` |
| 业务员修改未办结字段 | `WorkOrderService.update` 上的 fieldChangeHook | `order.creator_modified` |
| 业务员撤回（pending/approved） | `WorkOrderService.withdraw` | `work_order.withdraw_request` / `work_order.withdraw_approved` |
| 业务员作废 | `WorkOrderService.void` | `work_order.void_request` / `work_order.void_approved` |

`notification.service.ts:toNotificationBucket` 已经覆盖大部分 biz_type 字符串匹配，**只需补 `creator_modified` / `urge_feedback` 等枚举映射，无需大动。**

C. **SLA 调度**：当前后端目录里没看到 SLA 巡检 job。需要新增 `backend/src/modules/sla/sla-monitor.service.ts`：
   - 每日 N 次扫描 `dispatched_orders` `due_at`（`work-order.mapper.ts:22-27` 默认 +3 天）；
   - 与 `due_at` 比较：剩 24h 触发 `sla_warning`，超过触发 `sla_breached`；
   - 通过 `notificationService.bulkCreate` 发给 `handler_id`。
   - 依据现有 `WorkOrderSubOrderItem.isOverdue` 已有计算逻辑可复用。

D. **「派单」始终不出现在消息中心**：
   - `notification.service.ts:list` 默认 `includeDispatch=false`；前端 `BasicLayout:301` 主动传 `includeDispatch:true` 用于加载"全部"做铃铛展示。建议改为：
     - 铃铛只展示**非派单**消息（移除 `includeDispatch:true`）；
     - 派单类（`dispatched_new` 等）走"我的待办"已有页面 `pages/MyDispatched/`。
