# 入职模块字段配置基线（一拆四）

> 文档日期：2026-05-15
> 数据来源：用户提供的《浙江企服服务外包增员信息表-模板（待确认版）》（杭州 sheet）—— 这是入职模块一拆四的**字段元数据**口径，不是 Excel 导入要识别的表头。
> 用途：
>  - 后端：seed-fields / seed-module-fields 落库依据；条件必填、字段类型、选项均以本文档为准；
>  - 前端：入职新建表单、子工单详情字段渲染、分组、必填校验、条件联动均以本文档为准；
>  - QA：字段—子工单—权限矩阵的验收用例依据。
> 范围限定：仅入职模块字段配置基线，**不涉及** Excel 导入识别 / ai-mapping / FIELD_ALIASES。本轮不调优导入。

## 0. 总览

| 维度 | 数值 |
|---|---|
| 字段总数 | 54 |
| 分组 | 5 大组：基本信息 / 劳动合同签订 / 入职联系 / 发薪信息 / 社保公积金类 |
| 子工单 | 4 个：入职联系（onboarding_contact）/ 劳动合同签订（contract）/ 数据录入（data_entry）/ 社保公积金办理（social_insurance） |

## 1. 字段总表

> 列说明：
>  - **#**：Excel 表中字段顺序（1~54）。
>  - **字段代码**：与 `backend/src/database/seeds/seed-fields.ts` 中 `code` 完全对齐。
>  - **分组**：按 Excel 顶部合并标题归组：基本信息（含 1-40 个人 / 合同 / 薪资 / 社保 / 银行 / 备注）/ 劳动合同签订（41-47）/ 入职联系（48-49）/ 发薪信息（50-51）/ 社保公积金类（52-54）。
>  - **类型**：单行文本 / 多行文本 / 数字 / 日期 / 下拉 / 邮箱 / 电话 / 身份证。
>  - **必填**：必填 / 非必填 / 条件必填 / **必填？**（产品未确认，悬挂问题，第 5 节列出）。
>  - **下拉选项**：当 类型 = 下拉 时给出，文案以表格中"填写要求"为准。
>  - **示例**：来自表格示例行。
>  - **备注**：保留产品在"备注说明"中给出的原话（疑问 / 关联规则等）；不要替产品决定。

| 子工单 code | 中文名 | 触发条件 | 触发字段（fieldCode = 值） |
|---|---|---|---|
| `data_entry` | 数据录入 | **所有入职单必生成** | — |
| `social_insurance` | 社保公积金办理 | **所有入职单必生成** | — |
| `contract` | 劳动合同签订 | 当"是否企服发起劳动合同" = **是** 才生成 | `need_company_contract = '是'` |
| `onboarding_contact` | 入职联系 | 当"入职材料是否需要集约收集" = **是** 才生成 | `need_onboarding_contact = '是'`（注：seed-fields.ts 当前中文名为"是否需要入职联系"，需统一为"入职材料是否需要集约收集"） |

### 3.2 条件必填规则（关联字段）

| 受控字段 | 触发字段 | 规则 |
|---|---|---|
| 劳动合同主体 `contract_subject` | 是否企服发起劳动合同 `need_company_contract` | =是 → 必填；=否 → 非必填 |
| 劳动合同模板 `contract_template` | 是否企服发起劳动合同 `need_company_contract` | =是 → 必填；=否 → 非必填 |
| 劳动合同签署是否需要催办员工 `need_contract_urge` | 是否企服发起劳动合同 `need_company_contract` | =是 → 必填；=否 → 非必填 |
| 发薪地 `payroll_location` | 是否企服发薪 `need_company_payroll` | =是 → 必填；=否 → 非必填 |

### 3.3 实施提示

- 后端 `field_configs.conditional_required` 应按上述 4 条 AST 写入：`{ op: 'EQ', field: '<触发字段>', value: '是' }`。
- 前端 DynamicForm 已支持 `ConditionalRequired`，按 `requireFields` 把 4 个受控字段挂在对应触发字段下即可。

## 4. 业务员可空 + 后道补全字段

### 4.1 范围

| 字段代码 | 中文名 | 业务员发起时 | 后道补全节点 | 补全后回灌目标 |
|---|---|---|---|---|
| `bank_name` | 开户银行信息 | 可空 | 入职联系（onboarding_contact） | 总单 `extra_data` + 数据录入子单（data_entry）字段快照 |
| `bank_account` | 银行借记卡帐号 | 可空 | 入职联系（onboarding_contact） | 总单 `extra_data` + 数据录入子单（data_entry）字段快照 |

### 4.2 行为约束

1. 业务员在新建 / 草稿 / 提交时，**不强校验**这两个字段；保存为 `null` 或空串。
2. 入职联系办理岗在子单办理过程中收齐银行卡信息，使用"字段补全"接口（既有 `field-supplement` 模块或后端等价能力）填入。
3. 后端写入时同步：
   - 更新 `work_orders.extra_data.bank_name / bank_account`；
   - 同步刷新 `data_entry` 子单的字段快照（按既有 `FieldSupplementRule.syncToModules` 机制）；
   - 写 `operation_logs`，记录补全人 / 补全时间。
4. 前端：业务员侧字段渲染时显式加副标签"由入职联系节点补全"，避免业务员误以为必填。

### 4.3 与其他字段的区别

- 这 2 个字段是"**业务员可空 + 后道补全**"；与"反馈类字段"（共享岗位填写）行为不同，后者由办理岗在**子单完成时**填写，不需要回灌总单 `extra_data`，只更新子单 `feedback_data`（参见第 6 节）。
