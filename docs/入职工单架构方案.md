# 入职工单字段、权限与一拆三流程架构方案

## 一、问题分析

### 1.1 用户角色显示"无角色"问题

**根本原因**：
- 前端代码 `frontend/src/pages/Admin/Users/index.tsx:104` 显示逻辑：当 `roles` 数组为空时显示 `<Tag>无角色</Tag>`
- 后端数据模型：用户角色通过 `user_roles` 关联表存储（user_id + role_id + department_id 三元组）
- **核心问题**：后端 API `/admin/users` 返回用户列表时，未正确 JOIN `user_roles` 和 `roles` 表，导致 `roles` 字段为空数组

**解决方案**：
后端 `UsersService.findAll()` 方法需要：
```typescript
// 添加关联查询
.leftJoinAndSelect('user.userRoles', 'userRole')
.leftJoinAndSelect('userRole.role', 'role')
.leftJoinAndSelect('userRole.department', 'department')
```

返回数据格式需包含：
```typescript
{
  roles: [
    { role_id: string, role_name: string, department_id: string, department_name: string }
  ]
}
```

### 1.2 字段权限配置问题

**现状**：
- 字段权限表 `field_permissions` 已存在，包含 `role_id`, `field_code`, `permission`, `scenario`
- 权限模式：`VISIBLE`, `HIDDEN`, `READONLY`, `MASKED`
- **问题**：缺少针对入职工单各字段的权限配置数据

**需要补充**：
- 入职工单 55 个字段的权限矩阵（见下文 2.3 节）
- 字段分类配置（业务员填写 vs 后道填写）
- 场景化权限（发起、查看、编辑、审批）

### 2.2 入职工单一拆三流程设计

#### 流程触发条件

业务员提交入职工单后，系统根据以下字段自动拆分：

1. **入职联系工单**：`need_onboarding_contact = "是"` → 流转到共享团队（入离职联系专员）
2. **劳动合同签订工单**：`need_contract_signing = "是"` → 流转到共享团队（合同专员）
3. **数据录入工单**：**所有入职工单** → 流转到数据录入组长

#### 数据模型设计

**主工单表** `work_orders`（已存在）：
- `order_type = 'onboarding'`
- `extra_data` 存储 56 个字段的 JSON 数据

**拆分工单表** `dispatched_orders`（已存在）：
- `parent_order_id` 关联主工单
- `module_code` 模块代码：`onboarding_contact` / `contract_signing` / `data_entry`
- `handler_id` 处理人 ID
- `visible_fields` 可见字段列表（JSON 数组）

#### 拆分逻辑实现（后端伪代码）

```typescript
// backend/src/modules/work-orders/work-order.service.ts

async submitOnboardingOrder(orderId: string) {
  const order = await this.findOne(orderId);
  const extraData = order.extraData;
  
  // 1. 入职联系工单拆分
  if (extraData.need_onboarding_contact === '是') {
    await this.dispatchedOrderService.create({
      parentOrderId: orderId,
      moduleCode: 'onboarding_contact',
      handlerId: await this.getHandlerByRole('入离职联系专员'),
      visibleFields: [
        'customer_name', 'customer_code', 'employee_name', 'id_card',
        'mobile_phone', 'email', 'current_address', 'household_address',
        'need_material_collection', 'onboarding_feedback'
      ],
      status: 'PENDING'
    });
  }
  
  // 2. 劳动合同签订工单拆分
  if (extraData.need_contract_signing === '是') {
    await this.dispatchedOrderService.create({
      parentOrderId: orderId,
      moduleCode: 'contract_signing',
      handlerId: await this.getHandlerByRole('合同专员'),
      visibleFields: [
        'customer_name', 'employee_name', 'id_card', 'gender', 'mobile_phone', 'email',
        'contract_term_type', 'contract_term', 'contract_start_date', 'contract_end_date',
        'probation_start_date', 'probation_months', 'probation_end_date',
        'work_city', 'working_hours_system', 'salary_form', 'basic_salary',
        'contract_entity', 'contract_template', 'need_contract_reminder', 'contract_feedback'
      ],
      status: 'PENDING'
    });
  }
  
  // 3. 数据录入工单拆分（所有入职工单都需要）
  await this.dispatchedOrderService.create({
    parentOrderId: orderId,
    moduleCode: 'data_entry',
    handlerId: await this.getHandlerByRole('数据录入组长'),
    visibleFields: ['*'], // 所有字段可见
    status: 'PENDING'
  });
}
```

### 2.3 权限矩阵设计

#### 角色与数据可见范围

| 角色 | 角色代码 | 数据可见范围 | 操作权限 |
|------|---------|-------------|---------|
| 系统管理员 | `admin` | 全部工单 | 全部操作 |
| 业务负责人 | `business_owner` | 全部业务工单 | 仅查看，不可操作 |
| 业务组长 | `business_group_leader` | 本组所有工单 | 作为业务员时可发起/修改/撤回 |
| 业务员 | `business_group_member` | 仅自己发起的工单 | 发起/修改/撤回 |
| 共享团队负责人 | `shared_team_owner` | 合同签订+入离职联系模块全量 | 接单/完成/退回/补充/改派 |
| 合同专员 | `labor_contract_member` | 合同签订模块 | 接单/完成/退回/补充 |
| 入离职联系专员 | `onboarding_resignation_member` | 入职联系模块 | 接单/完成/退回/补充 |
| 数据录入组长 | `data_entry_leader` | 数据录入模块全量 | 接单/完成/退回/补充/审核 |

async findAll(query: ListQueryDto) {
  const qb = this.userRepository.createQueryBuilder('user')
    .leftJoinAndSelect('user.userRoles', 'userRole')
    .leftJoinAndSelect('userRole.role', 'role')
    .leftJoinAndSelect('userRole.department', 'department')
    .where('user.isActive = :active', { active: true });
  
  const [users, total] = await qb.getManyAndCount();
  
  return users.map(user => ({
    id: user.id,
    username: user.username,
    real_name: user.realName,
    email: user.email,
    phone: user.phone,
    is_active: user.isActive,
    roles: user.userRoles.map(ur => ({
      role_id: ur.roleId,
      role_name: ur.role.name,
      department_id: ur.departmentId,
      department_name: ur.department.name
    })),
    group_name: user.userRoles[0]?.department.name || '',
    created_at: user.createdAt
  }));
}

## 四、接口改造清单

### 4.1 后端接口

#### 新增接口

1. **POST** `/api/work-orders/:id/submit-onboarding`
   - 功能：提交入职工单并触发一拆三
   - 请求体：无
   - 响应：`{ dispatchedOrders: DispatchedOrder[] }`

2. **GET** `/api/dispatched-orders/my-tasks`
   - 功能：获取当前用户的待办工单列表
   - 查询参数：`moduleCode`, `status`, `page`, `pageSize`
   - 响应：分页的 `DispatchedOrder[]`

3. **PUT** `/api/dispatched-orders/:id/complete`
   - 功能：完成拆分工单
   - 请求体：`{ feedback: string, supplementData: Record<string, any> }`
   - 响应：`DispatchedOrder`

#### 修改接口

1. **GET** `/api/admin/users`
   - 修改：添加 `userRoles`, `role`, `department` 的 JOIN 查询
   - 确保返回 `roles` 数组非空

2. **GET** `/api/work-orders`
   - 修改：根据用户角色过滤数据
     - 业务员：`createdBy = currentUserId`
     - 业务组长：`department IN (用户所属部门)`
     - 业务负责人：`orderType = 'onboarding'`（全部业务工单）
     - 系统管理员：无过滤

3. **POST** `/api/work-orders`
   - 修改：验证 56 个字段的必填规则
   - 添加字段分类标签（用于前端表单分组）

## 七、风险与注意事项

### 7.1 数据一致性风险

**问题**：拆分工单的字段更新如何同步到主工单？
**方案**：
- 拆分工单完成时，将 `supplementData` 合并回主工单的 `extra_data`
- 使用数据库事务确保原子性

### 7.2 权限配置复杂度

**问题**：56 字段 × 8 角色 × 3 场景 = 1344 条权限配置
**方案**：
- 使用默认权限 + 例外配置
- 按字段分类批量配置（如"基础信息"字段对所有角色可见）

### 7.3 前端表单性能

**问题**：56 个字段的表单渲染可能卡顿
**方案**：
- 使用虚拟滚动或分页加载
- 折叠面板默认收起，按需展开
