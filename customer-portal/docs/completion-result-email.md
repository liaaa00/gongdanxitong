# 工单办结结果确认邮件规格（一期）

更新时间：2026-09-04

## 1. 需求结论

需求文档明确写有“邮件-关键信息结果按附件回传客户确认-监测到已完成”。会议进一步确认：系统监测到工单状态变为“已完成”后，通过共享邮箱将关键办理结果作为附件发送给客户指定联系人，作为双方可追溯的确认凭证。入职、离职、薪资三类业务全部纳入该规则。

本规格只描述**工单办结结果确认邮件**，不包含：

- 账单日前的薪资催办邮件；
- 客户来信的公共邮箱分流；
- 登录验证码邮件。

## 2. 角色与配置位置

| 内容 | 维护角色 | 维护位置 | 客户门户是否可见/可改 |
|---|---|---|---|
| 是否启用办结结果邮件 | 内部业务员/管理员 | 内部客户管理 | 否；入职/离职/薪资均默认纳入 |
| 收件人、抄送人 | 内部业务员/管理员 | 内部客户管理 | 否 |
| 业务类型模板 | 管理员 | 内部邮件模板管理 | 否 |
| 结果关键字段 | 管理员/产品 | 内部邮件模板管理 | 否 |
| 发送记录与失败原因 | 内部业务员/管理员 | 内部工单详情/邮件记录 | 否 |
| 已发送提示 | 系统 | 客户办理进度 | 只读 |

## 3. 最小触发流程

1. 工单状态由非 `completed` 首次变为 `completed`。
2. 事务提交后创建一条待发送任务，不能在工单事务中直接阻塞调用邮件服务。
3. 按工单客户 ID 读取已启用的邮件规则和指定联系人。
4. 根据工单业务类型生成结果 Excel，记录模板版本和附件摘要。
5. 通过公共邮箱发送邮件。
6. 保存收件人、抄送人、主题、附件 ID、发送时间、状态、失败原因和重试次数。
7. 发送成功后，客户进度中可只读显示“结果确认邮件已发送”。
8. 失败后按规则重试，达到上限后通知对应业务员人工处理。

## 4. 幂等和争议留痕

- 幂等键建议为：`workOrderId + completedVersion + templateCode`。
- 同一次办结事件不得重复发送。
- 工单重新打开后再次办结，应生成新的办结版本；是否自动再发需业务确认。
- 附件必须保存版本或不可变文件引用，不能发送后再被覆盖。
- 邮件正文、主题、收件人和附件摘要需要留痕。
- 客户异议期限必须由业务确认后才能写入正式邮件模板。

## 5. 建议的数据对象

### 客户邮件规则

- `customerId`
- `completionEmailEnabled`
- `toRecipients`
- `ccRecipients`
- `replyTo`
- `businessTypes`
- `objectionDeadlineDays`
- `updatedBy` / `updatedAt`

### 邮件发送任务/记录

- `workOrderId`
- `completedVersion`
- `templateCode` / `templateVersion`
- `toRecipients` / `ccRecipients`
- `subject` / `bodySnapshot`
- `attachmentId` / `attachmentHash`
- `status`: pending / sending / sent / failed
- `attemptCount` / `nextRetryAt` / `lastError`
- `sentAt`

## 6. 开发前必须确认

- 一期覆盖的工单类型；
- 每种工单的结果字段；
- 客户联系人数据来源；
- 是否抄送业务员；
- 异议期限；
- 重新办结的重复发送规则；
- 公共邮箱接入方式；
- Excel 和邮件主题命名规范。

## 7. 2026-09-04 会议最终确认

- 业务范围：入职、离职、薪资三类业务均发送办结结果邮件。
- 附件通道：入职、离职、薪资附件全部走共享邮箱，不绑定内部工单附件 API，也不强制要求 `workOrderId`。
- 离职证明：是否需要、证明形式和送达地址均由后台配置，客户侧不展示、不填写。
- 薪资提醒：账单日前 3 个工作日提醒客户，前 2 个工作日再次催办客户，前 1 个工作日升级提醒业务员。
- 数创系统：作为客户信息最终兜底数据源；门户与内部工单系统保持边界，不把客户门户当作内部工单系统。

以上为业务口径确认；本地客户规则配置页面、数据库持久化和门户可信注入已完成，真实 SMTP/API、结果模板字段及服务器环境联调仍需按内部系统实施。
